How Memcached Evicts Items With Same Expiration

When multiple items in Memcached share the identical expiration time, the system resolves eviction conflicts using its Least Recently Used (LRU) mechanism rather than the expiration timestamp itself. Memcached decouples expiration logic from memory management, meaning identical time-to-live (TTL) values have no bearing on eviction priority. Instead, Memcached inspects access patterns within the relevant memory slab and evicts the item that has gone the longest without being requested.

The Separation of Expiration and Eviction

To understand how ties are broken, it is essential to distinguish between how Memcached handles item expiration and how it handles eviction:

  • Expiration (TTL): Memcached uses lazy expiration combined with an optional background crawler. An item is not automatically removed the exact second it expires; instead, it is checked and discarded when a client requests it, or when an asynchronous crawler thread encounters it.
  • Eviction: Eviction occurs only when Memcached runs out of allocated memory in a specific slab class and needs to store a new item.

Because expiration time is merely a metadata check during item retrieval, Memcached does not organize its eviction queues by TTL. Having identical expiration times does not create a conflict inside the eviction engine.

How the LRU Resolves Identical Expiration Times

Memcached structures its memory into slab classes based on item size. Each slab class maintains its own LRU queue, structured internally as a doubly linked list.

Every time a key-value pair is written or read, Memcached updates its position, moving the item to the head of the list. When an item sits untouched, it gradually drifts toward the tail as newer or more frequently queried items take the front.

If memory in a slab is full and a new entry arrives:

  1. Memcached searches the tail of the LRU list for that specific slab class.
  2. If an item at the tail is already expired, Memcached reclaims its memory immediately.
  3. If all candidate items are still valid—even if dozens share the exact same future expiration timestamp—Memcached simply evicts the item located at the very tail of the queue.

The decisive factor is the item's last-access timestamp. The item that was queried least recently is pruned first, regardless of whether its expiration date matches other stored entries.

Segmented LRU Considerations

Modern versions of Memcached implement a Segmented LRU architecture, splitting each slab class into four sub-queues: TEMP, HOT, WARM, and COLD.

Even within this architecture, identical expiration times are irrelevant to eviction ordering:

  • New items with TTLs longer than a few seconds enter the HOT queue.
  • As memory fills, items migrate from HOT to WARM or directly to COLD.
  • Evictions are drawn strictly from the tail of the COLD queue.

If two or more items share the same expiration timestamp, their survival depends entirely on access frequency. An item that receives continuous GET commands is periodically moved to the front of the queue, while the untouched item drifts to the end of the COLD list and is evicted first.
