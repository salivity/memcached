Memcached TCP vs UDP: Client Communication Trade-Offs

When integrating Memcached into an application stack, choosing between Transmission Control Protocol (TCP) and User Datagram Protocol (UDP) for client-server communication fundamentally shapes performance, network overhead, and system reliability. While UDP offers theoretically lower latency and reduced connection overhead for simple read requests, TCP provides the reliability, connection tracking, and security required for modern production systems. This article breaks down the key trade-offs between both protocols when used with Memcached.

Latency and Connection Overhead

TCP requires a three-way handshake to establish a connection, which introduces initial latency and consumes memory on the Memcached host to maintain connection states. For architectures with thousands of ephemeral client connections, this overhead can become a significant bottleneck unless persistent connection pooling is implemented.

In contrast, UDP is stateless and connectionless. Clients can immediately dispatch requests without handshaking, which minimizes latency for single-packet read operations (get requests). Because the server does not maintain connection states for UDP, it can theoretically handle higher request spikes from fragmented or distributed sources without exhausting file descriptors or memory associated with socket buffers.

Reliability and Data Integrity

TCP guarantees ordered delivery, packet retransmission, and error detection. In a caching layer, this means every command sent—whether a read, write, or eviction—will arrive intact and in sequence, or fail explicitly with an actionable error.

UDP provides no delivery guarantees, ordering, or flow control. In high-traffic scenarios or congested networks:

  • Packets may drop silently, resulting in client-side timeouts.
  • Out-of-order execution can cause consistency issues.
  • The client application must implement its own timeout and retry mechanisms to handle missing responses, effectively shifting the complexity of network reliability from the transport layer into application code.

Because of this lack of delivery guarantees, Memcached’s UDP implementation historically restricted write operations (like set or delete) to mitigate the risk of corrupting cache states due to dropped or reordered packets.

Security and Amplification Vulnerabilities

Security is the most critical differentiator. Memcached over UDP is historically vulnerable to UDP reflection and amplification Distributed Denial of Service (DDoS) attacks. Because UDP allows IP address spoofing and Memcached responses can be significantly larger than the initial query, malicious actors can send small requests with a spoofed target IP, causing the Memcached instance to flood the victim with massive responses.

Due to large-scale attacks leveraging this vector, modern distributions of Memcached have disabled UDP listening by default. Running Memcached over UDP requires strict network-level isolation, private network access controls, and firewall restrictions to prevent public exploitation.

TCP, on the other hand, requires a mutual handshake, preventing IP address spoofing and making amplification attacks virtually impossible.

Payload Sizing and Fragmentation

TCP seamlessly manages large objects by streaming data across multiple segments, handled transparently by the operating system’s network stack.

UDP is constrained by the Maximum Transmission Unit (MTU) of the network, typically 1,500 bytes. When a cached item exceeds the MTU, the payload must be fragmented into multiple UDP datagrams. If even a single fragment is dropped in transit, the entire response is lost, severely degrading performance for large payloads.

Conclusion

For almost all modern production environments, TCP is the standard choice for Memcached client communication. While UDP offers marginal latency gains for lightweight, loss-tolerant reads, it introduces severe security risks, operational complexity, and packet fragmentation limitations. TCP ensures predictable, secure, and reliable communication, with its latency trade-offs easily mitigated by using persistent client connection pools.
