Memcached Item Crawler and Expired Key Scanning

This article explores the function of the item crawler in Memcached, focusing on how it scans and purges expired keys during background routines. Readers will gain a clear understanding of the limitations of lazy expiration, how the background crawler traverses internal LRU lists asynchronously, and the way this mechanism optimizes memory utilization without degrading read or write performance for client applications.

Lazy Expiration and Its Limitations

By default, Memcached uses a passive or "lazy" expiration strategy. When an item reaches its expiration time (TTL), Memcached does not immediately delete it from memory. Instead, the item is only checked and removed when a client attempts to access it via a read command like get.

If an expired key is never queried again, it continues to occupy space in its designated slab class. Under heavy write loads with fluctuating key lifespans, these "dead" items accumulate. If memory becomes full before these dead items are requested, Memcached might prematurely evict valid, non-expired keys using its Least Recently Used (LRU) algorithm, resulting in unnecessary cache misses.

The Role of the Item Crawler

To solve the drawbacks of lazy expiration, Memcached introduced the item crawler. The item crawler is an asynchronous background thread dedicated to proactively discovering and freeing expired keys across all slab classes.

Instead of waiting for client interactions, the item crawler continuously or periodically navigates the cache's internal memory structures to identify records whose TTLs have elapsed. By doing so, it ensures that memory occupied by dead items is returned to the slab allocator, keeping slab pages free for incoming writes.

How the Item Crawler Operates in the Background

The item crawler works directly with Memcached’s segmented LRU architecture (which divides items into queues such as HOT, WARM, and COLD):

  1. Traversal: The crawler thread attaches to an LRU queue within a specific slab class and moves backward or forward along the doubly linked list of items.
  2. Evaluation: For each item it visits, it compares the item's expiration timestamp against the current system time.
  3. Reclamation: If the item is expired, the crawler unlinks the item from the hash table and the LRU chain, immediately returning the memory chunk to the slab pool.
  4. Non-Blocking Operation: To prevent latency spikes for client requests, the crawler operates incrementally. It acquires short-lived locks per item or chunk rather than locking entire slab classes, yielding execution time to incoming worker-thread queries.

Crawler Configuration and Tuning

Administrators can control the behavior of the item crawler via Memcached's management interface or startup flags:

  • Automatic Scanning: When enabled via lru_crawler enable, the background thread runs automatically, sleeping between steps to maintain low CPU overhead.
  • Sleep Adjustments: The rate of the crawler can be regulated using the lru_crawler sleep parameter (measured in microseconds). A lower sleep time scans memory more aggressively at the cost of higher CPU consumption, while a higher sleep time minimizes resource utilization.
  • Targeted Crawls: The command lru_crawler crawl <slab_class_id> allows operators to trigger an immediate, on-demand scan of specific slabs experiencing high memory pressure.

By actively purging expired items in the background, the item crawler reduces premature LRU evictions, stabilizes cache hit ratios, and ensures optimal memory distribution throughout Memcached's operational lifecycle.
