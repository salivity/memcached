Memcached Network Interface Saturation Metrics

When Memcached performance degrades, the bottleneck often lies not in CPU or memory allocation, but at the physical or virtual network interface card (NIC). Network interface saturation limits packet processing rates, increases request latency, and triggers packet drops. This article outlines the primary operating system, TCP/IP stack, and Memcached-specific metrics used to identify whether network saturation is throttling your caching tier.

1. NIC Bandwidth and Throughput Utilization

The most direct indicator of network saturation is throughput approaching the physical or cloud-enforced limits of the network interface.

  • rxkB/s and txkB/s: Found using tools like sar -n DEV 1 or dstat, these show receive and transmit volume in kilobytes per second. If these values reach 80–90% of the maximum theoretical link speed (e.g., nearing 1.25 GB/s on a 10 GbE interface), bandwidth saturation is imminent or occurring.
  • Cloud Provider Network Throttling Caps: On platforms like AWS EC2, instance-level bandwidth caps are enforced independently of link speed. Check metrics such as bw_in_allowance_exceeded and bw_out_allowance_exceeded via ethtool -S <interface> to detect bandwidth throttling.

2. Interface Drops and Ring Buffer Exhaustion

When incoming or outgoing packets arrive faster than the interface or the kernel can process them, the NIC’s hardware or software ring buffers overflow.

  • rx_dropped and tx_dropped: Reported by ip -s link show <interface> or /proc/net/dev. Non-zero or steadily increasing drop rates indicate buffer exhaustion.
  • rx_missed_errors and rx_fifo_errors: Viewed using ethtool -S <interface>. Missed errors confirm that the NIC had to discard packets at the hardware layer because the driver ring buffer was completely full.

3. TCP Retransmissions and Queue Overflows

Physical network saturation leads to lost segment acknowledgments, connection latency, and TCP-level retries.

  • TCP Retransmissions (TcpRetransSegs): Monitored using netstat -s or nstat -az TcpRetransSegs. A spike in retransmissions alongside high network traffic suggests packets are being dropped in flight or discarded at the interface.
  • Listen Queue Drops (ListenDrops and ListenOverflows): Available via netstat -s | grep -i listen. These counters increment when Memcached cannot accept new TCP connections quickly enough, often caused by the OS being stalled processing heavy network traffic.

4. Software Interrupt (softirq) CPU Utilization

Processing incoming network interrupts consumes CPU time. If softirq processing cannot keep up with high packet rates (PPS), packets are dropped before reaching Memcached.

  • %soft in mpstat -P ALL 1 or top: If one or more CPU cores show near 100% time spent in %soft, the network driver's receive processing (e.g., NAPI polling) is saturated. This frequently happens when Receive Side Scaling (RSS) is misconfigured and a single CPU core handles all NIC interrupts.
  • /proc/net/softnet_stat (Second Column): The second column represents squeezed events, where the network processing budget ran out before all packets in the queue could be processed. A rising count indicates packet-processing backlog.

5. Memcached Internal Indicators

While operating system metrics confirm the physical constraint, Memcached exposes operational metrics that reflect network-induced stalls.

  • listen_disabled_num: Viewed through the Memcached stats command. If this value increases, Memcached was forced to temporarily stop listening for new connections because it reached its internal connection limit or the local socket buffer backed up.
  • Latency Spikes with Low Engine CPU: If client-reported p99 and p999 response latencies surge while Memcached’s core CPU usage (rusage_user, rusage_system) remains low or steady, packets are queuing at the kernel or network interface level before reaching the Memcached application threads.
