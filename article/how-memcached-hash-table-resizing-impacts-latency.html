How Memcached Hash Table Resizing Impacts Latency

Memcached dynamically expands its internal hash table to maintain \(O(1)\) lookup efficiency as the number of cached keys grows. Although this automatic resizing prevents severe hash collisions, the underlying migration process introduces concurrent locking operations, dual-table lookups, and memory overhead that can cause noticeable query latency spikes. This article examines the internal mechanics of Memcached hash table expansion, how the incremental rehashing mechanism functions, and the exact sources of latency degradation during the migration phase.

The Hash Table Resizing Mechanism

Memcached relies on a primary hash table to associate keys with their corresponding slab-allocated data structures. The size of this hash table is determined by a power of two, known internally as hashpower.

When the number of stored items exceeds 1.5 times the current capacity of the hash table (\(1.5 \times 2^{\text{hashpower}}\)), Memcached initiates a resize operation to prevent bucket chains from growing too long. Rather than executing a stop-the-world reallocation, Memcached doubles the table size (incrementing hashpower by 1) and migrates items incrementally using a dedicated background thread: the association maintenance thread (assoc_maintenance_thread).

Why Latency Spikes Occur During Resizing

While the background maintenance thread is designed to minimize disruptions, it cannot eliminate performance overhead entirely. Query latency—particularly 99th and 99.9th percentile tail latency—is affected through three primary mechanisms:

1. Bucket and Item Lock Contention

Memcached employs fine-grained bucket-level locks to maintain thread safety across its worker threads. During rehashing:

  • The maintenance thread moves items in chunks (controlled by hash_bulk_move, typically 1 to 256 buckets at a time).
  • To move a bucket, the maintenance thread must acquire the corresponding locks for both the old bucket and the new bucket.
  • If a client request (such as a GET, SET, or DELETE) targets an item located within the chunk currently being moved, the worker thread handling that connection must block until the maintenance thread releases the locks.
  • In high-concurrency environments, multiple worker threads may queue up waiting for locked buckets, leading to head-of-line blocking and immediate latency spikes.

2. Dual-Table Lookup Overhead

While a rehash is in progress, the hash table exists in a split state:

  • Any key whose old bucket has already been processed resides in the new, expanded table.
  • Any key whose bucket has not yet been processed remains in the old table.
  • For read operations targeting keys that have not yet moved, worker threads must perform address resolution against the old table while consulting state flags to determine migration progress. This adds branch prediction penalties and extra memory lookups per request.

3. CPU Cache Invalidation and Memory Bandwidth

Rehashing involves reading pointers from the old table and writing them to the newly allocated memory space. This continuous memory traversal generates substantial traffic on the memory bus and evicts hot data from the CPU's L1/L2/L3 caches. Consequently, worker threads processing unrelated read operations experience higher hardware cache-miss rates, marginally slowing down overall query processing speeds across the entire instance.

Minimizing Resizing Latency in Production

To prevent unexpected latency degradation in high-throughput workloads, administrators can manage hash table growth proactively:

  • Pre-allocate Hashpower: Use the -o hashpower=N startup flag to set the initial hash table size based on expected peak key counts. For example, setting hashpower=20 pre-allocates an array with \(2^{20}\) (1,048,576) buckets, avoiding resizing events altogether if the dataset stays within bounds.
  • Monitor Rehash Status: Track the hash_is_expanding, hash_power_level, and hash_bytes metrics via the stats command to detect active expansions and evaluate whether memory growth correlates with observed latency spikes.
