Memcached Memory Allocation for Fluctuating Payloads

Memcached manages memory through a deterministic slab allocation subsystem designed to eliminate external memory fragmentation. When item payload sizes fluctuate randomly, the system routes each write operation to the best-fitting slab class based on predefined size thresholds, utilizing internal memory chunks. However, highly variable payloads introduce challenges such as internal fragmentation, uneven memory distribution, and slab calcification, which modern versions of Memcached mitigate using dynamic slab reassignment and adaptive Least Recently Used (LRU) eviction algorithms.

The Slab Allocation System

To prevent memory fragmentation caused by repeated malloc and free operations, Memcached pre-allocates memory in 1MB blocks called pages. These pages are assigned to specific "slab classes." Each slab class divides its assigned pages into fixed-size memory slots called chunks.

Slab classes are arranged in an increasing geometric progression controlled by a growth factor (defaulting to 1.25). For example:

  • Slab Class 1: 96-byte chunks
  • Slab Class 2: 120-byte chunks
  • Slab Class 3: 152-byte chunks

Assignment Logic for Random Payload Sizes

When a write command (such as SET or ADD) is received, Memcached calculates the total memory requirement: the key length, the payload size, internal metadata, and flags.

  1. Size Lookup: Memcached inspects its slab classes and selects the class with the smallest chunk size that can fully accommodate the item.
  2. Chunk Reservation: If an empty chunk exists within that slab class, the data is written directly to that chunk.
  3. Internal Fragmentation: Because chunks have fixed sizes, an item rarely fits perfectly. For instance, storing a 100-byte payload into a 120-byte chunk leaves 20 bytes of unused memory ("slack space"). When sizes fluctuate wildly, internal fragmentation increases, reducing overall memory efficiency.

Slab Exhaustion and Class-Specific LRU

Memory is managed independently per slab class rather than globally. If a slab class runs out of free chunks:

  1. New Page Allocation: If global memory remains unallocated, Memcached assigns a new 1MB page to that specific slab class and partitions it into new chunks.
  2. Class-Level Eviction: If global memory is full, Memcached triggers an LRU eviction strictly within that slab class. It will overwrite the oldest item in that class, even if other slab classes have abundant free chunks.

Under randomly fluctuating workloads, this class-bound design can cause localized eviction storms, where specific chunk sizes face heavy evictions while others remain idle.

Handling Payload Shifts with Slab Reassignment

Early versions of Memcached suffered from "slab calcification," where pages permanently locked into classes that were no longer needed when workload profiles changed. Modern Memcached implements dynamic rebalancing mechanisms to handle shifting and random distributions:

  • Slab Reassign (slabs reassign): An administrative command that manually moves an idle 1MB page from one slab class to a class facing higher demand.
  • Slab Automove (slab_automove): A background thread that monitors memory pressure. If it detects that a slab class is regularly evicting items while another has unused pages or low eviction pressure, it automatically detaches a page from the underutilized class and reallocates it to the starved class.

Through strict slab-class chunk mapping combined with dynamic page reassignment, Memcached handles unpredictable payload sizes without succumbing to operating-system-level heap fragmentation.
