Memcached Load Testing with memaslap and mutilate

Benchmarking a Memcached deployment is critical for identifying throughput limits, tail latencies, and network bottlenecks before traffic hits production. This guide outlines how administrators can simulate realistic, high-throughput workloads against a Memcached instance using two standard benchmarking utilities: memaslap, a feature-rich load generator included with libmemcached, and mutilate, a modern load generator engineered specifically to measure latency at high query rates.

Simulating Load with memaslap

memaslap is part of the libmemcached suite. It supports complex workload profiles, multi-threading, custom get/set ratios, and variable key-value sizing via configuration files.

1. Installation

On Debian/Ubuntu systems, install memaslap through the libmemcached-tools package:

sudo apt-get update
sudo apt-get install -y libmemcached-tools

On Enterprise Linux (RHEL/Rocky/CentOS):

sudo dnf install -y libmemcached

2. Running a Basic Test

To execute a standard benchmark using command-line arguments:

memaslap -s 127.0.0.1:11211 -t 30s -c 64 -T 4
  • -s: The target Memcached server and port.
  • -t: Duration of the test (e.g., 30s, 2m).
  • -c: Concurrency level (total number of active TCP connections).
  • -T: Number of OS threads generating traffic.

3. Simulating Realistic Workloads with a Configuration File

memaslap allows administrators to configure realistic distributions of keys, values, and command types using a configuration file.

Create a file named workload.cnf:

key
64 64 1

value
1024 2048 0.8
4096 8192 0.2

cmd
0 0.9
1 0.1
  • key: Specifies minimum key size (64 bytes), maximum key size (64 bytes), and distribution ratio.
  • value: Generates 80% of values between 1 KB and 2 KB, and 20% between 4 KB and 8 KB.
  • cmd: Defines the command ratio: 90% GET operations (0) and 10% SET operations (1).

Execute the test using the configuration:

memaslap -s 127.0.0.1:11211 -F workload.cnf -t 60s -c 128 -T 8

Simulating Load with mutilate

mutilate is engineered for modern, high-throughput Memcached testing. It can generate millions of queries per second across multiple agent machines and measures tail latencies (such as the 99th and 99.9th percentiles) down to the microsecond.

1. Installation

mutilate is commonly built from source:

sudo apt-get install -y build-essential scons libevent-dev gengetopt libzmq3-dev
git clone https://github.com/leverich/mutilate.git
cd mutilate
scons

2. Running a Standalone Test

To evaluate latency at a fixed request rate:

./mutilate -s 127.0.0.1:11211 -c 16 -r 50000 -t 30 -u 0.1 -K 32 -V 512
  • -s: The target Memcached IP and port.
  • -c: Total number of connections.
  • -r: Target request rate (Queries Per Second).
  • -t: Test duration in seconds.
  • -u: Ratio of update/SET commands (0.1 represents 10% writes, 90% reads).
  • -K: Key size in bytes.
  • -V: Value size in bytes.

3. Measuring Peak Throughput

To identify the absolute maximum capacity of the Memcached instance, omit the -r flag to allow the client to flood the server as fast as possible:

./mutilate -s 127.0.0.1:11211 -c 64 -t 60 --loadonly
./mutilate -s 127.0.0.1:11211 -c 128 -t 60 -u 0.05
  • --loadonly: Pre-populates the cache with data before running the read-heavy benchmark.

4. Distributed Load Generation (Master/Agent Mode)

When testing large clusters, a single load-generator machine often runs out of network bandwidth or CPU capacity. mutilate resolves this through a distributed agent architecture.

On secondary load-generating nodes, run the agent:

./mutilate -A -T 8 -p 5556

On the master node, coordinate the traffic across the agents:

./mutilate -s memcached-server.internal:11211 \
  -a agent1.internal:5556 \
  -a agent2.internal:5556 \
  -c 256 \
  -r 500000 \
  -t 60

Key Operational Considerations

  1. Client Isolation: Run the benchmarking tools on dedicated instances distinct from the Memcached server. Running clients locally over the loopback interface (127.0.0.1) artificially inflates throughput and consumes CPU cycles needed by the Memcached daemon.

  2. Pre-Warming: Pre-populate keys prior to measuring GET operations. Measuring misses instead of hits leads to inaccurate network egress and memory-access performance data.

  3. OS Limits: Increase system limits on both the generator and Memcached hosts before benchmarking:

    ulimit -n 65535
sudo sysctl -w net.ipv4.ip_local_port_range="1024 65535"
sudo sysctl -w net.ipv4.tcp_tw_reuse=1
