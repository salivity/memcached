Memcached Key Uniqueness During Concurrent Writes

This article explores how Memcached maintains key uniqueness and resolves conflicts when multiple clients attempt concurrent write operations. At its core, Memcached utilizes a multithreaded architecture backed by fine-grained thread locking, a shared primary hash table, and atomic memory operations. Understanding these internal mechanisms—specifically hash table bucket locking, command semantics, and CAS (Check-And-Set) tokens—clarifies how the cache reliably evaluates uniqueness without race conditions.

The Primary Hash Table and Bucket Locking

Memcached organizes all stored keys in a single, globally shared hash table. To achieve high throughput across multiple CPU cores, the engine divides this hash table into discrete partitions, each protected by an internal lock (often referred to as an item lock or bucket lock).

When multiple clients issue write requests simultaneously, Memcached distributes the network connections across worker threads. When a thread processes a write command:

  1. It computes the hash of the target key using a hashing algorithm (such as Murmur3 or Jenkins).
  2. It identifies the target hash bucket where the key resides or should reside.
  3. It acquires the lock specific to that bucket or item slot.

Because only one worker thread can hold the lock for a given key's hash bucket at any single microsecond, the actual evaluation of key uniqueness is strictly serialized. Even if dozens of clients attempt to write to the same key simultaneously, their requests are queued at the lock level and evaluated sequentially.

Key Evaluation and Matching Logic

Once a worker thread acquires the bucket lock, it traverses the bucket's linked list to see if an item with the exact same key (evaluated byte-for-byte in length and content) already exists.

During this lookup, the thread also checks the item's expiration metadata. If an item matching the key is found but its Time-To-Live (TTL) has elapsed, Memcached invalidates the expired entry immediately via lazy expiration. In this scenario, the engine treats the key as if it does not exist, freeing the slot for the incoming write.

Command Semantics and Uniqueness Enforcement

How uniqueness dictates the outcome depends directly on the command executed by the client:

  • ADD: Explicitly enforces uniqueness. If the locked lookup finds an active, identical key, the operation immediately fails, returns NOT_STORED, and releases the lock. If the key is not found, the item is inserted, and STORED is returned.
  • SET: Bypasses uniqueness enforcement by acting as an "insert or overwrite." If the key exists, the old item's memory is dereferenced and replaced with the new data. If it does not exist, the item is newly allocated.
  • REPLACE: The inverse of ADD. It succeeds only if the key is actively found. If the key is unique and does not exist in the hash table, it returns NOT_STORED.
  • CAS (Check-And-Set): Evaluates both key existence and data versioning. Each item in Memcached carries an internal, monotonically increasing 64-bit CAS token. A CAS operation evaluates whether the key exists and verifies that its current token matches the token provided by the client. If another client updated the key in the interim, the CAS token will mismatch, and Memcached rejects the write with EXISTS.

Thread Safety in Item Allocation

Evaluating uniqueness also interacts with Memcached’s slab allocator. When an operation requires adding a new key-value pair, memory must be allocated from a specific slab class. Memcached manages item reference counters and slab locks independently or in conjunction with item locks to ensure that allocating new memory or freeing old versions of an overwritten key does not corrupt memory pointers while concurrent threads read or write adjacent keys.
