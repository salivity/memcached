Memcached Graceful Stop and Active Connections

When a Memcached daemon undergoes a graceful stop, it systematically terminates its networking interfaces, finishes or aborts in-flight commands according to configured timeouts, and closes all open connection handles to prevent resource leaks. Understanding this teardown sequence clarifies how active client connections are resolved, how pending input/output operations are treated, and how client applications experience the disconnection at the network layer.

Halting New Incoming Traffic

The first action taken during a graceful stop (initiated via signals such as SIGINT or SIGTERM, or via the administrative shutdown command) is closing the listening sockets. By unbinding and closing the listening file descriptors, Memcached immediately prevents new TCP handshakes from completing. Any new incoming connection attempt from a client will receive a TCP RST (Connection Refused) packet from the operating system's network stack.

Handling Active Connection Handles

For connection handles that are already established when the shutdown signal is processed, the daemon behaves as follows:

  1. Event Loop Notification: The main thread signals the worker threads handling the active event loops (via libevent) that a shutdown has begun.
  2. Current Request Processing: If an active connection is in the middle of executing a command or transmitting a completed response, the daemon attempts to complete the write buffer to the client.
  3. Closing Open Sockets: Once pending writes are transmitted—or immediately if a graceful timeout threshold is reached—Memcached calls close() on each active client connection handle (file descriptor).
  4. TCP Teardown: The kernel sends a TCP FIN packet to the client for each closed connection handle, cleanly terminating the bidirectional TCP session rather than leaving the socket in an orphaned state.

Impact on In-Flight and Idle Clients

  • Idle Keep-Alive Connections: Connections sitting idle in a connection pool are closed immediately. The client side receives an EOF (End-of-File) indication when attempting to read from the socket.
  • In-Flight Requests: Requests received just as the shutdown sequence commences may not be processed if the worker thread has already entered its termination phase. In these instances, the connection is abruptly closed, and the client will observe a socket reset or an empty read error.

Client-Side Experience

From the perspective of client libraries, active handles will encounter an immediate disconnect:

  • Blocking reads return 0 bytes (indicating the server closed the connection) or an error such as ECONNRESET.
  • Client connection pools mark the corresponding handles as dead and remove them from circulation.
  • Unfulfilled cache queries fail, usually triggering standard cache-miss behavior or fallback mechanisms within the application layer.

Because Memcached is an in-memory, non-persistent key-value store, all memory associated with connections, slab allocators, and cached items is freed by the operating system when the process finally terminates.
