Memcached Slab Rebalancing Triggers Explained

Memcached manages memory through a slab allocation system, dividing memory into 1MB pages dedicated to specific item size classes. In modern Memcached, moving a slab page from one class to another—a process known as slab rebalancing or reassignment—prevents memory calcification where memory is permanently locked into underutilized sizes. This page movement is triggered either manually via administrative commands or automatically by the background automove thread when it detects persistent memory pressure imbalances between different slab classes.

Manual Rebalancing

The most direct trigger is administrative intervention. An operator can initiate a page move via the administrative interface using the slabs reassign <source class> <destination class> command. When issued, the slab rebalancer thread unlinks a 1MB page from the donor slab class, evicts or migrates any existing items on that page, and attaches the blank memory page to the receiving class to accommodate its workload.

Automatic Rebalancing (Slab Automove)

Modern Memcached handles slab migration autonomously when started with the -o slab_automove option. The internal slab automove thread periodically samples operational statistics (typically once per second) and triggers a migration when specific behavioral thresholds are met.

The primary triggers for automated movement include:

  • Persistent Eviction Pressure in the Target Slab: The receiving slab class must be actively evicting items due to memory exhaustion. If a class continuously evicts items over multiple consecutive sampling windows (historically three windows), it becomes flagged as a target requiring additional pages.
  • Idle or Free Pages in the Donor Slab: For a donor to release a page, it must have surplus memory. The standard algorithm identifies classes with fully empty pages or classes that have experienced zero allocations over the observation period, ensuring that active traffic is not destabilized.
  • LRU Tail Age Disparities (Modern LRU Automove): In advanced configurations (slab_automove=2 or using the modern segmented LRU system), the trigger relies on the relative "age" of items at the tails of the respective Least Recently Used (LRU) queues. If class A is evicting items that were created or accessed recently (a "hot" tail with a very low age), while class B holds items that have remained untouched for an excessively long time (a "cold" tail with a high age), the automover triggers a transfer. This shifts memory from slabs holding stale data to slabs experiencing high eviction rates for newer data.
  • Windowed Stability Validation: To prevent "page thrashing"—where a page rapidly bounces between classes during transient traffic spikes—the automove algorithm enforces a stabilization window. The observed conditions (such as low tail age in one class and surplus memory in another) must remain consistent over multiple evaluation cycles before the engine marks the trigger criteria as met and initiates the physical page transfer.
