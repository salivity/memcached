How Memcached Manages Small Value Memory Overhead

Storing values under 100 bytes in Memcached presents a unique challenge where internal metadata and memory fragmentation can significantly exceed the size of the cached data itself. This article explains how Memcached’s slab allocation architecture handles small items, the exact sources of memory overhead involved, and the configuration strategies used to minimize wasted memory.

The Slab Allocation Engine

Memcached avoids operating system-level memory fragmentation by using a slab allocator. When Memcached starts, it reserves memory in large contiguous blocks (typically 1 MB pages) and slices them into smaller, fixed-size chunks grouped into "slab classes."

When an item is stored, Memcached determines the total byte size required—including internal metadata, the key, and the value—and assigns it to the smallest available slab class that can accommodate that total size. Once an item is placed in a chunk, that chunk cannot be resized.

Sources of Overhead for Sub-100-Byte Values

When storing a payload under 100 bytes, the actual data often represents less than half of the total memory consumed. The overhead stems from two primary areas:

1. Internal Item Metadata

Every cached entry requires an internal structure (an item header) to manage its lifecycle. On a 64-bit architecture, this structure consumes roughly 48 to 56 bytes. It stores critical runtime data, including:

  • Pointers for the Least Recently Used (LRU) doubly linked list
  • Pointers for the hash table bucket chains
  • Expiration timestamps and access flags
  • Key length and value length
  • Optional CAS (Check-And-Set) identifiers (typically an additional 8 bytes)

If a user stores a 20-byte value with a 15-byte key, the item header adds approximately 48 bytes, resulting in a total footprint of at least 83 bytes before slab assignment.

2. Internal Fragmentation (Slack Space)

Slab classes increase in size geometrically. If the smallest available chunk in a slab class is 120 bytes, and an item requires 85 bytes total (metadata + key + value), the remaining 35 bytes inside that chunk remain unused. This unused space is referred to as internal fragmentation or slack space. For small values, this percentage of wasted space can be substantial.

Configuration Strategies to Reduce Small Item Overhead

Memcached provides startup parameters specifically designed to fine-tune chunk allocation and reduce memory overhead for small payloads.

Adjusting the Minimum Chunk Size (-n)

The -n (or --min-item-size) flag sets the minimum allocated space for the smallest slab class key, value, and flags. The default value is typically 48 bytes. If your keys and values are consistently tiny, ensure this value is set low enough so the initial slab class does not allocate unnecessary baseline padding.

Lowering the Growth Factor (-f)

By default, Memcached scales slab class chunk sizes by a factor of 1.25 (-f 1.25), meaning each successive slab class is 25% larger than the previous one.

For small values, a 25% jump creates wide gaps between classes. Reducing the factor to 1.05 or 1.1 forces Memcached to create more granular slab classes with smaller size increments. This drastically reduces internal fragmentation by ensuring that small items fit into chunks that closely match their exact byte footprint.

Disabling CAS (-C)

If your application does not rely on atomic compare-and-swap operations, you can run Memcached with the -C flag. Disabling CAS removes the 8-byte CAS identifier from every item header, immediately recovering 8 bytes of overhead per item across millions of cached keys.

Application-Level Optimization

Because the per-item metadata is relatively fixed, storing millions of individual values under 100 bytes individually is rarely the most memory-efficient approach. Applications handling high volumes of tiny records often mitigate overhead by packing multiple related key-value pairs into a single structured payload (such as a compressed binary format, MessagePack, or Protocol Buffers) before writing to Memcached. Packing allows multiple values to share a single item header and hash table entry, significantly lowering the overhead-to-data ratio.
