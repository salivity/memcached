Memcached Memory Locking via mlockall

This article explores how Memcached implements the mlockall system call to preserve ultra-low latency by preventing its allocated memory from being swapped to disk. By locking its virtual address space into physical RAM, Memcached avoids the severe performance penalties associated with operating system paging. Below is an examination of why paging degrades in-memory cache performance, how Memcached executes memory locking, the necessary system configurations required, and the operational trade-offs involved.

The Problem with Paging in Memcached

Memcached is designed for high-throughput, low-latency key-value storage. Its primary performance guarantee relies on serving requests directly from physical RAM, typically yielding sub-millisecond response times.

When a host system experiences memory pressure, the operating system kernel's virtual memory manager attempts to free physical memory by moving inactive pages to swap space on disk. If pages belonging to the Memcached process are swapped out, any subsequent read or write to those memory addresses triggers a page fault. Resolving this fault requires fetching data from disk storage (even fast NVMe drives), introducing latencies that can be hundreds to thousands of times slower than direct RAM access. This introduces unpredictable latency spikes and can cascade into application-level timeouts.

How Memcached Uses mlockall

To eliminate swapping risks entirely, Memcached includes an option to lock its entire address space into physical memory using the POSIX mlockall system call.

Administrators enable this feature at startup by passing the -k (or --lock-memory) flag to the memcached daemon. When this flag is set, Memcached calls:

mlockall(MCL_CURRENT | MCL_FUTURE);

The parameters utilized instruct the operating system kernel how to handle the process memory:

  • MCL_CURRENT: Directs the kernel to immediately lock all pages currently mapped into the process's virtual address space, ensuring that existing allocations are in RAM and cannot be paged out.
  • MCL_FUTURE: Directs the kernel to automatically lock any pages that are mapped into the process’s address space in the future. This is critical for Memcached because it dynamically allocates memory for its slab allocator and item storage as connections are made and data is stored.

Once mlockall is successfully executed, the kernel marks these memory pages as unevictable. The kernel will never select them as targets for swapping, guaranteeing that all cache operations remain in physical RAM.

Prerequisites and System Configuration

Because locking memory limits the kernel's flexibility in managing system resources, unprivileged users are restricted from calling mlockall. Running Memcached with -k requires proper permission and resource limit configurations:

  1. Process Capabilities: The process must possess the CAP_IPC_LOCK capability, or it must be initially started as root (which can subsequently drop privileges using the -u flag after locking memory).
  2. Resource Limits (ulimit): The system enforces a maximum locked-memory limit per process (RLIMIT_MEMLOCK). If this limit is lower than the amount of memory Memcached attempts to lock, the daemon will fail to start or abort during allocations. Administrators must configure ulimit -l unlimited or set a high value in /etc/security/limits.conf or the corresponding systemd service unit:
[Service]
LimitMEMLOCK=infinity

Operational Considerations and Risks

While mlockall eliminates swap-induced latency, it shifts risk to system stability. When memory is locked:

  • No Fallback on Exhaustion: If the system runs entirely out of free physical RAM, the kernel cannot page out Memcached to protect other processes.
  • OOM Killer Invocation: System memory exhaustion in a locked-memory environment typically results in the kernel's Out-Of-Memory (OOM) killer terminating processes to recover pages, which often targets Memcached itself if it occupies the largest memory footprint.
  • Capacity Planning: Memcached memory limits (set via -m) must be planned conservatively. Administrators must ensure sufficient overhead exists for OS kernel buffers, network socket buffers, and other essential system processes.
