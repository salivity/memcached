Memcached Slab Page Size Impact on Small Items

Configuring large slab page sizes in Memcached primarily affects memory efficiency, chunk distribution, and memory allocation granularity. While increasing the slab page size allows Memcached to store individual items larger than the default 1MB limit, applying this configuration to workloads dominated by small items leads to internal memory fragmentation, inefficient page allocation across slab classes, and premature cache evictions.

Understanding Memcached Slab Allocation

Memcached manages memory through a slab allocation system to prevent operating system-level memory fragmentation. Memory is divided into pages (defaulting to 1MB), and each page is pre-allocated to a specific "slab class." Each slab class carves its assigned pages into fixed-size chunks determined by the growth factor. When a key-value pair arrives, Memcached places it into the slab class with the smallest chunk size capable of holding the data.

Coarser Memory Granularity and Trapped Memory

The most direct impact of increasing the slab page size (configured via the -I or --max-item-size parameter) is the loss of allocation granularity. When you increase the page size—for example, to 10MB or 64MB—the minimum unit of memory Memcached can allocate to any slab class becomes that larger page size.

If your application stores predominantly small items (e.g., 256-byte session tokens or small JSON objects), a slab class will receive an entire large page even if it only needs to store a handful of items. For instance:

  • A 10MB page assigned to a 256-byte chunk slab class creates roughly 40,960 chunks.
  • If your workload only ever needs 2,000 items in that specific size class, the remaining ~38,960 chunks sit idle within that page.
  • Memcached cannot lend that unused, allocated space within the page to other slab classes that might be running out of memory.

This leads to "trapped memory," where significant amounts of RAM are technically allocated to slab classes but remain unused, reducing the effective capacity of the cache.

Premature Evictions and Slab Starvation

Memcached operates within a fixed total memory boundary set by the -m flag. Total memory is partitioned into a finite number of pages:

\[\text{Total Pages} = \frac{\text{Total Memory}}{\text{Page Size}}\]

Increasing the page size drastically reduces the total number of pages available:

  • With 1GB of total memory and a default 1MB page size, the instance manages 1,024 pages.
  • With 1GB of total memory and a 32MB page size, the instance manages only 32 pages.

Because pages are distributed among different slab classes, having fewer total pages increases the likelihood of slab starvation. If a spike occurs in one item size, an entire 32MB page is assigned to it, consuming over 3% of the total instance memory in a single allocation. Other slab classes with small items may quickly run out of their few allocated pages, triggering Least Recently Used (LRU) evictions prematurely, even when significant total capacity appears to be available globally.

CPU Cache and Memory Access Patterns

While small items continue to occupy chunks sized appropriately for their payload, organizing small items across very large contiguous memory blocks can alter access locality. Large memory strides across expansive pages may increase CPU L1/L2/L3 cache misses and Translation Lookaside Buffer (TLB) thrashing under heavy multi-threaded access, slightly degrading throughput compared to the default 1MB paging layout.

Configuration Recommendations

To maintain optimal performance for small item workloads:

  • Retain the default 1MB page size: Do not increase -I unless your workload strictly requires caching individual values larger than 1MB.
  • Segregate clusters: If the system must handle both large payloads and small items, run two distinct Memcached clusters. Dedicate one instance with the default 1MB page size to small, high-throughput items, and tune a separate instance with a larger slab page size exclusively for bulk data.
  • Enable slab rebalancing: If varying item sizes are unavoidable, ensure modern memory rebalancing features (-o slab_reassign,slab_automove) are active to mitigate imbalances caused by coarse page allocations over time.
