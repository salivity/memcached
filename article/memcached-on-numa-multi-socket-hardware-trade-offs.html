Memcached on NUMA: Multi-Socket Hardware Trade-Offs

Deploying Memcached on multi-socket Non-Uniform Memory Access (NUMA) architecture forces a compromise between shared memory capacity and low-latency throughput. While a single large Memcached instance maximizes key-space capacity and simplifies operational management, cross-node memory access and inter-socket bus saturation degrade performance. Alternatively, partitioning Memcached into node-pinned instances delivers predictable, ultra-low latency at the expense of memory efficiency, operational complexity, and data duplication risks.

The NUMA Problem in Memcached

In modern multi-socket systems, each CPU socket governs its own dedicated local memory bank and communicates with adjacent sockets over high-speed interconnects (such as Intel UPI or AMD Infinity Fabric). Accessing memory attached to a remote socket incurs substantially higher latency (often 1.5x to 3x) and lower throughput compared to accessing local memory.

Memcached relies on high concurrency, fast thread synchronization, and shared in-memory data structures. When run as a single process spanning multiple NUMA nodes, it inevitably triggers cross-socket memory reads and writes, creating several structural bottlenecks.

Architectural Trade-Offs

1. Cross-Socket Latency vs. Global Cache Utilization

  • Single Instance across Sockets: Running one large Memcached instance exposes the entire physical RAM of all sockets to a unified cache. However, threads running on Socket 0 frequently access key-value pairs stored in RAM physically wired to Socket 1. This cross-traffic traverses the processor interconnect, inflating read/write latencies and lowering requests per second (RPS).
  • Partitioned Instances (NUMA-Pinning): Running isolated Memcached instances pinned via numactl or taskset to specific NUMA nodes guarantees all memory access remains local. While latency drops dramatically and scales linearly, total cache space is fragmented. Clients must implement hash rings across multiple ports or endpoints on the same host, and an imbalance in key popularity can lead to premature evictions on one node while another remains underutilized.

2. Thread Synchronization and Interconnect Saturation

Memcached uses fine-grained locking, particularly around hash table buckets and slab allocators, but core synchronization primitives (atomic instructions, mutexes, cache-line invalidations) must cross the interconnect when threads are distributed across sockets.

When a thread on Socket 0 modifies an item or updates an LRU list, the cache coherence protocol must invalidate the relevant cache lines across all sockets. High write workloads induce severe interconnect saturation, resulting in CPU stalls, cache coherence storms, and increased lock wait times.

3. Slab Allocation and Memory Fragmentation

Memcached pre-allocates memory using a slab allocator. In a non-NUMA-aware deployment:

  • Memory pages backing slab classes are allocated dynamically or uniformly striped across NUMA nodes based on the operating system’s allocation policy (e.g., default round-robin or first-touch).
  • If a worker thread on Socket 1 frequently grabs items allocated on memory wired to Socket 0, the latency penalty is sustained permanently for the lifecycle of those slabs.
  • Conversely, splitting Memcached into one process per NUMA node avoids cross-socket allocations but multiplies internal fragmentation. Each instance must independently maintain its own set of slab classes, leading to more unused reserved memory across the system.

4. Network and I/O Locality

Network Interface Cards (NICs) connect to specific PCIe root complexes tied to a single NUMA node.

  • If Memcached worker threads reside on Socket 1, but the 100GbE NIC is attached to Socket 0, all network packet transfers (via DMA and CPU processing of packet queues) must traverse the inter-socket interconnect.
  • Achieving peak throughput requires binding network interrupts (IRQs), socket handling threads, and Memcached worker threads to the specific NUMA node hosting the active NIC. In a multi-instance setup, instances running on non-NIC-attached sockets still incur PCIe traversal penalties unless dual-NICs or NUMA-aware I/O routing are explicitly configured.

Recommended Architectural Strategy

To achieve deterministic performance and maximize multi-socket hardware:

  1. Avoid the Single-Instance Approach: Do not run a single Memcached process spanning multiple NUMA nodes for high-throughput, low-latency requirements.

  2. Deploy Multiple Pinned Instances: Run one Memcached daemon per NUMA domain, pinning CPU cores and memory allocations strictly to that domain using:

    numactl --cpunodebind=<node> --membind=<node> memcached -m <allocated_ram> -t <threads_per_socket> -p <port>

  3. Align Network IRQs: Map the network queues of the local NIC to the corresponding NUMA node, or utilize multi-NIC configurations where each NUMA node directly handles its own I/O pipeline.

  4. Abstract with Client-Side Hashing: Shift cache aggregation to the client level using consistent hashing to route traffic across the per-node local instances running on different ports of the same physical host.
