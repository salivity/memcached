How Memcached Handles Slab Chunk Reallocation

When a modified item in Memcached grows beyond the boundary of its current slab chunk, Memcached cannot expand the chunk in place due to its fixed-memory architecture. Instead, it treats the update as an out-of-place reallocation, searching for a larger slab class that fits the new data, allocating a brand-new chunk, updating internal pointers, and releasing the old chunk back to its original slab class.

The Fixed-Size Slab Allocation Model

Memcached manages memory through a slab allocator to avoid fragmentation. Memory is carved into slab classes, where each class contains pages subdivided into chunks of a predetermined, uniform size (scaled by a growth factor). When an item is initially stored, Memcached assigns it to the smallest chunk size that can accommodate the key, value, metadata, and overhead. Because chunk sizes within a given slab class are immutable, an existing chunk cannot expand.

The Step-by-Step Reallocation Workflow

When an operation—such as append, prepend, or a replace with a larger payload—causes an item to exceed its assigned chunk capacity, Memcached executes the following sequence:

  1. Size Calculation and Class Selection: Memcached calculates the total memory requirement for the modified item (metadata + key + new payload size). It queries the slab engine to find the smallest slab class with a chunk size large enough to hold this new footprint.
  2. New Chunk Allocation: Memcached attempts to allocate a new chunk from the target slab class. It first checks the target slab class’s freelist. If no freed chunks are available, it allocates a new page if total memory allows, or invokes the Least Recently Used (LRU) crawler/eviction mechanism within that specific slab class to reclaim memory.
  3. Data Assembly: Once the new chunk is secured, Memcached writes the updated metadata, the key, and the modified value directly into this newly allocated chunk.
  4. Pointer Swapping: The memory engine updates the central hash table so the key points to the memory address of the new chunk. It also re-links the item within the new slab class's LRU list.
  5. Reclaiming the Old Chunk: Memcached decrements the reference count of the original item. Once the reference count drops to zero, the old chunk is unlinked from its previous LRU queue and returned to the freelist of its original slab class, making it available for future items of that original size.

Failure Handling

If the target slab class is completely full and cannot evict an item (for example, if all existing chunks in that class are locked by active read references, or if evictions are explicitly disabled via -m flags), the reallocation fails.

In this scenario, Memcached leaves the original item completely unmodified in its original chunk. The update operation is aborted, and Memcached returns an out-of-memory error (such as SERVER_ERROR out of memory storing object) to the client, ensuring data integrity is maintained despite the allocation failure.
