Troubleshooting High Latency in Memcached

Diagnosing high latency reports between client applications and Memcached requires a systematic methodology to isolate whether the bottleneck stems from the client environment, the network, or the Memcached server itself. By examining operational metrics, network health, client configuration, and host-level resource contention, you can quickly identify the root cause of slow response times and restore optimal cache performance.

1. Isolate the Source of Latency

Before modifying configurations, determine where time is being spent in the request-response lifecycle:

  • Measure baseline round-trip time (RTT): Use tools like ping, traceroute, or mtr between the client host and the Memcached server to verify if baseline network latency matches the reported delays.
  • Segment client-side processing: Add application-level timing around the raw socket read/write operations versus data serialization and deserialization. Often, high latency attributed to Memcached is actually caused by CPU-heavy object deserialization on the client.

2. Inspect Memcached Internal Metrics

Connect directly to the Memcached instance via telnet or nc and run the stats command to identify server-side bottlenecks:

  • rusage_user and rusage_system: High CPU utilization indicates the server is saturated, frequently processing large volumes of commands or dealing with lock contention.
  • curr_connections and listen_disabled_num: If listen_disabled_num is greater than zero, the server is hitting its maximum connection limit (-c flag) and temporarily refusing new connections, leading to connection timeouts and latency spikes.
  • threads and thread contention: Ensure Memcached is utilizing multiple threads properly (-t option). High worker-thread lock contention can delay query handling.
  • evictions and reclaimed: A high rate of evictions indicates memory pressure, which can cause internal slab allocation overhead.

3. Check for Memory Swapping and Host Contention

Memcached is designed entirely for in-memory operations; any disk interaction will degrade performance drastically:

  • Swap usage: Check free -m or vmstat on the host. If Memcached memory pages are swapped to disk, latency will jump from microseconds to milliseconds. Use the -k option to lock memory pages if supported, or disable swap on the host.
  • Host CPU saturation: Check top or htop to ensure other processes on the same host (noisy neighbors) are not stealing CPU cycles from the Memcached worker threads.

4. Evaluate Network and Socket Performance

Memcached operations rely heavily on efficient packet delivery:

  • TCP retransmissions: Run netstat -s or ss -ti to look for TCP retransmits and dropped segments. Dropped packets trigger TCP backoff algorithms, causing sporadic latency spikes.
  • NIC saturation: Check interface bandwidth and packet rates using sar -n DEV 1 or ethtool -S <interface>. Hitting bandwidth or packet-per-second (PPS) limits will queue requests at the network layer.

5. Audit Client-Side Settings and Payloads

Improper client usage often simulates server degradation:

  • Connection pooling: Verify that clients reuse persistent connections. Creating a new TCP connection (and tearing it down) for every cache operation adds significant latency overhead.
  • Item size and network buffering: Querying large items (nearing the default 1MB limit or customized slab limits) saturates network buffers. Use the stats sizes command to check the distribution of item sizes.
  • Client timeout thresholds: Excessively aggressive client-side socket timeouts can cause clients to drop connections prematurely, creating cascading retries that overwhelm the cache cluster.
