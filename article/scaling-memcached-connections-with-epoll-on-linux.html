Scaling Memcached Connections with epoll on Linux

This article explores the critical role that the Linux epoll system call plays in enabling Memcached to scale from thousands to hundreds of thousands of concurrent network connections. It details the performance bottlenecks of legacy I/O mechanisms like select and poll, explains how epoll achieves \(O(1)\) event-notification complexity, and examines how Memcached integrates with modern Linux kernels via event loops and multi-threading to handle massive connection capacities with minimal CPU overhead.

The Problem with Legacy I/O: select and poll

In early network architectures, servers relied on select() and poll() system calls to monitor multiple file descriptors (sockets) for readability or writability. Both mechanisms suffer from fundamental scaling limitations:

  • Linear Complexity (\(O(N)\)): Every time an application calls select() or poll(), the kernel must scan through the entire list of passed file descriptors to check their readiness states.
  • Repeated State Copying: The entire set of file descriptors must be copied from user space to kernel space on every call, and the results copied back, creating severe memory bandwidth and CPU bottlenecks as connection counts grow.
  • Scalability Drop-off: While Memcached servers frequently manage tens of thousands of idle or intermittently active client connections, select() and poll() force the CPU to waste cycles evaluating all connections rather than only those with pending data.

How epoll Achieves Scalability

Introduced in the 2.6 Linux kernel, epoll replaces linear scanning with an event-driven mechanism optimized for high-density connection handling. It provides three primary design advantages:

  1. State Persistence in the Kernel (epoll_create and epoll_ctl): Sockets are registered once with the kernel using an internal red-black tree. Connections can be added, modified, or removed dynamically without having to re-pass the entire connection set on every poll cycle.
  2. \(O(1)\) Event Notification (epoll_wait): When a network interface receives packets for a specific socket, kernel interrupt handlers fire a callback that places the ready file descriptor into an internal doubly-linked ready list. When the application invokes epoll_wait(), the kernel only returns the descriptors that are actively ready for I/O. The lookup time depends strictly on the number of active events, not the total number of connected clients.
  3. Reduced Context Switching: epoll minimizes user-kernel boundary transitions and memory copies, conserving memory bandwidth and CPU cycles under heavy workloads.

Memcached's Integration via Libevent

Memcached delegates low-level networking and event handling to libevent, a cross-platform abstraction layer that automatically chooses the most performant backend available. On modern Linux, libevent binds directly to epoll.

Memcached couples this backend with non-blocking I/O (O_NONBLOCK). When a client initiates a request or completes a command:

  • Sockets are monitored by epoll in a level-triggered mode.
  • When data arrives, epoll_wait() notifies the application layer immediately.
  • Memcached reads the buffered bytes until the socket would block (EAGAIN or EWOULDBLOCK), returns to the event loop, and waits for the next kernel notification.

Multi-Threaded Event Architecture

To prevent a single CPU core from becoming a bottleneck, Memcached implements a multi-threaded connection-handling model:

  • The Dispatcher Thread: A dedicated master thread listens for new incoming TCP connections on the listening socket.
  • Worker Threads: Memcached launches multiple worker threads, typically matching the host's CPU core count. Each worker thread runs its own isolated libevent instance backed by an independent epoll instance.
  • Load Distribution: When the dispatcher accepts a new connection, it assigns the connection to a worker thread via an internal pipe or queue. The receiving worker registers the new client socket into its local epoll instance.

This architecture decouples connection distribution from request execution, ensuring that locking is minimized and I/O wait times remain uniform across all available CPU cores.

Impact on Modern Linux Kernels

On modern Linux deployments, epoll enables Memcached instances to support hundreds of thousands of concurrent connections per node without memory thrashing or CPU saturation. By removing the dependency between connection count and CPU utilization, epoll ensures that Memcached’s throughput is bound solely by available memory and network bandwidth rather than socket-management overhead.
