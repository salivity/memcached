How Memcached replace Handles Non-Existent Keys

The replace command in Memcached is designed to update existing cache entries without the risk of creating new ones. When you attempt to execute a replace operation on a key that does not exist on the server, the command fails immediately, making no changes to the cache and returning a NOT_STORED status response.

Protocol Response and Mechanism

At the protocol level, Memcached evaluates whether the target key currently resides in memory before applying any modifications. If the key is absent, expired, or has been explicitly deleted, Memcached will not allocate space or insert the payload.

In the ASCII text protocol, the interaction appears as follows:

replace user:1001 0 3600 5
hello
NOT_STORED

In the binary protocol, Memcached responds with a non-zero response status code corresponding to KEY_ENOENT (Key does not exist), rather than a successful status.

Client Library Behavior

Because Memcached returns NOT_STORED, client libraries translate this response into predictable return values or exceptions depending on the language:

  • PHP (Memcached extension): The method $memcached->replace('key', 'value') returns false. Calling $memcached->getResultCode() yields Memcached::RES_NOTSTORED.
  • Python (pymemcache / python-memcached): The client.replace('key', 'value') call typically returns False.
  • Node.js (memcached): The callback returns false for the execution result without a fatal error.
  • Go (gomemcache): The call returns an ErrNotStored error.

replace vs. set and add

Understanding how replace handles missing keys clarifies its role alongside Memcached's other primitive storage commands:

  • set: Unconditionally stores the data. If the key exists, it overwrites it; if it does not exist, it creates it.
  • add: Stores the data only if the key does not exist. If the key exists, it fails and returns NOT_STORED.
  • replace: Stores the data only if the key does exist. If the key does not exist, it fails and returns NOT_STORED.

Common Use Cases

The failure of replace on non-existent keys is useful in scenarios where cache initialization must be strictly controlled:

  1. Preventing Stale Cache Population: If a key has been invalidated or purged due to an update, background workers using replace will not inadvertently restore obsolete data back into the cache if the original entry is already gone.
  2. State Synchronization: It ensures that an update applies only to active, "warm" cache entries, leaving cold cache misses to be handled cleanly by the standard read-through fetching logic.
