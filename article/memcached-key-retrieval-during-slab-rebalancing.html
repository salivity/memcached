Memcached Key Retrieval During Slab Rebalancing

Memcached maintains high availability and continuous read operations even while memory pages migrate between slab classes through a background process called slab rebalancing. When memory needs shift, Memcached moves 1MB memory pages from underutilized slab classes to classes experiencing memory pressure without taking the cache offline. Key retrieval during this migration relies on fine-grained hash table locking, immediate item unlinking, and non-blocking read paths that prioritize low latency at the expense of evicting active keys residing on the migrating page.

The Slab Rebalancing Architecture

Memcached allocates memory in fixed 1MB pages divided into chunks corresponding to specific slab classes. When the slab automove thread identifies an imbalance, it initiates a migration process to reassign a 1MB page from a donor class to a target class.

This migration runs asynchronously via a dedicated background maintenance thread (slab_rebalance_thread). By offloading the heavy lifting of page reallocation to this background thread, worker threads handling incoming client requests—including key retrieval commands like get—are spared from global blocking operations.

Fine-Grained Locking and Concurrency

Memcached does not use a global lock to freeze the cache during page reassignment. Instead, concurrency is handled through item-level lock buckets keyed to the item's hash:

  • Bucket Item Locks: Worker threads processing get commands acquire a read/write lock for the specific hash bucket of the requested key.
  • Granular Interference: The rebalance thread only acquires the specific item lock corresponding to the chunk it is currently evicting.
  • Lock Contention: Requests for keys located on different pages or in different hash buckets execute with zero lock contention. A client reading a key currently being processed by the rebalance thread will briefly wait for the granular item lock to release.

Key Retrieval Lifecycle During Migration

When a page is targeted for migration, the memory chunks on that page must be emptied. The retrieval behavior for any key residing on that page depends on the exact stage of the migration:

  1. Before the Item Is Processed: If a client requests a key residing on a page scheduled for reassignment before the rebalance thread reaches that specific chunk, the hash table lookup succeeds normally. The item is read from memory and returned to the client as a cache hit.
  2. During Item Eviction: When the rebalance thread processes a chunk on the donor page, it acquires the item's hash lock. It removes the item from the central hash table and the LRU (Least Recently Used) doubly linked list. Any incoming get request for this key pauses until the item is unlinked.
  3. After Eviction: Once unlinked from the primary hash table, the key is no longer discoverable. Any subsequent get command hashing to this key immediately results in a cache miss (END or NOT_FOUND). The client application must handle this miss by fetching the source data from the primary database and repopulating the cache.

Memory Safety and Reference Counting

Memcached ensures that in-flight reads do not read corrupted memory if a page's layout is repurposed while data is actively being sent across the network socket.

Every item in Memcached maintains an internal reference counter (refcount). When a worker thread finds an item during a get command, it increments the item's reference count. Even if the rebalance thread evicts the item from the hash table immediately afterward, the underlying memory chunk is protected from physical overwrite until the worker thread finishes transmitting the payload and decrements the counter back to zero. Once all references drop to zero, the rebalance thread completes the reclamation, wiping and reformatting the 1MB page for its new slab class.
