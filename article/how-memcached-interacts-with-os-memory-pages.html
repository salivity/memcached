How Memcached Interacts With OS Memory Pages

This article examines how Memcached communicates with the operating system's virtual memory subsystem when managing large memory allocations. It covers the initial memory reservation process, the division of virtual address space into slab classes, the role of page faults and memory mapping, the performance impacts of Translation Lookaside Buffer (TLB) hits, and strategies such as Transparent Huge Pages (THP) and memory locking to eliminate latency spikes.

Initial Memory Reservation and Virtual Addressing

When Memcached starts with a configured memory limit (using the -m flag), it requests a contiguous block of virtual address space from the operating system, typically using standard allocation functions like malloc or memory-mapped files via mmap.

At the moment of allocation, the operating system assigns virtual memory addresses without immediately committing physical RAM. The OS utilizes demand paging: physical memory pages (standard 4KB frames in most x86 architectures) are not mapped to these virtual addresses until Memcached actually writes to or reads from those locations. As a result, the process's Virtual Size (VIRT) will reflect the entire configured pool immediately, whereas the Resident Set Size (RSS) will grow incrementally as keys and values populate the cache.

Slab Allocation to Prevent OS-Level Fragmentation

Repeatedly allocating and freeing dynamic memory across millions of small caching operations would overwhelm the operating system's memory manager and lead to severe kernel-level memory fragmentation. To circumvent this, Memcached bypasses traditional OS allocations for individual items by implementing an internal slab allocator.

Memcached cuts its large allocated virtual memory pool into fixed-size memory blocks, typically 1MB in size, referred to as slab pages. These 1MB blocks are then carved into smaller, uniformly sized chunks tailored to store items within specific size ranges. Because Memcached manages item allocation and reuse internally within these slab pages, the underlying operating system sees a static, permanent allocation. Physical memory pages allocated to Memcached stay dedicated to the process rather than being returned to the OS kernel on cache item deletions or evictions.

Page Faults and Physical Frame Mapping

As Memcached receives data and writes items into its slab memory, it touches previously untouched virtual addresses within its reserved pool:

  1. Minor Page Faults: When a thread attempts to write to a virtual memory address that lacks a corresponding physical page, the CPU hardware raises a minor page fault.
  2. Page Allocation: The OS kernel handles the fault by locating a free 4KB physical frame from its free list, updating the page table entry (PTE) to map the virtual address to the physical address, and returning execution to the application.
  3. Zeroing: The kernel zeroes out the physical memory frame before granting access to prevent data leakage from previous processes.

Because this fault-handling mechanism introduces a slight latency penalty, large Memcached instances with rapid initial warm-ups experience a burst of minor page faults until the memory footprint stabilizes at its target RSS.

Page Table Overhead and Huge Pages

When managing large memory pools—such as tens or hundreds of gigabytes—standard 4KB memory pages introduce significant architectural overhead:

  • Page Table Bloat: A 64GB pool mapped with 4KB pages requires over 16 million Page Table Entries (PTEs). Maintaining these structures consumes several gigabytes of physical RAM solely for kernel metadata.
  • TLB Misses: The CPU relies on the Translation Lookaside Buffer (TLB) to cache virtual-to-physical address translations. An excessively large page table overwhelms the TLB cache, causing frequent TLB misses that force the CPU to perform high-latency page table walks.

To solve this, Memcached can utilize Huge Pages (typically 2MB or 1GB in size):

  • Explicit Huge Pages (-L Flag): Memcached can be started with the -L (pre-allocate huge memory pages) option. This instructs the application to request large contiguous memory pages from the kernel using mmap with flags like MAP_HUGETLB. This shrinks the number of required page entries by a factor of 512 (for 2MB pages), dramatically reducing TLB cache misses and stabilizing read/write latencies.
  • Transparent Huge Pages (THP): Modern Linux kernels feature THP, which attempts to merge adjacent 4KB pages into 2MB pages dynamically. While this requires no manual huge page configuration, background defragmentation (khugepaged) can induce unpredictable latency spikes or memory locks during high-throughput workloads. Consequently, production deployments often prefer statically allocated huge pages over dynamic THP.

Memory Locking and Swapping Prevention

Under system memory pressure, the operating system kernel's virtual memory manager (kswapd) attempts to reclaim memory by writing inactive anonymous pages out to swap space.

If parts of the Memcached memory pool are swapped to disk, access to an expired or infrequently read key requires disk I/O to bring the 4KB page back into RAM. This turns sub-millisecond in-memory cache operations into multi-millisecond operations, degrading throughput.

Memcached provides the -k flag to execute the mlockall system call. This instructs the OS kernel to pin all current and future virtual pages belonging to the Memcached process into physical RAM. By locking the pages, the operating system is strictly forbidden from paging out or swapping any portion of the Memcached memory pool, ensuring access times remain bound strictly to RAM latency.
