Memcached Chunk Allocation and Slab Boundaries

This article explains how Memcached manages chunk allocation when data sizes sit close to slab class boundaries. Memcached employs a slab allocation system to manage memory efficiently and prevent external fragmentation. When a key-value pair approaches or marginally exceeds a slab threshold, the engine evaluates the full item footprint—including internal metadata and key size—and allocates the smallest chunk that fits the item. This boundary behavior can trigger internal fragmentation, shift memory pressure between slab classes, and require targeted configuration tuning to maintain peak performance.

The Slab Allocation Architecture

Memcached bypasses standard operating system dynamic memory allocation (malloc/free) to eliminate external memory fragmentation. It allocates memory in 1 MB units called slab pages. Each slab page is sliced into uniform chunks.

The sizing of these chunks across different slab classes is governed by a growth factor (defaulting to 1.25). For example:

  • Slab Class 1: 96 bytes
  • Slab Class 2: 120 bytes
  • Slab Class 3: 152 bytes

Each sequential slab class provides incrementally larger chunks to house larger items.

Total Item Size Calculation

When evaluating whether an item fits within a slab boundary, Memcached does not evaluate the key and value in isolation. The engine calculates the total item size using:

  1. Item Header: The internal item struct (typically 48 to 56 bytes on 64-bit systems).
  2. Key Length: The raw byte size of the key string.
  3. Suffix Data: Text-based representations of flags, value length, and CAS (Check-And-Set) counters.
  4. Value Payload: The raw data being stored.

The total byte count of all four elements dictates which slab class must accept the write.

Behavior at Slab Boundaries

When the calculated item size is near a slab boundary, one of two scenarios occurs:

1. Total Size Is Just Below the Boundary

If an item's combined size is marginally smaller than the chunk size of Slab Class \(N\), it is stored in Slab Class \(N\). This is the ideal scenario for memory density, as nearly all allocated bytes inside that chunk are utilized.

2. Total Size Crosses the Boundary

If an item exceeds the chunk size of Slab Class \(N\) by even a single byte, it cannot be accommodated in that class. Memcached rounds up to the next available tier: Slab Class \(N+1\).

For example, if Slab Class 5 provides 240-byte chunks and Slab Class 6 provides 300-byte chunks, an item measuring 241 bytes is allocated a 300-byte chunk in Class 6.

Consequences of Crossing Boundaries

Internal Fragmentation (Slack Space)

Crossing a boundary introduces internal fragmentation. In the 241-byte example assigned to a 300-byte chunk, 59 bytes of memory (nearly 20% of the chunk) remain allocated but unused. When millions of keys exhibit this pattern, significant portions of memory become wasted "slack space."

Disproportionate Evictions

Memcached allocates memory dynamically by assigning 1 MB pages to slab classes as demand dictates. If an application update increases average payload size just enough to cross a boundary, items jump to the next slab class. If that target slab class is out of free chunks and cannot acquire new pages, Memcached begins evicting items via the Least Recently Used (LRU) algorithm in that specific class—even if the previous slab class has ample free capacity.

Mitigating Slab Boundary Inefficiencies

To control memory distribution and limit slack space near slab boundaries, administrators can tune Memcached runtime parameters:

  • Adjust the Growth Factor (-f): Lowering the factor (e.g., -f 1.1 instead of 1.25) creates smaller gaps between slab classes. More granular chunk sizes reduce the maximum possible internal fragmentation when an item crosses a boundary.
  • Enable Slab Automove (-o slab_automove=1 or 2): Modern versions of Memcached can detect imbalances where one slab class suffers evictions while others hold dormant memory, dynamically reassigning 1 MB pages between classes.
  • Optimize Key and Metadata Overhead: Because keys and suffixes count toward the boundary threshold, keeping key names concise can prevent items from spilling into higher, less efficient slab classes.
