jemalloc vs Standard malloc in Memcached

This article examines how memory allocation in Memcached differs when using jemalloc compared to the standard system allocator (typically glibc's ptmalloc). While Memcached uses its own internal slab allocator to manage cached data items, the underlying C memory allocator handles slab page allocation, network buffers, connection states, and internal metadata. Choosing between jemalloc and standard malloc significantly impacts heap fragmentation, multi-threaded concurrency, Resident Set Size (RSS) predictability, and overall throughput under heavy workloads.

Memcached's Memory Architecture

Memcached avoids standard operating system memory fragmentation for cached keys and values by using a built-in slab allocator. It pre-allocates memory in 1MB slab pages and slices them into fixed-size chunks to store items.

However, the internal slab system does not manage all process memory. Memcached still relies on the underlying system allocator for:

  • Allocating the 1MB slab pages themselves.
  • Managing connection buffers (read/write network buffers via libevent).
  • Tracking hash table expansion and internal data structures.
  • Handling transient allocations generated during high-concurrency client requests.

Under heavy traffic, the performance and behavior of these secondary allocations dictate the server's stability.

Thread Contention and Concurrency

Standard glibc malloc uses a fixed pool of memory arenas to reduce lock contention across threads. By default, it scales arenas based on the number of CPU cores. However, when Memcached runs with many worker threads handling tens of thousands of concurrent network connections, threads inevitably contend for arena locks. This lock contention leads to increased CPU latency and performance bottlenecks.

jemalloc was explicitly engineered for high-concurrency multi-threaded environments. It isolates threads using thread-specific caches (tcache) and a larger number of arenas mapped directly to threads via round-robin or thread IDs. Small allocations—such as temporary network buffers—are served entirely from the thread's local cache without acquiring a lock. This architecture allows Memcached to scale throughput linearly across high core counts without suffering allocator-induced wait states.

Memory Fragmentation and RSS Drift

Memory fragmentation is the most significant operational difference between standard malloc and jemalloc in long-running Memcached instances.

  • Standard malloc: Glibc's allocator organizes memory into chunks and heaps. When small, short-lived buffers are interleaved with long-lived allocations, glibc often cannot return freed memory pages back to the operating system. Even if Memcached reports that it is only storing 10 GB of data, the process's Resident Set Size (RSS) can balloon to 20 GB or more. This phenomenon, known as heap bloat, frequently triggers Out-Of-Memory (OOM) killer events in production.
  • jemalloc: Employs precise size classes (binning) and extent-based allocation. It groups allocations of similar sizes together, dramatically reducing external fragmentation. Furthermore, jemalloc actively purges unused physical memory pages back to the operating system using madvise(MADV_DONTNEED) or madvise(MADV_FREE). This keeps Memcached's actual RSS tightly aligned with its true memory utilization.

Slab Management and Page Eviction

When Memcached dynamically moves memory between slab classes (slab automove) or allocates new slab pages, it issues 1MB allocation requests.

Under glibc, repeatedly allocating, freeing, and reallocating large blocks alongside high rates of small connection allocations can cause address space fragmentation. Over time, glibc may fail to find contiguous physical pages for new 1MB slabs, forcing allocation latency spikes.

jemalloc manages chunk and extent allocations cleanly through direct mmap calls, maintaining clear separation between small, short-lived metadata objects and large, long-lived slab allocations. This guarantees that large page requests are fulfilled predictably without scanning fragmented heaps.

Introspection and Diagnostics

Standard malloc provides minimal runtime visibility into allocation health without external profiling tools that introduce performance overhead.

In contrast, jemalloc includes built-in introspection. When Memcached is compiled with jemalloc, administrators can query allocator statistics directly through Memcached diagnostic commands or via jemalloc's malloc_stats_print() API. This exposes precise metrics regarding thread cache utilization, active vs. allocated pages, fragmentation ratios, and metadata overhead, simplifying capacity planning and debugging.
