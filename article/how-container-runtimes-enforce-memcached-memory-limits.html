How Container Runtimes Enforce Memcached Memory Limits

Modern container runtimes rely on Linux kernel-level primitives to isolate and restrict the resource footprint of memory-intensive applications like Memcached. This article explores how runtimes use control groups (cgroups) to track and cap physical memory usage, how the Linux Out-Of-Memory (OOM) killer acts as the final enforcement mechanism, and why Memcached’s internal memory management must be explicitly aligned with these container boundaries to prevent process eviction.

The Role of Control Groups (cgroups)

Container runtimes—such as containerd, CRI-O, and Docker—do not directly monitor or intercept memory allocations in user space. Instead, they configure Linux control groups (cgroups) during the container creation phase, delegating the tracking and enforcement directly to the Linux kernel.

When a memory constraint is defined (such as resources.limits.memory in Kubernetes or --memory in Docker), the container runtime communicates with the low-level Open Container Initiative (OCI) runtime (typically runc or crun). The OCI runtime creates a dedicated cgroup directory for the container and writes the target values into specific kernel interface files:

  • cgroups v1: The limit is written to memory.limit_in_bytes.
  • cgroups v2: The hard limit is written to memory.max, and an optional throttling threshold is written to memory.high.

Once the Memcached process is started, its Process ID (PID) is added to the cgroup's cgroup.procs file. From that moment, every byte allocated by Memcached and its child threads is accounted for by the kernel's memory controller.

Memory Accounting: What the Kernel Counts

The kernel tracks total memory consumption within the cgroup by aggregating several components:

  • Anonymous Memory (RSS): Heap and stack allocations created by Memcached, including dynamic allocations made via malloc or alternative allocators like jemalloc.
  • Page Cache: File system buffers mapped into memory (typically minimal for Memcached, as it operates entirely in RAM).
  • Kernel Memory: Kernel structures created on behalf of the process, such as socket buffers (TCP read/write buffers) and memory slab objects.

Because Memcached maintains thousands of concurrent network connections, socket buffers and connection tracking overhead consume measurable amounts of kernel memory, all of which count toward the cgroup limit.

Threshold Enforcement and the OOM Killer

Enforcement occurs dynamically at the page allocation level:

  1. Reclaim Attempt: When Memcached requests additional memory that causes the cgroup to approach or hit its hard limit (memory.max), the kernel first attempts to reclaim memory. Because Memcached does not rely heavily on reclaimable file page caches, the kernel cannot free substantial amounts of memory through reclamation.
  2. OOM Invocation: If the memory usage reaches the hard boundary and cannot be reclaimed, the kernel invokes the Out-Of-Memory (OOM) killer.
  3. Process Termination: The OOM killer inspects the processes inside the offending cgroup, selects the Memcached process based on its memory footprint and oom_score_adj, and abruptly terminates it with a SIGKILL (exit code 137).

Interaction with Memcached's Internal Allocation

Memcached manages its own cache space using an internal slab allocator configured via the -m runtime flag (which defines the maximum memory dedicated to item storage). However, the container runtime's cgroup limit governs the entire footprint of the running process, not just the slab cache.

A Memcached container's total memory consists of:

\[\text{Total Memory} = \text{Item Cache } (-m) + \text{Connection Overhead} + \text{Thread Stacks} + \text{Allocator Fragmentation}\]

If an administrator sets the container limit equal to the Memcached -m value, the process will inevitably be terminated by the kernel's OOM killer. As active network connections scale up or heap fragmentation increases, the overall memory usage exceeds the cgroup ceiling, triggering a hard enforcement event even if the item cache is not completely full.

To prevent runtime-level eviction, the container memory limit must provide adequate headroom above Memcached's configured -m parameter to absorb TCP buffers, metadata overhead, and memory allocator overhead.
