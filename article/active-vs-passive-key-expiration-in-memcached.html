Active vs Passive Key Expiration in Memcached

Memcached manages memory efficiency and data freshness using time-to-live (TTL) values, relying on two distinct mechanisms to purge outdated data: passive expiration and active expiration. This article examines the core differences between these two strategies, detailing how passive (lazy) expiration evaluates keys upon access while active expiration relies on background routines like the LRU crawler to reclaim memory proactively.

Passive Expiration (Lazy Expiration)

Passive expiration, traditionally referred to as lazy expiration, is Memcached's primary and original method for handling TTL values. Under this mechanism, the server does not continuously monitor keys or set immediate timers to destroy them the moment their TTL reaches zero.

Instead, expiration is deferred until a client issues a read command (such as get or gets) for a specific key. When the request arrives, Memcached inspects the item's metadata:

  1. If the current timestamp is greater than the expiration timestamp, the item is considered dead.
  2. Memcached immediately unlinks the item, releases the memory back to the slab allocator, and returns a cache miss to the client.
  3. If the item has not expired, it is returned normally.

The primary advantage of passive expiration is low CPU overhead. The server expends zero processing power on expired keys that are never queried again. The drawback is that dead data can linger in memory indefinitely if no client ever requests it again, consuming allocated memory slabs until an eviction occurs.

Active Expiration (The LRU Crawler)

To prevent expired, unread data from consuming RAM indefinitely, modern versions of Memcached incorporate active expiration mechanisms, most notably the LRU Crawler.

Active expiration runs asynchronously in the background. Rather than waiting for client queries, an internal maintenance thread walks through the memory slabs to find and purge dead data:

  • Background Inspection: The crawler inspects items sitting in the Least Recently Used (LRU) queues.
  • Proactive Reclamation: If an item's expiration time has passed, the crawler immediately unlinks it and frees the memory chunk, even if no client has queried that key.
  • Configurable Execution: Active crawling can be triggered manually, run on a scheduled interval, or configured to run automatically when memory limits or specific churn thresholds are reached.

The main benefit of active expiration is cleaner memory utilization and reduced pressure on the LRU eviction mechanism. The trade-off is resource usage: running background threads consumes CPU cycles and can introduce minor lock contention if not tuned properly.

Key Differences Summary

Feature Passive Expiration Active Expiration
Trigger On-demand via client access (get operations) Background background threads (e.g., LRU Crawler)
CPU Impact Extremely low; distributed across regular operations Slight background CPU consumption
Memory Footprint Stale data remains in memory until requested or evicted Stale data is removed systematically, freeing memory
Predictability Memory state depends entirely on client traffic Memory state is maintained consistently by the server

In practice, Memcached relies on both approaches concurrently. Passive expiration handles day-to-day access with maximum throughput and minimum latency, while active background crawling prevents neglected keys from monopolizing cache capacity.
