Memcached Active LRU vs Background LRU Crawler

Memcached relies on Least Recently Used (LRU) mechanisms to manage memory constraints, primarily using active LRU maintenance and background LRU crawling. While both systems manage cached items within slab classes, active LRU maintenance operates synchronously on the critical path of client requests to update item recency and evict cold data when memory is full. In contrast, the background LRU crawler runs asynchronously on a dedicated thread to discover and reap expired items proactively without impacting request latency.

What Is Active LRU Maintenance?

Active LRU maintenance is the synchronous management of cache items directly driven by client interactions (GET, SET, ADD, etc.). Whenever an item is accessed or updated, Memcached updates its position in the LRU list to reflect its recency.

  • Inline Eviction: When a slab class runs out of allocated memory and cannot allocate a new slab page, active LRU eviction kicks in. Memcached examines the tail of the LRU queue and immediately deletes the least recently used item to free space for the incoming item.
  • Modern Segmented LRU: Modern Memcached uses a segmented LRU (HOT, WARM, COLD, and TEMP queues) to reduce lock contention and prevent temporary spikes from flushing out long-term cached data. Active maintenance handles item migrations between these queues (for example, bumping an item from COLD back to WARM when accessed).
  • Latency Trade-off: Because active maintenance occurs during the request-response cycle, tail evictions and lock acquisitions introduce microsecond-level latency directly into client operations under heavy write or memory pressure.

What Is Background LRU Crawling?

The background LRU crawler is an asynchronous maintenance utility that traverses slab LRU lists independently of client traffic. Instead of waiting for a client to request an expired item (lazy expiration) or waiting for memory exhaustion (active eviction), the crawler searches for items whose Time-To-Live (TTL) has already lapsed.

  • Asynchronous Reclaiming: The crawler operates on separate background worker threads. When it finds an item that has passed its expiration time, it frees the memory back to the slab allocator without blocking client threads.
  • Preserving Valid Cache Data: Without the crawler, an expired item sitting at the tail of an LRU queue might only be evicted when memory is full. If active eviction triggers, Memcached could inadvertently evict valid, non-expired items if the tail evaluation logic hits cold-but-valid data before lazily discovering expired keys. The crawler cleans these dead keys out beforehand.
  • Rate-Limited Execution: The crawler can be configured to run continuously or on demand, pacing itself via configurable sleep intervals to minimize CPU overhead on the server.

Key Differences

Feature Active LRU Maintenance Background LRU Crawler
Execution Context Synchronous (client request path) Asynchronous (dedicated background thread)
Trigger Mechanism Triggered by client reads, writes, and capacity limits Triggered periodically, continuously, or via administrative commands
Primary Goal Recency ordering and immediate space allocation Proactive purging of expired items (TTL-based)
Latency Impact Can cause latency spikes under high eviction pressure Minimal impact on client request latency
Data Targeted Evicts valid or invalid cold data at the tail when full Reclaims strictly expired data throughout the queues

Active LRU maintenance ensures that Memcached never exceeds its configured memory boundaries during real-time ingest, while the background LRU crawler optimizes memory efficiency by eliminating dead data before it forces unnecessary active evictions.
