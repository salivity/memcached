Memcached Timers and System Time Adjustments

Memcached maintains high-throughput caching performance by decoupling its expiration logic from frequent system clock calls, using an internal, event-driven timer based on process uptime. This architecture allows the server to manage millions of expiring items with minimal overhead while establishing specific behaviors when the underlying operating system clock shifts, jumps, or synchronizes via NTP.

The Internal Clock Architecture

Rather than executing a gettimeofday or clock_gettime system call on every cache lookup or insertion, Memcached maintains an internal clock variable named current_time. A dedicated periodic event fires once every second within the main event loop to update this value.

The internal timer measures seconds elapsed since the Memcached process started (process_started). All internal expiration times for stored keys are stored relative to this process uptime counter, not the global Unix epoch. This design significantly reduces system call overhead, allowing worker threads to read a single integer in memory when evaluating whether a key has expired.

Handling Relative vs. Absolute Expiration

Memcached interprets Time-To-Live (TTL) values passed by clients in two distinct ways based on a 30-day threshold (2,592,000 seconds):

  • Relative Deltas (values \(\le\) 30 days): Treated as an offset from the present. Memcached adds this value directly to current_time.
  • Absolute Epoch Timestamps (values > 30 days): Treated as standard Unix epoch timestamps. Memcached converts the value into an internal relative timestamp by subtracting process_started from the provided epoch value.

System Time Adjustments and Clock Drift

Because Memcached links its internal time to the operating system's wall clock, external adjustments to the system time impact the cache differently depending on how keys were stored:

1. Wall-Clock Jumps and NTP Steps

When a system administrator manually alters the time or an NTP daemon performs a stepped correction (jumping the clock forward or backward abruptly), the relationship between time(NULL) and process_started can become desynchronized.

  • Backward Jumps: If the system clock steps backward, existing absolute timestamps may suddenly evaluate as further into the future than intended. Furthermore, newly inserted absolute timestamps might map to an internal time lower than current_time, causing keys to expire prematurely.
  • Forward Jumps: If the clock jumps forward, active items with absolute expiration timestamps may instantly expire because the recalculated internal target is surpassed.

Relative expirations remain largely resilient to small shifts because they calculate lifetime based strictly on the advancing internal tick counter. However, if the operating system time changes significantly enough to require Memcached to recalibrate process_started, anomalies in key lifetime can occur.

2. Monotonic Timers vs. Real-Time Tracking

Modern versions of Memcached integrate CLOCK_MONOTONIC where possible for connection timeouts, internal locks, and thread operations to ensure that networking layers and thread workers are completely immune to leap seconds and system time steps. However, data storage expiration retains its epoch-aware baseline to satisfy the Memcached protocol's support for absolute Unix timestamps.

Operational Recommendations

To ensure timer accuracy and prevent unexpected cache invalidations across system time changes:

  • Configure NTP with Slewing: Run NTP daemons (such as chrony or ntpd) in slew mode (-x). Slewing gradually adjusts the system clock frequency rather than jumping, preserving continuity in the internal timer tick.
  • Prefer Relative TTLs: Client applications should pass relative expiration deltas (e.g., 3600 for one hour) rather than calculated Unix timestamps. This isolates the cache items from changes in wall-clock time.
