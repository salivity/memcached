Memcached TTL: Seconds vs Unix Timestamps Explained

Memcached determines key lifetimes using a dual-mode expiration mechanism that distinguishes between relative durations in seconds and absolute Unix timestamps. By evaluating whether the provided expiration parameter is greater than a fixed 30-day threshold, Memcached automatically decides whether to calculate the expiration relative to the current server time or treat the input as a fixed point in the future. Understanding this internal boundary is critical for preventing premature key evictions and unintended cache invalidations.

The 30-Day Boundary Rule

When setting an item's expiration (exptime) in Memcached, the system evaluates the integer value against a hardcoded constant: 2,592,000 seconds (60 seconds × 60 minutes × 24 hours × 30 days).

  • Values up to 2,592,000: Memcached interprets the number as a relative offset in seconds from the exact moment the command is received.
  • Values greater than 2,592,000: Memcached treats the number as an absolute Unix timestamp (the number of seconds elapsed since January 1, 1970, 00:00:00 UTC).
  • Value of 0: The key is configured to never expire automatically, remaining in cache until explicitly removed or evicted under memory pressure via the Least Recently Used (LRU) algorithm.

Handling Relative Expiration (Seconds)

If an application specifies a key lifetime between 1 and 2,592,000, Memcached adds this value to the current server time (current_time + exptime). For instance, passing 3600 instructs Memcached to expire the key exactly one hour from storage time. This mode is the standard approach for short-to-medium cache lifetimes, such as session data, rate-limiting counters, and short-term query caching.

Handling Absolute Expiration (Timestamps)

Any integer exceeding 2,592,000 is processed directly as an absolute Unix epoch timestamp. For modern applications, standard epoch timestamps are well above 1.7 billion, safely exceeding the 30-day limit. When using this format, Memcached sets the expiration to that exact target time regardless of when the key was written. This approach is optimal for synchronizing cache expirations across multiple distributed servers or aligning cache purges with scheduled events, such as midnight rollouts or batch database updates.

Critical Pitfalls and Edge Cases

The automatic switching mechanism can produce severe bugs if dynamic values cross the 30-day threshold without format conversion:

  • Durations Exceeding 30 Days: If a developer intends to store a key for 40 days and passes 3,456,000 as a relative offset, Memcached misinterprets this as a Unix timestamp corresponding to early February 1970. Because that timestamp is in the distant past, Memcached immediately purges the item upon insertion. To store an item longer than 30 days, the application must compute and supply the target Unix timestamp (time() + 3456000).
  • Server Clock Skew: Absolute timestamps rely on clock synchronization between client servers and Memcached nodes. If a client's system clock drifts ahead of the Memcached host, keys assigned an absolute timestamp may survive longer than expected. Conversely, if the Memcached server is ahead of the client, keys will expire prematurely. Relative offsets avoid this issue by calculating expiration purely against the local time of the Memcached process.
