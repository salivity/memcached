Memcached High Availability Without Clustering

Memcached is inherently a stateless, non-replicated caching system that relies on client-side partitioning rather than native clustering or data replication. Because a failure of an individual node can result in cache misses and severe database load, applications must implement external architectural patterns to ensure uptime and performance. This article outlines the primary strategies—including proxy layers, active-active dual writing, advanced consistent hashing, and layered caching—that allow engineering teams to achieve high availability with Memcached.

Proxy-Based Routing and Replication

The most scalable method for decoupling Memcached availability from the application layer is deploying an intelligent proxy, such as Mcrouter. Developed by Facebook, Mcrouter sits between your application and your Memcached instances to provide capabilities not natively supported by the daemon:

  • Automatic Failover: Mcrouter can be configured with failover route handles. If a primary Memcached server fails to respond, requests are immediately redirected to a designated backup instance without application intervention.
  • Connection Pooling: It maintains persistent connection pools to the backend instances, reducing connection churn and latency.
  • Shadowing and Cross-Region Replication: Mcrouter enables asynchronous replication across separate server pools or distinct data centers, ensuring that a total failure in one availability zone does not impact the cache hit ratio in another.

Alternative proxies, such as Twemproxy (nutcracker), can also manage connection overhead and distribute traffic across a dynamic pool of servers, abstracting failure management away from application code.

Dual-Writing (Active-Active Clusters)

For architectures that do not use a dedicated proxy, application-level dual-writing provides direct control over redundancy.

In this model, two distinct and isolated Memcached pools are deployed. When updating or invalidating data, the application writes simultaneously to both pools. When reading data:

  1. The client requests data from the primary cluster.
  2. If the primary request times out or returns a cache miss, the client automatically falls back to the secondary cluster.
  3. If the primary cluster node is determined to be offline, a background health-check mechanism temporarily suppresses traffic to that node, reading exclusively from the secondary.

While this approach doubles the network write overhead and requires strict handling of race conditions during updates, it guarantees that an entire pool can fail with zero downtime and minimal degradation of cache hit rates.

Consistent Hashing with Ketama and Dynamic Removal

Memcached client libraries typically distribute keys using consistent hashing, most commonly the Ketama algorithm. Consistent hashing maps both cache keys and server nodes to a virtual hash ring.

To maintain availability during a single-node failure:

  • Graceful Degradation: When a node fails, consistent hashing ensures that only the keys mapped to the failed node are invalidated, leaving the rest of the cache intact.
  • Dynamic Node Ejection: Modern client libraries can be configured to automatically eject unresponsive nodes from the ring. When an instance drops, its slice of the hash ring is redistributed across the remaining live nodes.
  • Circuit Breakers: Implement circuit breakers around cache calls. If a node begins timing out, the application should fast-fail requests to that specific instance rather than exhausting worker threads waiting for network timeouts.

Note: Automatically adding or removing nodes causes cache redistribution, which can temporarily increase database load. Pair this strategy with rate limiters or cache warmers to manage the impact.

Layered Caching (L1/L2 Topology)

High availability can also be achieved by insulating Memcached with a tiered caching architecture:

  • L1 (In-Memory Application Cache): Store frequently accessed, read-heavy keys inside the application process memory using local libraries (such as Guava or Caffeine in Java, or local process memory in Node.js/Go). This layer absorbs the bulk of requests and survives network partitions.
  • L2 (Distributed Memcached): Memcached acts as the shared second layer.

If a Memcached instance becomes unavailable, the local L1 cache prevents immediate thundering herds from overwhelming the primary database, providing a buffer period for the Memcached node to recover or be replaced.

Stampede Protection on Failover

A major risk during cache node failure is the cache stampede (or "dogpile" effect), where thousands of concurrent processes attempt to rebuild the missing data in the primary database simultaneously. To maintain system availability during a cache outage:

  • Mutex Locks: Require workers to acquire a distributed or local mutex before recomputing a cache value. Only one thread recomputes the data, while others wait or return stale data.
  • Probabilistic Early Expiration (XFetch): Background workers recompute keys slightly before their actual time-to-live (TTL) expires based on request probability, ensuring high-traffic keys rarely experience a total miss, even during cluster degradation.
