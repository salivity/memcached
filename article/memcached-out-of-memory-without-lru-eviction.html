Memcached Out of Memory Without LRU Eviction

When a Memcached node runs out of memory with Least Recently Used (LRU) eviction disabled, it immediately stops accepting new data writes and returns server errors. While read operations for existing cached items continue to function normally, any attempt to insert or expand data fails until memory is explicitly freed. This behavior shifts Memcached from a typical self-managing transient cache into a rigid in-memory store, which can trigger cascading performance bottlenecks in downstream databases.

The -M Flag and the Failure Mode

By default, Memcached automatically frees up space by identifying and evicting the least recently accessed items when its memory limit is reached. However, running the Memcached daemon with the -M flag (or disable_evictions configuration) explicitly disables this mechanism.

Once the allocated slab memory is completely saturated under these settings, the following behaviors occur:

  • Write Failures: Commands that attempt to allocate new memory—such as set, add, or prepend—fail. Memcached returns an explicit error to the client, typically SERVER_ERROR out of memory storing object.
  • Read Operations Persist: All get operations for keys already residing in memory continue to work as expected, provided those items have not surpassed their individual Time-To-Live (TTL).
  • Deletions and Expirations Still Free Space: While Memcached will not actively discard valid data to accommodate incoming traffic, keys explicitly removed via the delete command or items that naturally reach their expiration timestamp will release their memory, making room for new writes within their respective slab classes.

Slab Allocation Complications

Memcached manages memory through a slab allocation system, grouping data into specific memory chunks based on item size. Even if total global memory has not reached 100%, an individual slab class can become fully saturated.

With LRU eviction disabled, if a specific slab class runs out of available pages and the global memory pool is exhausted, Memcached cannot redistribute memory or evict items in that specific class. Consequently, writes for items of that specific size profile will fail immediately, even if other slab classes still contain unused slots.

Impact on Downstream Architecture

Operating Memcached without evictions fundamentally alters how applications interact with the caching tier, often producing severe operational side effects:

  1. Cache Stampedes and Database Load: In a typical cache-aside pattern, a write failure in Memcached means application threads cannot store fresh query results. The application continues to query the primary database on every single request, causing database CPU spikes and potential outages.
  2. Unhandled Application Exceptions: Many client libraries expect Memcached writes to succeed quietly or fail soft. Unhandled SERVER_ERROR responses can lead to 500-level HTTP errors, broken sessions, or stalled application threads.
  3. Stale Data Accumulation: If keys are inserted without a TTL and eviction is turned off, memory cannot be reclaimed automatically. The cache becomes static, holding onto old items indefinitely while rejecting all updates.

Disabling LRU eviction is typically reserved for specialized architectures where data loss within the cache cannot be tolerated under any circumstances, and where upstream applications actively manage cache sizing, explicit invalidation, and memory thresholds.
