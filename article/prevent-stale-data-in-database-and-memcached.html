Prevent Stale Data in Database and Memcached

Maintaining cache consistency between a primary database and Memcached is a classic distributed systems challenge known as the dual-write problem. When updates occur concurrently, network latencies and race conditions can leave Memcached with obsolete values, causing applications to serve stale data. This article explores the primary software design patterns used to prevent stale reads, including Cache-Aside with Invalidation, Delayed Double-Deletion, Change Data Capture (CDC) via the Transactional Outbox pattern, and Cache Leases.

The Problem with Concurrent Dual-Writes

The dual-write problem arises when an application attempts to write to both a database and a cache sequentially. If the cache is directly updated with new values alongside the database, concurrent writes can arrive out of order (e.g., Thread A writes DB, Thread B writes DB, Thread B updates Cache, Thread A updates Cache). As a result, the cache holds the older data indefinitely. To mitigate this, robust systems rely on cache invalidation and coordinated update patterns.

1. Cache-Aside with Cache Invalidation

Instead of updating the cache value on a write, the Cache-Aside (Lazy Loading) pattern with invalidation deletes the cache key.

  • Read Path: The application checks Memcached. If a cache hit occurs, it returns the data. If a cache miss occurs, it queries the database, writes the result to Memcached, and returns.
  • Write Path: The application writes directly to the database first. Upon a successful database transaction commit, the application explicitly deletes (invalidates) the corresponding key from Memcached.

Deleting the key instead of updating it prevents race conditions caused by out-of-order writes. The next read operation is forced to fetch the fresh state from the database.

2. Delayed Double-Deletion Pattern

A subtle race condition can still occur in Cache-Aside:

  1. Thread A reads the database (old data) after a cache miss.
  2. Thread B updates the database and deletes the cache key.
  3. Thread A writes the old data it fetched back into Memcached.

The Delayed Double-Deletion pattern mitigates this window of inconsistency:

  1. The application updates the database.
  2. The application deletes the Memcached key immediately.
  3. The application sleeps for a configured duration (e.g., 500ms, calculated based on read query latency).
  4. The application deletes the Memcached key a second time asynchronously.

This second deletion ensures that any read operation that fetched old data during the write transaction will have its cached result wiped out shortly after.

3. Change Data Capture (CDC) and Transactional Outbox

To decouple application logic from cache updates and ensure transactional consistency, many architectures adopt asynchronous Change Data Capture (CDC).

  • Mechanism: The application writes only to the database. A background daemon (such as Debezium tailing database transaction logs like MySQL binary logs or PostgreSQL WAL) reads committed changes sequentially.
  • Action: The CDC consumer processes the stream of committed changes and invalidates the corresponding Memcached keys.
  • Benefit: This eliminates partial failures where a database write succeeds but the network call to Memcached fails. Because CDC operates on committed transactions in exact commit order, stale data cannot overwrite newer data.

4. Cache Leases (Check-And-Set / Gutter Pattern)

Pioneered at scale by architectures like Facebook's Memcached infrastructure, cache leases address both stale reads and thundering herd problems:

  • Mechanism: When a cache miss occurs, Memcached grants the client a "lease" (a short-lived token) to fetch and set the data.
  • Stale Invalidation: If the database updates while the client is fetching data, Memcached invalidates the lease token. When the client attempts to write the fetched data back using the lease, the write fails because the token is no longer valid.
  • Result: The application avoids overwriting freshly invalidated keys with older database reads.

Summary of Implementation Strategy

For low-concurrency systems, standard Cache-Aside with post-commit deletion paired with reasonable TTLs (Time-To-Live) is generally sufficient. For high-concurrency environments with strict data freshness requirements, deploying Change Data Capture (CDC) or implementing Cache Leases provides the strongest safeguards against race conditions and permanent cache drift.
