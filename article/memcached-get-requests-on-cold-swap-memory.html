Memcached Get Requests on Cold Swap Memory

When Memcached receives a get request for a key whose memory page has been moved to cold swap space, the retrieval process shifts from a sub-millisecond memory lookup to a high-latency disk operation managed entirely by the operating system kernel. Because Memcached is agnostic to physical memory management, it relies on the operating system’s virtual memory manager to resolve hardware page faults, bringing the cold data back into physical RAM before completing the request. This article explains the exact technical sequence that occurs when fetching swapped data and highlights the performance implications for Memcached deployments.

The Virtual Memory Abstraction

Memcached allocates its memory using slab allocators mapped directly into its virtual address space. It does not track whether a specific slab or item structure physically resides in physical RAM or on a swap partition or file. From the perspective of the Memcached process, all memory is simply a collection of virtual addresses. Memory paging, swapping out idle pages to disk, and paging them back in are managed completely by the host operating system's kernel.

Step-by-Step Execution of a Get Request on Swapped Data

When a client issues a get <key> command targeting data held in cold swap, the request executes through the following phases:

  1. Request Parsing and Hash Table Lookup
    The dedicated worker thread reads the command from the network socket buffer. It hashes the key to locate the appropriate bucket in the primary hash table. If the hash table entry itself resides in physical RAM, this step completes immediately, identifying the virtual memory address of the target item pointer.

  2. Pointer Dereference and Page Fault Trigger
    The worker thread attempts to dereference the pointer pointing to the item structure to read its metadata (flags, expiration time, and data payload). Because the data was moved to swap memory due to memory pressure or inactivity, the CPU's Memory Management Unit (MMU) cannot find the physical address in the page table. This triggers a major hardware page fault.

  3. Kernel Intervention and Disk I/O
    The CPU halts the execution of the Memcached worker thread and yields control to the operating system kernel's page fault handler. The kernel identifies the disk block containing the required 4KB virtual memory page within the swap space and initiates a synchronous or asynchronous read from disk.

  4. Page-In to Physical RAM
    The operating system reads the data from disk into an available physical memory frame. If physical memory is completely exhausted, the OS may first evict another active page using its own page replacement algorithm (such as Least Recently Used) to make room. Once the page is loaded into physical RAM, the kernel updates the process's page table entries.

  5. Thread Resumption and Response Dispatch
    The kernel marks the Memcached worker thread as runnable. Once scheduled back onto a CPU core, the thread re-executes the memory read instruction. It successfully accesses the key's metadata and data payload, constructs the text or binary protocol response, writes it to the socket output buffer, and returns the value to the client.

Performance Impact of Swapped Lookups

The transition from RAM to swap fundamentally degrades Memcached's primary utility:

  • Latency Spikes: A typical in-memory retrieval takes tens of microseconds. If a page fault forces a read from an SSD or NVMe drive, latency increases to hundreds of microseconds or low milliseconds; on mechanical hard drives, it can exceed 10 milliseconds.
  • Worker Thread Blocking: Memcached relies on an event-driven, non-blocking I/O model (using libevent) to manage network traffic. However, OS page faults block the entire thread at the CPU instruction level. While one worker thread waits on disk I/O, all other client connections multiplexed onto that same worker thread are queued, causing cascading latency spikes and connection timeouts across the application.
