Memcached Key Invalidation in Cache-Aside

In a cache-aside architecture, Memcached operates as a passive data store that has no direct awareness of the underlying database. Consequently, managing key invalidation is not handled by Memcached itself, but rather orchestrated by the application layer using explicit key deletion, automated expiration through Time-to-Live (TTL) settings, and fallback eviction via the Least Recently Used (LRU) algorithm.

Application-Driven Explicit Invalidation

The primary method for invalidating data in a cache-aside pattern is explicit deletion handled by the application logic during write operations.

When an application performs an update, insert, or delete operation on the primary database, it directly sends a delete command to Memcached for the corresponding key. Rather than updating the cache value directly with the new data, deleting the key is preferred to prevent race conditions.

When a subsequent read request arrives:

  1. The application checks Memcached for the key.
  2. Because the key was deleted, a cache miss occurs.
  3. The application queries the updated record from the primary database.
  4. The application populates Memcached with the fresh data before returning it to the user.

Time-To-Live (TTL) Expiration

To account for potential network partitions, application crashes, or edge-case bugs where an explicit delete command fails to execute, every key should be stored with an expiration timestamp (TTL).

Memcached uses passive or "lazy" expiration. It does not actively scan memory to delete expired keys. Instead, it checks the TTL of an item only when a read request is made for that specific key. If the current timestamp is greater than the expiration timestamp, Memcached marks the item as expired, returns a cache miss, and frees the memory for that key.

Least Recently Used (LRU) Eviction

When Memcached reaches its configured memory limit and new data must be stored, it invalidates keys via memory eviction. Memcached utilizes a segmented LRU (Least Recently Used) mechanism per slab class.

Under memory pressure, the engine identifies and evicts the least recently accessed items to free memory chunks for incoming writes. While not a method for enforcing data freshness, LRU eviction serves as an automated invalidation safeguard to prevent the cache from running out of memory.

Mitigating Race Conditions with Key Versioning

A common failure mode in cache-aside invalidation occurs when a slow read request fetches stale data from the database, an update occurs and deletes the cache, and the slow read then writes the stale data back to the cache.

To prevent stale writes without complex locking, applications can use key versioning. By appending a version counter or a timestamp to the key name (e.g., user:100:v2), an update merely increments the version reference stored in a centralized pointer or database record. When the key format changes, any pending write from a slow read targets an abandoned key version, effectively invalidating the previous cache entry.
