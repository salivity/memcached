How Memcached Handles Writes at Memory Limit

When Memcached reaches its maximum allocated memory limit, it relies on predefined memory management policies to determine whether to accept, evict, or reject incoming write operations. Under standard configurations, the system uses a segmented Least Recently Used (LRU) algorithm within its slab allocation system to purge older items and make room for new data. However, if administrators strictly enforce memory limits by disabling automatic evictions, Memcached alters this process, refusing new allocations and returning out-of-memory errors to clients once capacity is saturated.

The Role of Slab Allocation

Memcached manages memory through a slab allocation mechanism rather than allocating individual bytes on demand. Memory is carved into large 1 MB pages, which are then subdivided into chunks of fixed sizes grouped into "slab classes."

When a write command (such as set, add, or replace) arrives:

  1. Memcached determines the exact size of the payload.
  2. It assigns the key-value pair to the most suitable slab class with chunks large enough to hold the data.
  3. It checks for available chunks within that specific slab class.

Because memory is partitioned into these isolated classes, write operations are constrained by memory availability within the target class, not just the global pool.

Standard Eviction Behavior (Default Mode)

By default, Memcached never stops accepting writes simply because it reaches its global memory limit. Instead, it follows a cascading sequence to store the incoming write:

  1. Reclaim Expired Items: The system first searches for expired keys (based on Time-To-Live, or TTL) within the targeted slab class to reuse their memory slots.
  2. LRU Eviction: If no expired keys are available and the slab cannot allocate a new page, Memcached evicts the least recently used item within that specific slab class to accommodate the new record.
  3. Segmented LRU Queues: Modern versions of Memcached split the LRU into multiple sub-queues (HOT, WARM, and COLD) to protect actively read items from being immediately flushed by bursts of incoming writes.

Strict Enforcement Mode (-M Flag)

When strict memory limits are explicitly enforced—typically enabled by passing the -M (disable eviction) command-line flag during startup—Memcached disables the LRU eviction fallback entirely.

Under this configuration:

  • Existing Key Updates: If a write operation targets an existing key and the new value fits within the already allocated chunk, the write succeeds.
  • Expired Item Replacement: If expired items exist in the appropriate slab class, Memcached reclaims that space for the new write.
  • Write Failures (Out of Memory): If the memory ceiling has been met and no expired chunks exist in the required slab class, the write operation is aborted.

When a write fails under strict memory limits, Memcached returns an out-of-memory response (such as SERVER_ERROR out of memory storing object) directly to the client application. The client must then handle the failure, either by implementing backoff strategies, deleting stale keys manually, or bypassing the cache.

Slab Rebalancing

In situations where one slab class is exhausted while others retain free memory, Memcached utilizes an automatic slab rebalancing thread. This background worker periodically identifies underutilized memory pages and shifts them to slab classes facing heavy write contention. Even under strict memory limits, this mechanism can dynamically free up space for writes, provided the total server memory limit has not been fully saturated across all classes.
