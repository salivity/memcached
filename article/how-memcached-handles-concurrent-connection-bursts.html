How Memcached Handles Concurrent Connection Bursts

Memcached maintains system stability during sudden bursts of concurrent client connections through an asynchronous, event-driven architecture paired with a fixed multi-threaded design. Rather than creating a new thread or process for each incoming client, Memcached delegates connection handling to non-blocking network sockets managed by an underlying event library. This decoupled design, supported by fixed connection limits and granular internal locking, prevents resource exhaustion, minimizes operating system context switching, and ensures predictable throughput under severe traffic spikes.

Asynchronous I/O via libevent

At the core of Memcached’s connection handling is libevent, an asynchronous event notification library that wraps operating-system-specific polling mechanisms like epoll on Linux or kqueue on BSD/macOS.

Instead of blocking an execution thread while waiting for network data, Memcached sets all client sockets to non-blocking mode. The event notification system alerts Memcached only when a socket has data ready to be read or buffer space available to be written. This allows a minimal number of operating system threads to monitor tens of thousands of idle or bursty connections with negligible CPU overhead.

Multi-Threaded Dispatcher Model

Memcached divides the workload between two distinct roles: a single main listener thread and a configured pool of worker threads.

  1. The Dispatcher Thread: The primary listener thread runs its own event loop dedicated exclusively to the listening socket. When a sudden burst of new TCP connections arrives, the main thread accepts these connections and immediately delegates the resulting file descriptors to worker threads via inter-thread communication pipes in a round-robin distribution.
  2. Worker Threads: Each worker thread maintains its own independent libevent loop. Once a worker receives a connection descriptor from the dispatcher, it registers the socket with its local event loop and handles all subsequent network I/O, protocol parsing, and command execution for that client.

Because the pool of worker threads is fixed (typically matched to the host's available CPU cores), the system avoids thread-creation overhead and the severe performance degradation caused by CPU context switching during connection spikes.

Connection Limits and Backlog Queues

Memcached relies on predefined boundaries to protect its operating environment:

  • Maximum Connections (-c): By default, Memcached enforces a connection cap (typically 1024, though adjustable). When this ceiling is hit during an aggressive burst, Memcached rejects new connections immediately rather than consuming memory and file descriptors until the host operating system crashes.
  • Listen Backlog (-b): Pending TCP connections that have not yet been accepted by the dispatcher wait in the operating system's kernel TCP backlog queue. If the dispatcher thread experiences a momentary delay, the kernel buffers the handshakes up to the backlog limit, smoothing out brief spikes.

Buffer Management and Memory Allocation

Connection bursts frequently induce memory spikes because each connected client requires read and write buffers. Memcached mitigates this pressure by dynamically allocating and freeing read/write buffers according to request sizes, returning idle buffers to an internal freelist rather than constantly allocating memory via the system malloc.

Furthermore, key-value storage operations occur within a pre-allocated slab allocator. Because storage memory is already reserved at startup, sudden connection spikes never trigger out-of-memory (OOM) states for dataset storage, ensuring that the daemon maintains predictable memory consumption regardless of client volume.

Granular Thread Synchronization

To prevent worker threads from bottlenecking one another when executing commands from concurrent connections, Memcached employs fine-grained locking. Hash table lookups and item accesses utilize a collection of striped item locks rather than a single global lock. Consequently, requests arriving concurrently across different worker threads rarely contend for the same mutex, enabling linear scaling and low latency during traffic surges.
