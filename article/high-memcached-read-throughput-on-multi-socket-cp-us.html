High Memcached Read Throughput on Multi-Socket CPUs

Memcached achieves exceptional read throughput on multi-socket CPU architectures by combining an asynchronous, event-driven multithreading model with fine-grained concurrency controls and NUMA-aware system tuning. Rather than relying on a single global lock, it distributes network I/O across worker threads and utilizes hash-table lock striping to minimize lock contention. Under heavy read workloads, Memcached avoids modifying shared memory states whenever possible, mitigating the cross-socket interconnect bottlenecks and cache-line invalidation penalties typical of multi-socket Non-Uniform Memory Access (NUMA) hardware.

Multithreaded Event-Driven Architecture

Memcached uses libevent to drive an asynchronous, non-blocking network model based on a master-worker thread pattern. When deployed on high-core, multi-socket servers, the workload is distributed as follows:

  • Dispatcher Thread: Listens for incoming client TCP/UDP connections and assigns them to worker threads via a round-robin mechanism over internal pipes.
  • Worker Threads: Each worker thread manages its own event loop and handles multiple client connections concurrently. This prevents context switching overhead and allows the server to fully saturate available CPU cores across all sockets.

By isolating connection handling to distinct threads, Memcached eliminates inter-thread coordination for network reads and writes.

Hash Table Lock Striping

Early versions of Memcached utilized a single global cache lock, which severely degraded performance on multi-core and multi-socket setups due to lock contention. Modern Memcached replaces this with granular lock striping across its primary hash table:

  • Item Locks: The hash table is partitioned into thousands of distinct lock buckets (using a power-of-two array of mutexes).
  • Targeted Synchronization: When a worker thread reads an item, it computes the key's hash and acquires only the specific lock governing that hash bucket.
  • High Concurrency: Concurrent reads targeting different hash buckets execute simultaneously across different CPU sockets without blocking each other.

Because read operations do not require updating the hash table structure itself, contention on these bucket locks remains minimal during read-heavy traffic.

Mitigating Cache-Line Bouncing on Multi-Socket CPUs

In a multi-socket machine, CPUs communicate across high-speed interconnects (such as Intel UPI or AMD Infinity Fabric). If multiple sockets frequently write to the same memory address, the hardware cache coherence protocol continuously invalidates CPU L1/L2 caches, causing "cache-line bouncing" and degrading memory bandwidth.

Memcached optimizes the read path to prevent this:

  • Read-Only Key Traversal: Read operations traverse the hash table and read the data payload without mutating shared structures.
  • Decoupled Statistics: Global counters and telemetry are often thread-local or aggregated asynchronously, preventing cross-socket atomic updates on every single get operation.
  • Optimized Reference Counting: While reference counts on items must be adjusted to prevent premature eviction during a read, modern optimizations minimize the duration of these atomic increments and decrements, reducing cross-socket synchronization latencies.

NUMA Awareness and Memory Placement

Multi-socket architectures feature Non-Uniform Memory Access (NUMA), where accessing memory attached to a local socket is significantly faster than accessing remote memory attached to another socket.

To maximize read throughput:

  • Thread and Memory Pinning: Administrators often run Memcached with CPU affinity using utilities like numactl or taskset. Pinning specific worker threads to the CPU socket physically closest to the memory nodes holding the hash table reduces interconnect traversal.
  • Interleaved Allocation: In instances where a single Memcached instance spans all sockets, configuring NUMA policy to interleave memory across all nodes prevents memory bus saturation on a single socket.
  • Instance Partitioning: In high-scale deployments, the standard practice is running multiple distinct Memcached instances bound to individual NUMA nodes rather than a single large instance spanning sockets, effectively eliminating cross-socket latency altogether.

Network Stack Scaling via SO_REUSEPORT

To prevent the kernel network stack from becoming the bottleneck across sockets, Memcached supports the SO_REUSEPORT socket option. This allows multiple worker threads to bind independently to the exact same listening port. The Linux kernel then distributes incoming connections directly across the worker threads at the socket layer, distributing packet processing across the CPU sockets and eliminating the single dispatcher thread bottleneck entirely.
