How Memcached Handles Client Connection Resets

When a client unexpectedly aborts an active transmission by sending a TCP reset (RST) packet, Memcached detects and absorbs the failure without interrupting worker threads or crashing the server. By pairing non-blocking sockets with the libevent asynchronous I/O framework, Memcached immediately catches the broken connection at the system call level, systematically unwinds active transmission states, decrements reference counters on in-flight cache items, and recycles connection resources back to its internal thread pools.

Signal Handling and Failure Detection

When a client resets a socket during an active read or write, subsequent network operations on that file descriptor fail. During an active transmission, Memcached typically pushes outgoing data via non-blocking write calls such as writev() or sendmsg(). Writing to a reset socket would normally trigger a kernel-level SIGPIPE signal, which terminates an unconfigured process.

To prevent this, Memcached explicitly ignores this signal on startup using signal(SIGPIPE, SIG_IGN). As a result, the failed system call returns -1 and sets the thread-local errno to EPIPE or ECONNRESET. If the reset occurs while Memcached is reading requests, recv() or read() similarly returns 0 (EOF) or -1 with ECONNRESET.

The State Machine and libevent

Memcached assigns client connections to worker threads, each driving an independent libevent event base. Every active connection is tracked via a connection structure (conn) governed by an internal finite state machine.

Upon encountering ECONNRESET or EPIPE, the worker thread immediately halts its transmission loop. Instead of retrying the operation, the worker thread transitions the connection state to conn_closing. The event loop ceases polling the associated socket descriptor for both read and write readiness, detaching the event from libevent to avoid busy-wait loops or descriptor leaks.

Resource Cleanup and Item Dereferencing

A critical part of handling an abrupt disconnect during transmission is ensuring memory consistency, particularly for large objects spanning multiple network packets.

When Memcached begins transmitting a cached entry to a client, it increments the reference count of the corresponding item structure within the slab allocator. This prevents the LRU (Least Recently Used) cache eviction engine from freeing or overwriting the item while it is being read from memory.

When the state machine moves to conn_closing:

  1. Item Dereferencing: Memcached iterates through any partially transmitted or queued items attached to the connection's I/O vectors (iovec) and calls item_remove(). This safely decrements their reference counters, allowing the items to be evicted or updated normally in the future.
  2. Buffer Reclamation: Any dynamic transmit buffers allocated for protocol headers or responses are reset or returned to the thread’s memory cache.
  3. Descriptor Teardown: The socket file descriptor is closed using standard system calls (close()), alerting the kernel to clean up remaining TCP buffer control blocks.
  4. Structure Recycling: Rather than freeing the conn struct via free(), Memcached places it into a pre-allocated pool of free connection objects managed by that worker thread, eliminating memory fragmentation and reducing allocation overhead for incoming connections.
