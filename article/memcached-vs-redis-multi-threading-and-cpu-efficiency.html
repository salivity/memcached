Memcached vs Redis: Multi-Threading and CPU Efficiency

When comparing Memcached and Redis on CPU utilization and execution models, their foundational architectures present fundamentally different approaches. Memcached is natively built with a multi-threaded architecture capable of scaling linear throughput across modern multi-core processors out of the box. In contrast, Redis relies primarily on a single-threaded event loop for command execution, recently augmented by multi-threaded I/O, requiring horizontal process scaling to fully saturate multi-core CPUs.

Memcached: Native Multi-Threading Architecture

Memcached uses an event-based, multi-threaded model utilizing libevent. When the daemon starts, it creates a master thread and a pool of worker threads assigned to handle incoming connections and cache operations.

  • Linear Multi-Core Scaling: Memcached distributes network connections across its worker threads. As CPU core counts increase on a single server, allocating more threads directly scales read and write capacity without the need to run separate daemon instances.
  • Granular Locking: Memory in Memcached is shared across all threads. To maintain data consistency, it employs granular item-level and slab-level mutex locks. While this enables high multi-core utilization, extreme contention on identical keys or memory slabs can introduce lock-overhead bottlenecks at massive concurrency levels.
  • Operational Simplicity on Large Hardware: A single Memcached process can easily consume 32, 64, or more CPU cores and hundreds of gigabytes of RAM, keeping operational and routing complexity minimal on large compute instances.

Redis: Single-Threaded Core with Multi-Threaded I/O

Redis was deliberately designed around an event-driven, single-threaded execution core. A single thread sequentially processes all client commands using non-blocking I/O multiplexing.

  • Deterministic Command Execution: Because commands run sequentially on one thread, Redis eliminates the need for internal locks, mutexes, or synchronization mechanisms. This guarantees atomicity and ultra-low latency for complex data types (such as sorted sets, hashes, and bitmaps), but it limits core command execution to the speed of a single CPU core.
  • Threaded I/O (Redis 6.0+): While the main execution thread remains single-threaded, Redis offloads time-consuming socket read and write operations, as well as protocol parsing, to secondary I/O threads. This substantially improves CPU utilization on multi-core systems compared to older versions, but the actual command processing still caps at one core.
  • Scaling Across Cores: To utilize all CPU cores on a multi-core machine, administrators must deploy multiple Redis instances on separate ports and use client-side sharding or Redis Cluster. This introduces management overhead, including connection pooling across processes, higher memory overhead per instance, and partitioned data management.

Summary

For pure key-value caching where the goal is to extract maximum throughput from a multi-core server with a single process, Memcached offers superior CPU utilization efficiency. It seamlessly scales with CPU core counts without architectural workarounds. Redis trades raw multi-threaded CPU saturation for algorithmic richness and lock-free deterministic performance, requiring cluster-level sharding to achieve comparable multi-core hardware utilization.
