Memcached Slab Class Memory Allocation Parameters

Memcached manages memory using a slab allocation mechanism designed to eliminate memory fragmentation. Instead of allocating memory dynamically on a per-item basis, Memcached pre-allocates memory in fixed-size blocks called pages (typically 1 MB) and assigns them to specific slab classes that store items of similar sizes. This article outlines the startup parameters and runtime controls that directly dictate how these memory pages are divided and allocated across different slab classes.

1. Total Memory Limit (-m)

The -m flag defines the maximum amount of RAM (in megabytes) that Memcached is allowed to use for data storage. This total pool represents the global budget from which individual memory pages are allocated to different slab classes as data is written. Once this pool is completely consumed by assigned pages, Memcached can no longer allocate new pages without either evicting items (LRU) or moving pages between classes.

2. Minimum Item Size (-n)

The -n parameter specifies the minimum initial space allocated for an item's key, value, and internal flags (defaulting to 48 bytes). This value dictates the chunk size for Slab Class 1, which serves as the base baseline size for the smallest cached items. Every subsequent slab class calculates its chunk size upward starting from this value.

3. Growth Factor (-f)

The -f flag sets the chunk growth factor (default is 1.25), which dictates the rate at which chunk sizes increase from one slab class to the next. For example, with a growth factor of 1.25, each successive slab class provides chunks that are 25% larger than the preceding class:

  • Class 1: \(n\) bytes
  • Class 2: \(n \times f\) bytes
  • Class 3: \((n \times f) \times f\) bytes

This parameter directly governs how many total slab classes exist and how finely granular the chunk sizes are between the minimum chunk size and the maximum item size.

4. Maximum Item / Page Size (-I)

The -I parameter specifies the maximum item size allowed in the cache (defaulting to 1 MB). Because a slab page is sized to accommodate at least one maximum-sized item, this parameter also defines the size of an individual memory page. The largest slab class will have a chunk size equal to this maximum limit. Consequently, this determines the ceiling of the slab class hierarchy.

5. Runtime Demand and Page Assignment

At startup, memory pages are not distributed across slab classes equally. Instead, memory pages remain in an unallocated global pool. Page assignment is driven by incoming write operations:

  • When an item is stored, Memcached identifies the smallest slab class with a chunk size large enough to hold the item.
  • If that slab class has no free chunks left, Memcached allocates a new 1 MB page from the global free pool directly to that class and slices it into chunks.
  • Thus, the volume and size distribution of incoming traffic determine which slab classes acquire pages first.

6. Dynamic Reallocation Parameters (-o slab_reassign and slab_automove)

Under default older behavior, once a memory page is assigned to a slab class, it remains with that class permanently, which can lead to memory starvation if traffic patterns shift. Modern Memcached versions mitigate this using dynamic reallocation settings:

  • slab_reassign: Enables the manual or automated moving of pages between slab classes without restarting the server.
  • slab_automove: Dictates the algorithmic behavior for automatically moving pages from idle slab classes to classes experiencing high eviction pressure. It accepts specific operating modes:
    • 0: Automove is disabled.
    • 1: Standard automove; moves a page if a class has had no evictions and excess free pages, giving it to a class that is actively evicting items.
    • 2: Aggressive, highly responsive page movement based on detailed class utilization and hit-to-eviction ratios.
