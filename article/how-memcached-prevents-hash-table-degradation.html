How Memcached Prevents Hash Table Degradation

Memcached maintains optimal throughput and sub-millisecond latency under heavy traffic by actively preventing hash table key distribution degradation. When the ratio of stored keys to available buckets increases, lookup times in a standard hash table can degrade from \(O(1)\) to \(O(n)\) due to collision chains. Memcached circumvents this bottleneck through a combination of high-dispersion hashing algorithms, asynchronous dynamic table resizing, background incremental rehashing, and fine-grained lock striping.

Dynamic Table Resizing and Thresholds

Memcached organizes its internal hash table into a number of buckets defined by a power of two (\(2^{\text{hashpower}}\)). As new items are inserted, Memcached tracks the total number of active items relative to the total number of buckets.

When the number of stored keys exceeds 1.5 times the current bucket capacity, the load factor threshold is crossed. Rather than allowing hash collision chains to lengthen and slow down key lookups, Memcached initiates an automated hash table expansion, doubling the bucket array size (\(2^{\text{hashpower} + 1}\)).

Asynchronous Incremental Rehashing

Immediate, synchronous rehashing of millions of keys under peak traffic would introduce catastrophic latency spikes, often referred to as "stop-the-world" pauses. Memcached solves this by offloading the migration of keys to an independent, dedicated maintenance thread.

When an expansion is triggered:

  • A new, larger bucket array is allocated in memory alongside the existing table.
  • The maintenance thread moves keys from the old table to the new table incrementally, processing a small batch of buckets at a time.
  • Normal worker threads are not blocked; they continue to service read, write, and delete requests.
  • Lookups during rehashing are routed dynamically: the worker checks whether the target bucket index has already been migrated past the expansion cursor. If it has, the worker queries the new table; if not, it queries the old table.

Fine-Grained Lock Striping

Under heavy concurrent access, locking the entire hash table during reads, writes, or rehashing would create massive contention. Memcached implements lock striping using an array of discrete mutexes (item_locks).

Instead of a single global table lock, individual buckets map to specific locks within the lock stripe array. This architecture allows multiple worker threads to read and mutate different parts of the hash table simultaneously. During the rehashing process, the maintenance thread only acquires the locks corresponding to the specific bucket slice it is actively migrating, ensuring key distribution scales cleanly without stalling inbound traffic.

Uniform Distribution via Murmur3 and Jenkins Hashes

The prevention of key distribution degradation relies heavily on the quality of the hashing algorithm itself. Clustered keys create long linked-list collision chains within individual buckets even if the overall table capacity is sufficient.

Memcached utilizes non-cryptographic, high-dispersion hash algorithms—predominantly MurmurHash3 and Jenkins hash (lookup3). These algorithms provide an avalanche effect where minor variations in key names result in drastically different hash values. This produces an even, pseudorandom distribution across the entire bucket space, preventing "hot buckets" and keeping collision chains minimal.
