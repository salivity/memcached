Memcached Requests During Hash Table Rehash

When a Memcached instance reaches its hash table capacity threshold, it doubles the table size and initiates a non-blocking background rehash. This article explains how Memcached processes incoming client requests while this rehash occurs, detailing how the dual-table routing mechanism identifies key locations, how bucket-level locking maintains data integrity, and why clients experience virtually zero disruption.

The Incremental Rehashing Architecture

Memcached avoids "stop-the-world" latency spikes by performing rehashing incrementally in a dedicated background maintenance thread. When the total number of stored items exceeds 1.5 times the current hash table size, the server allocates a new hash table (primary_hashtable) that is twice the size of the existing one. The existing table is retained as the old_hashtable.

A cursor variable tracks migration progress by recording the highest bucket index that has already been moved from the old table to the new table. The maintenance thread moves a small batch of buckets at a time, yielding periodically to prevent starving the CPU.

Key Resolution and Request Routing

When a client sends a read or write command (such as GET, SET, DELETE, or TOUCH) while rehashing is active, the worker thread servicing that connection must determine which hash table contains the key.

  1. Hash Calculation: The worker thread calculates the 32-bit hash value of the requested key.
  2. Cursor Comparison: The thread maps the hash value to a bucket index in the old_hashtable. It then compares this index against the current rehash cursor position:
    • If the bucket index is lower than the cursor: The bucket has already been migrated. The worker thread maps the key's hash to the primary_hashtable (new table) and performs the operation there.
    • If the bucket index is equal to or higher than the cursor: The bucket has not yet been processed. The worker thread routes the operation to the old_hashtable.

Handling Specific Client Operations

  • Read Operations (GET, BGET): The worker thread checks the appropriate table based on the cursor position. If the bucket has not yet migrated, it reads directly from the old table. If the bucket has migrated, it reads from the new table. The client receives the response with standard sub-millisecond latency.
  • Write and Update Operations (SET, REPLACE, CAS): Writes follow the same cursor check. If the item belongs to an unmigrated bucket, the update occurs in the old table, and it will subsequently be migrated by the background thread. If it belongs to a migrated bucket, it writes directly to the new table.
  • Insertion Operations (ADD): New keys are checked against the designated table to ensure uniqueness before insertion.
  • Delete Operations (DELETE): Deletions locate and remove the item from whichever table currently holds its designated bucket.

Concurrency and Bucket Locking

To prevent race conditions between client-facing worker threads and the background migration thread, Memcached uses granular bucket locks. Instead of locking the entire hash table during migration, the engine divides the hash space across an array of mutexes (typically power-of-two partitions).

When the maintenance thread moves a batch of buckets, it acquires the specific locks governing those buckets, moves the linked lists of items from the old table into their corresponding locations in the new table, updates the cursor, and releases the locks. If a client request attempts to access an item within the exact bucket partition currently being migrated, the worker thread blocks only for the brief duration required to transfer that small batch. All other requests accessing different buckets continue execution in parallel without delay.

Performance Impact on the Client

From the client's perspective, rehashing is entirely transparent. Requests do not fail, connections do not drop, and cache hit rates remain unaffected. The only measurable impact is a slight, temporary increase in 99th-percentile tail latency caused by occasional thread contention on the specific bucket locks being actively processed by the maintenance thread. Once the cursor reaches the end of the old table, the memory for the old table is freed, the maintenance thread goes to sleep, and normal single-table routing resumes.
