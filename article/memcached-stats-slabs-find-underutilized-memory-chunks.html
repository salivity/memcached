Memcached Stats Slabs: Find Underutilized Memory Chunks

Memcached organizes memory into slab classes containing fixed-size chunks to minimize dynamic memory allocation overhead. However, variations in item sizes and shifting traffic patterns can lead to inefficient memory use, including idle allocations and internal fragmentation. By querying the stats slabs command, administrators can monitor specific metrics—such as used_chunks, total_chunks, free_chunks, and mem_requested—to precisely identify and resolve underutilized memory across slab classes.

Key stats slabs Metrics for Diagnosing Underutilization

To evaluate memory efficiency per slab class, issue the stats slabs command via telnet or an administrative socket. The output provides per-class statistics (denoted by the slab class ID prefix, such as 1:chunk_size):

  • chunk_size: The fixed byte size allocated for every item assigned to this slab class, including Memcached key and metadata overhead.
  • total_chunks: The total capacity of chunks available across all memory pages assigned to the slab class (total_pages * chunks_per_page).
  • used_chunks: The number of chunks currently storing active cache items.
  • free_chunks: The count of chunks that have been allocated to the slab class but are currently unused and sitting on the free list (e.g., after an eviction, expiration, or pre-allocation).
  • free_chunks_end: The number of unused chunks remaining at the end of the most recently allocated page that have not yet been placed onto the free list.
  • mem_requested: The actual total byte count of the data payload and metadata stored in the slab class.

Diagnosing Idle and Over-Allocated Chunks

A slab class experiences idle underutilization when it reserves memory pages and chunks that are never populated with data.

To determine the chunk allocation utilization rate:

\[\text{Chunk Utilization Rate} = \frac{\text{used\_chunks}}{\text{total\_chunks}}\]

If a slab class displays a low utilization rate alongside high values for free_chunks or free_chunks_end, memory has been locked into that specific slab class and cannot be shared with classes under eviction pressure. In early Memcached versions, this memory remains stranded permanently unless slab rebalancing is active.

Diagnosing Internal Fragmentation (Slack Space)

Internal fragmentation occurs when the stored item is significantly smaller than the slab's chunk_size. Memcached allocates the entire chunk regardless of payload size.

To quantify internal fragmentation per slab class, compare mem_requested against the gross memory consumed by all active chunks:

\[\text{Wasted Memory (Bytes)} = (\text{used\_chunks} \times \text{chunk\_size}) - \text{mem\_requested}\]

A large discrepancy indicates that items routed to this slab class are leaving substantial "slack space" empty inside each chunk.

Corrective Actions

  • Enable Slab Automove: If idle chunks (free_chunks) dominate a slab class while other classes experience evictions, enable the slab automover runtime option (slab_automove=1 or slab_automove=2) to reassign unused pages to classes that need them.
  • Tune the Growth Factor (-f): If mem_requested reveals excessive slack space, the growth factor between slab chunk sizes is likely too coarse. Lowering the growth factor (default 1.25) reduces the size gaps between slab classes, ensuring items land in chunk sizes closer to their actual payload size.
  • Adjust Minimum Item Size (-s or -n): If the smallest slab class (Slab 1) exhibits high internal fragmentation, adjust the initial chunk size to align with your application's smallest stored objects.
