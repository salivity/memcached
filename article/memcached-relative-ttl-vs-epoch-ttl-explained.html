Memcached Relative TTL vs Epoch TTL Explained

Memcached determines when an item expires using either a relative time-to-live (TTL) or an absolute Unix epoch timestamp. This article breaks down how Memcached differentiates between the two based on a hardcoded 30-day threshold, the mechanics of each approach, and how to avoid the common pitfall that causes cached items to expire immediately.

The 30-Day Threshold Rule

Memcached accepts an integer value for an item's expiration parameter (often denoted as exptime). To determine whether this integer represents a duration or a specific date, Memcached checks if the value is less than or equal to the number of seconds in 30 days:

  • 2,592,000 seconds (60 seconds × 60 minutes × 24 hours × 30 days)

Any integer up to 2,592,000 is treated as a relative TTL. Any integer greater than 2,592,000 is treated as an epoch TTL.

What is Relative TTL?

A relative TTL specifies the lifespan of a cache item in seconds, counted from the moment the item is stored or updated.

  • Value Range: 1 to 2,592,000 seconds.
  • Mechanism: If you pass 300, Memcached calculates the expiration time as current_time + 300. The item expires after 5 minutes.
  • Best Use Cases: Short- to medium-term caching where items should persist for a set duration, such as API response caching, session management, or rate limiting.

What is Epoch TTL?

An epoch TTL specifies the exact point in time when an item should expire, represented as the number of seconds that have elapsed since the Unix epoch (00:00:00 UTC on January 1, 1970).

  • Value Range: Any integer greater than 2,592,000.
  • Mechanism: Memcached compares this timestamp directly against the server’s current Unix time. When the system clock passes the specified timestamp, the item is considered expired.
  • Best Use Cases: Setting cache lifetimes that must exceed 30 days, or synchronizing cache invalidation to an absolute event (e.g., midnight UTC, or the end of a scheduled marketing promotion).

The Common 30-Day Bug

The dual-interpretation mechanism creates a frequent bug when developers attempt to store items for longer than 30 days using relative seconds.

For example, if you want an item to persist for 40 days and supply 3,456,000 seconds (40 × 86,400), Memcached sees a number greater than 2,592,000 and interprets it as an epoch timestamp:

  • 3,456,000 as a Unix timestamp corresponds to February 9, 1970.
  • Because this timestamp is decades in the past, Memcached immediately marks the item as expired upon insertion.

To cache an item for 40 days correctly, you must calculate the target timestamp explicitly:

expiration = current_unix_timestamp + 3456000

The Special Case: Zero (0)

Setting an expiration value of 0 tells Memcached that the item should never expire automatically based on time. However, the item is not guaranteed to remain in memory indefinitely; Memcached may still evict it if memory runs out, according to its Least Recently Used (LRU) algorithm.
