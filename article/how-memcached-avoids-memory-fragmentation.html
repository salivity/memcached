How Memcached Avoids Memory Fragmentation

Memcached prevents memory fragmentation caused by frequent variable-length writes through an internal memory management system known as the Slab Allocator. Instead of relying on the operating system’s standard memory allocation (malloc and free) for every write and delete operation, Memcached pre-allocates large blocks of memory and divides them into fixed-size chunks. This article explains how the slab allocation mechanism works, how it eliminates external fragmentation, and the trade-offs involved in its design.

The Problem with Standard Memory Allocation

In high-throughput caching environments, keys and values vary significantly in size and have unpredictable lifespans. Using standard operating system memory allocation for each insert and delete causes memory to become peppered with small, non-contiguous free spaces over time. This condition—known as external fragmentation—eventually prevents the system from allocating memory for larger items, even when the total amount of free memory across the system is sufficient.

The Slab Allocation System

Memcached solves external fragmentation by implementing a slab allocator. Memory is organized hierarchically into slabs, slab classes, and chunks.

1. Slabs (Pages)

Memcached allocates memory in large, uniform blocks called slabs (or pages), typically 1 megabyte in size. These pages are requested from the operating system up front or in bulk increments, ensuring the underlying OS memory layout remains contiguous.

2. Slab Classes

To accommodate different data sizes, Memcached defines a series of slab classes. Each slab class is responsible for storing items within a specific size bracket. By default, the chunk sizes between successive slab classes grow exponentially by a configured factor (known as the factor, typically defaulting to 1.25).

For example:

  • Slab Class 1: 96-byte chunks
  • Slab Class 2: 120-byte chunks
  • Slab Class 3: 152-byte chunks

3. Chunks

Each 1MB slab page is assigned to a specific slab class and immediately carved into equal-sized chunks corresponding to that class. An individual chunk holds exactly one cached item, consisting of its key, flags, metadata, and value.

Storing and Deleting Data

When a write operation occurs, Memcached executes the following steps:

  1. Size Calculation: Memcached calculates the total memory needed for the item (key, value, and metadata).
  2. Class Selection: It identifies the slab class with the smallest chunk size that can still accommodate the item.
  3. Allocation from Free List: The item is placed into an available chunk within that slab class's free list.
  4. Deallocation and Reuse: When an item is deleted or expires, its chunk is simply marked as available and returned to the free list of its respective slab class.

Because chunks are reused exclusively by items that fit that specific chunk size, memory addresses are never split, merged, or left as arbitrary holes. The allocator never requests random micro-allocations from the host OS, thereby completely eliminating external fragmentation.

Internal Fragmentation: The Design Trade-Off

While the slab allocation model eliminates external fragmentation, it introduces internal fragmentation. If an item requires 100 bytes of memory and is assigned to a slab class with 128-byte chunks, the remaining 28 bytes inside that chunk are left unused.

Memcached accepts internal fragmentation because it provides deterministic performance and guarantees that the server will not crash or stall due to out-of-memory errors caused by fragmented address spaces. Administrators can tune the growth factor parameter (-f) to adjust the spacing between slab classes, narrowing the gap between chunk sizes and minimizing wasted memory based on their specific workload patterns.

Slab Reassignment

In earlier versions of Memcached, once a 1MB slab was assigned to a slab class, it was permanently locked to that class. If the application's data size profile changed, memory could become stranded in unused slab classes. Modern versions of Memcached include an automated slab rebalancer (slab automove) that detects when a particular slab class is starving for memory while another class has idle slabs, dynamically reassigning 1MB pages to where they are needed most.
