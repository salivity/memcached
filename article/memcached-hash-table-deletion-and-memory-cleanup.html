Memcached Hash Table Deletion and Memory Cleanup

Memcached manages high-throughput caching by utilizing an internal hash table alongside a slab memory allocator. When a key is deleted, Memcached does not perform a traditional garbage collection cycle on the hash table buckets themselves; instead, it immediately unlinks the item node from the corresponding hash table bucket chain and marks the underlying item memory for immediate reuse within its slab class, leaving the primary bucket array intact.

Internal Hash Table Architecture

Memcached uses a primary hash table to provide \(O(1)\) lookups for stored keys. This hash table consists of an array of bucket pointers, where the size of the array is always a power of two. Because multiple keys can hash to the same bucket index, Memcached resolves collisions using separate chaining via a singly linked list. Each cached item structure (item) contains an internal pointer (h_next) that points to the next item in the same hash bucket.

The Key Deletion Process

When a client issues a delete command, Memcached executes an immediate, deterministic cleanup process rather than waiting for an asynchronous garbage collector:

  1. Hash Lookup: Memcached computes the hash of the target key using MurmurHash3 (or Jenkins hash, depending on configuration) and maps it to the corresponding bucket index.
  2. Chain Traversal: It traverses the singly linked list at that bucket, comparing keys to locate the specific target item.
  3. Unlinking from the Hash Table: Once found, Memcached adjusts the pointers. The preceding pointer in the chain (either the bucket head pointer itself or the h_next pointer of the prior item) is updated to bypass the deleted item and point directly to the deleted item’s h_next.
  4. LRU Unlinking: The item is unlinked from the global or slab-class Least Recently Used (LRU) doubly linked list.
  5. Reference Decrement: The item's reference count is decremented. If no active read threads hold a reference, the item is immediately freed.

Why Hash Table Buckets Are Not Garbage Collected

The individual "buckets" in Memcached's hash table are simply pointer slots in a large, contiguous memory array. As a result, deleting a key does not deallocate or garbage collect the bucket itself:

  • Pointer Reset: If an item was the only entry in a bucket, unlinking it simply sets that bucket's pointer to NULL. The pointer slot remains part of the allocated bucket array.
  • No Array Shrinking: Memcached dynamically expands its hash table size via a dedicated maintenance thread when the number of stored items exceeds 1.5 times the table size. However, Memcached does not shrink the hash table array when keys are deleted. The array remains at its peak size to avoid the CPU overhead and synchronization locks required to rehash items into a smaller table.

Slab Memory Reclaiming

While the hash table bucket pointers remain fixed in memory, the memory allocated for the item itself (the key, metadata, and value payload) is reclaimed instantly. Memcached does not return this memory to the operating system via standard C library calls like free(). Instead, it hands the chunk back to the internal slab allocator:

  • The freed chunk is placed onto the slab class’s free list (slots).
  • The next write operation requiring memory within that specific chunk size category immediately reuses that allocated slot.
  • This design eliminates memory fragmentation and avoids the latency spikes typically associated with stop-the-world garbage collection routines.
