Preventing Memcached Cache Stampedes With Soft Locks

A cache stampede occurs when high-traffic cached data expires, prompting multiple concurrent application threads to query the underlying database simultaneously and causing performance degradation or outages. Implementing a soft lock technique in Memcached mitigates this by allowing only a single worker to regenerate the expired cache item while continuing to serve slightly stale data to other incoming requests. This article outlines the mechanics of the soft lock approach and provides a practical implementation strategy for application developers.

The Mechanics of Soft Locking

Standard cache expiration removes a key completely, forcing the next request—and all simultaneous subsequent requests—to rebuild the cache from the primary datastore.

Soft locking separates the application's perceived expiration from Memcached's actual eviction time. By maintaining two expiration thresholds (a logical TTL and a physical TTL), the application identifies that a key has "expired" while the data remains available in memory.

  1. Logical Expiration (Soft TTL): A timestamp stored inside the cached object indicating when the data should ideally be refreshed (e.g., after 5 minutes).
  2. Physical Expiration (Hard TTL): The native Memcached TTL set considerably longer than the logical TTL (e.g., 15 minutes) to ensure stale data remains accessible during regeneration.

Step-by-Step Implementation

To implement soft locks with Memcached, follow this logical flow in your application layer:

1. Retrieve the Value and Check the Soft TTL

Store your data wrapped in an envelope containing the payload and the logical expiration timestamp:

{
  "data": { ... },
  "logical_expiry": 1711972800
}

When fetching the key:

  • If the key does not exist at all (a complete cache miss), acquire a mutex lock, query the database, populate the cache, and return the data.
  • If the key exists, evaluate current_timestamp > logical_expiry. If false, return the data immediately.

2. Acquire a Mutex Using Atomic Operations

If the logical expiration has passed, the data is stale. The application must attempt to claim the exclusive right to refresh the data using Memcached's atomic ADD command:

  • Call ADD lock:{cache_key} with a short expiration (e.g., 5 to 10 seconds).
  • Because ADD only succeeds if the key does not already exist, it acts as a mutual exclusion lock (mutex).

3. Handle Lock Acquisition Outcomes

  • If the lock succeeds: The current thread is responsible for updating the cache. Fetch the latest data from the primary database, compute a new logical expiration, write the updated payload to Memcached using SET, and delete the lock key.
  • If the lock fails: Another thread is already regenerating the data. Instead of waiting or querying the database, immediately return the current stale data to the client. The client receives a fast response, and the database remains protected.

Best Practices and Edge Cases

  • Lock Timeouts: Always assign a short hard TTL to the lock key. If the process fetching the new data crashes mid-operation, the lock will automatically expire, preventing a permanent deadlock.
  • Stale Tolerance: Ensure your application can tolerate serving data that is older than the soft TTL by a matter of seconds. Soft locking relies on acceptable staleness during regeneration windows.
  • Cold Starts: If a key is completely absent (hard miss), soft locking cannot serve stale data. In this scenario, implement a standard locking pattern or probabilistic early expiration (such as the XFetch algorithm) to pre-warm keys before they disappear entirely.
