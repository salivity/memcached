Detecting Memcached Thread Contention: Key Metrics

Memcached is designed for high-concurrency caching using a multi-threaded architecture, but improper configuration or access patterns can cause worker threads to block while competing for shared resources. This article outlines the key internal statistics, operating system metrics, and performance indicators that reveal when a Memcached node is suffering from heavy thread contention.

1. High System CPU Time (rusage_system) vs. User Time (rusage_user)

In Memcached's stats output, monitor the ratio between rusage_user and rusage_system. Under healthy conditions, Memcached spends the majority of its CPU cycles in user space (rusage_user) executing read, write, and hashing logic. When thread contention occurs, worker threads repeatedly acquire, wait on, and yield mutexes (such as item locks or slab locks). This forces the Linux kernel to manage synchronization primitives, resulting in an abnormal spike in system CPU time (rusage_system) while total throughput stagnates.

2. High Context Switching Rates

Operating system monitoring tools (such as vmstat, pidstat, or mpstat) provide direct insight into thread synchronization overhead:

  • Voluntary Context Switches: An unusually high rate of voluntary context switches per second indicates that Memcached threads are constantly yielding the CPU because they are blocked waiting on locked mutexes.
  • Involuntary Context Switches: Elevated involuntary switches suggest CPU saturation caused by too many configured worker threads competing for execution time on too few physical CPU cores.

3. Mutex and Lock Wait Metrics (Lock Profiling)

If Memcached is compiled with mutex profiling enabled (--enable-lock-profiling), the stats conns, stats locks, or debug lock outputs expose direct contention metrics. Key indicators include:

  • Lock wait counts: High counter values for item locks or the global slab rebalancer lock.
  • Lock wait time: Elevated cumulative or average time spent waiting to acquire a lock rather than executing cache operations.

4. Latency Spikes with Flat or Dropping Throughput (QPS)

Thread contention degrades the efficiency of query processing. If client-side p95 and p99 latency sharply increases while the queries per second (QPS) processed by the node plateaus or falls, threads are likely queuing internally for lock acquisition rather than processing network requests.

5. Asymmetric Item Access and Hot-Key Collisions

Memcached splits item storage locks into discrete buckets across the hash table. If your access pattern contains extreme "hot keys," multiple worker threads attempt to read or mutate the exact same item lock simultaneously. While the stats command does not show individual key metrics, a dramatic drop in cache throughput during heavy access to a specific subset of data is a classic indicator of lock serialization.

6. Queueing and listen_disabled_num

When worker threads are heavily blocked by lock contention, they process incoming connections and requests significantly slower. This backpressure can cause the accept queue to fill up, resulting in increments to the listen_disabled_num metric in Memcached stats, which indicates that the daemon has temporarily stopped accepting new TCP connections because workers cannot keep pace.
