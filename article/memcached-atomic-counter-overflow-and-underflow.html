Memcached Atomic Counter Overflow and Underflow

Memcached provides native incr and decr commands to safely manipulate numeric counters in high-concurrency environments without race conditions. This article examines the internal mechanisms Memcached uses to process these atomic operations, specifically detailing how the engine implements a zero-floor threshold to prevent underflows, relies on 64-bit integer wraparound behavior at upper limits, and uses internal item locking to guarantee that boundary evaluations remain strictly atomic.

64-Bit Numeric Representation

While Memcached stores all cached data internally as serialized byte arrays (strings), the incr and decr commands require the target item to represent a numeric decimal value.

When a counter command executes, the engine parses the stored ASCII string into an unsigned 64-bit integer (uint64_t). All arithmetic calculations occur using this 64-bit data type before the final result is converted back into an ASCII string and written back to the memory block.

Handling Counter Underflow with decr

Memcached explicitly prevents unsigned integer underflow during decrement operations through saturation arithmetic.

Because counters are unsigned (uint64_t), a naive subtraction below zero would wrap the value around to the maximum possible 64-bit value (\(2^{64} - 1\), or \(18,446,744,073,709,551,615\)). To prevent this:

  • The engine compares the current counter value against the decrement delta.
  • If the decrement delta is greater than or equal to the current value, Memcached floors the result directly at 0.
  • Negative values are never produced, and the counter will never roll over into upper integer bounds.

Handling Counter Overflow with incr

Unlike underflow handling, Memcached does not floor or saturate at the upper bound during an increment operation.

  • The maximum value a Memcached counter can reach is \(2^{64} - 1\).
  • When an increment operation exceeds this 64-bit ceiling, standard C-level unsigned integer overflow rules apply: the integer wraps around to 0 (modulo \(2^{64}\)).
  • Memcached does not return an error or reject the command upon reaching this limit; the application layer is responsible for monitoring or resetting keys if a wraparound would disrupt application logic.

Concurrency and Atomic Execution

To ensure that calculations and boundary checks are reliable, Memcached executes the entire cycle atomically:

  1. Lock Acquisition: Memcached acquires an item lock (or bucket lock depending on the engine version) corresponding to the target key's hash.
  2. Evaluation: The string value is parsed into a uint64_t, validated, and the arithmetic check (including the zero-floor evaluation for decr) takes place.
  3. Commit: The updated value is formatted back into an ASCII string, replacing the existing item in memory.
  4. Lock Release: The lock is freed.

Because these steps occur exclusively while the item's lock is held, concurrent read-modify-write collisions are impossible, ensuring that overflow wraparounds and underflow floors happen deterministically.
