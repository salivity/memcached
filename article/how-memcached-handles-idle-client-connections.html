How Memcached Handles Idle Client Connections

Memcached manages idle and unresponsive client connections primarily through an event-driven network architecture, configurable connection timeouts, operating system TCP keepalives, and strict connection limits. By relying on non-blocking I/O, Memcached ensures that inactive clients do not consume execution threads, while specific socket-level and application-level mechanisms actively terminate stale or dead sockets to preserve memory and file descriptors.

Event-Driven Architecture via libevent

Memcached utilizes libevent to achieve non-blocking, asynchronous network I/O. When a client establishes a connection but sends no commands, it does not lock an entire worker thread. Instead, Memcached registers the client socket with the event notification loop and yields CPU resources to active traffic. While this ensures that idle clients do not degrade processing throughput, open sockets still consume memory buffers and file descriptors, requiring specific mechanisms to clean them up.

Configurable Idle Timeouts

By default, older configurations of Memcached allowed idle connections to remain open indefinitely as long as the underlying TCP connection appeared healthy. Modern versions of Memcached introduce an explicit idle timeout setting using the -o idle_timeout=<seconds> runtime flag.

When this option is enabled:

  • The server monitors the timestamp of the last interaction on every open socket.
  • If a connection remains completely silent for longer than the designated duration, Memcached initiates a clean shutdown on the server side.
  • The socket is closed, and associated read/write buffers are deallocated and returned to the system.

TCP Keepalive Detection

Unresponsive connections often occur when a client machine crashes, a network cable is unplugged, or an intermediate firewall drops state without sending a FIN or RST packet. These are known as half-open connections.

To identify these dead sockets, Memcached relies on TCP keepalive probes configured at the operating system level or through the -o tcp_keepalive flag. When enabled:

  1. The kernel periodically sends empty probe packets to idle clients.
  2. If the client responds with an ACK, the connection remains marked as valid.
  3. If the client fails to respond after a defined number of retries, the OS marks the connection as broken and alerts the application.
  4. Memcached receives an error on the socket descriptor and automatically cleans up the connection structures.

Connection Limits and Resource Protection

Memcached enforces a maximum concurrent connection ceiling, defined by the -c parameter (which defaults to 1,024). When the limit is reached, Memcached does not immediately terminate existing idle connections to make room for new ones. Instead, it stops accepting new incoming connections until existing ones are closed via client termination, idle timeouts, or keepalive drops. This makes the proper configuration of timeouts critical to prevent connection starvation in high-scale environments.
