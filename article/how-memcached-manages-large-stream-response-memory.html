How Memcached Manages Large Stream Response Memory

Memcached handles large stream responses by combining non-blocking event-driven I/O, zero-copy network transmission, item reference counting, and slab-based memory chunking. Rather than allocating large contiguous temporary buffers in memory to stage outgoing payloads, Memcached streams data directly from its internal cache structures to network sockets using scatter-gather I/O. This design minimizes memory overhead, mitigates buffer bloat, and maintains high throughput even when serving large volumes of data to slow-reading clients.

Slab Allocator and Chunked Items

Memcached manages its core memory footprint through a slab allocator, dividing memory into predefined slab classes to avoid external memory fragmentation. For items exceeding the default 1MB page size, modern versions of Memcached utilize chunked items (ITEM_CHUNK). Instead of requiring a massive contiguous slab page, large items are broken into a linked list of smaller fixed-size chunks. When streaming a large response, Memcached traverses this linked list sequentially rather than reassembling the object in a separate transient memory space.

Zero-Copy Streaming with Scatter-Gather I/O

To minimize CPU usage and redundant memory duplication, Memcached does not copy data from cache slabs into intermediate connection-level output buffers. Instead, it relies on system-level scatter-gather I/O via the writev system call. Memcached constructs an array of I/O vectors (iovec structures) containing memory pointers and byte lengths pointing directly to the item headers, keys, and cached chunk payloads within the slab memory. The operating system kernel reads directly from these locations and streams the bytes into the TCP socket send buffer.

Item Reference Counting and Eviction Safety

Because a large response may take several network cycles to transmit completely, Memcached must guarantee that cached items are not modified, overwritten, or freed by the Least Recently Used (LRU) crawler during the operation. To achieve this, Memcached increments the internal reference count (refcount) of every item included in an active transmission queue. As long as an item's reference count is greater than zero, the memory slab hosting that data cannot be reallocated or freed. Once the kernel acknowledges the transmission of the data or the client connection terminates, Memcached decrements the reference count, returning the memory to normal eviction eligibility.

Non-Blocking I/O and Network Backpressure

Memcached runs on an event loop driven by libevent. When transmitting large streams, network throughput is constrained by the client's TCP receive window and network latency. If a client reads too slowly and the TCP socket buffer fills up, writev returns EAGAIN or EWOULDBLOCK.

Memcached handles this backpressure without ballooning connection memory:

  • It updates the current position in its array of iovec structures to track what has already been transmitted.
  • It registers the client socket with libevent to listen for write-readiness (EV_WRITE).
  • The worker thread pauses data transmission for that connection and yields the CPU to process requests for other clients.
  • When the kernel signals that the network socket can accept more bytes, the worker resumes streaming the remaining chunks without maintaining auxiliary in-memory queues.

Dynamic Connection Buffers

Connections in Memcached maintain small, dedicated read and write buffers for command parsing and protocol framing. When transmitting large responses, the connection's dynamic memory footprint is limited to the memory required to store the iovec tracking structures. These tracking structures consume a negligible fraction of memory compared to the actual payload sizes, ensuring that concurrent large streams do not cause high transient memory usage across worker threads.
