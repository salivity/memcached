Memcached Behavior During Memory Page Swapping

When an operating system encounters intense memory page swapping, Memcached experiences severe latency spikes and throughput degradation during key retrieval operations. Because Memcached assumes its entire data set resides in physical RAM, it does not implement internal disk I/O mechanisms. When an item targeted by a retrieval request has been shifted to the operating system's swap space, synchronous major page faults force the responsible worker thread to halt execution while waiting for disk reads, transforming sub-millisecond in-memory lookups into multi-millisecond disk operations.

The Key Retrieval Process in a Swapping Environment

Memcached utilizes an event-driven, multithreaded architecture powered by libevent. Worker threads multiplex client connections and handle request processing using non-blocking network sockets. However, memory access itself is fundamentally synchronous at the CPU level.

When a client issues a get command during heavy swap activity, the retrieval follows these steps:

  1. Hash Table Lookup: The worker thread computes the hash of the requested key and accesses the internal hash table to locate the item's pointer. If the hash bucket resides in a swapped page, a hardware page fault occurs immediately.
  2. Page Fault Interruption: The CPU pauses the worker thread and triggers a context switch to the kernel.
  3. Paging In: The operating system's virtual memory manager issues synchronous I/O commands to read the required memory page from the swap partition (SSD or HDD) back into physical RAM.
  4. Item Pointer Dereferencing: Once the hash table page is restored, the thread reads the item pointer. If the slab containing the actual key-value payload is also swapped out, a second page fault occurs, initiating another disk read.
  5. Response Transmission: Once the payload resides in physical memory, Memcached formats the response and writes it to the client socket.

Thread Starvation and Latency Cascades

The primary failure mode of Memcached under memory pressure is thread starvation. While Memcached relies on asynchronous network polling to handle thousands of concurrent network connections, a major page fault suspends the operating thread entirely.

Because each worker thread handles a subset of all active client connections via connection multiplexing, a blocked thread does not merely delay the request that triggered the page fault; it stops processing all other client events assigned to that thread. As multiple threads hit swapped-out memory addresses:

  • Event Loops Stall: Threads spend the vast majority of their CPU time in an uninterruptible sleep state (often visible as high iowait in system metrics).
  • Buffer Saturation: Kernel-level TCP receive buffers fill up because stalled worker threads are not calling read() or recv() on the sockets.
  • Client Timeouts: Latencies jump from tens of microseconds to dozens of milliseconds. Upstream application servers exceed their socket read timeouts and drop connections.
  • Connection Stampedes: Dropped connections often cause application layers to retry requests or open new connections, overwhelming the Memcached master thread that handles incoming TCP connection handshakes.

Sluggish LRU Eviction

Memcached incorporates its own Least Recently Used (LRU) eviction algorithm to free slabs when configured memory limits (-m) are reached. However, Memcached's internal memory limit is decoupled from the operating system's physical memory boundaries.

If Memcached is allocated more memory than is physically available—or if co-located processes consume the remaining physical RAM—the operating system initiates swapping before Memcached reaches its internal memory limit. Consequently, Memcached’s internal LRU engine fails to evict cold items to free up RAM, because from Memcached’s perspective, its memory quota is not yet exhausted.

Furthermore, when the internal LRU crawler traverses memory chains to reorder or evict items, touching cold items can inadvertently trigger a storm of page faults, accelerating system thrashing.

Prevention and Operational Configuration

Because Memcached cannot gracefully manage key retrievals from disk-based swap space, system architectures must prevent swap interactions altogether:

  • Reduce Memcached Allocation: Ensure the -m flag is strictly configured to account for Memcached internal memory overhead, thread stacks, and connection buffers, typically leaving 15% to 20% of system RAM free for the host OS.
  • Kernel Swappiness: Adjust the Linux kernel swappiness parameter to an extremely low value, such as vm.swappiness = 1 or vm.swappiness = 0, forcing the kernel to favor evicting file system caches over paging anonymous process memory.
  • Memory Locking: Launch Memcached with the -k (mlockall) flag, which requests the operating system to lock all of Memcached's virtual memory space into physical RAM, preventing the kernel from paging it out under any circumstance. If physical memory runs out with memory locking enabled, allocation requests fail immediately (triggering out-of-memory errors) rather than stalling the entire retrieval pipeline on disk I/O.
