How Memcached Handles Abrupt Connection Drops

When client connections terminate abruptly—whether from network failures, client crashes, or dropped packets—Memcached relies on event-driven I/O notifications, OS-level socket error reporting, and TCP keepalive mechanisms to detect and reclaim orphaned file descriptors. By pairing the libevent library with strict state machine routines (primarily via its internal conn_close procedure), Memcached quickly deregisters inactive events, closes the underlying operating system file descriptor, and recycles internal connection memory back into an allocation pool.

Event-Driven Detection via libevent

Memcached operates an asynchronous, event-driven network model powered by libevent, which abstracts operating system notification facilities such as epoll, kqueue, or select. Worker threads monitor registered file descriptors for read and write readiness.

When an abrupt connection drop occurs:

  • Active Disconnects (TCP RST or FIN): If a client process terminates unexpectedly, the client OS typically sends a TCP FIN or RST packet. The server's network stack marks the socket, prompting libevent to fire a readable event.
  • Zero-Byte Reads: When Memcached's event loop executes read() on a closed socket, the system call returns 0. In standard POSIX sockets, a return value of 0 denotes End-Of-File (EOF).
  • System Call Errors: If the connection was abruptly reset, the read() or write() call fails immediately and sets errno to values such as ECONNRESET (Connection reset by peer) or EPIPE (Broken pipe).

Handling Silent Drops with TCP Keepalive

In scenarios where a client loses power, an intermediate router crashes, or a network cable is unplugged, no FIN or RST packet reaches the server. The connection enters a half-open state where the server assumes the client is still alive.

To prevent file descriptor leaks during silent drops:

  • Memcached enables the SO_KEEPALIVE socket option by default on client sockets.
  • The operating system periodically sends empty ACK probes after a period of idle time.
  • If the remote client fails to respond to multiple consecutive keepalive probes, the operating system marks the connection broken.
  • The next read or write operation triggered on that socket encounters ETIMEDOUT or EHOSTUNREACH, signaling Memcached to initiate cleanup.

The Cleanup Sequence (conn_close)

Once a read returns 0 or an I/O error is returned, Memcached shifts its internal connection state machine (drive_machine) into a closing state and triggers conn_close():

  1. Event Deregistration: Memcached calls event_del() via libevent to remove the client’s file descriptor from the monitoring loop, ensuring the worker thread stops polling the dead connection.
  2. Descriptor Closure: The server invokes the standard close(sfd) system call on the socket file descriptor. This releases the descriptor back to the operating system's kernel table, preventing file descriptor exhaustion.
  3. Buffer Management: Dynamic read and write buffers allocated to that specific connection are cleared or returned to the thread-local freelist.
  4. Structure Recycling: Rather than deallocating the internal connection wrapper (conn struct) via standard free(), Memcached pushes the struct into a reusable pool (conn_free()). This design minimizes memory fragmentation and avoids malloc overhead when new clients connect.
