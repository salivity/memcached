How Memcached Handles Malformed Protocol Packets

Memcached handles malformed wire protocol packets by evaluating the corrupted data against its protocol parser, returning distinct error responses, and actively terminating the TCP connection if state synchronization is lost. Depending on whether the client communicates via the legacy ASCII text protocol or the binary protocol, Memcached employs structured error strings, binary status codes, or immediate connection resets to prevent malformed requests from compromising server stability or corrupting subsequent commands.

ASCII Text Protocol Responses

When a client sends a corrupted or invalid request using the text-based protocol, Memcached evaluates the syntax per line terminated by \r\n. It classifies failures into distinct tiers:

  • ERROR\r\n: Returned when the server receives a completely unrecognized command line that does not match standard operations such as get, set, or delete.
  • CLIENT_ERROR <error message>\r\n: Returned when the command name is recognized, but the payload, parameters, or arguments are syntactically invalid. Examples include non-numeric values for expiration or flags, invalid key characters (such as embedded whitespace or control characters), or an invalid byte count for data blocks.
  • SERVER_ERROR <error message>\r\n: Returned if processing a request fails due to an internal server-side constraint rather than client syntax error.

In standard text protocol errors, Memcached sends the error message back to the client and keeps the socket open, advancing the parser to read subsequent commands. However, if data chunk sizes misalign—such as a client sending fewer or more bytes than specified in the command header—the parser enters an unrecoverable state and forcibly closes the underlying socket.

Binary Protocol Responses

The binary protocol relies on a rigid 24-byte header that allows for stricter boundary validation. When a malformed packet arrives, Memcached handles it through binary response frames:

  • Magic Byte Validation: Every binary request must start with the magic byte 0x80. If this byte is corrupted or missing, Memcached cannot reliably determine the packet boundaries and immediately closes the connection without issuing a response.
  • Binary Error Codes: If the header is structurally readable but contains invalid inputs, Memcached constructs a standard 24-byte response header containing the magic byte 0x81 and populates the two-byte Status field with an error code:
    • 0x0081 (Unknown Command): Returned when the opcode field in the header is invalid.
    • 0x0084 (Invalid Arguments): Returned when attributes such as the key length, extra length, or body length fail validation.
    • 0x0003 (Key Not Found) or 0x0004 (Key Exists): Returned when operations violate expected key states.
  • Diagnostic Strings: The binary response may also include a human-readable description in the response body explaining why the request failed.

Framing Desynchronization and Connection Termination

Memcached prioritizes process resilience over fault-tolerant stream recovery. In scenarios involving packet corruption:

  1. Buffer Bounds: If a corrupted packet specifies an impossibly large body length or key length that exceeds defined thresholds (such as default key limits of 250 bytes or slab memory limits), Memcached rejects the request immediately.
  2. Stream Desynchronization: If the server cannot determine where the malformed packet ends and where the next valid command begins, it treats the corruption as a framing failure. Attempting to parse out-of-order bytes risks executing unintended commands. Consequently, Memcached drops the connection and frees the associated file descriptor and buffers to protect the integrity of the cache.
