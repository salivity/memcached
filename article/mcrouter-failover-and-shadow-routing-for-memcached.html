Mcrouter Failover and Shadow Routing for Memcached

This article examines how mcrouter, an open-source Memcached proxy developed by Facebook, handles advanced traffic orchestration through failover and shadow routing strategies. By abstracting cache architecture away from the application tier, mcrouter uses configurable route trees to maintain high availability during hardware outages and enable safe production testing through asynchronous traffic mirroring.

Understanding Mcrouter Route Trees

At the core of mcrouter's routing capabilities is the route tree, configured via a JSON-based domain-specific language. Instead of an application talking directly to individual Memcached nodes, it connects to mcrouter via the standard Memcached protocol. Mcrouter parses the incoming commands (such as get, set, or delete) and routes them through a hierarchy of route libraries, such as FailoverRoute and ShadowRoute, depending on the operational requirements of the caching tier.

Implementing Failover Routing Strategies

The primary objective of failover routing in mcrouter is to ensure high availability and prevent cache stampedes when a cache node degrades or fails entirely. This is achieved primarily through the FailoverRoute handle.

  1. Sequential Request Fallback: When configured with a FailoverRoute, mcrouter specifies a list of targets (pools or specific instances), designated as primary and secondary targets. Mcrouter attempts to dispatch the command to the primary target first.
  2. Error Detection: If the primary target returns an error (such as a connection timeout, network failure, or an explicit server error), mcrouter captures the failure rather than returning it directly to the client.
  3. Failover Execution: Upon detecting the qualifying error, mcrouter immediately retries the operation on the subsequent targets in the configured list until a successful response is received or all targets are exhausted.
  4. Error Masking and TMO Handling: Mcrouter can distinguish between hard network failures and data misses (NOT_FOUND). A cache miss is treated as a valid response and returned to the application, whereas an unresponsive server triggers the next route in the failover chain.

Advanced failover configurations can also leverage FailoverWithExptimeRoute, which automatically alters the Time-To-Live (TTL) on writes routed to failover pools. This prevents stale data from persisting indefinitely in backup instances once the primary cluster recovers.

Implementing Shadow Routing Strategies

Shadow routing allows engineers to mirror live production traffic to a secondary, non-production Memcached cluster without affecting application latency or data integrity. This is handled by the ShadowRoute.

  1. Traffic Duplication: A ShadowRoute defines a "normal" child route and one or more "shadow" routes. When a client issues a query, mcrouter sends the request to the normal destination synchronously.
  2. Asynchronous Dispatch: Concurrently, mcrouter duplicates the command and dispatches it to the shadow target. This shadow request runs asynchronously in the background.
  3. Response Handling: The response from the primary target is returned immediately to the client application. The response from the shadow target is completely discarded by mcrouter, ensuring that errors or slow response times in the shadow cluster never impact the end user.
  4. Rate Limiting and Sampling: Shadowing can be configured with sampling rates (e.g., mirroring only 10% of total commands) and specific key prefixes. This protects shadow clusters from being overwhelmed if they run on smaller hardware footprints.

Common Use Cases for Combined Routing

Because mcrouter routes are composable, administrators frequently nest FailoverRoute and ShadowRoute instances inside one another:

  • Safe Cluster Upgrades: Deploy a new Memcached version in a shadow pool. By routing mirrored production reads and writes to it via ShadowRoute, engineers can validate memory usage, latency profiles, and stability under real workloads before cutting over traffic.
  • Warm Cache Deployment: Before replacing a failing or degraded node, a new node can be configured as a shadow target for writes. Once its cache is sufficiently populated, it can be promoted to the primary position in a FailoverRoute without inducing a cold-cache performance hit on backend databases.
