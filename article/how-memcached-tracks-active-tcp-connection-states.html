How Memcached Tracks Active TCP Connection States

This article explores how Memcached monitors and manages thousands of concurrent incoming TCP streams using an asynchronous, event-driven architecture. By pairing the libevent notification library with a multi-threaded master-worker model, Memcached represents every open socket as a dedicated connection state machine. This design allows the daemon to handle non-blocking read and write cycles, process commands, and clean up idle or terminated streams with minimal overhead and zero thread contention per connection.

The Master-Worker Thread Architecture

Memcached separates network connection acceptance from request processing using a primary dispatcher thread and a pool of worker threads. The dispatcher thread binds to the configured network interface and listens for new incoming TCP handshakes. When a client establishes a connection via accept(), the dispatcher creates a connection queue item containing the new file descriptor (fd) and assigns it to a worker thread using a round-robin algorithm.

Communication between the dispatcher and worker threads occurs through internal UNIX pipes. Each worker thread monitors its own pipe end via libevent. Once notified of an assigned descriptor, the worker thread extracts the socket, registers it with its local event loop, and takes complete ownership of tracking that connection's lifecycle.

The conn State Machine

Memcached tracks the state of each TCP stream using an internal C structure known as conn. The conn structure serves as a stateful container that persists for the entire lifetime of a TCP stream. It stores:

  • The socket file descriptor.
  • Dynamic read and write buffers.
  • The current state of the connection within its lifecycle.
  • Protocol-specific parsing metadata (ASCII or binary).
  • Pointer references to data items currently being fetched or stored.

The core of Memcached's execution loop is a finite state machine implemented in the drive_machine() function. At any point in time, an active connection resides in a specific state, such as:

  • conn_listening: Awaiting new incoming connections (used by the main thread).
  • conn_read: Reading incoming packets from the TCP stream into the read buffer.
  • conn_parse_cmd: Parsing protocol commands from accumulated buffer data.
  • conn_nread: Reading raw binary payload data (such as value bytes for a set command).
  • conn_write / conn_mwrite: Transmitting responses back to the client over the socket.
  • conn_waiting: Pausing processing until external operations or pending data become available.
  • conn_closing: Gracefully shutting down the connection and freeing buffers.

Asynchronous Event Monitoring with libevent

TCP is a stream-oriented protocol, meaning packets can arrive fragmented, out of order, or delayed. To prevent worker threads from blocking while waiting for data, Memcached sets all client sockets to non-blocking mode (O_NONBLOCK).

Instead of polling sockets, worker threads register each connection’s file descriptor with an underlying OS-specific multiplexing mechanism—such as epoll on Linux or kqueue on BSD/macOS—via libevent. When the operating system signals that a socket has data ready to read (EV_READ) or capacity to send data (EV_WRITE), libevent invokes the registered callback handler. The handler assigns the connection state machine to execute transitions inside drive_machine() until the socket would block again, at which point the thread yields back to the event loop.

Stream Fragmentation and Buffer Management

Each conn struct allocates dedicated read (rbuf) and write (wbuf) memory areas to manage stream boundaries:

  1. Partial Reads: If a client sends a partial command, the read operation exhausts available bytes and returns EAGAIN or EWOULDBLOCK. Memcached leaves the connection in the conn_read state, updates buffer offsets to track received bytes, and returns control to libevent until more segments arrive.
  2. Partial Writes: When sending large cached values back to a client, the socket send buffer may become saturated. Memcached transitions the connection to conn_write, tracks how many bytes were sent, and registers an EV_WRITE event with libevent to resume writing the remaining payload as soon as the kernel drains the socket buffer.

Connection Termination and Resource Reclamation

Memcached monitors TCP tear-down semantics through read return values and error flags. If a read call returns 0, indicating that the client has sent a TCP FIN packet to close the stream, or returns a socket error like ECONNRESET, the state machine immediately transitions to conn_closing. In this phase, the worker thread unregisters the file descriptor from libevent, closes the network socket, deallocates or recycles the dynamic buffers back into an internal memory freelist, and destroys the conn reference, ensuring zero resource leakage across millions of transient TCP streams.
