Restricting Network Access to Memcached Ports

Memcached is a high-performance, distributed memory caching system designed to speed up dynamic web applications by alleviating database load. However, exposing Memcached directly to the public internet poses severe security risks, including unauthorized data exposure and participation in massive UDP-based Distributed Denial of Service (DDoS) amplification attacks. This guide outlines the essential network security policies, configuration changes, and firewall rules required to effectively restrict direct access to Memcached ports and ensure your caching layer remains strictly private.

Default Port and Associated Risks

By default, Memcached listens on port 11211 for both TCP and UDP connections. If left open to public interfaces:

  • Data Leakage: Memcached lacks built-in encryption and historically does not enable authentication by default, allowing anyone to inspect, alter, or purge cached data.
  • Amplification Attacks: Attackers can send spoofed requests over UDP port 11211 to reflect enormous data responses onto target victims, turning your server into an attack vector.

1. Bind Memcached to Local or Private Interfaces

The first line of defense is ensuring the Memcached daemon does not listen on public interfaces (0.0.0.0).

Update the Memcached configuration file (typically /etc/memcached.conf on Debian/Ubuntu or /etc/sysconfig/memcached on RHEL/CentOS):

  • Localhost Only: If the caching server resides on the same machine as the application:

    -l 127.0.0.1

  • Internal Private IP: If the cache is shared across a cluster, bind exclusively to the server’s internal private network interface:

    -l 10.0.0.15

2. Disable the UDP Listener

Memcached is rarely required to run over UDP. Disabling UDP removes the possibility of reflection DDoS attacks entirely.

Add the following flag to your Memcached configuration:

-U 0

Restart the service to apply the change. Verify with ss -plunt | grep 11211 to ensure no UDP listener remains active.

3. Implement Cloud and Perimeter Security Groups

If deployed in a cloud environment (AWS, Google Cloud, Azure), isolate Memcached at the software-defined networking layer:

  • Private Subnets: Deploy Memcached instances within private subnets with no public IP addresses and no direct route to an Internet Gateway.
  • Security Groups / Network ACLs:
    • Create an ingress rule allowing traffic on TCP port 11211 only from the specific security groups or private CIDR blocks of your authorized application servers.
    • Explicitly block or drop all inbound internet traffic (0.0.0.0/0 and ::/0) targeting port 11211.

4. Configure Host-Based Firewalls

For dedicated or on-premises servers, enforce strict filtering via host firewalls.

Using ufw (Debian/Ubuntu):

# Deny all access to port 11211 by default
sudo ufw deny 11211

# Allow access only from a specific application server
sudo ufw allow from 10.0.0.20 to any port 11211 proto tcp

Using iptables:

# Allow established connections
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# Allow loopback access
iptables -A INPUT -i lo -p tcp --dport 11211 -j ACCEPT

# Allow trusted application server
iptables -A INPUT -p tcp -s 10.0.0.20 --dport 11211 -j ACCEPT

# Drop all other access to Memcached
iptables -A INPUT -p tcp --dport 11211 -j DROP
iptables -A INPUT -p udp --dport 11211 -j DROP

5. Network Segmentation and Access Verification

  • VLANs and VPC Peering: Place caching layers in a dedicated Virtual Local Area Network (VLAN) or dedicated Virtual Private Cloud (VPC), controlling cross-tier communication using strict routing policies.

  • External Auditing: Regularly audit your network perimeter using external port scanners (such as Nmap) to verify port 11211 is unreachable from the public internet:

    nmap -sT -sU -p 11211 <YOUR_PUBLIC_IP>

    The state for both TCP and UDP should report as filtered or closed.
