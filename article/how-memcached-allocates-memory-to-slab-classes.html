How Memcached Allocates Memory to Slab Classes

Memcached prevents memory fragmentation by dividing its total memory pool into pre-allocated memory chunks grouped into distinct slab classes. When starting Memcached, specific command-line flags define the geometry of these slab classes—determining the smallest chunk size, how rapidly chunk sizes scale, the maximum item size, and the total memory pool. Understanding these startup configuration parameters is essential for optimizing memory utilization and preventing wasted space.

Key Startup Configuration Parameters

Memcached does not assign fixed memory amounts to each class immediately upon booting; instead, it establishes the geometry (the size tiers) of the slab classes and assigns 1MB memory pages to these classes as data is written. The following configuration flags dictate this behavior:

1. Total Memory Limit (-m)

The -m parameter defines the maximum amount of RAM (in megabytes) that Memcached is permitted to use for storing items.

  • Default: 64 MB
  • Impact: This sets the overall ceiling for the entire slab system. As slab classes require space, 1MB memory pages are carved out of this total pool until the ceiling is reached.

2. Minimum Item Size (-n)

The -n parameter dictates the minimum space allocated for a key, value, and flags, establishing the chunk size of Slab Class 1.

  • Default: 48 bytes
  • Impact: Any stored item smaller than this threshold is padded to fit this minimum chunk size. Increasing -n raises the floor for the smallest data structures, preventing the creation of unnecessarily small chunk classes if your workload consists solely of larger items.

3. Chunk Size Growth Factor (-f)

The -f flag specifies the multiplier used to determine the chunk size of each subsequent slab class relative to the previous one.

  • Default: 1.25
  • Formula: \(\text{Chunk Size}_{n} = \text{Chunk Size}_{n-1} \times f\)
  • Impact: A lower factor (e.g., 1.1) creates more slab classes with smaller size increments between them, reducing internal fragmentation (wasted space within a chunk) at the cost of more metadata overhead. A higher factor creates fewer slab classes with wider gaps, which can cause significant memory waste if item sizes consistently fall just above a class threshold.

4. Maximum Item / Page Size (-I)

The -I parameter defines the maximum permitted item size, which also sets the size of each allocated slab page.

  • Default: 1 MB (1m)
  • Impact: This establishes the upper bound for the final, largest slab class. Items larger than this value cannot be stored unless this setting is increased. Because memory is allocated in units of this page size, changing -I changes the size of the memory blocks assigned to slab classes during runtime.

5. Memory Locking and Preallocation (-k and -L)

  • -k (Lock Memory): Prevents the operating system from swapping out Memcached memory pages to disk.
  • -L (Large Memory Pages): Enables the use of huge memory pages (if supported by the underlying OS) on startup, which improves CPU memory mapping performance for large allocations.

How the Parameters Work Together at Startup

When the Memcached process initializes:

  1. Size Tier Calculation: Memcached begins at the minimum chunk size defined by -n. It repeatedly applies the growth factor -f to generate progressive slab class tiers (e.g., Class 1 = 96 bytes, Class 2 = 120 bytes, Class 3 = 152 bytes) until the calculated chunk size reaches the maximum limit defined by -I.
  2. Page Reservation: The process calculates how many chunks can fit into a single page of size -I for each class.
  3. On-Demand Distribution: While the total memory envelope is constrained by -m, pages are not equally divided among all slab classes on startup. Instead, pages are reserved from the -m pool and assigned to specific slab classes on demand as keys matching those chunk dimensions are inserted.
