How to Limit Memcached Slab Class Memory

Memcached utilizes a slab allocation mechanism to manage memory, partitioning its overall memory pool into distinct slab classes tailored to specific item sizes. While Memcached does not provide a direct static configuration flag to assign hard byte limits to individual slab classes, operators can control, restrict, and balance slab class memory consumption through slab reassignment, chunk size tuning, and modern LRU maintenance tools. This guide outlines the operational strategies required to prevent individual slab classes from monopolizing system memory.

Understand the Slab Allocation Model

Memcached pre-allocates memory in chunks grouped into slab classes, typically inside 1 MB pages. Once a page is assigned to a specific slab class, it remains dedicated to that class by default. If a workload pattern changes or one item size experiences high write volume, that particular class can claim a disproportionate number of total pages—a condition known as slab calcification. Because Memcached lacks a directive like --max-slab-memory, managing per-class consumption relies on tuning allocation mechanics and enabling dynamic page redistribution.

Enable Dynamic Page Reassignment (Slab Automove)

The most effective way to restrict a slab class from indefinitely locking up memory is to enable the dynamic reassignment engine. This allows Memcached to take unused or lower-priority pages from one slab class and reallocate them to another class experiencing higher demand.

To enable this feature at startup, launch Memcached with:

memcached -o slab_reassign,slab_automove=1

Memcached offers different slab_automove algorithms:

  • slab_automove=1 (Standard): Evaluates slab activity over a moving window. If a slab class has three consecutive pages with no evictions and other classes are actively evicting items, Memcached reassigns pages away from the idle slab class.
  • slab_automove=2 (Aggressive/Tail LRU): Highly responsive. It continuously tracks eviction rates and moves pages specifically from classes with low eviction pressures to the classes undergoing heavy LRU churn.

Operators can adjust the reassignment algorithm dynamically over the Memcached administrative interface:

set slab_automove 2

Manually Reassign Slab Pages

When an operator identifies that a specific slab class has accumulated excessive memory, pages can be manually moved using administrative socket commands.

  1. Query slab distribution using the stats slabs command. Identify the source slab class ID consuming too much memory and the destination slab class ID that requires capacity.
  2. Issue the manual reallocation command:
slabs reassign <source_class_id> <destination_class_id>

This returns OK if the reassignment process has started. Memcached slowly clears the targeted 1 MB page and assigns it to the destination class without dropping existing connections.

Shape Memory Boundaries via Chunk Sizing Flags

Operators can restrict how memory spreads across slab classes by controlling chunk sizing parameters at startup:

  • Growth Factor (-f): Controls the scale factor between consecutive slab classes (default is 1.25). Increasing this value creates larger size intervals, reducing the total number of distinct slab classes generated and concentrating allocations into fewer, more predictable buckets.
  • Minimum Item Size (-n): Defines the space allocated for the smallest slab class (default is 48 bytes). Raising this value prevents micro-allocations from spawning low-capacity slab classes.
  • Maximum Item Size (-I): Sets the hard ceiling for the largest allocatable object (default is 1 MB). Lowering this parameter entirely caps the memory footprint of higher-end slab classes by disallowing large allocations.

Implement Segmented LRU (lru_maintainer)

To prevent specific slabs from consuming memory indefinitely without freeing space, ensure the modernized segmented LRU is active. Starting in version 1.5+, this is enabled by default. It partitions memory inside each slab class into four queues (HOT, WARM, COLD, and TEMP):

memcached -o modern

The LRU crawler and maintainer background threads continuously evict expired items and prevent inactive data from bloating a slab class, ensuring that the effective memory used by that slab class stays tethered strictly to active, frequently requested data.
