How Memcached Handles Hash Collisions

Memcached is a high-performance, distributed memory caching system that relies on an internal hash table for near-instantaneous key-value lookups. This article explores how Memcached manages key collisions through separate chaining, how it traverses collision chains during lookups, and how dynamic background rehashing keeps these chains short to preserve constant-time, O(1) performance.

The Hash Table Architecture

Memcached uses a global hash table (primary_hashtable) to store references to cached data items. When a client performs a write operation (such as set or add), Memcached computes a 32-bit hash value for the key using a fast hashing algorithm—historically Jenkins hash, and modernly MurmurHash3.

To determine the index of the bucket where the item belongs, Memcached applies a bitmask to the computed hash value:

bucket_index = hash_value & hashmask(hashpower);

Here, hashpower represents the current table size as an exponent of two (\(2^{\text{hashpower}}\) buckets). Because the number of possible keys far exceeds the number of available buckets, two distinct keys will inevitably map to the identical bucket index.

Collision Resolution: Separate Chaining

Memcached resolves hash collisions using separate chaining implemented via singly linked lists.

Instead of searching for alternative open slots in the array (open addressing), each hash bucket acts as the head of a linked list. The core storage unit, the item structure, contains an internal pointer called h_next. When a collision occurs:

  1. Memcached allocates and populates the new item struct in memory.
  2. It assigns the current head of the bucket list to the new item's h_next pointer.
  3. It updates the bucket pointer to reference the new item.

By prepending new items to the head of the list, Memcached accomplishes collision insertion in \(O(1)\) time complexity without needing to traverse the existing items in the chain.

Key Retrieval and Traversal

During a get or update operation, Memcached calculates the hash and identifies the target bucket index. If multiple keys have collided in that bucket, Memcached walks the linked list using the h_next pointers:

  1. It traverses the chain node by node.
  2. For each node, it first checks if the item's stored full hash matches the target key's hash.
  3. If the hash matches, it performs an exact string comparison (memcmp) between the stored key and the requested key to avoid false positives.
  4. Once a match is found, the item is returned. If the end of the list (NULL) is reached without a match, a cache miss occurs.

Preventing Chain Degradation: Incremental Rehashing

As more items are added, collision chains naturally grow longer. If long chains are left unchecked, lookup performance degrades from \(O(1)\) to \(O(N)\), where \(N\) is the length of the chain.

To prevent this degradation, Memcached monitors the ratio between total stored items and the number of buckets (the load factor). When the item count exceeds 1.5 times the table capacity, Memcached automatically doubles the hash table size (incrementing hashpower by 1) and begins a process called rehashing.

To avoid latency spikes or blocking client requests during large expansions, Memcached performs rehashing incrementally using a dedicated background maintenance thread (assoc_maintenance_thread):

  • Two Tables Active: During expansion, Memcached maintains both the old hash table and a newly allocated, doubled hash table.
  • Gradual Migration: The maintenance thread moves buckets from the old table to the new table in small, controlled batches (typically a few thousand buckets per iteration).
  • Concurrent Reads: When clients perform lookups during a rehash, Memcached checks the new table first if the bucket has already migrated; otherwise, it checks the old table.
  • Granular Locking: Mutexes protect the specific hash buckets currently undergoing migration, allowing read and write operations on unaffected buckets to proceed without interruption.

Once all items are migrated to the expanded table, the old table's memory is released, resetting the average chain length and ensuring that lookup operations remain nearly instantaneous.
