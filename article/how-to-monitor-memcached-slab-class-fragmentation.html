How to Monitor Memcached Slab Class Fragmentation

Monitoring memory fragmentation across individual Memcached slab classes is essential for optimizing cache efficiency and preventing unexpected evictions. This article explains how Memcached's slab allocation engine works, how to extract memory usage metrics via standard administrative commands, the exact mathematical formulas required to calculate slab-level fragmentation, and how to automate this monitoring using Prometheus and custom tooling.

Understanding Memcached Slab Allocation

Memcached manages memory using a slab allocator to prevent operating system-level memory fragmentation. Memory is divided into 1MB pages, which are then assigned to specific "slab classes." Each slab class divides its assigned pages into fixed-size chunks based on a growth factor (configured via the -f flag).

Fragmentation within Memcached primarily occurs internally within these chunks. If a slab class provides 512-byte chunks and stores a 300-byte item, the remaining 212 bytes inside that chunk are wasted. When repeated across millions of keys, this internal fragmentation can consume vast amounts of memory without triggering high-level alerts until cache evictions begin.

Extracting Metrics with stats slabs

To monitor individual slab classes, developers can connect directly to Memcached over its text protocol using tools like nc (netcat) or telnet:

echo "stats slabs" | nc 127.0.0.1 11211

Memcached outputs metrics prefixed with the slab class ID (e.g., 1, 2, 3). The critical metrics for monitoring fragmentation include:

  • chunk_size: The fixed size (in bytes) allocated for each chunk in this slab class.
  • used_chunks: The number of chunks currently holding stored items.
  • total_chunks: The total number of chunks allocated to this slab class.
  • mem_requested: The actual number of bytes requested and consumed by the stored data (keys, values, and per-item metadata).

Calculating the Fragmentation Ratio

There are two primary fragmentation metrics you should calculate per slab class: Active Internal Fragmentation and Total Class Memory Waste.

1. Active Internal Fragmentation Ratio

This measures the efficiency of the chunks that are currently in use. It shows how much memory is lost simply due to chunk size mismatch:

\[\text{Active Fragmentation Ratio} = 1 - \left( \frac{\text{mem\_requested}}{\text{used\_chunks} \times \text{chunk\_size}} \right)\]

  • A ratio close to 0.0 (0%) indicates near-perfect alignment between data sizes and chunk sizes.
  • A ratio above 0.3 (30%) indicates significant internal fragmentation, meaning data stored in this class is substantially smaller than the allocated chunk size.

2. Overall Slab Waste Ratio

This measures the active data against the total capacity currently reserved for the slab class (including unused chunks):

\[\text{Overall Waste Ratio} = 1 - \left( \frac{\text{mem\_requested}}{\text{total\_chunks} \times \text{chunk\_size}} \right)\]

This metric helps identify slab classes that have claimed memory pages they are no longer fully utilizing.

Automating with Prometheus

In modern production environments, manual metric extraction is impractical. The official Prometheus memcached_exporter scrapes stats slabs and exposes the necessary gauges:

  • memcached_slab_chunk_size_bytes{slab="<ID>"}
  • memcached_slab_chunks_used{slab="<ID>"}
  • memcached_slab_mem_requested_bytes{slab="<ID>"}

Using PromQL, developers can calculate the active fragmentation ratio for each slab class in real time:

1 - (
  memcached_slab_mem_requested_bytes
  / (memcached_slab_chunks_used * memcached_slab_chunk_size_bytes)
)

Alerting rules can be configured to fire whenever any slab class with significant utilization (memcached_slab_chunks_used > 1000) exhibits a fragmentation ratio exceeding 0.35 for sustained periods.

Remediating High Slab Fragmentation

If monitoring reveals high fragmentation in specific classes, developers have several remediation strategies:

  • Adjust the Growth Factor (-f): The default growth factor is 1.25. Lowering it (e.g., to 1.1 or 1.15) creates more granular slab classes with smaller size jumps, decreasing internal waste at the cost of higher slab metadata overhead.
  • Tune Minimum Chunk Size (-s or -n): If smaller slabs are underutilized or fragmented, adjusting the initial chunk size aligns the lower end of the slab ladder with actual key-value dimensions.
  • Enable Slab Automove: Run Memcached with -o slab_reassign,slab_automove=2 to allow the engine to automatically reassign unused pages from stagnant slab classes to classes experiencing high eviction pressure.
