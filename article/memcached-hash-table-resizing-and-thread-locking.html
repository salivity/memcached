Memcached Hash Table Resizing and Thread Locking

Memcached maintains high-throughput concurrency by avoiding global stop-the-world locks during its internal hash table expansion. When item density triggers a resize, Memcached delegates the migration of items to a dedicated background maintenance thread. By utilizing dual-table indexing, an incremental migration cursor, and partitioned item locks, the engine allows worker threads to continue serving read and write traffic concurrently with minimal latency spikes.

The Expansion Trigger and the Maintenance Thread

Memcached stores key-value pointers in an associative array (hash table) implemented as a power-of-two array of buckets. When the number of stored items exceeds 1.5 times the current hash table size, Memcached triggers an expansion to prevent hash collisions from degrading lookup performance to \(O(n)\).

Instead of forcing a worker thread to perform the resize, the engine signals a dedicated background thread known as the assoc_maintenance_thread. This thread is awakened via a condition variable and allocates a new, larger hash table that is double the size of the current primary table. The current table is marked as old_hashtable, and the newly allocated memory becomes the new target.

Dual-Table Lookups and the Migration Cursor

Once the resize begins, Memcached enters an expanding state tracked by the global flag expanding. During this phase, items exist in either the old table or the new table.

To manage this without blocking worker threads, Memcached uses an atomic cursor variable named expand_bucket. This integer indicates the current bucket index being migrated. When a worker thread needs to read, insert, or delete an item:

  1. It hashes the key to determine the bucket index.
  2. If expanding is true, the worker checks if the item's old bucket index is lower than expand_bucket.
  3. If the bucket index is less than expand_bucket, the item has already moved to the new table, so the worker routes the operation to the new hash table.
  4. If the bucket index is greater than or equal to expand_bucket, the worker routes the request to the old hash table.

For inserts, if the target bucket has already been visited by the cursor, the new item is placed directly into the new hash table. If not, it is placed into the old hash table to be migrated later by the maintenance thread.

Granular Locking with Partitioned Item Locks

Early versions of Memcached relied on a single global lock (the "cache lock") that serialized nearly all cache operations. Modern Memcached replaces this with a partitioned locking scheme using an array of discrete locks known as item_locks.

The number of item locks is typically a fixed power of two (such as 8,192 or 65,536). When accessing a bucket, a thread acquires only the lock associated with that bucket’s hash value:

\[\text{lock\_index} = \text{hash} \pmod{\text{lock\_count}}\]

During a resizing event, locking behavior is managed as follows:

  • Bucket-Level Isolation: The maintenance thread does not lock the entire table. It locks only the specific bucket (or small batch of buckets) it is actively migrating. It obtains the corresponding lock from item_locks, re-links the linked list nodes from the old bucket into the appropriate buckets in the new table, updates the expand_bucket cursor, and immediately releases the lock.
  • Worker Contention: Worker threads only block if they attempt to read or modify a key that maps to the exact lock currently held by the maintenance thread. Requests for keys in all other buckets proceed without contention.
  • Lock Switching: Memcached supports dynamic resizing of the item lock table itself if configured to scale item locks. In such cases, worker threads acquire locks using a two-phase check to verify whether the lock array itself is undergoing a resize, though standard hash resizing typically operates within the fixed item lock partitions.

Throttled Batch Migration

If the maintenance thread migrated the entire table in an unthrottled loop, it could exhaust system memory bus bandwidth and starve worker threads trying to acquire bucket locks. To prevent this, the maintenance thread processes items in configurable chunks (controlled internally, migrating a few buckets at a time).

Between chunks, the maintenance thread briefly releases locks and optionally yields the CPU (usleep or pause mechanisms depending on compile-time configurations). This throttling guarantees that worker threads receive priority access to the CPU and lock resources, ensuring that latency stays predictable even while shifting millions of hash table entries.

Completion of Resizing

Once expand_bucket reaches the total capacity of the old table:

  1. The maintenance thread acquires a brief lock to clear the expanding flag.
  2. The pointer to old_hashtable is set to NULL.
  3. The memory occupied by the old bucket pointer array is freed.
  4. The maintenance thread goes back to sleep until the load factor reaches the 1.5 threshold on the newly enlarged table.
