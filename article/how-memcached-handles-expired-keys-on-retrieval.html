How Memcached Handles Expired Keys on Retrieval

Memcached employs a lazy expiration strategy to process data retrieval requests for keys that have exceeded their Time To Live (TTL). Rather than actively scanning memory to delete expired items in the background, Memcached checks an item's expiration status only when a client explicitly attempts to retrieve it. If a requested key's TTL has elapsed, Memcached immediately treats the item as non-existent, reclaims its memory, and returns a cache miss to the client.

The Lazy Expiration Mechanism

When an item is written to Memcached with a TTL, the server records an absolute expiration timestamp based on the server's internal clock. To minimize CPU overhead, Memcached does not attach active timers to individual keys, nor does it run a continuous background thread to sweep expired data out of memory.

The Retrieval Workflow for Expired Keys

When a client sends a retrieval command (such as get or gets) for a key whose TTL has passed, Memcached executes the following steps:

  1. Hash Table Lookup: Memcached searches its internal hash table for the requested key. If the key exists in memory, Memcached retrieves the pointer to the item.
  2. Timestamp Evaluation: Before returning the data payload, the server compares the item's stored expiration timestamp against the current server time.
  3. Data Invalidation and Memory Reclamation: Upon identifying that the current time is greater than the expiration timestamp, Memcached marks the item as invalid. It unlinks the item from the hash table and the Least Recently Used (LRU) list, returning the memory chunk back to the appropriate slab allocator for future writes.
  4. Cache Miss Response: The server responds to the client with a standard cache miss (such as END in the ASCII protocol or a Key Not Found status in the binary protocol).

Behavior from the Client Perspective

From the client application's perspective, retrieving an expired key is indistinguishable from requesting a key that was never stored or one that was explicitly deleted. The application receives a cache miss, prompting it to follow standard cache-aside logic: querying the primary database for fresh data and writing the updated value back to Memcached with a new TTL.

Interaction with the LRU Cleaner

While lazy expiration handles the retrieval path, unrequested expired items could theoretically occupy memory indefinitely. To prevent this, Memcached also utilizes its LRU crawler and slab allocation logic. If memory becomes full, expired items are prioritized for eviction to make space for new writes, ensuring that stale keys do not permanently consume system memory even if they are never requested again.
