Memcached LRU Eviction Factors Under Full Capacity

When a Memcached node reaches its configured memory limit, it relies on a Least Recently Used (LRU) algorithm to free space for incoming writes by discarding older items. The rate at which these evictions occur is not merely a function of overall memory exhaustion, but depends on an interplay of architectural and operational variables. Key drivers include slab class memory allocation, write throughput, item size distribution, expiration settings, and Memcached's segmented LRU architecture. Understanding these factors allows engineers to diagnose unexpected cache drops, reduce latency spikes, and optimize overall hit rates.

Slab Class Allocation and Imbalance

Memcached manages memory through slab allocation, partitioning memory into slab classes dedicated to specific item size ranges. A critical operational reality is that evictions occur on a per-slab basis, rather than globally across the entire instance.

If memory has been fully allocated to various slabs, an influx of items sized at 500 bytes will only target the corresponding slab class. If that specific class is full, Memcached will evict items from that class even if other slab classes holding 10 KB items are largely idle. Consequently, a mismatched slab distribution or sudden shifts in object size profiles can trigger aggressive local evictions despite seemingly adequate global capacity.

Write Throughput and Cache Churn

The volume of incoming write operations (SET, ADD, REPLACE) directly drives eviction frequency. Because Memcached does not write to disk, any new write into a saturated slab class requires an immediate eviction of an older item unless an expired item is available. High write throughput—especially bursts of writes or cache updates—accelerates item turnover, pushing older, non-expired keys out of memory prematurely.

Time-to-Live (TTL) Configurations

Key expiration times determine how long an object remains logically valid. When memory is full, Memcached will attempt to reclaim memory from expired items before evicting unexpired keys.

  • Excessively long TTLs: Force Memcached to evict active, logically valid keys via the LRU mechanism because memory cannot be reclaimed via natural expiration.
  • Appropriately tuned TTLs: Allow items to expire naturally, allowing background processes or passive lookups to free pages without triggering LRU drops of valid working-set data.

Segmented LRU Queues and Hit Patterns

Modern versions of Memcached use a segmented LRU model (incorporating HOT, WARM, COLD, and TEMP queues) rather than a single flat list per slab:

  • Access Frequency: Keys are not placed into a single queue. Items with repeated reads migrate toward the WARM queue, shielding them from quick eviction.
  • Cold Queue Evictions: Only keys that sink to the tail of the COLD queue are eligible for eviction. If access patterns involve a high volume of one-hit-wonders, the COLD queue fills rapidly, causing a sharp increase in the eviction rate of low-utility keys while protecting frequently read data.

LRU Crawler and Maintenance Worker Activity

Memcached includes background threads such as the LRU Crawler and the Slab Automover. The LRU Crawler proactively traverses the queues to invalidate and reclaim expired items.

If the crawler is disabled or throttled by low thread priority, expired items linger at the tail of the queues, occupying physical chunks. When a write occurs, the node may perform an immediate LRU eviction of valid keys instead of seamlessly reusing the space of an expired item. Similarly, the Slab Automover can dynamically reassign unused memory pages from quiet slab classes to congested ones; if inactive, slab starvation persists, artificially accelerating evictions in congested classes.

Item Size Variance and Fragmentation

Irregular variations in key-value payloads force data into multiple distinct slab classes. Applications that frequently change serialization formats, append growing arrays to cache values, or store highly variable payload sizes introduce churn across the slab continuum. This variance minimizes the likelihood of reusing existing chunk spaces efficiently, driving rapid page consumption and forcing constant LRU turnover across multiple slab classes simultaneously.
