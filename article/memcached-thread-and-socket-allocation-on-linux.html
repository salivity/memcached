Memcached Thread and Socket Allocation on Linux

Memcached maximizes throughput and scalability on Linux systems by pairing a multi-threaded event-driven model with the libevent library. In standard operation, a single master dispatcher thread handles initial connection intake across network sockets and distributes them via round-robin to a pool of dedicated worker threads. Each worker thread runs its own isolated event loop to monitor and process assigned client sockets, avoiding lock contention and fully utilizing multi-core hardware.

The Master-Worker Architecture

Memcached separates network connection acceptance from request processing using a classic dispatcher-worker architecture. When initialized with the -t flag, Memcached creates a configurable number of worker threads alongside a primary dispatcher (main) thread.

The architecture functions through three core elements:

  • Dispatcher Thread: Manages the listening socket, accepts incoming connections, and assigns them to worker threads.
  • Worker Threads: Handle all data reads, protocol parsing, cache lookups, cache mutations, and response writes for assigned connections.
  • Connection Queues and Pipes: Facilitate thread communication between the dispatcher and the workers.

The Connection Handshake Flow

On Linux systems, the process of receiving a client socket and routing it to a worker thread follows a strict sequence:

  1. Listening and Accepting: The dispatcher thread binds to the specified port and registers the listening socket with its local libevent instance, which interfaces directly with the Linux epoll system call. When a client initiates a TCP handshake, epoll_wait flags the listening socket as readable. The dispatcher calls accept() (or accept4() to set non-blocking flags immediately) to generate a new connected socket file descriptor (fd).
  2. Round-Robin Selection: The dispatcher selects a target worker thread using a round-robin algorithm. This ensures an even distribution of client sockets across the thread pool without complex load-balancing calculations.
  3. Queue Enqueueing: The dispatcher packages the new file descriptor and its initial state into a connection queue item (CQ_ITEM) and pushes it onto the chosen worker thread’s private thread-safe connection queue.
  4. Worker Notification: Because the worker thread is typically blocked waiting for network events inside its own epoll_wait call, the dispatcher must wake it up. It does this by writing a single byte to the write-end of an inter-process pipe (or an eventfd) established specifically between the dispatcher and that worker.
  5. Registration to the Worker Loop: The worker’s event loop detects incoming data on the pipe. The worker wakes up, reads the byte to clear the notification, pops the CQ_ITEM from its queue, and registers the client socket fd with its own libevent (epoll) instance.
  6. Subsequent Processing: From this point forward, the dispatcher has no involvement with the connection. The worker thread directly handles all subsequent network I/O, cache queries, and socket termination.

Multi-Queue Optimization and SO_REUSEPORT

While the traditional single-dispatcher model prevents multi-threaded synchronization issues on the listening socket, the dispatcher thread itself can become an intake bottleneck on modern high-bandwidth networks exceeding tens of gigabits per second.

To address this, modern Linux kernels support the SO_REUSEPORT socket option. When configured with this capability, Memcached allows multiple threads (or multiple worker instances) to bind directly to the same IP address and port. Instead of user-space round-robin distribution by a single dispatcher:

  • The Linux kernel itself creates multiple receive queues for the listening port.
  • Incoming TCP SYN packets are hashed across the bound sockets by the kernel (typically using a 4-tuple or 5-tuple hash of source and destination IPs and ports).
  • Each worker thread accepts connections directly from its own listening socket, entirely bypassing the single-dispatcher bottleneck and eliminating inter-thread pipe notifications.
