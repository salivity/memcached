How Memcached Handles Hash Collisions in Key Lookups

Memcached resolves key lookup operations during hash collisions by utilizing a classic separate chaining strategy combined with exact key validation. Internally, Memcached indexes cached items using a primary hash table consisting of an array of buckets. When two distinct keys produce the same hash value or map to the identical bucket index, Memcached chains these records together in a singly linked list. During a retrieval request, the server locates the appropriate bucket and traverses this list, performing exact byte comparisons to identify and return the correct record or confirm a cache miss.

The Underlying Data Structure: Separate Chaining

Memcached allocates an internal array of pointers, commonly referred to as the primary hash table. Each entry in this array serves as the head of a bucket.

Every cached record in Memcached is wrapped in an internal item structure. To facilitate collision handling without secondary memory allocations, the item structure includes a dedicated pointer member named h_next. When multiple items hash to the same bucket index, they are organized into a singly linked list where each item points to the next item via its h_next field.

Step-by-Step Collision Resolution During Key Lookup

When a client issues a get command for a specific key, the lookup sequence follows these distinct steps:

  1. Hash Calculation: Memcached computes a 32-bit integer hash of the requested key using its configured hashing algorithm (typically Murmur3 or Jenkins hash).
  2. Bucket Selection: The computed hash is masked against the current hash table size using a bitwise AND operation (hash & hashmask(hashpower)), which pinpoints the exact bucket index within the primary hash table array.
  3. Chain Traversal: Memcached accesses the head pointer at the target bucket index. If the pointer is NULL, the key does not exist, and the server immediately registers a cache miss. If the bucket contains an item, traversal begins through the h_next pointers.
  4. Exact Key Matching: Because multiple keys can produce identical bucket indices—or even identical hash outputs—Memcached does not rely solely on the hash. For each node in the chain, it executes two checks:
    • It checks whether the stored key length matches the query key length.
    • If the lengths match, it performs an exact byte-for-byte comparison using memcmp().
  5. Result Handling:
    • If a matching key is found, the traversal stops, the item's reference count is incremented, and its payload is returned to the client.
    • If the end of the chain (NULL) is reached without a match, Memcached treats the request as a cache miss.

Mitigation of Degraded Lookup Performance

If a collision chain grows too long, lookup complexity for that bucket degrades from optimal \(O(1)\) time toward linear \(O(n)\) time. Memcached actively prevents long collision chains through dynamic table expansion:

  • Automatic Resizing: When the total number of stored items exceeds 1.5 times the number of available buckets, Memcached triggers an automatic hash table expansion. The table doubles in size (increasing hashpower by 1).
  • Incremental Rehashing: To avoid locking the entire cache, a dedicated background maintenance thread progressively migrates buckets from the old table to the new, larger table.
  • Dual-Table Lookup During Migration: If a lookup occurs while rehashing is active, Memcached checks the migration progress. If the target bucket has already been moved, it searches the new hash table; if not, it traverses the collision chain in the old table.

This combination of linked list traversal, explicit memory comparison, and dynamic rehashing ensures that hash collisions are handled deterministically without data corruption or unbounded latency spikes.
