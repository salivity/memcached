How Memcached Append Modifies Cached Values

The append command in Memcached allows developers to add data to an existing cached item without needing to fetch, modify, and re-upload the entire value from the client application. By delegating the modification process directly to the Memcached server, this command eliminates network round trips, prevents race conditions caused by concurrent writes, and optimizes write performance. This article explains the internal mechanics of how Memcached processes the append command, manages memory reallocation, and ensures atomic updates without full data replacement on the client side.

The Inefficiency of Client-Side Updates

Under standard operations, updating a cached string requires a "read-modify-write" cycle:

  1. The client issues a get command to fetch the current value.
  2. The client concatenates the new data onto the existing payload in local application memory.
  3. The client issues a set command to replace the old value in Memcached.

This workflow introduces substantial network latency and creates concurrency hazards. If two client threads attempt to update the same key simultaneously, one client's update will overwrite the other's, leading to data loss.

How the append Command Works

The append command streamlines this process by executing the concatenation directly within Memcached's memory space. The syntax for the command is:

append <key> <flags> <exptime> <bytes>\r\n
<data>\r\n

When this command is received, Memcached executes the following steps:

  1. Existence Verification: Memcached checks whether the target key currently exists in its hash table. Unlike the set command, append requires an existing target. If the key does not exist or has expired, Memcached returns NOT_STORED and aborts the operation.
  2. Metadata Retention: Although the command protocol requires <flags> and <exptime> parameters for structural consistency, Memcached ignores these values during an append operation. The item's existing expiration time and flag settings remain unchanged.
  3. Atomic Execution: The operation is locked at the item level. This ensures that no other reading or writing thread can access the key until the append operation is finished, providing full atomicity.

Memory Reallocation Under the Slab Allocator

Because Memcached uses a slab allocator system, items are stored in fixed-size memory chunks. Modifying the size of an existing value cannot be done by simply expanding the memory segment in place. Instead, Memcached handles the modification internally as follows:

  • New Item Allocation: Memcached calculates the new payload size (existing_bytes + append_bytes). It then requests a new memory chunk from the appropriate slab class capable of holding the combined size.
  • Data Transfer: Memcached copies the original data into the beginning of the newly allocated buffer, immediately followed by the new bytes provided in the append command.
  • Pointer Swapping: The server updates its internal hash table to point the key to the newly created memory address.
  • Garbage Reclamation: The previous memory chunk containing the original data is freed and returned to the slab pool for reuse.

Limitations and Operational Considerations

While append prevents full round-trip replacement, it has operational boundaries:

  • Maximum Item Size: The resulting concatenated string must not exceed the maximum allowed item size (default is 1 MB). If the combined data exceeds this threshold, the command fails.
  • Plaintext and Raw Byte Operations: Memcached treats the payload as an opaque byte array. If cached objects are serialized (e.g., JSON, Protocol Buffers, or language-specific objects), appending raw bytes will corrupt the serialized structure. As a result, append is best suited for raw strings, log streams, or delimited buffers.
