How to Use Memcached CAS for Conditional Updates

In concurrent environments, multiple application processes updating the same cache key simultaneously can lead to race conditions and data corruption. This article explains how developers can prevent these concurrency issues in Memcached by implementing conditional storage logic using the Check-and-Set (CAS) command. You will learn the mechanics behind CAS tokens, how the optimistic locking pattern works in Memcached, and how to structure a resilient read-modify-write retry loop in your application code.

The Problem: Race Conditions in Cache Updates

A standard read-modify-write cycle consists of three steps:

  1. Reading data with get key
  2. Modifying the value locally in the application
  3. Writing the updated value back with set key value

If two independent clients read the same key at the same time, modify it, and write it back, the second write silently overwrites the first write without accounting for those changes. This is known as a lost update.

How Memcached CAS Works

Memcached solves this using optimistic concurrency control powered by two primary commands:

  • gets (Get with CAS): Behaves like a standard get command, but returns an additional 64-bit integer called a CAS token alongside the key's value. This token acts as a version identifier that changes every time the key's value is modified.
  • cas (Check-and-Set): Stores data conditionally. It requires the client to pass the CAS token obtained during the initial gets call. If the token in the request matches the current token on the server, the data is updated. If another client modified the key in the interim, the token will not match, and Memcached rejects the write.

Protocol Syntax

The syntax for the ASCII cas command is:

cas <key> <flags> <exptime> <bytes> <cas_token> [noreply]\r\n
<data_block>\r\n

Memcached will return one of the following responses:

  • STORED: The update succeeded; the CAS token matched.
  • EXISTS: The update failed; another process modified the key since the token was retrieved.
  • NOT_FOUND: The key expired or was deleted between retrieval and update.

Implementing the CAS Retry Pattern

To implement conditional storage, wrap the read-modify-write operation in a loop that handles token validation failures.

Implementation Steps:

  1. Fetch: Retrieve the current value and CAS token using gets.
  2. Compute: Apply your application logic to modify the data.
  3. Attempt Update: Send the new data to Memcached using cas along with the fetched token.
  4. Evaluate Result:
    • If STORED, exit the loop successfully.
    • If EXISTS, discard changes, reload the new value and token, and retry.
    • If NOT_FOUND, decide whether to re-initialize the key with add or abort.

Example Implementation (Python / pymemcache)

from pymemcache.client.base import Client

client = Client(('localhost', 11211))

def update_counter(key, increment_by=1, max_retries=5):
    retries = 0
    while retries < max_retries:
        # Step 1: Fetch value and CAS token
        result = client.gets(key)
        
        if result is None:
            # Handle key creation if it does not exist
            if client.add(key, increment_by):
                return increment_by
            retries += 1
            continue

        value, cas_token = result
        new_value = int(value) + increment_by

        # Step 2 & 3: Attempt conditional write
        if client.cas(key, new_value, cas_token):
            return new_value  # Update succeeded

        # Step 4: CAS failed due to concurrent modification; retry
        retries += 1

    raise RuntimeError(f"Failed to update {key} after {max_retries} attempts.")

Best Practices

  • Enforce Retry Limits: Always set a cap on retries (e.g., 3 to 5 attempts) to prevent infinite loops during high write contention.
  • Exponential Backoff with Jitter: If write collisions are frequent, introduce brief randomized pauses (jitter) between retries to desynchronize competing clients.
  • Keep Modifications Fast: Minimize the computation time between gets and cas calls to reduce the window of vulnerability where another client can update the key.
