Profiling Memcached Memory Usage Per Tier

Running multiple application tiers on a shared Memcached cluster often leads to the "noisy neighbor" problem, where one service exhausts cache space at the expense of others. Because Memcached is inherently unaware of multi-tenancy and stores items purely as key-value pairs inside global slab allocators, profiling memory consumption per application tier requires specialized operational strategies. This guide covers actionable techniques to attribute, measure, and monitor memory consumption by application tier in shared Memcached environments.

1. Hierarchical Key Namespacing and LRU Crawler Metadumps

The most reliable server-side method for tracking memory consumption by tier involves enforcing a strict key-naming convention across all applications (for example, tier:service:identifier, such as auth:session:12345 or catalog:item:67890).

To profile memory without impacting live traffic:

  • Run the asynchronous LRU Crawler via the Memcached administration protocol using the command lru_crawler metadump all.
  • Unlike the legacy stats cachedump, the LRU Crawler runs non-blockingly on background threads and dumps key metadata, including expiration time (exp), size in bytes, and slab class.
  • Stream this metadump output into an aggregation pipeline (using scripts in Python, Go, or a log parser). Parse the prefix delimiters to compute total allocated bytes, average item size, and total key count per application tier.

2. Client-Side Telemetry and Metrics Instrumentation

Because Memcached does not track the client origin of stored bytes, accounting can be shifted upstream to the application tiers themselves. By wrapping client SDKs (such as pymemcache, spymemcache, or custom wrappers):

  • Track the exact payload size in bytes during set, add, and replace operations.
  • Emit custom metrics to your telemetry collector (Prometheus, Datadog, or OpenTelemetry) tagged by tier, such as memcached_bytes_written_total{tier="checkout"}.
  • Pair this with tracked read hits and misses to compute not just total footprint, but the memory efficiency (hit-to-footprint ratio) of each individual tier.

3. Layer 7 Proxy Inspection Using Mcrouter or Envoy

Introducing an intelligent proxy layer such as Facebook's mcrouter or an Envoy proxy with a Memcached filter decouples connection routing from backend storage. Proxies can inspect and segment traffic per tier:

  • Prefix-based Routing and Accounting: Configure mcrouter with routing prefixes dedicated to each tier. Mcrouter records detailed stats per route prefix, allowing you to observe throughput, byte rates, and command types per tier.
  • Envoy Access Logs and Metrics: Envoy can parse the Memcached binary and text protocols to output command histograms, request payload sizes, and response sizes labeled by downstream client identities.

4. Slab Class Attribution

Memcached organizes memory into slab classes based on item size chunk intervals (governed by the growth factor, typically 1.25).

  • Different application tiers typically store distinct data shapes. For example, a user session tier may consistently store ~512-byte payloads (Slab Class 4), while an inventory tier caches large JSON payloads exceeding 16KB (Slab Class 16).
  • Query stats slabs and stats items to inspect individual slab utilization, page counts, and eviction rates.
  • By cross-referencing your application tiers' known serialization sizes with active slab classes, you can infer which tier is driving slab allocation and triggering evictions.

5. eBPF Network Tracing by Source IP

In environments where application tiers occupy distinct IP blocks, Kubernetes namespaces, or VPC subnets, kernel-level eBPF programs (using tools like bcc or bpftrace) can trace incoming network traffic to the Memcached port:

  • Attach eBPF probes to socket buffers (sock:sock_data_ready or tcp_recvmsg) on the Memcached host.
  • Extract the command payload length from write commands (set, add) and associate the byte count with the source IP address.
  • Aggregate the incoming write volume by CIDR or service identity to determine which application tier is injecting the highest volume of data over time without introducing client-side overhead or modifying application code.
