Linux Kernel Tuning for Sub-Millisecond Memcached

Achieving sub-millisecond latency with Memcached requires eliminating bottlenecks within the underlying Linux networking stack. Out-of-the-box kernel configurations are optimized for balanced, general-purpose throughput rather than extreme low-latency packet processing. Under high-throughput, small-packet workloads typical of Memcached, default network parameters lead to packet drops, buffer exhaustion, and costly CPU context switching. Tuning network buffer allocations, connection backlogs, TCP behavior, and interrupt handling enables the operating system to process incoming requests at line rate, ensuring Memcached operates at its maximum potential speed.

Socket Buffer Sizing and Memory Limits

Memcached typically handles high volumes of small keys and values. Default Linux socket buffers can either truncate throughput by being too small or waste memory and induce bufferbloat by being too large.

The kernel limits the memory allocated to socket read and write buffers via sysctl parameters:

  • net.core.rmem_max and net.core.wmem_max: Define the maximum allowable size for OS receive and send buffers.
  • net.ipv4.tcp_rmem and net.ipv4.tcp_wmem: Specify the minimum, default, and maximum vector sizes in bytes for individual TCP sockets.

For sub-millisecond responses, set these values to scale with high-concurrency traffic without introducing latency-inducing buffer queues:

net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216

Queue Management and Connection Backlogs

Sudden traffic spikes can overwhelm system queues before Memcached's event loop processes the connection or incoming data. When queues overflow, the kernel silently drops packets, forcing TCP retransmissions that increase latency from sub-milliseconds to hundreds of milliseconds.

Three parameters govern queue capacity:

  • net.core.somaxconn: Controls the maximum length of the listen queue for accepting new TCP connections. The default value (often 128 or 4096) is insufficient for high-concurrency instances and should be increased to match or exceed Memcached's -b (backlog) setting (e.g., 65535).
  • net.ipv4.tcp_max_syn_backlog: Determines the number of half-open connections tracked during the TCP three-way handshake. Increasing this to 65535 prevents drops during connection storms.
  • net.core.netdev_max_backlog: Defines the maximum number of packets queued on the input side after reception from the network interface card (NIC) driver before being processed by the network stack. Raising this to 10000 or higher prevents packet drops at high packet-per-second (PPS) rates.

Minimizing TCP Handshake and Connection Overhead

Connection turnover can saturate network resources. If clients connect and disconnect frequently rather than using persistent connection pools, kernel parameters must mitigate connection overhead:

  • net.ipv4.tcp_tw_reuse = 1: Allows the kernel to safely reuse TIME_WAIT sockets for outgoing connections when protocol safety can be guaranteed, avoiding ephemeral port exhaustion.
  • net.ipv4.tcp_fin_timeout = 15: Reduces the time a socket remains in the FIN-WAIT-2 state, freeing up kernel memory faster.
  • net.ipv4.tcp_fastopen = 3: Enables TCP Fast Open on both client and server sides, allowing data exchange during the initial SYN packet and eliminating a round-trip time (RTT).

Reducing Latency with Busy Polling

Traditional network packet processing relies on hardware interrupts to notify the CPU of incoming packets. Interrupts introduce context switching overhead and CPU scheduling delays.

The Linux kernel supports low-latency busy polling, which permits the network stack or application to actively poll the network device queue:

  • net.core.busy_read: Sets the number of microseconds to wait on socket reads for new packets before yielding.
  • net.core.busy_poll: Sets the number of microseconds to wait on socket poll or select system calls.

Setting these parameters to 50 reduces processing jitter and eliminates interrupt latency at the expense of higher continuous CPU utilization.

CPU Affinity and Hardware Offloading

Kernel parameters intersect directly with physical hardware configuration. To ensure packets reach Memcached threads with minimal cache invalidation:

  • NIC Ring Buffers: Increase device ring buffers using ethtool -G <interface> rx 4096 tx 4096 to prevent frame drops during bursty network transfers.
  • Receive Side Scaling (RSS): Distribute packet processing across multiple CPU cores to prevent a single core from becoming a bottleneck on the NIC interrupt line.
  • Core Pinning: Bind Memcached worker threads and specific NIC queue interrupt lines (IRQs) to the same NUMA node to maximize L3 cache hits and avoid cross-socket memory bus penalties.
