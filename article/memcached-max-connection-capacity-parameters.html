Memcached Max Connection Capacity Parameters

Understanding the maximum client connection capacity of a default Memcached setup requires looking at both Memcached's internal configuration and the underlying operating system limits. By default, Memcached restricts simultaneous connections through an internal threshold, but standard Linux user and kernel limits often serve as secondary, or even primary, bottlenecks. This guide breaks down the core parameters that dictate connection capacity and how they interact in a default installation.

1. The Internal Memcached Parameter (-c)

The primary setting controlling client connections inside Memcached is the -c flag (or MAXCONN in distribution configuration files):

  • Parameter: -c <num>
  • Default Value: 1024 simultaneous connections.
  • Mechanism: Memcached uses libevent to handle asynchronous I/O. When the number of active connections reaches the value defined by -c, the daemon ceases accepting new incoming TCP connections until active ones disconnect or time out.

In Debian/Ubuntu environments, this is set in /etc/memcached.conf (e.g., -c 1024). In Red Hat/CentOS/Fedora systems, it is defined in /etc/sysconfig/memcached as MAXCONN="1024".

2. Operating System File Descriptor Limits (nofile)

Because every network connection in a Unix-like system consumes a file descriptor, the OS limit on open files dictates whether Memcached can actually reach its internal connection cap:

  • User Limit (ulimit -n): By default, many Linux distributions enforce a soft limit of 1024 open files per process. Because Memcached requires file descriptors for listening sockets, internal pipes, and logging in addition to client connections, setting -c 1024 under a ulimit -n 1024 environment will cause connection failures before reaching 1024 clients.
  • Systemd Configuration (LimitNOFILE): Modern Linux installations run Memcached as a systemd service. Systemd ignores traditional limits defined in /etc/security/limits.conf. Instead, connection capacity is bounded by the LimitNOFILE directive within the service unit (/lib/systemd/system/memcached.service or an override file). If LimitNOFILE is lower than -c, Memcached will fail to scale.

3. Kernel TCP Queue Parameters

Even when open file limits and the -c parameter are tuned, kernel-level socket queue parameters dictate how many inbound connection requests can be handled concurrently during spikes:

  • net.core.somaxconn: This parameter controls the maximum size of the listen queue for accepting incoming TCP connections. Defaulting to 128 or 4096 depending on the kernel version, an overrun in this backlog results in dropped or ignored client connection requests before Memcached can accept them.
  • net.ipv4.tcp_max_syn_backlog: Dictates the maximum number of remembered half-open connection requests (clients that have sent a SYN packet without completing the three-way handshake). If this queue fills up, incoming connection attempts fail.

4. Memory Allocations Per Connection

While not an explicit integer limit, Memcached allocates memory buffers for reading and writing data across every active connection. In default deployments, connection structures and standard network buffers require memory headroom outside the designated item cache (-m). If the system runs out of physical memory or reaches process memory ceilings under a surge of connections, the operating system's OOM killer will terminate the Memcached process.
