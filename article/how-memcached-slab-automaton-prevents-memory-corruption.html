How Memcached Slab Automaton Prevents Memory Corruption

This article explores how Memcached utilizes its slab allocation automaton to guarantee memory safety and stability under high-concurrency workloads. High-throughput caching services face extreme risks of memory fragmentation, race conditions, and pointer corruption when relying on standard dynamic memory allocation. By partitioning memory into deterministic slab classes, enforcing strict state-driven lifecycles, and coupling thread-safe reference counting with LRU (Least Recently Used) management, Memcached prevents memory corruption, buffer overflows, and use-after-free errors when operating near maximum capacity.

The Problem with Standard Memory Allocation

Under heavy load, conventional runtime memory allocators relying on standard malloc and free operations struggle with rapid cycles of item creation and invalidation. Variable-sized allocations lead to severe external fragmentation, where free memory becomes scattered in non-contiguous blocks. Over time, the operating system kernel and runtime allocators experience lock contention, latency spikes, and an increased risk of memory exhaustion. In multi-threaded environments, asynchronous writes and evictions heighten the possibility of race conditions, dangling pointers, and double-free bugs.

Slab Allocation Architecture

Memcached avoids dynamic heap fragmentation by pre-allocating a large, continuous memory pool during startup. This pool is managed via a slab allocation architecture:

  • Slab Pages: The pool is carved into discrete 1-megabyte chunks called slab pages.
  • Slab Classes: Each page is assigned to a specific slab class based on item size. A geometric progression factor (typically 1.25) dictates chunk capacities across classes (e.g., Class 1 holds 96-byte items, Class 2 holds 120-byte items, and so on).
  • Pre-partitioned Chunks: Once a page is assigned to a slab class, it is cut into fixed-size slots. An incoming item is assigned strictly to the smallest slab class capable of holding its data.

Because chunks within a slab class are uniform, Memcached completely avoids external fragmentation. Pointers never need to address variable offsets dynamically within a page, virtually eliminating memory boundary overruns.

The Slab Automaton and Lifecycle States

The memory manager functions as a deterministic finite-state machine (automaton). Memory items move through distinct, non-overlapping lifecycle states:

  1. Unallocated/Free: The chunk resides in the slab class's free list.
  2. Allocated/Initializing: Memory is reserved for an incoming payload; socket I/O writes data directly into the pre-sized chunk boundaries.
  3. Active/Linked: The item is linked into the primary hash table and the LRU doubly linked list.
  4. Stale/Expired: The item’s time-to-live (TTL) lapses or it is targeted by an explicit eviction mechanism.
  5. Reclaimed: The chunk is unlinked from the hash table and returned to the freelist or overwritten directly.

By strictly defining the transitions between these states, the slab automaton ensures that an item cannot be consumed or overwritten until its state has atomically shifted.

Reference Counting and Concurrency Protection

Under concurrent access, a common vector for memory corruption is the "use-after-free" bug—occurring when one thread evicts an item while another thread is transmitting its contents over a socket. Memcached resolves this through item-level reference counting (refcount):

  • Every reader or worker thread handling an item increments its reference count while holding an item lock.
  • When an item expires or is targeted for eviction by the LRU crawler, the memory manager removes it from the global hash table so no new threads can discover it.
  • The actual memory chunk is not returned to the slab allocator or overwritten until the refcount drops to zero.

This prevents read/write race conditions and ensures memory remains valid throughout the entire duration of a network transmission.

Dynamic Slab Rebalancing and the Automaton Worker

When application access patterns shift, one slab class may run out of memory while others remain largely idle. Memcached handles this using a background thread known as the slab rebalancer.

The rebalancer operates as an autonomous worker that migrates an entire 1MB page from an underutilized slab class to a starved one. To prevent data corruption during this process:

  • The rebalancer locks the targeted page and halts allocations targeting that specific page slice.
  • It systematically unlinks every active item on that page from the hash table, verifying reference counts.
  • Only when all chunks within the page are idle and unreferenced does the automaton reformat the page into new chunk dimensions and assign it to the new slab class.

Bounded Limits and Thread Safety

Memcached uses item locks partitioned across hash buckets alongside dedicated slab mutexes. The memory footprint of any given key-value pair is strictly bounded by the maximum slab size (typically 1MB), preventing arbitrary payload sizes from overflowing allocated buffers. By managing memory through predictable chunk assignments, strict state machines, and reference-tracked lifecycles, Memcached maintains zero memory corruption and predictable performance under high-concurrency loads.
