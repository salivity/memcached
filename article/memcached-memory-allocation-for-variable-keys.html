Memcached Memory Allocation for Variable Keys

Memcached uses a specialized slab allocation mechanism to manage memory, preventing fragmentation caused by continuous dynamic allocations. When keys and values vary dramatically in size, Memcached determines memory placement based on the total item footprint—combining the key, data payload, and internal metadata—rather than allocating space for the key alone. This article explains how the slab allocator places variable-length items into fixed-size chunks, the performance trade-offs involved such as internal fragmentation, and how the system mitigates memory imbalances caused by erratic item sizes.

The Slab Allocation System

To avoid the overhead and operating system fragmentation of standard C-library malloc and free operations, Memcached pre-allocates a continuous block of memory. This pool is divided into 1MB pages (by default). Each page is assigned to a specific Slab Class, which slices the 1MB page into equal-sized units called Chunks.

Slab classes are arranged in an increasing progression of chunk sizes governed by a growth factor (defaulting to 1.25). For example:

  • Slab Class 1: 96 bytes per chunk
  • Slab Class 2: 120 bytes per chunk
  • Slab Class 3: 152 bytes per chunk

How Variable Key Sizes Impact Allocation

When an item is written to Memcached, the engine calculates the total byte size required:

\[\text{Total Size} = \text{Key Length} + \text{Value Length} + \text{Item Structure Metadata (roughly 48–56 bytes)}\]

Because the key is bundled directly with the value and metadata into a single contiguous item structure, dramatic differences in key length directly shift the total item size into different slab classes:

  1. Class Selection: Memcached inspects the total item size and identifies the smallest slab class with chunks large enough to hold it.
  2. Chunk Placement: The item is placed into an available pre-allocated chunk within that slab class. The remaining unused bytes inside that chunk cannot be shared with any other key-value pair.

Challenges with Drastically Varying Keys

When key lengths vary wildly—for instance, standard 16-byte keys mixed with multi-kilobyte composite keys—two main issues arise:

1. Internal Fragmentation

If an item requires 121 bytes, it cannot fit into a 120-byte chunk and must be placed into a 152-byte chunk. The remaining 31 bytes represent internal fragmentation (slack space). If key lengths fluctuate unpredictably, the ratio of wasted chunk space can increase, lowering the effective cache capacity.

2. Slab Calcification

If a workload initially stores millions of short keys with small values, Memcached dedicates the majority of its 1MB pages to smaller slab classes. If the application later shifts to using very long keys, Memcached may encounter slab calcification: small-slab pages cannot naturally accommodate large-slab items, causing premature evictions in larger slab classes even if small-slab chunks remain underutilized.

How Memcached Mitigates These Disparities

Modern versions of Memcached implement several features to handle dramatic shifts in item sizes:

  • Tunable Growth Factor (-f flag): Administrators can decrease the growth factor (e.g., from 1.25 down to 1.1 or 1.05) to create a denser gradient of slab classes. This minimizes internal fragmentation by ensuring chunk sizes closely match the requested item sizes.
  • Slab Automove and Slab Reassign (slab_automove): Background threads monitor eviction rates across classes. If larger slabs are evicting hot keys while smaller slabs have surplus memory, the engine dynamically moves 1MB pages from one slab class to another.
  • Key Length Limits: Memcached enforces a hard limit on key length (typically 250 bytes by default). This design restriction ensures that keys cannot independently consume an entire slab chunk, forcing applications to hash or truncate oversized keys before caching.
