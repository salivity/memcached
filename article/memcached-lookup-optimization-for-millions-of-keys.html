Memcached Lookup Optimization for Millions of Keys

Memcached delivers deterministic, sub-millisecond data retrieval for applications storing millions of keys by relying on an in-memory architecture centered around an expandable hash table, fine-grained concurrency, and custom memory management. By eliminating disk I/O, utilizing efficient hashing algorithms, dynamically expanding its internal bucket structures, and preventing operating system memory fragmentation through slab allocation, Memcached maintains \(O(1)\) constant-time lookup performance regardless of the total dataset size.

Global Hash Table and Fast Hashing

At the core of Memcached's lookup engine is an internal hash table. When an application queries a key, Memcached computes a 32-bit hash value using optimized algorithms like Murmur3 or Jenkins Hash. These algorithms distribute keys uniformly across available buckets, minimizing collisions even when scaling to tens of millions of records.

Memcached maps the computed hash to a specific bucket index. Because the hash table operates in pure RAM, resolving this index to a memory pointer requires only a few CPU instructions. If multiple keys hash to the same bucket, Memcached resolves the collision using a singly linked list (separate chaining), checking the full key name to find the exact match.

Non-Blocking Dynamic Hash Table Expansion

As an application inserts millions of keys, the ratio of items to buckets (the load factor) increases. If left unmanaged, linked-list chains within buckets would grow longer, degrading lookup speed from \(O(1)\) toward \(O(n)\).

Memcached prevents this by monitoring the load factor. When the number of stored items exceeds 1.5 times the number of hash buckets, a background maintenance thread automatically doubles the hash table size. The rebalancing process moves items from the old table to the new, larger table incrementally over time. Because this resizing occurs on a dedicated thread in small batches, read and write operations continue uninterrupted without latency spikes.

Granular Locking and Multithreading

High lookup speeds under heavy concurrent traffic require efficient thread synchronization. Early versions of caching systems relied on a single global lock, which created CPU bottlenecks when multiple threads attempted concurrent reads.

Modern Memcached employs cache-aware multithreading with fine-grained item locks (lock striping). The hash table is divided into thousands of discrete lock segments. When a worker thread performs a lookup, it acquires a read lock only for the specific bucket chain containing the target key. This allows dozens of worker threads to execute lookups simultaneously across different buckets with virtually zero lock contention.

Slab Allocation and Cache Locality

Standard OS-level memory allocators (like standard malloc and free) suffer from external fragmentation when managing millions of variable-sized objects, leading to scattered memory pointers and expensive CPU cache misses.

Memcached bypasses this issue using its Slab Allocator:

  • Pre-allocated Chunks: Memory is divided into 1MB pages, which are further divided into uniform chunks of specific sizes (slab classes).
  • Direct Pointer Access: Items are placed into the slab class that best fits their size.
  • Deterministic Layout: Memory addresses remain predictable and contiguous, optimizing CPU L1/L2/L3 cache line utilization during pointer dereferencing.

Constant-Time Eviction

When memory is exhausted, Memcached avoids scanning the entire dataset to free space. Instead, it utilizes an isolated Least Recently Used (LRU) doubly linked list per slab class. Finding and evicting an expired or stale item to make room for new data is strictly an \(O(1)\) operation, ensuring that memory exhaustion never degrades read or write lookup latency.
