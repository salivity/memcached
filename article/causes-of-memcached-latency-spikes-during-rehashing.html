Causes of Memcached Latency Spikes During Rehashing

Memcached utilizes an in-memory hash table to achieve sub-millisecond key-value lookups, doubling its internal bucket array when the stored item count exceeds capacity. Although this rehashing process is designed to run asynchronously in the background, production workloads often experience acute tail latency spikes during hash table expansion. These performance degradations are primarily caused by thread lock contention, memory allocation overhead, CPU resource starvation, and hardware cache churn as data structures migrate to the new table.

Lock Contention Between Worker Threads and the Maintenance Thread

Memcached handles rehashing incrementally using a dedicated background thread (assoc_maintenance_thread). To remain thread-safe, the engine employs granular bucket locks (hash table item locks). When migrating items from the old table to the new one, the maintenance thread must acquire locks on the target buckets.

If incoming client requests attempt to read, update, or delete keys residing in the bucket range currently locked by the maintenance thread, those worker threads are forced to block. Under high-throughput conditions, this serialized access creates a queue of stalled worker threads, rapidly inflating connection backlogs and P99 response times.

Granular Chunk Sizes and Lock Holding Time

The speed and footprint of the rehashing process are governed by the hash_bulk_move setting, which determines how many hash buckets are migrated in a single iteration.

  • If the batch size is set too high, the maintenance thread holds bucket locks for prolonged intervals, directly blocking worker threads that target those keys.
  • If the batch size is too low, the frequency of lock acquisition and release cycles spikes, generating excessive CPU overhead and lock synchronization traffic across processor cores.

Hash Table Memory Allocation and OS Paging

Before rehashing begins, Memcached must allocate memory for the new hash table, which is double the size of the previous one. For instances handling tens of millions of keys, this requires allocating a massive, contiguous block of memory for the new bucket pointer array.

This allocation triggers kernel-level memory management tasks:

  • Page Zeroing: The operating system must zero out newly allocated memory pages before handing them to user space.
  • Page Faults: As the maintenance thread touches new buckets, minor page faults occur continuously until all virtual memory pages are backed by physical RAM.
  • Memory Fragmentation: If system RAM is fragmented, allocating large arrays forces the kernel into direct memory reclamation or compaction, causing multi-millisecond stalls across the entire process.

CPU Cache Line Invalidation

Rehashing requires traversing millions of pointers sequentially. As the maintenance thread reads items from the old table and writes them to the new array, it saturates the CPU’s L1, L2, and L3 caches with cold pointer data. This continuous cache churn evicts the "hot" keys and frequently accessed data pages used by worker threads serving live client traffic. As a result, worker threads suffer elevated hardware cache misses, degrading overall execution speed and lowering request throughput.

Thread Scheduling and CPU Contention

Memcached instances often run in resource-constrained environments or are configured to use all available CPU cores via worker threads. Because the maintenance thread requires non-trivial CPU cycles to compute hashes, verify bucket pointers, and execute migrations, it actively competes with worker threads for execution time. Without dedicated CPU affinity (core pinning), the operating system's thread scheduler frequently context-switches between worker threads and the maintenance thread, further increasing processing overhead and jitter.
