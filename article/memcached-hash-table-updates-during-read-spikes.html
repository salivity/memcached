Memcached Hash Table Updates During Read Spikes

Memcached achieves high throughput during intense read spikes by offloading hash table resizing to an asynchronous background maintenance thread, utilizing incremental bucket migration, and employing fine-grained lock striping. Instead of halting incoming queries to rebuild its primary hash table when collisions increase, Memcached preserves read performance through a dual-table lookup strategy that directs readers to the appropriate bucket without blocking the event loop.

The Expansion Trigger and Maintenance Thread

Memcached manages key-value lookup pointers using a primary hash table with separate chaining for collision resolution. When the total number of stored items exceeds 1.5 times the current bucket capacity, the system initiates an expansion to double the number of hash buckets.

Rather than forcing worker threads to perform this computationally heavy resize inline—which would trigger tail-latency spikes during traffic surges—Memcached signals a dedicated background maintenance thread (assoc_maintenance_thread). Worker threads continue servicing network I/O, cache hits, and cache misses without pause.

Dual-Table Lookups During Expansion

While resizing is active, two hash tables exist simultaneously: the old table (old_hashtable) and the new, doubled table (primary_hashtable). To route concurrent reads correctly without complex transactional barriers, Memcached tracks migration progress using a global expansion index.

When a worker thread processes a read command during an ongoing expansion:

  1. It hashes the incoming key to determine the bucket index.
  2. It compares the index against the expansion progress tracker.
  3. If the bucket index is lower than the progress tracker, the data has already moved, and the worker queries the new table.
  4. If the bucket index is greater than or equal to the progress tracker, the worker queries the old table.

Because this index comparison involves a lightweight integer check, read operations incur virtually zero computational overhead during spikes.

Granular Lock Striping

Lock contention is the primary threat to read throughput during structural modifications. Modern Memcached prevents lock contention by decoupling hash table mutations from global locking through item lock striping.

Instead of a single global lock over the entire associative array, the hash space is partitioned across a power-of-two array of discrete item locks (typically 4,096 or more). When the maintenance thread migrates buckets:

  • It acquires only the specific item locks corresponding to the narrow chunk of buckets currently being moved (often in small batches of a few dozen buckets at a time).
  • It updates the item pointers from the old bucket linked list to the new bucket linked list.
  • It releases those specific locks and yields briefly to prevent starvation.

Concurrent read spikes targeting keys in any other part of the hash table proceed entirely unobstructed. Even if a read maps directly to the specific bucket currently being transferred, it only waits for that single, microscopic pointer update to complete, preventing worker thread stalls and cascading socket timeouts.
