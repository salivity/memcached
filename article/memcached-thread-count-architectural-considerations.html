Memcached Thread Count Architectural Considerations

Configuring the optimal thread count in Memcached is critical for maximizing I/O performance and cache throughput while avoiding latency-inducing synchronization bottlenecks. This article examines the architectural constraints that govern thread allocation, detailing how CPU topology, libevent-based networking, internal lock contention, and multi-instance deployments influence the -t parameter.

CPU Topology and Core Allocation

Memcached relies on an event-driven, multithreaded architecture. Setting the thread count begins with the underlying hardware:

  • Physical Cores vs. Hyper-Threading: Assigning threads to match the number of physical cores generally yields predictable latency. While hyper-threads can provide extra throughput under I/O stalls, they share L1/L2 caches and execution units, which can increase lock contention under heavy cache operations.
  • NUMA Architecture: On multi-socket Non-Uniform Memory Access (NUMA) systems, worker threads operating across NUMA nodes suffer significant memory access latency penalties. If a thread on Node 1 accesses cache items allocated in memory physically wired to Node 0, the cross-interconnect overhead degrades performance. Pinning instances to specific NUMA nodes often outperforms running a single massive instance spanning all sockets.

The Event-Driven Networking Model

Memcached uses libevent to manage concurrent network connections. The architecture divides responsibilities between:

  • The Dispatcher Thread: Listens for incoming TCP/UDP connections and distributes accepted file descriptors across worker threads in a round-robin fashion.
  • Worker Threads: Each worker thread runs its own libevent instance, handling connection reads, command parsing, cache lookups, and writes for its assigned sockets.

If the thread count is set significantly higher than the number of active CPU cores, the operating system incurs unnecessary context-switching overhead. Conversely, too few threads can lead to head-of-line blocking on network processing if a subset of connections experiences bursty data traffic.

Internal Lock Contention and Scaling Limits

Although modern Memcached features fine-grained locking, it is not completely lock-free:

  • Item and Hash Table Locks: Reading and writing items requires acquiring bucket-level locks within the hash table. Highly concurrent workloads targeting the same hot keys will serialize on these locks, negating the benefit of additional worker threads.
  • Slab Allocator and LRU Locks: Memory allocation and Least Recently Used (LRU) maintenance rely on per-slab-class locking. Write-heavy workloads that frequently allocate, evict, or reassign memory trigger lock contention across threads.
  • Diminishing Returns: Due to lock synchronization overhead, Memcached typically scales well up to 4 to 8 threads. Scaling beyond 16 threads within a single process often results in flat or diminishing throughput gains accompanied by tail-latency spikes.

Workload Profile: Read vs. Write Ratios

The balance between read (GET) and write (SET/ADD/REPLACE) operations dictates concurrency limits:

  • Read-Heavy Workloads: Read operations primarily acquire shared locks and cause minimal state mutation, allowing the server to scale effectively across more threads (e.g., 8 to 16 threads).
  • Write-Heavy Workloads: Writes necessitate exclusive locks for item insertion, slab allocation, and LRU updates. On write-heavy workloads, higher thread counts exacerbate contention, making lower thread counts (e.g., 4 to 8) more stable.

Multi-Instance Strategy vs. High Thread Count

When running on high-core hardware (such as 32, 64, or 128 cores), scaling a single Memcached process via the -t flag is an architectural anti-pattern.

Instead, the standard industry practice is to deploy multiple independent Memcached instances on the same host, each bound to a dedicated NUMA node or CPU socket, utilizing 4 to 8 threads per instance. Client-side consistent hashing is then used to distribute traffic across these local instances. This horizontal-on-vertical scaling model eliminates cross-core lock contention, isolates memory footprints, and fully utilizes total network and memory bandwidth.
