Memcached Bottlenecks on High Core Count NUMA Servers

Deploying a single Memcached instance on modern servers featuring high core counts and Non-Uniform Memory Access (NUMA) architecture often results in diminishing returns and severe throughput degradation. While Memcached is engineered for multi-threaded performance, running a single monolithic process across multiple NUMA nodes exposes severe hardware and software bottlenecks. These issues primarily stem from cross-socket memory access latency, cache line invalidation over CPU interconnects, lock contention within critical data paths, and network stack inefficiencies at the kernel level.

Remote Memory Access Latency

NUMA architecture divides system memory into distinct nodes, where each CPU socket accesses its directly attached memory far faster than memory attached to other sockets. In a single Memcached instance spanning multiple NUMA nodes, worker threads are distributed across all available cores. Because memory allocations occur dynamically across the entire address space, threads on one socket frequently read from and write to remote memory on another. Accessing remote memory introduces higher latency—often double or triple local access times—causing CPU cycles to stall while waiting for data fetches to complete.

Interconnect Saturation and Cache Line Bouncing

When multiple cores modify shared data structures, the CPU's cache coherency protocol must synchronize state across sockets via interconnects like Intel Ultra Path Interconnect (UPI) or AMD Infinity Fabric. In Memcached, frequently accessed metadata—such as item reference counts, Least Recently Used (LRU) list pointers, and global statistics—continually bounce between CPU L1/L2/L3 caches. On high core count systems, this "cache line bouncing" saturates the inter-socket interconnect bandwidth, leading to serialization at the hardware level and drastically increasing average instruction execution latency.

Lock and Data Structure Contention

Memcached employs fine-grained locking (such as bucket-level hash table locks), but several global choke points remain:

  • The Slab Allocator: Memory allocation and deallocation require acquiring slab locks. When dozens or hundreds of threads compete for slab pages simultaneously, lock contention skyrockets.
  • Hash Table Expansion: Resizing the main hash table during heavy writes stalls worker threads and creates severe CPU spikes.
  • Thread Synchronization Primitives: Mutexes implemented via atomic instructions (e.g., compare-and-swap) become exponentially more expensive as thread counts rise across NUMA boundaries, forcing threads to spend more time spinning or context-switching rather than processing requests.

Operating System and Kernel Bottlenecks

A single Memcached process multiplexes client connections using an event loop (via libevent and epoll). At scale:

  • Socket Migration: Worker threads handling a single connection may be scheduled on different NUMA nodes over time, causing cache thrashing.
  • Network Interrupt Overhead: If Network Interface Card (NIC) receive queues (RSS) route packets to CPU cores on Node 0, but the Memcached worker thread handling that specific connection runs on Node 1, cross-node traffic spikes even before the application reads the payload.

Architectural Best Practice

To circumvent these bottlenecks, production architectures avoid running a single large Memcached instance on high-spec NUMA hardware. Instead, the standard approach is to run multiple, smaller, independent Memcached instances pinned directly to specific NUMA nodes using tools like numactl or taskset. Pair each instance with dedicated network queues and route traffic locally via a lightweight client-side or proxy-based partitioner.
