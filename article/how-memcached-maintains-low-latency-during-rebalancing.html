How Memcached Maintains Low Latency During Rebalancing

Memcached maintains sub-millisecond response times during background memory rebalancing through a combination of dedicated background threads, incremental item migration, and fine-grained locking. When memory demands shift across different item sizes, the slab rebalancer migrates 1MB memory pages between slab classes without freezing the system or stalling client operations. This architecture ensures high-throughput, predictable performance by breaking heavy memory maintenance into microscopic, non-blocking steps.

The Dedicated Slab Rebalancer Thread

Rather than burdening worker threads that handle incoming network read and write traffic, Memcached delegates memory reallocation to a dedicated background rebalancer thread. By isolating memory maintenance to its own execution context, worker threads remain fully available to process GET, SET, and DELETE commands. The rebalancer thread operates at a lower operational priority, ensuring client queries always take precedence over background reorganization.

Step-by-Step State Machine Processing

Rebalancing an entire 1MB slab page at once would introduce substantial latency if executed atomically. To prevent this, Memcached utilizes a cooperative state machine that processes the page incrementally:

  1. Selection: The slab automover identifies a source slab class with cold or surplus memory and a destination slab class that is starved for space.
  2. Item-by-Item Scanning: The rebalancer steps through the target 1MB page item by item rather than moving the block en masse.
  3. Cooperative Yielding: Between migrating individual chunks, the background thread yields execution, allowing worker threads access to memory locks and CPU cores.
  4. Completion: Once every chunk on the page is cleared, the physical 1MB page is unlinked from the source class and reassigned to the destination slab class.

Fine-Grained and Lockless Coordination

Lock contention is the primary source of latency spikes in multi-threaded caches. Memcached mitigates contention during rebalancing through targeted synchronization:

  • Short-Lived Locks: The rebalancer acquires the slab lock only for the duration needed to manipulate a specific item, releasing it immediately after.
  • Per-Item Hash Table Locks: When unlinking an active item from the cache during page migration, the thread locks only the specific hash bucket associated with that item, leaving the rest of the hash table completely open to concurrent traffic.
  • Lock Stealing Avoidance: If a worker thread requests an item currently targeted by the rebalancer, Memcached prioritizes the worker. Depending on the state, the worker either successfully reads the item or receives a normal cache miss while the item is evicted, avoiding serialization bottlenecks.

Minimal Impact on Concurrent Slab Classes

Memcached divides memory into discrete slab classes based on data size. The rebalancing mechanism is localized entirely to the two participating slab classes—the source and the destination. Operations targeting all other slab classes proceed without any synchronization overhead or lock checking, preserving zero-overhead concurrency across the vast majority of cached data.

Rate Limiting and Sleep Throttling

To prevent background rebalancing from exhausting memory bus bandwidth or CPU caches, the rebalancer incorporates sleep intervals. By intentionally pacing the speed at which pages are transferred, the system maintains flat latency curves even during significant workload shifts where multiple megabytes of cache are actively being restructured.
