Memcached Response to Oversized Command Headers

Memcached enforces strict size limitations on command headers, keys, and overall command lines to maintain high throughput and protect against memory exhaustion or denial-of-service (DoS) attacks. When a client application sends a command exceeding these predefined maximum header or buffer limits, Memcached handles the violation deterministically based on whether the client is communicating over the text protocol or the binary protocol. In general, the server rejects the command with an explicit client-side error code or abruptly terminates the underlying TCP connection to prevent buffer overflows.

Text Protocol Behavior

In the standard ASCII text protocol, Memcached processes commands line by line. The server allocates a fixed-size read buffer (typically 1,024 to 2,048 bytes depending on the compilation settings and version) to parse command lines before processing the associated value payload.

  • Key Length Violations: The text protocol enforces a strict key length limit of 250 bytes (KEY_MAX_LENGTH). If the command line contains a key exceeding this threshold, Memcached immediately halts command processing and returns the response:

    CLIENT_ERROR bad command line format

    or, in certain versions:

    CLIENT_ERROR key too long

  • Command Line Buffer Overflow: If a client sends a continuous stream of characters without a terminating newline (\r\n) that exceeds the read buffer limits, Memcached treats the input as unparseable. Because the server cannot safely allocate unbounded memory to find the end of an invalid command line, it returns a generic CLIENT_ERROR and immediately closes the TCP connection to protect internal state.

Binary Protocol Behavior

The binary protocol uses a strictly structured, fixed 24-byte header containing metadata fields such as the magic byte, opcode, key length (16-bit integer), extra data length (8-bit integer), and total body length (32-bit integer).

  • Validation Failures: Even though the binary protocol header theoretically allows key lengths up to 65,535 bytes via its 16-bit field, Memcached still enforces the internal 250-byte key limit. If the header specifies a key length or extras length that violates internal constraints, Memcached crafts a standard 24-byte error response with the status field set to 0x0003 (PROTOCOL_BINARY_RESPONSE_EINVAL / Invalid arguments).
  • Framing and Protocol Corruption: If the header parameters specify total body lengths that exceed maximum allowable command allocations, or if the header bytes do not conform to valid binary framing, Memcached categorizes the failure as protocol corruption. In this scenario, the server drops the socket connection immediately without sending an error response to avoid desynchronization between subsequent commands on the same connection.

Client-Side Implications

When an oversized header causes Memcached to reject a command or terminate a connection, client libraries typically handle the failure in one of two ways:

  • Protocol Exceptions: Well-behaved client libraries intercept keys larger than 250 bytes locally before transmission, raising a client-side exception to avoid network overhead.
  • Broken Pipe or Connection Reset: If an oversized command reaches the server and causes a connection drop, the client receives a socket-level error (such as ECONNRESET or EPIPE). The client connection pool must discard the terminated connection, establish a new socket, and mark the operation as failed.
