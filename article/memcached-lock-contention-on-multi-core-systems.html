Memcached Lock Contention on Multi-Core Systems

Memcached achieves high throughput on multi-core hosts by eliminating global lock bottlenecks and minimizing hardware-level resource competition. Rather than relying on a single monolithic mutex to guard its in-memory key-value store, modern Memcached architectures distribute synchronization across segmented item locks, decouple background operations from worker threads, and align internal lock primitives to CPU cache lines to prevent false sharing.

Fine-Grained Segmented Item Locks

Early versions of Memcached utilized a single global lock (cache_lock) for all internal operations, which caused severe thread contention as core counts scaled. To solve this, Memcached implemented fine-grained item locking.

The hash table used to look up keys does not use a single lock. Instead, it maintains a configured array of mutexes (typically an array sized to a power of two, such as 8,192 or 65,536 locks). When a worker thread performs a read, write, or update operation, it hashes the item’s key to select a specific lock index from this array. Multiple threads can simultaneously access, insert, or modify items located in different hash buckets without contending for the same lock structure.

Cache-Line Alignment to Prevent False Sharing

On multi-core architectures, multiple CPU cores share data through cache coherency protocols (such as MESI). If two distinct locks reside within the same 64-byte CPU cache line, an update to one lock by Core A invalidates the cache line for Core B, even if Core B is targeting the other lock. This phenomenon, known as false sharing, severely degrades performance.

Memcached prevents false sharing by enforcing memory padding and alignment on its lock structures. When allocating lock arrays—such as the item lock table—each mutex is explicitly padded to match the host CPU's L1 cache line size (commonly 64 bytes). This guarantees that modifying one lock does not trigger cache-line invalidation cycles across neighboring cores.

Slab Allocator and Memory Class Segregation

Memcached manages memory using a slab allocator to avoid operating system-level malloc and free overhead. To minimize contention during memory allocation:

  • Per-Slab-Class Locks: Memory allocations are split into distinct slab classes based on item size. Lock structures for these slabs are isolated, meaning an allocation in a 128-byte slab does not block an allocation in a 1-megabyte slab.
  • Thread-Local Storage (TLS): Worker threads buffer memory release requests locally, batching updates to the global slab structures rather than locking slab classes on every single delete or expire operation.

Dedicated Background Threads for Maintenance

Operations that require substantial structure modifications are detached entirely from the request-response path:

  • LRU Crawler and Maintainer: Evictions and Least Recently Used (LRU) list migrations are handled by background threads. Worker threads avoid locking the LRU structures during normal read operations by setting atomic access flags, allowing the background maintainer thread to handle lock acquisition and reordering asynchronously.
  • Hash Table Expansion: When the hash table requires resizing due to high load, a dedicated maintenance thread performs the expansion bucket by bucket. During this migration, worker threads only contend for locks on the specific bucket currently being transferred, leaving the rest of the table accessible.

Optimized Concurrency Primitives

Memcached leverages standard POSIX threads (pthread_mutex) optimized by platform-native fast userspace mutexes (futexes on Linux). When a thread encounters an uncontended lock, the acquisition occurs purely in user space via atomic instructions (such as compare-and-swap) without invoking a kernel context switch. When contention is unavoidable, threads yield or sleep, preventing CPU thrashing across multi-core processors.
