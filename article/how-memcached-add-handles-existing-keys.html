How Memcached Add Handles Existing Keys

In Memcached, the add command is specifically designed to store data only when a key does not already exist on the server. This article covers how Memcached processes the add command upon encountering an existing key, the specific protocol responses returned, the atomic nature of the operation, and practical use cases such as concurrency control and distributed locking.

Core Behavior of the Add Command

When you issue an add command to a Memcached server for a key that already exists, the server simply ignores the new payload. It does not overwrite the existing value, nor does it update the key's flags or reset its time-to-live (TTL) expiration. The existing item remains entirely unchanged.

Server Responses

The exact response returned by Memcached when an add fails due to an existing key depends on the protocol in use:

  • Text Protocol: The server responds with NOT_STORED\r\n. If the key had not existed, the server would have returned STORED\r\n.
  • Binary Protocol: The server returns a status response indicating a failure, specifically using the response status code 0x0002 (Key Exists).

Atomicity and Concurrency

The evaluation performed by the add command is strictly atomic. The server determines whether the key exists and applies the write in a single, non-blocking, thread-safe step. Because Memcached processes operations sequentially via internal item locks, there is no race condition where two simultaneous clients can successfully execute an add command on the same key at the same time. Exactly one client will receive success (STORED), and all concurrent attempts will fail (NOT_STORED).

Practical Use Cases

Because of its conditional write and atomic guarantees, developers frequently use the add command for synchronization tasks:

  • Simple Distributed Locks: A process attempts to add a key representing a lock (e.g., lock:process_reports) with a short TTL. If the command succeeds, the process holds the lock. If it returns NOT_STORED, another process is already executing the task.
  • Cache Stampede Prevention: When a popular cache item expires, multiple worker threads may attempt to regenerate it. Using add with a temporary lock key ensures only one worker queries the primary database to rebuild the cache, while others wait or serve stale data.
  • First-Writer-Wins Patterns: When multiple actors race to initialize a resource or assign an identifier, add guarantees that the first received submission takes precedence.

Comparison: Add vs. Set vs. Replace

To understand add clearly, contrast it with its companion commands:

  • set: Stores data unconditionally. It will create the key if missing, or overwrite it if it exists.
  • add: Stores data conditionally, succeeding only if the key does not exist.
  • replace: Stores data conditionally, succeeding only if the key already exists.
