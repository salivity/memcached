How Memcached Frees Memory on Key Deletion

When a key is explicitly removed using the delete command, Memcached does not return the allocated memory back to the operating system. Instead, it unlinks the item from its internal lookup structures and immediately marks the associated memory chunk as available for reuse within its assigned slab class. This article explains the underlying slab allocation system, the step-by-step process of explicit item deletion, and how Memcached recycles that memory for future writes.

The Slab Allocation Architecture

To understand how memory is freed, it is essential to understand how Memcached allocates it. Memcached avoids operating system memory fragmentation by using a slab allocation mechanism.

Upon startup, Memcached pre-allocates a large contiguous block of memory. This memory is divided into 1MB pages, which are then assigned to specific "slab classes." Each slab class handles items of a specific size range, breaking its pages into uniform slots called chunks. Once a page is assigned to a slab class, its chunks can only store items that fit that class's designated size.

What Happens During the delete Command

When an application issues an explicit delete command for a key, Memcached executes the following internal sequence:

  1. Hash Table Lookup: Memcached locates the item's reference using its primary internal hash table.
  2. Unlinking from References: The item is unlinked from the hash table so that subsequent get requests can no longer find it. It is also removed from the Least Recently Used (LRU) doubly linked list for that slab class.
  3. Reference Count Evaluation: Memcached checks the item’s reference counter. If another worker thread is actively reading the item, the memory release is briefly deferred until the read operation completes.
  4. Chunk Reclamation: Once the reference count reaches zero, the memory chunk containing the key, value, and metadata is placed back onto the freelist for that specific slab class.

Memory Recycling vs. Operating System Reclamation

Because Memcached manages its own memory pool, deleting keys does not decrease the overall memory footprint reported by system monitoring tools like top or ps. The memory remains claimed by the Memcached process.

The reclaimed chunk becomes immediately available for the next set or add operation that requests space within that exact slab class.

Slab Class Limitations

A key implication of this design is that freed memory is bound to the slab class to which it was originally allocated:

  • Class-Specific Reuse: If a 100-byte item is deleted, its chunk can only be reused by a new item that fits into the same small-size slab class. It cannot immediately be used to store a 10KB item.
  • Slab Rebalancing: In modern versions of Memcached, an automated background thread known as the slab automover can reassign entire 1MB pages from an underutilized slab class to a starved slab class if an imbalance persists over time. However, this occurs at the page level, not on an individual chunk-by-chunk basis during a single deletion.

By decoupling key deletion from operating system deallocation, Memcached ensures constant-time, low-overhead memory operations, allowing high-throughput read and write performance.
