Memcached CAS Command in Concurrency Control

The Memcached Compare-And-Swap (CAS) command is a concurrency control mechanism designed to prevent data inconsistency and race conditions in distributed caching environments. This article explains the purpose of the CAS command, how it resolves the "lost update" problem through optimistic locking, and the step-by-step process of using unique tokens to ensure that conflicting simultaneous writes do not corrupt shared data.

The Problem: Race Conditions and Lost Updates

In a typical caching scenario, updating an item requires a read-modify-write sequence:

  1. A client reads a value from the cache.
  2. The client modifies the value locally.
  3. The client writes the updated value back to the cache.

When multiple clients perform this sequence concurrently on the same key, a race condition occurs. If Client A and Client B read the same value at the same time, make different modifications, and both push their updates back, the client that writes last will overwrite the earlier write. The update from the first client is permanently lost without either client being aware of the collision.

The Purpose of the CAS Command

The CAS command provides optimistic locking for Memcached. Instead of locking a key to block other clients from reading or writing, Memcached uses CAS to verify that an item has not been altered by another process before applying an update.

Its primary purposes include:

  • Preventing Lost Updates: Guaranteeing that updates are applied only if the underlying data has remained unchanged since it was last read.
  • Atomic Modification: Ensuring atomic updates across distributed systems without the performance overhead of distributed locks.
  • Data Integrity: Ensuring multiple application threads or microservices safely synchronize changes to shared cached objects, such as counters, session data, or configuration settings.

How the CAS Mechanism Works

The CAS operation relies on a unique 64-bit identifier called a cas_token (or CAS identifier) assigned internally by Memcached to each key-value pair. This value updates automatically every time the item changes.

  1. Retrieving the Token (gets):
    Instead of a standard get command, the client uses gets. In response, Memcached returns the requested data along with its current cas_token.

  2. Modifying the Data:
    The client performs the required updates locally while preserving the received cas_token.

  3. Submitting the Update (cas):
    The client sends the update back using the cas command, passing the key, new data, and the saved cas_token.

  4. Validation and Execution:
    Memcached evaluates the request against the current state of the key:

    • STORED: The provided token matches the token in the cache. The key has not been altered since the client read it, so the update succeeds, and a new token is generated.
    • EXISTS: The token does not match because another process modified the key in the interim. Memcached rejects the write, protecting the recent change from being overwritten.
    • NOT_FOUND: The key expired or was deleted before the CAS update could execute.

Handling CAS Collisions

When an update returns an EXISTS response, the client handles the failure gracefully by executing a retry loop:

  1. Fetch the newly updated data and the new cas_token using gets.
  2. Re-apply the modifications to the fresh state.
  3. Attempt the cas operation again.

This optimistic approach minimizes latency and maintains high throughput, as write conflicts in fast caching layers are typically rare, making retries far more efficient than pessimistic locking strategies.
