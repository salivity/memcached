Memcached Multi-Threading Performance Trade-offs

Configuring Memcached with multiple listening threads allows the cache engine to handle higher concurrency and saturate high-bandwidth network interfaces across modern multi-core processors. However, scaling the thread count is not a strictly linear performance gain; it introduces critical trade-offs including internal lock contention, CPU cache coherency overhead, increased context switching, and diminished returns beyond hardware capacity. Understanding these trade-offs is essential to tuning Memcached for low-latency, high-throughput caching workloads.

Concurrency and Throughput Gains

By default, Memcached uses an event-driven architecture featuring a single main dispatcher thread and multiple worker threads (configured via the -t parameter). Each worker thread runs its own event loop to handle read and write operations for assigned client connections.

  • High Network Concurrency: Multiple threads allow Memcached to distribute thousands of simultaneous TCP connections evenly, preventing a single event loop from bottlenecking on I/O.
  • CPU Core Utilization: Adding threads enables the server to leverage multi-core CPU architectures, maximizing aggregate request throughput under heavy read-and-write traffic.

Lock Contention and Synchronization Overhead

While worker threads process network I/O independently, they share the underlying data storage, including the primary hash table, slab memory allocators, and LRU (Least Recently Used) cache lists.

  • Item and Hash Table Locks: Memcached uses fine-grained item locks to protect data integrity. When concurrent threads attempt to read or modify keys that map to the same hash bucket, they must wait for lock acquisition. High thread counts amplify lock contention, resulting in increased tail latencies (p99 and p99.9).
  • LRU and Slab Allocator Contention: Evictions and allocations require synchronization across threads. When memory is full, threads compete for the slab allocator and global LRU locks to reclaim space, drastically reducing efficiency under heavy write or update workloads.

CPU Cache Invalidation and Cache-Line Bouncing

As thread counts scale across multiple CPU cores—especially on multi-socket NUMA (Non-Uniform Memory Access) systems—hardware-level performance degradation can occur:

  • Cache Invalidation: Multiple processor cores executing Memcached threads frequently update shared data structures, such as item reference counts and global statistics counters. This triggers CPU cache line invalidations across cores, forcing memory buses to synchronize state.
  • False Sharing: Unrelated data points residing on the same 64-byte CPU cache line can force unnecessary cache invalidation across cores when modified by different threads, degrading CPU instruction efficiency.

Context Switching and Over-Provisioning

Configuring the thread count (-t) higher than the number of available physical CPU cores introduces kernel scheduling overhead:

  • Voluntary and Involuntary Context Switches: When more threads compete for execution time than there are physical cores, the operating system spends excessive cycles swapping thread contexts.
  • Latency Spikes: Context switches flush CPU registers and L1/L2 caches, directly translating to unpredictable response latencies for incoming cache requests.

Diminishing Returns and Optimal Sizing

In practice, Memcached exhibits an asymptotic performance curve relative to thread scaling. Because the workload is primarily network- and memory-bound rather than compute-intensive, throughput often peaks between 4 and 8 threads on modern hardware. Allocating beyond 8 to 16 threads rarely yields proportional throughput gains and frequently leads to degraded performance due to the cumulative cost of mutex synchronization and cross-core communication.

To achieve optimal performance, set the thread count to match dedicated physical cores (avoiding hyper-thread oversubscription) and continuously monitor lock statistics via the stats command to identify contention bottlenecks.
