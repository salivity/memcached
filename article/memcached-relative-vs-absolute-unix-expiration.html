Memcached Relative vs Absolute UNIX Expiration

Memcached manages item lifecycles using an expiration parameter that can be interpreted either as a relative time-to-live (TTL) in seconds or as an absolute UNIX timestamp. Memcached automatically distinguishes between these two formats based on a 30-day threshold (2,592,000 seconds). Understanding this distinction is essential to prevent common caching bugs, such as items expiring immediately upon creation.

The 30-Day Threshold Rule

When setting a key in Memcached, the expiration value (exptime) is passed as a 32-bit integer. Rather than having separate commands for relative and absolute times, the Memcached server evaluates the value of exptime against the number 2592000 (which is \(60 \times 60 \times 24 \times 30\) seconds, or 30 days):

  • Relative Expiration (Delta): Any value less than or equal to 2,592,000.
  • Absolute Expiration (UNIX Timestamp): Any value greater than 2,592,000.

There is also a special case: setting exptime to 0 disables expiration, keeping the item in cache indefinitely until it is displaced by newer items via the Least Recently Used (LRU) eviction algorithm or manually removed.

Relative Expiration (TTL)

Relative expiration specifies how many seconds an item should remain in the cache starting from the exact moment it is written.

  • How it works: If you provide a value such as 300, Memcached treats this as "expire in 300 seconds (5 minutes) from now."
  • Valid range: 1 to 2,592,000 seconds (up to 30 days).
  • Use case: Short- to medium-term caching where you simply want to refresh data periodically, such as session data, temporary rate limits, or short-lived API responses.

Absolute UNIX Timestamp Expiration

Absolute expiration specifies the exact second in epoch time (the number of seconds that have elapsed since January 1, 1970, 00:00:00 UTC) at which the item must expire.

  • How it works: If you provide a timestamp such as 1735689600 (representing January 1, 2025, 00:00:00 UTC), Memcached checks the system clock and discards the item once that point in time has passed.
  • Valid range: Any value greater than 2,592,000.
  • Use case: Cache entries that need to become stale at a specific real-world time (for example, at midnight, or precisely at the end of a scheduled marketing promotion), or items that need to live longer than 30 days.

The Common Pitfall: Expirations Greater Than 30 Days

The most common developer error with Memcached occurs when attempting to set a relative TTL longer than 30 days.

For example, if you want an item to expire after 40 days, you might mistakenly pass 3,456,000 seconds (\(40 \times 86,400\)). Because 3,456,000 is greater than 2,592,000, Memcached does not interpret this as 40 days from now; instead, it treats it as a UNIX timestamp. The timestamp 3456000 corresponds to mid-February 1970. Because that time is decades in the past, Memcached considers the item expired immediately and removes it on the spot.

To safely store an item for longer than 30 days, you must always compute and pass the future UNIX epoch timestamp:

current_unix_timestamp + desired_ttl_in_seconds

By supplying the absolute timestamp, the value safely exceeds the 30-day limit and allows Memcached to hold the data for months or years as intended.
