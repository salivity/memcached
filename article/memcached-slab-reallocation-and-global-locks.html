Memcached Slab Reallocation and Global Locks

This article explores how Memcached manages locking mechanisms during dynamic memory reallocation between slab classes. It details how the engine decouples memory reassignment from active client traffic using a dedicated background thread, fine-grained locking, and an asynchronous state machine to eliminate broad global lock contention and prevent system-wide latency spikes.

The Role of the Dedicated Rebalancer Thread

Memcached avoids running memory page reallocation directly inside worker threads handling incoming client requests. Instead, memory reallocation across slab classes is delegated to a separate, asynchronous background thread known as the slab rebalancer thread.

When a slab class requires more memory and dynamic reassignment is triggered—either manually or through the automated slab automover—the worker threads flag the request and alert the rebalancer thread via condition signaling. Because the reallocation logic runs on this isolated thread, the engine avoids stalling client operations with inline garbage collection or synchronous memory reorganization.

Eliminating Monolithic Global Locks

Older versions of caching engines relied on a coarse, global cache lock that serialized all operations during structural memory changes. Modern Memcached architecture replaces broad global locks with fine-grained, segmented locks:

  • Item Locks: The item hash table is split into multiple lock partitions (item locks), hashed by the key. A worker thread only locks the specific hash bucket associated with a given key.
  • Slabs Lock: A dedicated internal mutex (slabs_lock) protects slab class metadata, page allocations, and free lists.

During memory reallocation, Memcached does not elevate locking to an exclusive, system-wide state. Instead, it coordinates memory movement by acquiring these existing fine-grained locks strictly when necessary and releasing them immediately after modifying a specific reference.

The Asynchronous Rebalancing State Machine

To migrate a 1MB memory page from a source slab class to a destination slab class without freezing memory access, the rebalancer thread operates as an incremental state machine. This process is divided into distinct phases:

  1. Page Selection: The rebalancer identifies a 1MB page in the source slab class. It briefly acquires the slabs_lock to mark the page as actively undergoing reassignment, preventing worker threads from allocating new chunks inside that specific page.
  2. Item-by-Item Eviction: The page consists of multiple smaller memory chunks (items). The rebalancer thread iterates through each item sequentially. For each chunk:
    • It determines the item's key and acquires the corresponding fine-grained item lock.
    • If the item is currently referenced or held by a worker thread, the rebalancer temporarily backs off and retries to avoid lock inversion.
    • Once the item lock is secured, the item is unlinked from the hash table and the LRU list, effectively invalidating it.
    • The item lock is immediately released.
  3. Yielding Execution: Between processing individual items or small batches of items on the page, the rebalancer deliberately yields or sleeps briefly. This design guarantees that worker threads handling concurrent GET or SET requests are not starved of lock access.
  4. Page Transfer: Once every item on the designated page has been unlinked and memory references drop to zero, the rebalancer thread acquires the slabs_lock. It detaches the physical 1MB page from the source slab class, resets the page's memory layout, slices it into chunks matching the destination slab class's chunk size, and registers those chunks into the target slab class's free list.
  5. Completion: The slabs_lock is released, and the rebalance cycle terminates until another memory shift is requested.

Concurrency and Read/Write Impact

Because the slabs_lock is held only for brief pointer updates at the start and end of the transfer, and item locks are held only for the duration of single-item unlinking operations, client requests experience negligible overhead. If a client attempts to read an item on a page currently undergoing eviction, it either successfully reads the item before the rebalancer acquires that specific item lock, or receives a cache miss immediately after the item is unlinked. In neither case does a global lock block unrelated traffic across other slab classes or hash buckets.
