How Memcached Handles Concurrent Atomic Updates

In distributed systems, high concurrency can lead to race conditions where multiple clients attempt to modify the same cache key at the same time. Memcached ensures atomic updates and prevents data corruption through three primary mechanisms: internal item locking, native atomic counter commands, and an optimistic concurrency control protocol known as Check-and-Set (CAS). This article explains how these mechanisms function under the hood to guarantee safe, simultaneous writes to identical keys.

Internal Thread Locking

Memcached uses a multi-threaded, event-driven architecture, but it protects individual operations using fine-grained internal locks.

When a client executes a single primitive write command—such as set, add, or replace—Memcached does not allow other threads to interleave execution on that specific item. Internally, Memcached hashes the key to a specific bucket and acquires an item-specific mutex lock before modifying memory buffers or slab allocations.

Because of this locking mechanism, individual write commands are strictly serialized at the server level. If two clients issue a set command for the same key at the exact same microsecond, one will acquire the lock first and complete its write, followed immediately by the second. The server memory is never left in a partially updated or corrupt state, though the final value will simply reflect whichever operation finished last.

The Check-and-Set (CAS) Protocol

While individual writes are atomic, standard read-modify-write workflows (read a value, modify it locally, and write it back) are vulnerable to the "lost update" problem. If Client A and Client B both read the same key simultaneously, both modify it, and both write it back, the slower client inadvertently overwrites the faster client's changes.

Memcached solves this using the Check-and-Set (CAS) protocol:

  1. Token Generation: Every time an item is created or updated, Memcached assigns it an internal, monotonically increasing 64-bit identifier called a CAS token.
  2. Retrieval with gets: Instead of a standard get command, clients execute a gets command. The server returns the cached value along with the current CAS token.
  3. Conditional Update with cas: When writing the updated value back, the client sends the cas command, which includes the key, the new value, and the previously retrieved CAS token.
  4. Validation: Memcached compares the client-provided CAS token with the token currently stored in memory for that key.
    • If the tokens match, no other client has modified the item in the interim. Memcached updates the value, increments the CAS token, and returns STORED.
    • If the tokens do not match, another client has updated the key in the meantime. Memcached rejects the update and returns EXISTS.

When a client receives an EXISTS status, it must implement retry logic: fetching the new value and new token using gets, reapplying the local business logic, and attempting the cas operation again.

Atomic Counters (incr and decr)

For numeric values, using CAS loops can introduce unnecessary network round-trips. Memcached provides dedicated atomic operations: incr (increment) and decr (decrement).

When a client issues an incr or decr command:

  • The server parses the stored string as an unsigned 64-bit integer.
  • It applies the addition or subtraction directly in server memory while holding the item's lock.
  • The operation is performed in-place without the client needing to read the current value first.

Because the calculation happens entirely within the locked context on the server, incr and decr are immune to race conditions, making them ideal for high-throughput counters, rate limiters, and tracking metrics across thousands of concurrent clients.
