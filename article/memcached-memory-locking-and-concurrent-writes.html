Memcached Memory Locking and Concurrent Writes

Memcached handles simultaneous write operations across multiple worker threads through a fine-grained locking architecture. Instead of relying on a single global lock, modern versions of Memcached partition memory operations across an array of hash table item locks, dedicated slab allocator locks, and decoupled Least Recently Used (LRU) list locks. This design isolates concurrent writes to different keys, preventing thread contention while guaranteeing thread safety and data consistency.

Thread Model and Event Distribution

Memcached operates using an event-driven, multi-threaded model powered by libevent. A master thread listens for incoming network connections and dispatches them across a pool of pre-allocated worker threads using a round-robin mechanism. Once a connection is assigned, that worker thread is responsible for reading the request, executing the command, and writing the response. Because multiple worker threads can process write commands (SET, ADD, REPLACE, CAS, APPEND, PREPEND) at the exact same moment, concurrency control is handled inside the storage engine.

Fine-Grained Item Locks

In early versions of Memcached, concurrency was limited by a single global cache lock (cache_lock), which serialized all read and write activity. Modern Memcached replaces this bottleneck with an array of individual item locks:

  • Hash-Based Partitioning: The primary item hash table is protected by a table of mutexes. When a thread attempts a write, it computes the hash of the target key using a hashing algorithm (such as Murmur3 or Jenkins).
  • Targeted Locking: The computed hash maps to a specific bucket within the lock table. The worker thread acquires only the lock associated with that bucket via item_lock(hv).
  • Parallel Execution: Threads writing to items that map to different hash buckets execute in parallel without blocking one another. Threads attempting to write or read keys that map to the same bucket must wait until the mutex is released.

Slab Allocator Locks

Storing or updating a payload requires allocating or replacing memory chunks inside Memcached’s slab allocator. Memcached divides memory into slab classes based on item size.

  • Allocation Isolation: When a write requires a new memory buffer, the worker thread accesses the slab engine. Memory allocations are protected by a dedicated mutex (slabs_lock).
  • Short Hold Times: The allocator lock is held only for the minimum duration required to obtain a free chunk from the appropriate slab class or trigger a page rebalance. As soon as the pointer to the memory chunk is reserved, the lock is released.

Decoupled LRU Management

Writes frequently interact with the Least Recently Used (LRU) eviction system, either to insert new entries, move updated entries to the front of the queue, or evict old data when memory is exhausted.

  • Segmented LRU Locks: Memcached uses segmented LRU lists (HOT, WARM, and COLD) per slab class, each protected by dedicated LRU locks.
  • LRU Crawler and Maintainer Threads: Background threads manage data migration between these queues. By decoupling LRU maintenance from the worker thread's write path, worker threads do not need to lock the global state of the LRU during every write, significantly reducing lock contention.

The Lifecycle of a Concurrent Write Operation

When a worker thread processes a write command, it executes the following sequence:

  1. Acquire Item Lock: The thread hashes the incoming key and locks the corresponding item mutex.
  2. Lookup Existing State: The thread searches the hash table to check if the key already exists.
  3. Allocate Storage: If space is needed, the thread acquires the slabs_lock, claims a memory slot from the target slab class, and releases the slabs_lock.
  4. Copy Data: The thread copies the client’s payload into the allocated memory buffer.
  5. Update Hash Table and LRU: The thread points the hash table entry to the new memory chunk, links the item to the appropriate LRU queue, and unlinks any stale version of the key.
  6. Release Item Lock: The item mutex is unlocked, immediately allowing other threads to access that hash bucket.

Atomic Operations and CAS

For application-level concurrency where multiple clients attempt to update the same key simultaneously, Memcached provides the Check-And-Set (CAS) command.

Internally, every item contains an incrementing 64-bit integer (the CAS ID). When executing a CAS write, the worker thread maintains the item lock, verifies that the CAS ID provided by the client matches the current CAS ID in memory, and applies the write only if the IDs match. If another thread has modified the item in the interim, the CAS comparison fails, and the thread aborts the write and releases the item lock without corrupting the data.
