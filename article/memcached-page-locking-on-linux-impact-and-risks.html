Memcached Page Locking on Linux: Impact and Risks

Enabling page locking in Memcached instructs the Linux kernel to lock all allocated cache memory directly into physical RAM, entirely preventing it from being paged out to swap space. This configuration guarantees consistent, ultra-low latency by eliminating disk I/O penalties associated with memory swapping. However, it also introduces substantial operational risks, such as system instability, memory starvation for other services, and exposure to the Linux Out-of-Memory (OOM) killer. This article explores how page locking works in Memcached, its performance impacts, potential failure modes, and essential configuration requirements.

How Page Locking Works in Memcached

Memcached provides the -k (or --lock-memory) command-line flag to invoke the Linux system call mlockall(MCL_CURRENT | MCL_FUTURE). Under default operations, the Linux virtual memory manager may swap infrequently accessed pages of memory to disk when physical RAM experiences pressure.

When page locking is activated:

  • The kernel pins the virtual address space of the Memcached process to physical RAM.
  • Neither the initial process footprint nor any dynamically allocated slab memory can be moved to the swap partition or swap file.
  • Memory allocation stays resident in physical hardware, regardless of overall system memory contention.

Latency and Performance Advantages

The primary reason to enable page locking is latency predictability.

  • Elimination of Page Fault Latency: Standard memory access happens on the scale of nanoseconds, while retrieving swapped pages from an SSD or HDD incurs millisecond-level delays. For high-throughput caching layers, even a few milliseconds of latency can breach strict Service Level Agreements (SLAs).
  • Prevention of Cache Eviction Degradation: If swap is enabled on a host and page locking is off, the OS may choose to swap out Memcached pages instead of freeing filesystem page caches. Page locking guarantees that cached keys and values are immediately accessible at pure RAM bus speeds.

Operational Risks and Drawbacks

Locking memory removes an essential safety valve that the Linux kernel relies on to manage system resources under load.

  • Triggering the OOM Killer: If total system memory demand exceeds physical RAM and the kernel cannot reclaim space by swapping Memcached, the system enters an Out-of-Memory state. The Linux OOM killer will intervene and terminate processes to free memory. Because Memcached often holds the largest memory footprint, it is frequently chosen as the primary target for termination.
  • Starvation of Co-located Services: Locked pages cannot be repurposed for OS disk buffers, network buffers, or other running processes. If a server hosts both Memcached and application workers or database replicas, locking Memcached's memory can degrade the performance of these adjacent workloads.
  • Cold Cache Allocation Overhead: Locking dynamic allocations (MCL_FUTURE) forces the kernel to verify and allocate actual physical frames during slab creation, slightly shifting allocation overhead to cache initialization periods rather than deferring it via lazy paging.

System Prerequisites and Configuration

To use the -k option successfully, specific Linux environment parameters must be tuned:

  1. Adjusting memlock Limits: By default, standard Linux users have a low RLIMIT_MEMLOCK limit. If Memcached attempts to lock more memory than permitted, the process will fail to start. In /etc/security/limits.conf or a systemd service unit override, ensure LimitMEMLOCK=infinity or set the limit well above the maximum allocated cache size (-m parameter).
  2. Dedicated Resource Provisioning: Page locking is best applied to dedicated caching nodes. Avoid running heavy background tasks or co-locating write-heavy databases on the same host.
  3. RAM Headroom: Always set Memcached's maximum memory allocation (-m) well below the total physical RAM of the host—typically allocating no more than 75% to 80% of total memory to account for system overhead, network socket buffers, and kernel operations.
