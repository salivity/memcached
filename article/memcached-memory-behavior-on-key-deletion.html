Memcached Memory Behavior on Key Deletion

When a key is removed in Memcached using the delete command, the memory it occupied is not returned to the operating system. Instead, Memcached unlinks the item from its internal lookup structures, marks the allocated chunk within its slab allocator as free, and places that chunk on a list of available memory slots to be reused by future writes within the same slab class.

Hash Table and LRU Unlinking

When the delete command is executed, Memcached performs a lookup in its primary hash table. Once the item is located, the server immediately unlinks it from the hash table bucket chain. This ensures that any subsequent get requests for the key immediately return a cache miss, making the deletion effectively instantaneous from the client's perspective.

Simultaneously, the item is removed from the Least Recently Used (LRU) doubly linked list associated with its specific slab class, preventing the background LRU maintenance threads or eviction logic from processing it.

Reference Counting and Memory Reclamation

Memcached protects concurrent reads and writes using reference counting on individual items:

  1. Active Reads: If another thread is actively reading or transmitting the item when the delete command is issued, the item cannot be freed immediately. Memcached unlinks the item so no new operations can find it, but the memory remains allocated until the reading thread completes its task.
  2. Immediate Freeing: If the item's reference count drops to zero (meaning no threads are accessing it), the item’s memory is marked for immediate reclamation.

The Slab Allocator Mechanism

Memcached manages memory through a slab allocation system rather than traditional malloc and free calls for individual items:

  • No Memory Returned to the OS: Memcached pre-allocates memory pools divided into slabs, which are further divided into uniform chunks (slab classes). Deleting an item never shrinks the overall resident memory (RSS) of the Memcached process.
  • Return to the Free List: When an item's memory is reclaimed, the chunk is appended to the free_chunks list for that specific slab class.
  • Slot Reusability: That chunk becomes instantly available for any new incoming key-value pair that matches the size constraints of that specific slab class. However, because memory is segmented into fixed-size classes, a chunk freed from an 80-byte slab class cannot be used to store a 500-byte item unless memory reassignment (slab rebalancing) occurs.
