Memcached vs Redis Memory Allocation Strategies

This article examines the core differences in memory allocation strategies between Memcached and Redis. While Memcached relies on a pre-allocated slab allocation mechanism designed to eliminate external memory fragmentation, Redis uses dynamic memory allocation via general-purpose allocators like jemalloc to support rich data structures. Understanding these distinct approaches clarifies how each engine handles memory overhead, fragmentation, and performance under varying workloads.

Memcached: Slab Allocation Mechanism

Memcached manages memory through a deterministic system known as slab allocation. When Memcached starts, it reserves a large, contiguous block of memory and divides it into smaller units to avoid calling system-level allocation primitives continuously.

  • Slab Classes and Chunks: Memory is organized into slab classes. Each class contains 1 MB pages divided into fixed-size chunks. For example, Slab Class 1 might contain 96-byte chunks, Slab Class 2 might contain 120-byte chunks, scaling up exponentially by a configurable growth factor (default 1.25).
  • Allocation Process: When a key-value pair is stored, Memcached identifies the smallest chunk size capable of holding the data and assigns the item to that slab class.
  • Internal Fragmentation: Because chunk sizes are fixed, any unused space within a chunk is wasted. If an 80-byte item is placed into a 120-byte chunk, the remaining 40 bytes cannot be used by other keys.
  • Elimination of External Fragmentation: Because slabs are uniformly sized (1 MB) and chunks within a class are identical, the underlying operating system does not suffer from address-space fragmentation. Memory reuse within the same slab class is immediate and fast.

Redis: Dynamic Allocation via General-Purpose Allocators

Unlike Memcached, Redis does not pre-allocate a monolithic block of memory divided into static buckets. Instead, Redis delegates memory management to general-purpose allocators—primarily jemalloc by default on Linux, though it can compile with glibc malloc or tcmalloc.

  • On-Demand Allocation: Redis allocates and frees memory dynamically as data arrives, shrinks, or expands. This model accommodates complex data types such as Lists, Hashes, Sets, and Sorted Sets, which require variable, non-uniform memory layouts.
  • Compact Encoding: Redis optimizes memory at the data-structure level using compact encodings (such as ziplist or listpack). When collections contain small elements, Redis encodes them as continuous byte arrays, dramatically reducing pointer overhead.
  • External Fragmentation: Dynamic allocation can lead to external memory fragmentation over time. When keys of varying sizes are allocated and freed unpredictably, free memory becomes scattered in non-contiguous fragments, increasing the Resident Set Size (RSS) even when logical memory usage is low.
  • Active Defragmentation: To counter external fragmentation, Redis includes an active defragmentation engine. When enabled, Redis identifies fragmented memory regions at runtime, copies the data into continuous memory pages, and releases the fragmented pages back to the operating system without downtime.

Direct Comparison of Allocation Strategies

Feature Memcached Redis
Allocation Model Pre-allocated Slab Allocator Dynamic On-Demand (jemalloc/malloc)
Primary Fragmentation Risk Internal (unused space inside fixed chunks) External (scattered free memory across pages)
Memory Efficiency for Primitives High for uniformly sized strings High, with minimal padding
Complex Data Structure Handling Not supported (values are raw byte blobs) Native support with optimized internal encodings
Memory Reclamation Reuses slots in matching slab classes; LRU per class System free via allocator; global LRU/LFU eviction
Defragmentation Handling Slab reassigning / automove across classes In-memory active defragmentation

Architectural Trade-Offs

Memcached's slab model prioritizes predictability and raw read/write throughput for simple key-value data. The operating system rarely intervenes in memory management once the daemon is running, minimizing system-call overhead and avoiding memory compaction pauses. The trade-off is potential memory inefficiency if key sizes do not align closely with slab chunk increments.

Redis's dynamic approach prioritizes versatility and granular memory usage. By allocating only the exact bytes required and utilizing compact encodings, Redis maximizes data density for varied datasets. However, it requires an intelligent allocator like jemalloc and background defragmentation routines to manage the inherent memory fragmentation caused by dynamic allocations and deletions.
