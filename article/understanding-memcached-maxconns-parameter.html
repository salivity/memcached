Understanding Memcached maxconns Parameter

This article explains the purpose of the maxconns parameter found within the stats settings command output in Memcached. Readers will learn what this metric represents, how to configure it, its default behavior, and the operational implications of reaching the maximum connection limit in a production caching environment.

What is the maxconns Parameter?

In Memcached, maxconns stands for "maximum connections." When you query the server using the stats settings command, the maxconns output parameter indicates the absolute ceiling on the number of simultaneous client connections the Memcached instance is configured to accept.

By default, Memcached sets maxconns to 1024. This limit protects the host system's file descriptor table, memory, and CPU from being exhausted by an uncontrolled surge of incoming client sockets.

Viewing maxconns via stats settings

You can verify the active maxconns configuration by connecting directly to Memcached through tools like telnet or nc (netcat) and issuing the stats settings command:

stats settings

Among the key-value configuration pairs returned, the relevant line will appear as:

STAT maxconns 1024

This confirms that the server will allow up to 1,024 concurrent active connections before it begins rejecting or deferring new socket attempts.

How to Configure maxconns

The maxconns value is set when starting the Memcached daemon using the -c command-line option. For example, to raise the limit to 4,096 connections, you start Memcached with:

memcached -c 4096

If you manage Memcached via configuration files (such as /etc/memcached.conf on Debian/Ubuntu systems), you specify this value with the -c parameter:

-c 4096

Note that maxconns cannot exceed the operating system's open file descriptor limit (nofile in ulimit). If you set -c higher than the allocated system limit, Memcached will attempt to adjust its file descriptor limits or log an error during startup.

Operational Impact of Reaching maxconns

Memcached tracks active connections under the curr_connections metric (viewable via the standard stats command). When curr_connections equals maxconns, the server has reached capacity:

  • Connection Throttling: Memcached temporarily stops listening to its incoming connection queue.
  • Client-Side Errors: Incoming requests may hang, time out, or receive "connection refused" errors from the operating system once the TCP listen backlog (backlog) is also saturated.
  • Metric Indication: The listen_disabled_num counter in the general stats output will increment each time Memcached is forced to stop accepting connections due to the maxconns ceiling.

Best Practices

To maintain high availability and prevent connection exhaustion:

  • Employ Connection Pooling: Configure web applications to reuse persistent connections rather than creating and destroying a new connection for every cache query.
  • Monitor Metrics: Regularly alert on curr_connections when it approaches 80% of maxconns, and track listen_disabled_num to catch saturation issues early.
  • Align with System Limits: When increasing -c, ensure the host OS user running Memcached has a sufficiently high ulimit -n setting to accommodate the socket descriptors plus necessary system file handles.
