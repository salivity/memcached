How Memcached Calculates Ketama Hash Rings

Ketama is a consistent hashing algorithm designed to map cache keys to multiple Memcached servers without invalidating the entire cache when nodes are added or removed. This article explains how client libraries construct the Ketama continuum, distribute virtual nodes using MD5 hashes, and map cache keys to target servers using fast binary lookups.

The Purpose of Consistent Hashing in Memcached

In traditional modulo-based hashing (hash(key) % server_count), adding or removing a single server changes the destination of almost every key, causing a catastrophic cache miss storm. Ketama solves this by representing the available hash space as a continuous circle (or ring) ranging from 0 to 2^32 - 1. Both cache servers and cache keys are placed onto this ring based on their hash values.

Step 1: Generating Virtual Nodes (Points)

Directly hashing physical server identifiers (like IP addresses) onto the ring results in an uneven distribution of data, causing "hot spots." Ketama resolves this by creating multiple "virtual nodes" for each physical server.

By standard Ketama specification:

  1. Each physical server is assigned a weight (defaulting to 1). A standard weight typically translates to 160 virtual points on the ring.
  2. The client calculates the number of 4-point groups needed (e.g., 40 groups for 160 points).
  3. For each group index \(i\) from 0 to 39, the client creates a specific string identifier formatted as: "<server_ip>:<port>-<i>" (e.g., 10.0.0.1:11211-0, 10.0.0.1:11211-1).

Step 2: Hashing Servers onto the Ring

Ketama uses the MD5 cryptographic hash function to compute points. Even though MD5 is slow for general hashing, it is only computed once during client initialization or topology changes.

  1. MD5 Computation: The client runs an MD5 hash over the formatted virtual node string. MD5 produces a 16-byte (128-bit) digest.
  2. Splitting into 32-bit Integers: The 16-byte digest is sliced into four distinct 4-byte integers using little-endian byte ordering:
    • Point 1: Bytes 0 to 3
    • Point 2: Bytes 4 to 7
    • Point 3: Bytes 8 to 11
    • Point 4: Bytes 12 to 15
  3. Each 4-byte slice is converted into an unsigned 32-bit integer (\(0\) to \(4,294,967,295\)).
  4. Because one MD5 computation yields four points, 40 MD5 operations produce the standard 160 virtual points per server.

Step 3: Sorting the Hash Ring

The client stores all generated points in an internal array or balanced search tree structure. Each entry contains two elements:

  • The 32-bit point value (the coordinate on the ring).
  • The server reference (the actual physical server to contact).

Once all virtual nodes for all configured servers are generated, the client sorts the ring in ascending order based on the 32-bit integer values. This sorted array constitutes the Ketama continuum.

Step 4: Key Mapping and Lookup

When an application reads or writes a cache key (such as user:profile:100):

  1. Hash the Key: The client hashes the cache key using MD5 (or another fast hash like Murmur3 if the specific implementation allows, though standard Ketama mandates MD5). The first 4 bytes of the hash digest are decoded into an unsigned 32-bit integer.
  2. Locate the Node: The client searches the sorted array for the first virtual node whose point value is greater than or equal to the key's hash value. Because the array is sorted, this lookup runs in \(O(\log N)\) time using a standard binary search (e.g., bisect or std::lower_bound).
  3. Wrap Around (The Ring Behavior): If the key's 32-bit hash value is greater than the highest point on the ring, the binary search wraps around to the beginning, selecting the very first node in the array (index 0).
  4. Execute Request: The client retrieves the physical server associated with the matched virtual node and sends the command over that connection.

Handling Server Changes

When a server fails or a new instance is added, the client recalculates the ring. Because the positions of unaffected servers remain unchanged on the \(2^{32}\) spectrum, only keys that fall directly in the sector of the ring belonging to the altered node are remapped. All other keys continue routing to their existing servers, maintaining high cache hit ratios.
