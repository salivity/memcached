Memcached Consistency During Network Partitions

Maintaining consistency across a Memcached cluster during a network partition is fundamentally shaped by its decentralized, shared-nothing architecture. Because native Memcached nodes do not communicate or replicate data among themselves, the responsibility of managing node state and data placement falls entirely on client libraries and proxy layers. This article explains how client-side hashing, proxy routing, and time-to-live (TTL) mechanics work together to handle network partitions, along with the operational trade-offs between consistency and availability in a partitioned cluster.

The Shared-Nothing Model and Lack of Consensus

Native Memcached uses a shared-nothing design where individual nodes operate in complete isolation. Unlike distributed databases such as Cassandra or Redis Cluster, Memcached has no internal consensus protocols (like Raft or Paxos), no leader election, and no inter-node replication.

Because nodes do not coordinate, a network partition cannot cause a split-brain condition between the servers themselves. Instead, consistency issues emerge on the client side when network breaks isolate subsets of clients from specific nodes, causing disparate views of the cache topology.

Consistent Hashing and Dynamic Rebalancing

Most Memcached implementations use client-side consistent hashing algorithms, such as Ketama, to map cache keys to specific nodes. Consistent hashing arranges nodes in a virtual ring to ensure that adding or removing a server only affects a minimal number of keys.

During a network partition, client behavior typically follows one of two approaches:

  • Dynamic Re-hashing (Failover): If a client cannot reach a node, it removes the node from its local ring and remaps keys to the next available server. While this maintains high availability, it introduces consistency anomalies:
    • Duplicate Writes: A client partitioned from Node A writes a new value for a key to Node B. Another client that can reach Node A reads the old value.
    • Stale Reads: Once the partition heals, data on both nodes may conflict until expiration occurs.
  • Static Hashing (Fail-Stop): The client refuses to re-route requests destined for an unreachable node, treating all requests to that node as cache misses or network errors. This strategy prevents stale duplicate data on alternate nodes, prioritizing consistency over availability.

Proxy-Based Routing with Mcrouter

In larger architectures, organizations deploy proxies like Facebook’s Mcrouter to manage clustering logic centrally instead of relying on individual application runtimes. Mcrouter handles network partitions via configurable route handles:

  • AllSync or AllAsync Routes: Distribute writes to multiple pools or data centers. If a partition isolates one pool, the proxy can log the failed invalidation or retry asynchronously.
  • Failover Routes: Allow requests to fall back to secondary pools only under strict error conditions, reducing cross-client state divergence.
  • Cold Cache Warmup: Directs queries away from an isolated, newly rejoined node to prevent massive read spikes to the backing database.

Invalidation Conflicts and Cache Eviction

Because Memcached is an ephemeral cache rather than a durable datastore, maintaining strict consistency across partitions is generally deemed unnecessary. Instead, systems use defensive caching patterns to resolve eventual divergence:

  • Short Time-to-Live (TTL): Enforcing conservative TTL values guarantees that conflicting keys generated during a network partition naturally expire, bounding the duration of any inconsistency.
  • Leases and Gflags: Advanced clients issue short-lived lease tokens on a cache miss. If a partition occurs mid-transaction, stale writes are rejected if the lease token no longer matches.
  • Delete-on-Write (Cache Aside): Instead of updating values during a network disruption, application layers issue delete/invalidation commands. If an invalidation fails due to a network partition, the application relies on database-level read-through logic to reconcile the state once connectivity returns.
