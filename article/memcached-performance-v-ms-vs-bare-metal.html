Memcached Performance: VMs vs Bare Metal

Running Memcached on bare metal hardware consistently outperforms virtualized deployments in throughput, tail latency, and resource efficiency. While virtual machines (VMs) offer operational flexibility, dynamic provisioning, and simplified management, the virtualization layer introduces overhead in memory access, CPU scheduling, and network packet processing. This article examines the specific performance bottlenecks that emerge when running Memcached inside virtual machines compared to bare metal, focusing on latency, memory virtualization, and network throughput.

Latency and Tail Latency (p99/p999)

Memcached is an in-memory, key-value store optimized for sub-millisecond response times. The primary performance degradation in a VM manifests as latency jitter and elevated tail latency:

  • Hypervisor Interruption: In virtualized environments, the hypervisor's CPU scheduler handles multiple virtual CPUs (vCPUs) across physical cores. When a vCPU is preempted, any incoming Memcached request must wait for the hypervisor to schedule the vCPU back onto a physical core, causing latency spikes.
  • Context Switching: Bare metal runs Memcached directly on the host OS kernel, minimizing context switches. Virtualization introduces a second scheduling layer, increasing cache invalidations and system call overhead.
  • Network Stack Jitter: Virtualized network interfaces (vNICs) route traffic through a software switch (such as Open vSwitch or hypervisor bridge), introducing micro-delays that degrade 99th and 99.9th percentile response times compared to bare metal's direct hardware interrupts.

Memory Overhead and Translation Lookaside Buffer (TLB) Misses

Because Memcached workloads are heavily memory-bound, virtualization directly impacts how memory addresses are translated:

  • Two-Dimensional Paging: In a bare-metal setup, the CPU maps virtual memory addresses directly to physical addresses using single-tier page tables. VMs require Extended Page Tables (EPT on Intel) or Nested Page Tables (NPT on AMD) to translate guest virtual addresses to guest physical addresses, and then to host physical addresses. This two-tier walk doubles memory lookup penalties during TLB misses.
  • TLB Thrashing: Memcached frequently accesses a large, dispersed set of keys across its slab allocator. The increased cost of TLB misses in VMs reduces overall instructions per cycle (IPC) and throttles read/write speeds.
  • Huge Pages: While both bare metal and VMs can leverage Transparent Huge Pages (THP) or explicit huge pages (2MB/1GB) to mitigate TLB misses, configuring and pinning huge pages to avoid hypervisor page-swapping requires significantly more effort in virtualized setups.

Network Throughput and Packet Processing

Memcached is often network-bound before it becomes CPU-bound, processing hundreds of thousands of small UDP or TCP packets per second:

  • Packets Per Second (PPS) Limits: Hypervisors impose a software tax on packet traversal. On bare metal, high-throughput network cards (NICs) leverage features like Receive Side Scaling (RSS), multi-queue NICs, and Single Root I/O Virtualization (SR-IOV) directly. Without SR-IOV enabled in a VM, packet encapsulation and software-defined networking drastically limit maximum PPS.
  • Raw QPS Loss: In comparative benchmarks, running identical hardware configurations typically results in bare metal achieving 15% to 35% higher queries per second (QPS) compared to standard VM instances.

CPU Scheduling and "Noisy Neighbors"

In shared cloud or multi-tenant virtualization environments, Memcached suffers from resource contention:

  • Cache Contention: Memcached benefits heavily from large L3 processor caches. In VMs sharing physical sockets with other workloads, noisy neighbors can flush the L3 cache, causing sudden drops in read throughput.
  • vCPU Overcommit: If the host hypervisor oversubscribes physical cores, Memcached instances experience steal time, where CPU cycles are withheld from the VM, stalling request handling entirely.

Summary of Performance Trade-offs

Factor Bare Metal Virtual Machine
Throughput (QPS) Maximum possible network and memory saturation 15–35% lower due to virtualization tax
Tail Latency Highly predictable, sub-millisecond Subject to jitter from vCPU scheduling and vSwitching
Memory Access Single-layer page tables, minimal TLB penalty Nested page tables (EPT/NPT), higher TLB miss costs
Scalability Scale-up (requires hardware changes) Scale-out/Scale-up with high operational agility

Bare metal is the optimal deployment model for ultra-low latency requirements and massive, steady-state workloads where maximizing hardware efficiency per dollar is critical. Virtual machines remain viable for smaller workloads or environments where automated provisioning, hardware abstraction, and rapid horizontal scaling outweigh the cost of virtualization overhead.
