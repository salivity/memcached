Memcached Key Hashing and Bucket Assignment

Memcached handles item keys through a two-stage process that separates distributed routing from local storage indexing. The system does not automatically normalize keys on the server, instead treating them as raw byte sequences within defined protocol limits. Key distribution relies on client-side consistent hashing to select the appropriate server node, followed by server-side non-cryptographic hashing (such as Murmur3 or Jenkins) to assign the item to an internal hash table bucket for fast retrieval.

Key Normalization Handling

Memcached does not perform key normalization natively. The server engine treats every key as an immutable string of bytes with a maximum length of 250 characters. It does not perform operations such as case folding, whitespace stripping, Unicode normalization, or character escaping:

  • Text Protocol Constraints: Keys cannot contain control characters or spaces, as whitespace acts as a command delimiter. If an invalid character is transmitted, the server returns an error rather than sanitizing the key.
  • Binary Protocol: Keys can contain arbitrary binary sequences, but they are still evaluated byte-for-byte without modification.
  • Client Responsibility: Any standardizing or canonicalizing of keys (e.g., converting to lowercase, hashing overly long keys with SHA-250/MD5, or stripping prefixes) must be handled explicitly by the client application before issuing a command.

Client-Side Hashing: Node Routing

Before an item reaches an individual Memcached instance, the client library determines which server in the cluster should hold the key.

Most modern clients implement consistent hashing algorithms, most notably Ketama. Ketama maps both the Memcached servers (using their IP/port addresses duplicated across virtual nodes or "vnodes") and the item keys onto a 32-bit continuum (a circular hash ring). When an item key is hashed using an algorithm like MD5 or MurmurHash:

  1. The client computes the 32-bit integer token for the item key.
  2. The client traverses the hash ring clockwise to find the nearest virtual node.
  3. The request is dispatched directly to that specific server instance.

This architecture ensures that Memcached servers remain stateless regarding cluster topology, allowing nodes to be added or removed with minimal cache invalidation.

Server-Side Hashing: Internal Bucket Assignment

Once a specific Memcached instance receives the key, it maps the key to an internal hash table bucket using an internal hashing routine.

Hashing Algorithms

Memcached historically used Bob Jenkins' lookup3 hash algorithm. Modern releases default to Murmur3 or Jenkins, selectable via runtime flags. These algorithms are non-cryptographic, optimized for high throughput, low latency, and uniform distribution across the hash table space.

Bucket Computation

Memcached maintains an associative primary hash table sized to a power of two (\(2^{\text{hashpower}}\)). To assign a key to a specific bucket:

  1. The server hashes the raw key string using the selected algorithm to generate a 32-bit unsigned integer: \[\text{hash\_value} = \text{hash}(\text{key}, \text{key\_length})\]
  2. The bucket index is calculated using a bitwise mask rather than an expensive modulo operation: \[\text{bucket\_index} = \text{hash\_value} \ \& \ ((1 \ll \text{hashpower}) - 1)\]

Collision Resolution and Table Resizing

Each bucket in the hash table points to a singly linked list of item structures (item *). When multiple keys resolve to the same bucket index (a collision), the new item is chained into the list.

To maintain \(O(1)\) lookup performance, Memcached monitors the ratio of items to buckets. When the number of stored items reaches 1.5 times the number of available buckets, a dedicated background maintenance thread incrementally doubles the hash table size (\(\text{hashpower} + 1\)) and migrates items between buckets without locking the entire cache.
