Memcached Slab Item Structure Explained

Memcached relies on a slab allocation mechanism to manage memory efficiently and avoid fragmentation. Within each allocated slab class, memory is carved into pre-sized chunks designed to hold a single record, known internally as an item. This article details the specific structural components that compose an individual item stored within a Memcached slab, including its core metadata header, memory management pointers, addressing keys, and raw payload data.

The Item Header Struct

At the beginning of every slab chunk lies the fixed-size item metadata header. This structure maintains the state and lifecycle of the cached object within the engine and contains several primary fields:

  • Hash and LRU Pointers: Memcached maintains double-linked lists for its Least Recently Used (LRU) eviction algorithms and a singly linked list for hash table collision chains. The header holds pointers (next, prev, and h_next) to track the item's position in these queues.
  • Timestamps: Fields such as time (the last access time used for LRU tracking) and exptime (the absolute expiration timestamp defining when the entry becomes stale).
  • Length Attributes: Precise size records, specifically nkey (length of the key in bytes) and nbytes (size of the actual payload).
  • Reference Counter: A refcount integer tracking active worker threads currently reading or holding a lock on the item to prevent concurrent eviction or deallocation.
  • Flags and Identifiers: Internal bitwise status flags (it_flags), such as whether the item is linked, along with the slabs_clsid identifying which slab class and LRU list owns the chunk.

Optional CAS Identifier

If CAS (Check-And-Set) operations are enabled, an 8-byte, 64-bit integer (cas) is appended to the header structure. This value increments whenever the record is updated, providing optimistic concurrency control to prevent race conditions during parallel updates.

The Key

Immediately following the fixed-size metadata is the key itself. Stored as raw bytes up to Memcached’s standard limit of 250 bytes, this string uniquely identifies the object within the primary hash table lookup structure. Memcached stores the key directly in the item chunk rather than referencing an external memory block to minimize memory fragmentation.

The Client Flags and Protocol Suffix

Depending on the compile configuration and binary versus ASCII protocol usage, a suffix area is stored after the key. In the ASCII protocol, this area stores a text representation of the 32-bit client-defined flags alongside a carriage-return/line-feed (\r\n) delimiter. In binary mode, the 32-bit client flags are stored directly, preserving custom metadata passed by the application (such as data type or compression markers).

The Data Payload

The actual value, or data payload, occupies the space following the key and metadata suffix. This section holds the raw bytes supplied by the client application (e.g., serialized JSON, compressed strings, or binary blobs). Its length is determined by the nbytes parameter specified in the header.

End-of-Data Padding and Delimiters

To satisfy protocol parsing requirements, the data payload terminates with a standard two-byte carriage return and newline sequence (\r\n). Any remaining unallocated space between the end of this termination sequence and the boundary of the allocated slab chunk is left as unused padding, inherent to the slab sizing intervals.
