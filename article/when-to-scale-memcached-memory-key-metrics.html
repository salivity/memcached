When to Scale Memcached Memory: Key Metrics

Determining whether a Memcached node requires vertical memory scaling involves analyzing key performance indicators to ensure your working dataset fits adequately within the allocated RAM. Scaling up memory is crucial when premature data eviction harms cache efficiency and downstream database performance. This article outlines the essential Memcached metrics—including evictions, hit ratios, slab utilization, and byte limits—that indicate it is time to allocate more memory to your node.

1. Evictions (evictions)

The eviction count is the most critical metric for identifying memory exhaustion. When Memcached reaches its configured memory limit (limit_maxbytes), it uses a Least Recently Used (LRU) algorithm to remove valid, non-expired keys to make room for new writes.

  • What to look for: A continuously rising eviction rate or sharp spikes during peak traffic.
  • Action threshold: If items are being evicted before their natural time-to-live (TTL) expires and this leads to degraded performance, the node is running out of capacity for its active working set.

2. Cache Hit Ratio

The cache hit ratio reflects how effectively Memcached serves requests directly from memory versus letting queries fall through to the primary database. It is calculated as:

\[\text{Hit Ratio} = \frac{\text{get\_hits}}{\text{get\_hits} + \text{get\_misses}}\]

  • What to look for: A declining hit ratio that correlates directly with an increase in evictions.
  • Action threshold: While acceptable hit ratios vary by application, a downward trend accompanied by high miss rates generally means valid cached data is being purged too early due to memory constraints.

3. Total Memory Utilization (bytes vs. limit_maxbytes)

Memcached reports the total bytes currently used by active data via the bytes metric, alongside the maximum memory permitted via limit_maxbytes.

  • What to look for: Sustained usage hovering at or near 100% of limit_maxbytes.
  • Action threshold: High memory usage alone is normal because Memcached is designed to stay full. However, if utilization reaches maximum capacity and triggers constant evictions, the instance requires vertical memory expansion.

4. Per-Slab Evictions and Slab Class Saturation

Memcached allocates memory in chunks organized into distinct slab classes based on item size. Memory pressure can occur within specific slab classes even if the global instance appears to have headroom.

  • What to look for: Run stats items to inspect the evicted and evicted_nonzero metrics per slab class.
  • Action threshold: High eviction numbers concentrated in specific slab classes indicate that the memory distribution cannot accommodate your application's item size profile. If modern Memcached features like slab automove (slab_automove=1 or 2) fail to balance the slabs adequately, increasing the overall instance memory is required.

5. Out of Memory Errors (OOM)

By default, Memcached evicts old items when full. However, if the daemon is launched with the -M flag (which disables automatic evictions), the server will return an out-of-memory error when memory is exhausted.

  • What to look for: Application-level errors indicating cache write failures, or an increase in unfulfilled store commands.
  • Action threshold: Any non-zero count of OOM conditions under the -M configuration requires an immediate vertical memory scale-up to restore write operations.
