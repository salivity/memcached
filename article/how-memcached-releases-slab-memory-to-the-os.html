How Memcached Releases Slab Memory to the OS

Memcached fundamentally does not release slab memory back to the operating system, even during extended periods of low traffic or idle usage. Instead of deallocating unused space, its slab allocator retains all allocated memory within the process heap to prevent fragmentation and maintain sub-millisecond response times. This article explores the mechanics of Memcached's slab allocation, why memory is held indefinitely, how internal reclamation operates, and how system administrators can manage memory footprints during prolonged low-usage windows.

The Slab Allocation Model

To understand why memory is not released to the host kernel, it is necessary to examine how Memcached manages storage. When started, Memcached allocates memory in large chunks (typically 1 megabyte per slab page) using standard heap allocation.

These 1MB pages are partitioned into smaller, fixed-size chunks called slab classes. Each class is tailored to store items within a specific size bracket. Once a slab page is allocated from the operating system to a specific slab class, it remains committed to that class.

Why Memory Is Not Returned to the Kernel

When keys expire via their Time-To-Live (TTL) or are explicitly removed by a client via DELETE or FLUSH_ALL, Memcached does not invoke free() or munmap() to return the physical pages to the operating system. Instead, the freed chunk is simply appended to an internal freelist maintained for that particular slab class.

This architectural decision is intentional:

  1. Heap Fragmentation Prevention: Constantly allocating and freeing memory blocks of varying sizes leads to severe heap fragmentation in long-running C processes.
  2. Predictable Latency: Calling the kernel to allocate or release memory introduces system-call overhead, context switches, and page faults that compromise Memcached's low-latency guarantee.
  3. Reusability: Memcached operates on the assumption that cached datasets naturally expand back to their operational limits, making memory deallocation counterproductive.

Consequently, tools like top, htop, or memory monitoring agents will report high Resident Set Size (RSS) memory consumption indefinitely, even if the cache is virtually empty.

Internal Memory Reclamation: Slab Automove and Reassign

While memory does not leave the Memcached process, modern versions of Memcached (version 1.4.11 and newer) include features to redistribute memory internally between different slab classes during workload shifts.

Through the slab_reassign and slab_automove mechanisms, Memcached monitors slab usage:

  • If a slab class becomes starved for memory while another class holds empty pages, the automover thread can reassign an entire 1MB page from the idle class to the starved class.
  • This process reorganizes internal memory usage dynamically to avoid premature evictions, but the total memory footprint visible to the host operating system remains unchanged.

The Influence of the Underlying Allocator

Memcached is frequently compiled with advanced memory allocators like jemalloc. While modern allocators support returning unused virtual memory pages to the operating system using system calls such as madvise(..., MADV_DONTNEED), this only occurs when the application explicitly releases the memory back to the allocator. Because Memcached retains its chunk pointers in its internal freelists, jemalloc rarely sees entire multi-page segments marked as completely free, preventing automated kernel reclamation.

Strategies for Reclaiming Memory During Low Usage

Because Memcached does not downscale its memory allocation natively, administrators requiring dynamic memory reduction must rely on external operational strategies:

  • Process Restart: Restarting the memcached service terminates the process and immediately returns all committed pages to the OS kernel. This can be scheduled during known maintenance windows or extended off-peak seasons.
  • Dynamic Instance Scaling: In cloud environments, running multiple smaller Memcached nodes behind a consistent hashing proxy (such as Twemproxy) allows horizontally scaling down the number of nodes during low traffic, terminating unused instances entirely.
  • Lowering Maximum Footprint (-m flag): Setting the maximum memory parameter (-m) conservatively prevents the daemon from allocating large amounts of system memory in the first place, relying instead on LRU (Least Recently Used) evictions to discard stale data when capacity is reached.
