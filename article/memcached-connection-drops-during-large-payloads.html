Memcached Connection Drops During Large Payloads

When a network connection drops while Memcached is transmitting or receiving a large payload, the server relies on non-blocking I/O and an event-driven model managed by libevent to detect the failure, immediately abort the transaction, and safely reclaim allocated resources. Because Memcached treats operations atomically, incomplete incoming writes are discarded without polluting the cache, while interrupted outgoing reads trigger reference-count decrements to prevent memory leaks. The server cleans up the associated connection state machine instantly, ensuring dropped connections do not compromise system stability or data integrity.

Socket Error Detection via the Event Loop

Memcached uses non-blocking TCP sockets. When a connection drops due to a network partition, client crash, or timeout, the operating system marks the socket with an error or sends an EOF/RST packet.

Memcached's event loop detects this change in socket status:

  • For read operations, a system call (read or recv) returns 0 (indicating EOF) or -1 with an errno such as ECONNRESET or ETIMEDOUT.
  • For write operations, a system call (write or writev) fails and sets errno to EPIPE or ECONNRESET. Memcached explicitly ignores the SIGPIPE signal at the process level to prevent the daemon from terminating when a client abruptly closes the socket.

Handling Interrupted Incoming Payloads (SET Operations)

When a client uploads a large item, Memcached reads the command header, allocates a memory chunk from the appropriate slab class, and reads the payload from the network socket into that memory buffer.

If the connection terminates before the total declared number of bytes is received:

  1. Validation Failure: The state machine recognizes that the stream ended before reaching the byte count specified in the item header.
  2. Buffer Release: The pre-allocated slab memory holding the incomplete payload is immediately returned to the slab allocator.
  3. Cache Isolation: The item is never linked into the internal hash table or LRU (Least Recently Used) cache lists. No partial or corrupted data is ever stored or made visible to other clients.

Handling Interrupted Outgoing Payloads (GET Operations)

When a client requests a large item, Memcached locates the item in the hash table, increments its reference count to prevent eviction or modification during transfer, and constructs an I/O vector to stream the data using writev.

If the connection drops mid-transmission:

  1. I/O Abort: The write operation returns an error, halting further packet transmission immediately.
  2. Reference Decrement: Memcached decrements the reference count on the cached item. If the item was updated or expired while the transfer was ongoing, dropping the reference count allows the memory to be repurposed safely.
  3. Data Preservation: The item remains intact in the cache for other concurrent or future client requests, as read failures do not alter the underlying data in memory.

Connection State and Buffer Cleanup

Once an I/O failure is confirmed, Memcached transitions the client's internal connection state machine (conn) to a closing state:

  • The file descriptor for the socket is closed, releasing operating system handles.
  • Any read or write buffers allocated specifically to track that client's request state are cleared and returned to the connection buffer pool.
  • The internal conn structure is placed on a free list, making it available for reuse by new incoming client connections without requiring fresh heap allocations.
