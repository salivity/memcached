Memcached Worker Thread Assignment in Rapid Bursts

Memcached manages sudden spikes in incoming client traffic through a dedicated single-threaded listener architecture that dispatches connections across an array of worker threads using a non-blocking round-robin model. This article explores how Memcached decouples connection acceptance from request processing, utilizes per-thread connection queues, and leverages event-driven notifications to absorb high-concurrency traffic bursts without degrading cache performance or dropping sockets.

The Main Listener Thread and Non-Blocking Acceptance

At the core of Memcached's network architecture is a strict separation between connection acceptance and request execution. When Memcached initializes, it designates a single primary thread to run the main network event loop via libevent.

This main thread is the only thread bound to the listening socket. When a connection burst hits the server, the kernel buffers incoming TCP handshakes in the socket's listen backlog queue (configured via the -b command-line argument). The main thread invokes non-blocking accept() or accept4() system calls in a loop. Because connection acceptance is lightweight and free of data-parsing overhead, the main thread can accept thousands of incoming TCP sockets per second without stalling.

Round-Robin Distribution to Worker Threads

Once the main thread accepts a socket, it immediately delegates responsibility to a worker thread. Memcached achieves this using a strict round-robin scheduling algorithm:

  1. Target Selection: The main thread maintains an internal pointer representing the last assigned worker. For every accepted socket, it increments this pointer to identify the next thread in sequence: target_thread = (last_thread + 1) % total_threads.
  2. Item Allocation: The main thread encapsulates the newly accepted socket file descriptor and initial connection state into a lightweight CQ_ITEM (connection queue item) structure.
  3. Queue Insertion: The CQ_ITEM is pushed to the tail of the target worker thread's dedicated, mutex-protected connection queue.

By utilizing round-robin dispatching, Memcached guarantees an even distribution of incoming connection requests across all configured worker threads, preventing individual threads from becoming hotspots during a burst.

Inter-Thread Notification via Pipes and Eventfd

Worker threads run their own independent libevent loops to manage established connections. However, because a worker thread might be idle or waiting on network I/O, the main thread must notify it that a new connection is available in its queue.

To communicate across threads without complex locking:

  • Pipes / Eventfd: Each worker thread possesses a dedicated notification channel (a pipe or, on Linux, an eventfd). The read end is registered inside the worker's libevent instance, while the write end is controlled by the main thread.
  • Notification Byte: After pushing the CQ_ITEM to the worker's queue, the main thread writes a single byte ("c") to the notification channel.
  • Event Loop Wake-Up: The worker thread’s event loop detects the read event, wakes up immediately, and calls the connection handler function.

Draining the Connection Queue

Once woken, the worker thread locks its connection queue, extracts all pending CQ_ITEM structures, and unlocks the queue. This batching mechanism is critical during high-volume bursts: even if the main thread enqueues dozens of connections before the worker finishes its current task, the worker retrieves and processes the entire backlog in a single operation.

For each item popped from the queue:

  • The worker creates a full Memcached connection object (conn).
  • The accepted socket file descriptor is registered with the worker’s local libevent instance for read/write monitoring.
  • The worker enters the connection state machine, ready to parse client binary or text protocol commands.

Mitigating Burst Bottlenecks

Under extreme arrival rates, Memcached maintains stability through several defensive layers:

  • TCP Backlog Tuning: If incoming connections arrive faster than the main thread can call accept(), the operating system retains them in the TCP listen backlog. Sizing this queue appropriately prevents TCP SYN packets from being rejected during instantaneous spikes.
  • Minimal Mutex Contention: Locking is confined exclusively to pushing and popping from the connection queues. Worker threads do not contend for the listening socket, eliminating the "thundering herd" problem common in multi-threaded network servers.
  • Worker Isolation: Once registered to a worker thread, a client connection remains tied to that thread for the duration of its lifecycle. This thread-affinity prevents cross-thread synchronization overhead during subsequent data reads and writes, allowing the system to absorb high transaction loads immediately following connection bursts.
