Memcached CPU Pinning and NUMA in Containers

Modern container runtimes optimize high-throughput, latency-sensitive workloads like Memcached by leveraging Linux kernel primitives to enforce CPU pinning and Non-Uniform Memory Access (NUMA) node assignment. By combining container-level orchestrators, container runtimes, and low-level kernel interfaces such as cgroups v2 and cpuset, systems can bind Memcached execution threads and allocated memory pages directly to dedicated physical CPU cores and local memory controllers. This article explains how container runtimes configure, enforce, and coordinate these low-level hardware assignments to eliminate cross-node memory latency and cache thrashing for Memcached deployments.

The NUMA and Cache Challenge for Memcached

Memcached is fundamentally bound by memory bandwidth, memory latency, and CPU cache coherency. In modern multi-socket or multi-chip-module architectures, accessing memory from a remote NUMA node incurs significantly higher latency compared to accessing local memory attached directly to the executing CPU socket. Furthermore, if the Linux kernel scheduler migrates Memcached worker threads between different CPU cores, L1, L2, and L3 caches are invalidated, causing severe latency spikes (tail latency) and decreased requests-per-second (RPS).

The Linux Kernel Foundation: cgroups and the cpuset Controller

Container runtimes do not implement CPU pinning and memory isolation independently; instead, they interface with the Linux kernel's cgroup subsystem via the cpuset controller.

  1. cpuset.cpus: Restricts the container's processes to execute exclusively on a specified list or range of logical CPU cores.
  2. cpuset.mems: Restricts the container's memory allocation to specific physical NUMA memory nodes.

When Memcached allocates its slab memory pool at startup, running under a defined cpuset.mems policy guarantees that all allocated pages reside in the memory directly attached to the assigned NUMA node, avoiding remote interconnect (e.g., Intel UPI or AMD Infinity Fabric) saturation.

Low-Level Runtimes: OCI, runc, and crun

Open Container Initiative (OCI) runtimes, primarily runc and crun, translate runtime specifications into low-level Linux namespace and cgroup rules.

When a container engine specifies CPU pinning, the runtime configures the OCI config.json file under linux.resources.cpu:

"resources": {
  "cpu": {
    "cpus": "0-7",
    "mems": "0"
  }
}

During container initialization, the runtime writes the defined core ranges directly to the container's cgroup filesystem:

  • Writing 0-7 into /sys/fs/cgroup/cpuset/memcached/cpuset.cpus.
  • Writing 0 into /sys/fs/cgroup/cpuset/memcached/cpuset.mems.

When the Memcached binary executes, the kernel limits the process hierarchy to those exact physical resources. All child worker threads spawned by Memcached naturally inherit these constraints.

High-Level Runtimes: containerd and CRI-O

High-level runtimes like containerd and CRI-O receive specifications from orchestrators via the Container Runtime Interface (CRI). These runtimes are responsible for constructing the OCI bundle and delegating the actual isolation tasks to low-level runtimes like runc.

When running standalone containers (e.g., via Docker or Podman), the runtimes expose simple flags that map down to cpuset:

  • --cpuset-cpus="0-7": Pins execution to cores 0 through 7.
  • --cpuset-mems="0": Restricts memory allocations to NUMA node 0.

Orchestration Layer: Kubernetes Topology Manager and CPU Manager

In enterprise architectures, manual assignment of cores via flags does not scale. Kubernetes automates this allocation through the Kubelet's CPU Manager and Topology Manager:

  1. CPU Manager (static policy): When a Memcached pod requests integer CPU cores in the Guaranteed Quality of Service (QoS) class, the CPU Manager allocates dedicated, exclusive CPU cores from the node's allocation pool. It writes these allocated cores directly into the container's cpuset.cpus.
  2. Topology Manager (single-numa-node policy): The Topology Manager coordinates resource assignments across multiple subsystem providers (CPU Manager, Device Manager, and Memory Manager). It ensures that all requested resources—exclusive CPU cores, local RAM, and PCI devices like SR-IOV network interface cards (NICs)—originate from the same physical NUMA node.

If an aligned NUMA alignment cannot be satisfied, the pod admission fails or falls back based on the configured policy (strict, best-effort, or single-numa-node).

Aligning Memcached Internals with Runtime Assignments

While modern runtimes successfully confine Memcached to specific cores and NUMA nodes, optimal performance requires aligning Memcached's internal configuration with those boundaries:

  • Worker Thread Count (-t): The number of Memcached worker threads must closely match the number of pinned cores assigned by the container runtime. Oversubscribing worker threads inside a pinned container causes thread contention on a limited set of cores.
  • Avoiding Core Migration: Within the assigned core set, Memcached threads can still be scheduled across assigned cores by the kernel. For ultra-low latency, deployments run Memcached wrapper scripts utilizing tools like taskset or internal thread-binding patches to permanently bind thread \(N\) to pinned core \(N\).
  • Network Affinity: To extract maximum throughput, the pinned NUMA node for Memcached should match the NUMA node hosting the network interface card (NIC) handling client traffic, bypassing inter-socket bus traversals for packet processing.
