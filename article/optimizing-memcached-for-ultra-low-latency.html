Optimizing Memcached for Ultra-Low Latency

Achieving deterministic sub-millisecond response times in Memcached requires careful tuning of memory allocation, worker thread concurrency, and network event processing. This guide outlines the essential parameters and system-level settings you must calibrate to eliminate latency spikes, prevent lock contention, and optimize Memcached for ultra-low latency environments.

Slab Allocation and Memory Tuning

Memcached manages memory through a slab allocator to avoid system-level memory fragmentation. Misaligned slab settings force excessive internal memory movement or evictions, resulting in tail-latency spikes.

  • -f (Slab Growth Factor): Controls the scale factor between consecutive slab page sizes (default: 1.25). If your keys and values cluster tightly around specific sizes, lower this value (e.g., 1.05 to 1.15) to create finer-grained slab classes. This reduces internal memory waste and avoids premature evictions that trigger expensive cache misses.
  • -n (Minimum Item Size): Sets the minimum allocation size for key, value, and flags (default: 48 bytes). Set this close to your minimum expected payload size to ensure the smallest slab class accurately fits your smallest objects without padding overhead.
  • -m (Maximum Memory): Defines the maximum RAM allocated to Memcached in megabytes. Never allocate more than 75–80% of total host RAM to avoid operating system swapping. Paging memory to disk will immediately degrade latency from microseconds to milliseconds.
  • -o hashpower: Pre-allocates the internal hash table size at startup (e.g., -o hashpower=20 for 1 million buckets). Memcached dynamically doubles its hash table when capacity thresholds are reached, which causes a brief latency spike as keys are moved. Setting this upfront bypasses hash table expansion under heavy load.

Threading and Concurrency Parameters

Worker threads process inbound requests from network sockets. Improper thread allocation can cause severe context-switching overhead and lock contention.

  • -t (Thread Count): Sets the number of worker threads (default: 4). For ultra-low latency, match this value to the number of physical CPU cores, generally avoiding hyperthreaded virtual cores if high tail latencies emerge. Avoid over-provisioning beyond 8 to 16 threads, as internal lock contention (particularly on the item lock and cache lock) increases latency.
  • -R (Requests per Event): Controls the maximum number of requests a single worker thread processes from an active event loop before yielding to other connections (default: 20). Lowering this value to 5–10 prevents one noisy, pipelined client connection from starving other pending client requests.

Background Maintenance Offloading

Default synchronous cleanups can block worker threads during normal get and set operations. Moving these operations to background threads ensures consistent execution times.

  • -o modern: Automatically enables several low-latency optimizations, including the background LRU maintainer, LRU crawler, and hash table background adjustments.
  • -o lru_maintainer: Splits the LRU cache into sub-queues (HOT, WARM, COLD) and runs background operations to balance memory. This prevents worker threads from paying the latency cost of synchronous item evictions during set operations.
  • -o lru_crawler: Enables a low-priority background thread that crawls slabs to invalidate expired items, freeing memory proactively rather than reactively during active reads or writes.

Network and Transport Flags

The transport layer dictates how quickly packets move between client connections and worker event loops.

  • -c (Maximum Concurrent Connections): Sets the upper bound for open connections (default: 1024). Set this parameter higher than your peak connected client capacity (e.g., 10000 to 50000) to prevent incoming TCP connection drops or delays caused by pending backlog queues.
  • -o listen_backlog: Sets the kernel accept queue limit for incoming TCP connections (default: 1024). Increase this to 4096 or higher in burst-heavy traffic environments, matching your operating system's net.core.somaxconn sysctl limit.
  • Meta Protocol Adoption: Transition client drivers to Memcached's Meta Protocol (M commands) rather than the older ASCII or Binary protocols. The Meta Protocol reduces payload parsing overhead and allows clients to selectively pipeline commands and request minimal response headers, significantly trimming network latency.

Operating System Level Optimizations

Application-level parameters must be supported by the host operating system to achieve true ultra-low latency:

  • Disable transparent huge pages (THP) to avoid memory defragmentation pauses: echo never > /sys/kernel/mm/transparent_hugepage/enabled.
  • Pin worker threads using numactl or CPU affinity settings to eliminate cross-NUMA memory access penalties.
  • Increase kernel network ring buffers and use polling drivers (busy_read / epoll) to cut network stack transit times.
