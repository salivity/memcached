Memcached Memory Allocation for Growing Values

This article explains how Memcached manages memory chunk assignments when stored values grow incrementally over time. Because Memcached relies on a rigid slab allocation model to eliminate external memory fragmentation, items cannot simply expand their existing memory footprints in place. Instead, the engine dynamically handles size increases through reallocation across predefined slab classes, chunk replacement, and eviction mechanisms.

The Slab Allocation Engine

Memcached uses a slab allocation system to manage physical RAM. Rather than relying on standard operating system memory allocation routines (like malloc and free) for every write, Memcached pre-allocates memory in large blocks known as slabs (typically 1 megabyte each).

Each slab is sliced into smaller, fixed-size partitions called chunks. Slabs are categorized into slab classes based on chunk size, which scales by a configurable growth factor (defaulting to 1.25). An item is always assigned to the smallest chunk that can accommodate both its key, metadata, and value payload.

Handling Growth: Reallocation Instead of In-Place Expansion

Chunks in Memcached are strictly fixed-size boundaries. When a value grows incrementally—whether through successive set operations, cas replacements, or native commands like append and prepend—it cannot resize its existing chunk.

Memcached handles incremental size increases through the following process:

  1. Size Verification: The server calculates the new aggregate size (existing data plus newly introduced bytes, keys, and internal headers).
  2. Class Lookup: If the new size still fits within the existing chunk, Memcached updates the payload in place, leaving the item in its current slab class.
  3. New Chunk Allocation: If the updated payload exceeds the current chunk boundary, Memcached identifies the appropriate higher-tier slab class capable of holding the new size.
  4. Data Relocation: Memcached allocates an entirely new chunk from the target slab class, copies the combined data into it, and updates the internal hash table pointer to reference the new memory location.
  5. Reclaiming the Old Chunk: The initial, smaller chunk is detached and added back to the free list of its original slab class for reuse by other keys.

Behavior of append and prepend Commands

The native append and prepend commands explicitly add data to an existing key without client-side read-modify-write cycles. Internally, Memcached does not create a linked list of buffers or stretch the memory page. It allocates a completely new chunk matching the combined size, reads the original data, appends or prepends the new payload, stores the result in the new chunk, and unlinks the old chunk.

Because of this design, repeatedly appending small increments to a single key causes repeated reallocations, requiring free chunks across increasingly larger slab classes.

Memory Fragmentation and Eviction Implications

Incremental growth introduces specific operational side effects within Memcached:

  • Internal Fragmentation: Moving to a larger slab class may lead to unused space within the new chunk until the value grows enough to fill it.
  • LRU Eviction Pressure: If the target slab class is full and cannot claim new slab pages, Memcached triggers its Least Recently Used (LRU) algorithm within that specific slab class to free up space, potentially evicting other active keys.
  • Slab Automove and Rebalancing: When values continually migrate to higher slab classes, older slab classes may sit with idle, freed chunks while larger classes suffer from evictions. Modern Memcached builds use a slab automove thread to detect this imbalance and slowly reassign entire 1MB slab pages to the classes with higher demand.
