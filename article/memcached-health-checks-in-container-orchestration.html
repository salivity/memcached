Memcached Health Checks in Container Orchestration

Container orchestration platforms like Kubernetes, Docker Swarm, and Nomad rely on health checks and readiness probes to manage the lifecycle of containerized workloads, but implementing them for Memcached presents unique challenges due to its lack of a native HTTP interface. Because Memcached communicates over a proprietary text or binary protocol on TCP/UDP port 11211 rather than standard HTTP, orchestrators cannot rely on basic HTTP status checks. This article explains how orchestration systems manage Memcached health, comparing simple TCP socket tests, in-container command executions, and specialized monitoring techniques to ensure optimal caching tier reliability.

The Role of Health Checks in Memcached

In modern orchestrators, health checks are typically divided into three primary types:

  • Liveness Probes: Determine if the Memcached container is alive. If this probe fails, the orchestrator kills the container and initiates a restart according to its restart policy.
  • Readiness Probes: Determine whether the instance is ready to accept client traffic. If a readiness probe fails, the orchestrator removes the pod or container IP from internal routing (such as a Kubernetes Service), preventing cache clients from receiving connection errors.
  • Startup Probes: Inform the orchestrator that an application is still initializing, temporarily disabling liveness and readiness checks to prevent premature restarts during slow cold starts.

Methods for Implementing Probes

Because Memcached does not include a built-in web server to return 200 OK responses, orchestration tools evaluate its state using alternative strategies.

1. TCP Socket Probes

The simplest and most resource-efficient mechanism is a native TCP socket check. In platforms like Kubernetes, this is defined via tcpSocket pointing to port 11211.

  • How it works: The orchestration agent attempts to establish a three-way TCP handshake with the Memcached port. If the connection succeeds, the probe passes; if the connection is refused or times out, it fails.
  • Advantages: Extremely lightweight, requires no external utilities or binaries within the container, and consumes minimal CPU and network resources.
  • Disadvantages: It only verifies that the network daemon has bound to the port. It cannot verify whether the Memcached event loop is blocked, if worker threads are deadlocked, or if memory exhaustion is causing request drops.

2. Command Execution (Exec) Probes

To verify that Memcached is actually processing commands, orchestrators can run commands inside the container using an execution probe.

  • Protocol Ping via Netcat or Bash: The probe sends a basic command, such as version or stats, and checks for a valid response:

    echo -e "version\r\n" | nc 127.0.0.1 11211 | grep -q "VERSION"

  • Using memcached-tool: Container images that include Perl or administrative packages often bundle the memcached-tool utility. The orchestrator can run memcached-tool 127.0.0.1:11211 display to verify internal functionality.

  • Advantages: Validates that the engine is genuinely parsing commands and returning output, providing true application-level verification.

  • Disadvantages: Executing a process inside a container creates additional system overhead (forking processes, allocating memory) every few seconds, which can degrade low-latency cache performance at scale. Furthermore, modern minimal container images (distroless or alpine-based) often lack shells, nc, or grep for security reasons.

3. Sidecar and Monitoring Agent Probes

In high-throughput environments, engineers frequently deploy a sidecar container, such as the Prometheus memcached_exporter, alongside the main Memcached instance.

  • How it works: The sidecar connects to Memcached locally via the native protocol and exposes metrics over an HTTP endpoint (e.g., :9150/metrics).
  • Application: The orchestrator can point standard HTTP readiness probes to the exporter. If the exporter fails to scrape Memcached, the HTTP probe fails, allowing the orchestrator to route traffic away without adding shell tools to the Memcached image itself.

Best Practices for Memcached Probing

  • Use TCP Checks for Liveness, Not Readiness: A TCP socket check is ideal for liveness probes because it avoids unnecessary process-fork overhead while reliably catching hard crashes and hung processes.
  • Keep Timeouts Short: Memcached operations are measured in sub-milliseconds. Set probe timeouts low (e.g., 1 to 2 seconds) and avoid aggressive failure thresholds to prevent temporary network blips from triggering unnecessary cache flushes.
  • Avoid Disruptive Cache Restarts: When a Memcached container restarts, its entire in-memory dataset is lost, creating a "cache stampede" against backend databases. Configure liveness probes conservatively, requiring multiple consecutive failures before an orchestrator terminates the instance.
