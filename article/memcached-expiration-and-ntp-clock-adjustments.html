Memcached Expiration and NTP Clock Adjustments

This article provides an overview of how Memcached evaluates item expiration and manages timekeeping when system clocks are modified by Network Time Protocol (NTP) adjustments. It details the difference between relative and absolute expiration values, explains how Memcached relies on an internal monotonic clock to prevent premature evictions, and explores the operational effects of gradual clock slewing versus abrupt clock stepping.

Memcached Time Representation: Relative vs. Absolute

When a client sets a key with a Time to Live (TTL), Memcached interprets the expiration parameter based on the threshold of 30 days (2,592,000 seconds):

  • Relative TTL: If the value is equal to or less than 2,592,000, Memcached treats it as a relative offset in seconds from the current moment.
  • Absolute TTL: If the value exceeds 2,592,000, Memcached treats it as a specific Unix epoch timestamp (seconds since January 1, 1970).

Regardless of how the expiration time is provided by the client, Memcached standardizes these values internally against its own internal process timer.

Internal Timekeeping Mechanism

Memcached maintains an internal clock to avoid the overhead of issuing a gettimeofday or clock_gettime system call on every cache transaction. A dedicated event thread updates an internal variable, current_time, once per second.

Crucially, Memcached measures item lifetimes using internal process uptime rather than directly referencing the system's wall-clock time for active checks:

  1. Relative Expirations: If an item is given a 300-second TTL, Memcached sets the item's expiration to current_time + 300. This calculation is strictly relative to the process's own running time.
  2. Absolute Expirations: If an absolute Unix timestamp is supplied, Memcached calculates the difference between the provided timestamp and the system's current wall clock at that exact moment. It then converts that difference into an offset and adds it to current_time.

How NTP Adjustments Affect Expiration

NTP adjusts the local system clock using two methods: slewing (gradual drift correction) and stepping (instantaneous jumps).

1. NTP Slewing (Gradual Adjustments)

During standard operation, NTP daemons (such as Chrony or ntpd) slew the clock by speeding up or slowing down the system tick frequency by small fractions of a second until synchronization is achieved. Because slewing does not produce sudden jumps in the timeline, it has virtually no noticeable effect on Memcached. Relative TTLs tick down at their normal rates, and the internal time counter remains stable.

2. NTP Stepping Forward (Clock Jumps Ahead)

When a system clock jumps forward abruptly:

  • Existing Relative Items: Keys already stored using relative TTLs are completely unaffected. Because their expiration is anchored to process uptime (monotonic ticks), a sudden jump in the OS wall clock does not cause these items to expire early.
  • New Absolute Items: If a client calculates an absolute timestamp using an out-of-sync local clock or an external reference, a discrepancy occurs at ingestion. However, if the client derives the timestamp from the host’s updated system clock, Memcached properly calculates the remaining delta at the time the command is issued.

3. NTP Stepping Backward (Clock Jumps Behind)

When the system clock steps backward:

  • Existing Relative Items: As with forward jumps, previously cached relative items continue their standard countdown tied to internal process ticks. They will not have their lives extended artificially.
  • Absolute Expirations During Ingestion: If the system clock steps backward and a client submits an absolute Unix timestamp that represents a time prior to the newly adjusted local time, Memcached interprets the item as already expired and evicts or ignores it immediately.

Operational Recommendations

To ensure predictable cache eviction lifecycles:

  • Prefer Relative TTLs: Standardize application logic to send relative TTL offsets (e.g., 3600 seconds) instead of calculating absolute Unix timestamps in application code. This isolates cache invalidation logic entirely from wall-clock shifts.
  • Configure Slewing Over Stepping: Configure NTP services to use slewing mode (such as the -x flag in legacy ntpd or setting maximum slew rates in Chrony) to avoid sudden multi-second or multi-minute time jumps on Memcached host instances.
