How Memcached Clients Map Keys to Servers

Memcached employs a purely client-side architecture where the servers operate independently with no awareness of each other or the cluster as a whole. Because of this design, the client library is solely responsible for determining which physical server stores or retrieves a particular piece of data. By utilizing deterministic hashing algorithms—most notably consistent hashing via the Ketama algorithm—the client library maps any given key to the exact same server consistently, ensuring predictable data access across a distributed pool.

Step 1: Client Initialization and Ring Construction

Before processing any requests, the client library initializes by reading the cluster configuration.

  1. Server Inventory: The client loads a list of all available Memcached server endpoints (IP addresses or hostnames, ports, and optional weights).
  2. Virtual Node Creation: To ensure an even distribution of data and account for server capacity (weight), the client uses consistent hashing (such as libketama). It generates multiple "virtual nodes" (points) for each physical server by hashing server strings (e.g., server_ip:port-index).
  3. Continuum Array: These virtual nodes are placed on a 32-bit integer continuum (a circular ring ranging from 0 to \(2^{32} - 1\)) and stored in a sorted array or binary tree structure within the client’s memory.

Step 2: Key Ingestion and Preprocessing

When an application invokes a read (GET) or write (SET) command, the client library prepares the key for routing.

  1. Key Validation: The client verifies that the key conforms to Memcached protocol limits (e.g., a maximum length of 250 characters and no invalid control characters or whitespace).
  2. Prefixing/Namespacing: If configured by the application, the client prepends a namespace or prefix to the raw key string before calculating the hash.

Step 3: Hash Computation

The client executes a hashing function on the processed key string to produce a 32-bit integer.

  1. Algorithm Selection: Modern client libraries typically use fast, uniform hashing functions such as MurmurHash3, FNV-1a, or MD5 (specifically truncating the 128-bit MD5 digest into four 32-bit values in standard Ketama implementations).
  2. Hash Generation: The key is passed through the hashing algorithm to output a single integer value within the continuum’s range (\(0\) to \(2^{32} - 1\)).

Step 4: Locating the Target Server

With the numeric hash calculated, the client locates the appropriate server on the hash ring.

  1. Binary Search: The client performs a binary search (or looks up the successor) on the sorted array of virtual nodes to find the first virtual node whose hash value is greater than or equal to the key's hash value.
  2. Ring Wrap-Around: If the key's hash value is larger than the highest value on the ring, the search wraps around to the beginning of the ring, selecting the first node in the array.
  3. Node-to-Server Mapping: The selected virtual node directly references its underlying physical server, definitively mapping the key to that specific Memcached instance.

(Note: In legacy or simple setups using modulo hashing, this step simply computes hash(key) % number_of_servers to determine the server index directly).

Step 5: Connection and Command Dispatch

Once the server is identified, the client library dispatches the network request.

  1. Connection Pool Lookup: The client queries its internal connection pool for an active, idle TCP (or UDP) connection to the selected server.
  2. Execution: The command (e.g., get user:1001\r\n) is sent over the wire using the Memcached text or binary protocol.
  3. Response Handling: The client reads the server's response, handles any network errors or timeouts according to configured retry policies, and returns the data back to the calling application.
