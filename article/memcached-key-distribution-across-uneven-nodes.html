Memcached Key Distribution Across Uneven Nodes

Memcached relies on client-side routing rather than inter-node communication to partition data across a cluster. When operating cache nodes with varying memory capacities, standard hashing algorithms fail to balance the workload appropriately, risking out-of-memory errors on smaller instances and underutilization on larger ones. Client libraries solve this problem by implementing weighted consistent hashing, which uses virtual node replication to assign keys proportionally to each node's allocated capacity.

The Role of the Client in Memcached

In a Memcached architecture, individual servers are entirely unaware of one another. There is no cluster-level coordination, replication, or internal data routing. When an application issues a set or get command, the client library determines which specific physical node receives the request. Consequently, any strategy for handling nodes of different sizes must be executed entirely within the client application.

Why Modulo Hashing Fails

A naive approach to distribution uses modular arithmetic: hash(key) % number_of_nodes. This strategy has two major flaws:

  1. Topology Sensitivity: Adding or removing a node changes the divisor, causing nearly 100% of the keys to re-map to different servers, triggering a cache miss storm.
  2. Capacity Blindness: It assigns an equal share of keys to every node regardless of physical RAM, leading to premature evictions on small nodes while larger nodes remain mostly empty.

Weighted Consistent Hashing (The Ketama Algorithm)

Modern Memcached clients use consistent hashing algorithms, most commonly the Ketama algorithm, to map keys to servers on a continuous logical circle (the hash ring) ranging from \(0\) to \(2^{32}-1\).

To accommodate servers with different resource limits, client libraries incorporate a server weighting system. Instead of placing a single physical server onto one location on the ring, the client library generates multiple pseudo-random points known as "virtual nodes" (or vnodes) for each physical instance.

How Virtual Nodes Enable Proportional Distribution

When configuring the client, an administrator assigns a relative weight to each server, typically corresponding to its RAM capacity:

  1. Weight Assignment: If Node A has 4 GB of RAM and Node B has 16 GB of RAM, Node A is assigned a weight of 1, and Node B is assigned a weight of 4.
  2. Virtual Node Creation: The client hashes string combinations of the server's IP address and an incremental counter (for example, 192.168.1.10:11211-0, 192.168.1.10:11211-1, etc.).
  3. Multiplier Scaling: The library scales the total number of virtual nodes placed onto the hash ring directly in proportion to the node's assigned weight. If a base weight of 1 creates 160 virtual nodes, a weight of 4 creates 640 virtual nodes.
  4. Ring Interleaving: These virtual nodes are distributed pseudo-randomly across the entire \(2^{32}-1\) space, intermingling the entry points of both large and small servers.

The Key Lookup Process

When a client library reads or writes a key:

  1. The client applies a cryptographic or non-cryptographic hash (such as MD5 or MurmurHash) to the cache key to produce an integer coordinate on the ring.
  2. The client performs a binary search to find the closest virtual node equal to or greater than the key's hash value moving in a clockwise direction.
  3. The virtual node points to its corresponding physical server, and the client sends the network command to that target.

Because Node B occupies four times as many coordinates on the ring as Node A, the probability of any given key falling within an interval that resolves to Node B is roughly four times higher. This achieves an even, proportional data distribution that matches the exact capacity footprint of an asymmetric cache cluster.
