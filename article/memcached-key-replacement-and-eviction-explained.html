Memcached Key Replacement and Eviction Explained

This article explores how Memcached evaluates incoming keys and determines whether an existing item in memory should be updated, overwritten, or evicted. It covers the evaluation of direct key matching via storage commands, the constraints imposed by Memcached's slab allocation architecture, and the mechanics of the Least Recently Used (LRU) algorithm that governs data replacement when memory limits are reached.

1. Direct Key Matching and Storage Commands

The first evaluation Memcached performs is checking whether the incoming key already exists in its internal hash table. The action taken depends on the specific protocol command accompanying the key:

  • SET: Unconditionally stores the data. If the key already exists, Memcached invalidates or overwrites the existing item's metadata and data pointer with the new value.
  • ADD: Stores the data only if the key does not already exist. If the key is present, the server rejects the incoming item and returns NOT_STORED.
  • REPLACE: Stores the data only if the key already exists. If the key is not found, the operation fails and returns NOT_STORED.
  • CAS (Check-And-Set): Evaluates a unique 64-bit token associated with the key. The incoming item only replaces the existing item if the supplied token matches the token currently stored in Memcached, preventing concurrent write collisions.

2. Slab Allocation and Size Class Targeting

When an incoming key must be stored (either as a new item or an updated value of a different size), Memcached evaluates memory availability using its slab allocator rather than a global memory pool.

Memory is partitioned into slab classes, where each class handles items within specific size ranges (chunks). Memcached calculates the total footprint of the incoming item—including key length, flags, expiration time, internal metadata, and the payload—and assigns it to the smallest slab class capable of accommodating that size. Consequently, an incoming key never competes globally against all stored items; it only competes for memory within its assigned slab class.

3. Expiration and Memory Exhaustion

If the targeted slab class has free chunks or if Memcached can allocate a new 1MB memory page to that slab class from the global pool, the item is inserted without replacing unexpired keys.

If the slab class is entirely full and cannot allocate more pages, Memcached evaluates existing items for replacement in the following order:

  1. Expired Items (TTL Evaluation): Memcached inspects items at the tail of the slab's internal queue. If an item has surpassed its Time-To-Live (TTL), it is considered dead. The memory is reclaimed immediately and assigned to the incoming item.
  2. Least Recently Used (LRU) Eviction: If no expired items are found at the tail, Memcached checks its eviction policy. Unless configured with the -M flag (which returns an out-of-memory error instead of evicting), Memcached evicts the least recently accessed, unexpired item from that specific slab class to make room for the new data.

4. Segmented LRU Evaluation

Modern versions of Memcached use a segmented LRU model to prevent active working sets from being prematurely evicted by bursts of sequential writes. Within each slab class, items are evaluated across distinct queues:

  • TEMP: Holds items with very short lifespans (typically under a few seconds), preventing them from polluting long-term memory.
  • HOT: New items arrive here. If an item reaches the tail of HOT without being accessed again, it moves to WARM. If accessed, it stays at the head.
  • WARM: Holds items that have received multiple hits.
  • COLD: Inactive items trickle down to the COLD queue.

When memory must be reclaimed for an incoming key, Memcached targets only the tail of the COLD queue for eviction. Items that are actively read or updated remain protected in the HOT or WARM queues, ensuring that replacement decisions favor retaining frequently accessed data over newly written, single-access keys.
