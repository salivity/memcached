Monitoring Logs for Memcached Crashes

Memcached is designed to be a high-performance in-memory key-value store, but unhandled exceptions, memory exhaustion, and segmentation faults can cause the daemon to terminate abruptly. Because Memcached delegates memory management directly to the system and minimal internal error logging by default, detecting crashes requires monitoring a combination of operating system kernel logs, process supervisor outputs, and core dump facilities. This guide outlines the specific system logs and metrics you must monitor to identify and diagnose Memcached failures effectively.

1. Kernel Ring Buffer and Kernel Logs (dmesg, /var/log/kern.log)

When Memcached crashes due to severe memory exhaustion or memory access violations, the operating system kernel is often the first to record the event.

  • Out-Of-Memory (OOM) Killer: If Memcached exceeds the physical memory limits of the host or its assigned control group (cgroup), the Linux kernel's OOM killer may terminate the memcached process. Look for lines containing Out of memory: Kill process or Killed process <pid> (memcached).
  • Segmentation Faults: If an internal unhandled exception results in illegal memory access, the kernel logs a segfault. Look for memcached[PID]: segfault at ... error ... in memcached.
  • Where to check: Run dmesg -T or inspect /var/log/kern.log (Debian/Ubuntu) or /var/log/messages (RHEL/CentOS).

2. Systemd Journal (journalctl)

On modern Linux distributions, Memcached is typically managed as a systemd service. The systemd journal captures both service lifecycle changes and any standard error (stderr) output generated before termination.

  • Service Status Changes: The journal records unexpected exit codes, such as status=11/SEGV (segmentation fault) or status=9/KILL (abrupt kill signal).

  • Crash Indications: Watch for events stating memcached.service: Main process exited, code=killed, status=... and memcached.service: Failed with result 'signal'.

  • How to monitor: Query the service logs directly using:

    journalctl -u memcached.service -e

3. Core Dump Managers (coredumpctl)

If an unhandled exception triggers a fatal signal (like SIGSEGV or SIGABRT), the system can generate a core dump for post-mortem analysis.

  • If systemd-coredump is enabled, monitor coredumpctl list memcached to see if a dump was triggered.
  • Check /var/lib/systemd/coredump/ or the path defined in /proc/sys/kernel/core_pattern to detect if the binary crashed and left a memory image for debugger analysis with GDB.

4. General System Logs (/var/log/syslog or /var/log/messages)

Traditional system log daemons (such as rsyslog or syslog-ng) aggregate messages from system facilities, services, and kernel spaces into central text files.

  • Debian/Ubuntu: /var/log/syslog
  • RHEL/CentOS/Rocky Linux: /var/log/messages
  • Filter these files for strings such as memcached, segfault, and killed to catch broad operating environment errors, resource constraints, or dependent service disruptions.

5. Memcached Stderr Log

By default, Memcached produces minimal log output unless configured with verbosity flags (-v, -vv, or -vvv). In many production packages, output is redirected to /var/log/memcached.log.

  • Inspect this file for startup initialization failures, permission problems, or network binding errors.
  • Note that verbose flags should be used with caution in high-throughput environments, as excessive disk I/O from logging can degrade Memcached performance.
