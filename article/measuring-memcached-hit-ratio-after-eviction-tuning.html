Measuring Memcached Hit Ratio After Eviction Tuning

Tuning eviction rules in Memcached allows teams to protect high-value keys, balance slab classes, and prevent premature data drops, but these changes require precise measurement to confirm their effectiveness. To quantify improvements, developers must establish baseline cache metrics, track hit ratios across consistent traffic windows, monitor slab-level eviction counts, and employ automated time-series monitoring rather than relying on lifetime server totals.

Establish Baseline Metrics

Before modifying any eviction settings—such as modernizing segmented LRU behaviors (lru_maintainer, lru_crawler) or enabling automatic slab reassignment (slab_reassign, slab_automove)—capture the existing state. Connect to Memcached using telnet or nc and issue the stats command:

echo "stats" | nc localhost 11211

Record the following cumulative metrics:

  • cmd_get: Total read requests processed.
  • get_hits: Total successful key lookups.
  • get_misses: Total failed key lookups.
  • evictions: The total number of valid items removed to free memory for new items.
  • reclaimed: Number of times an expired entry was reused without needing a full eviction.

Calculate Cache Hit Ratio Accurately

The standard formula for cache hit ratio is:

\[\text{Hit Ratio} = \frac{\text{get\_hits}}{\text{get\_hits} + \text{get\_misses}}\]

Because standard stats counters accumulate from the moment the daemon starts, reading the raw numbers after a configuration change will dilute recent performance with historical data.

To measure actual improvements:

  1. Use Delta Calculations: Calculate the hit ratio using differences between two specific timestamps: \[\text{Delta Hit Ratio} = \frac{\Delta\text{get\_hits}}{\Delta\text{get\_hits} + \Delta\text{get\_misses}}\]
  2. Export to Time-Series Monitoring: Route metrics through an exporter (such as Prometheus Memcached Exporter) to capture per-minute or per-hour rates using functions like rate() or irate(). This reveals immediate trajectory shifts post-tuning.

Correlate Hit Ratio with Eviction Reductions

An improved hit ratio is only meaningful if it correlates with healthier memory behavior rather than a drop in overall traffic. Monitor the eviction rate alongside the hit ratio:

  • Eviction Rate Drop: A successful tune of slab allocations or LRU thresholds should cause the eviction rate per second to decrease or isolate evictions exclusively to temporary/cold slab queues.
  • Inspect Slab-Level Metrics: Run stats items and stats slabs to evaluate individual slab classes. If a specific slab class previously showed a high ratio of evictions to number of items, check whether your changes (e.g., dynamic slab movement) reduced evictions in that specific class.

Benchmark with Consistent Workloads

To eliminate confounding variables caused by natural user traffic fluctuations:

  • Traffic Shadowing: Replay identical production traffic traces against a control instance (untuned) and a target instance (tuned) concurrently.
  • Synthetic Workloads: Use tools such as mutilate or memtier_benchmark to simulate identical read/write access patterns, payload sizes, and key distribution curves (e.g., Zipfian distribution).

Compare the delta hit ratio and total evictions across both instances over identical run durations. A successful eviction configuration will demonstrate a higher hit ratio, lower or zero evictions in warm/hot queues, and reduced p95/p99 application response latency caused by fewer database fallback queries.
