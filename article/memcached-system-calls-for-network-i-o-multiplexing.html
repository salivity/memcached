Memcached System Calls for Network I/O Multiplexing

Memcached achieves high-performance caching and handles tens of thousands of concurrent connections through an event-driven, non-blocking I/O model. Rather than dedicating a thread to each client, it leverages the libevent library to abstract OS-level I/O multiplexing primitives. This article examines the core system calls Memcached relies on to manage events, accept incoming connections, exchange network data, and coordinate internal worker threads without introducing latency bottlenecks.

Event Multiplexing: epoll and kqueue

Memcached relies on modern, stateful kernel-polling system calls to monitor thousands of file descriptors simultaneously in \(O(1)\) time complexity, avoiding the \(O(N)\) overhead associated with legacy calls like select() or poll().

  • epoll_create1() / epoll_ctl() / epoll_wait() (Linux): On Linux platforms, Memcached relies on the epoll family. epoll_create1() initializes an epoll instance with close-on-exec flags. epoll_ctl() registers, modifies, or deletes socket file descriptors associated with readable or writable states using edge-triggered or level-triggered flags. epoll_wait() suspends the calling thread until network events occur, returning only the active descriptors to user space.
  • kqueue() / kevent() (FreeBSD, macOS, OpenBSD): On BSD-derived systems, Memcached uses kqueue and kevent. kqueue() creates the event filter queue, while kevent() registers filters and polls for events such as EVFILT_READ and EVFILT_WRITE.

Connection Lifecycle Management

The master listening thread handles new inbound TCP connections before assigning them to worker threads:

  • accept4() / accept(): When a read event triggers on the listening socket, Memcached invokes accept4() (on Linux) or accept() followed by fcntl(). Using accept4() allows Memcached to atomically set flags like SOCK_NONBLOCK and SOCK_CLOEXEC directly during descriptor creation, eliminating extra round-trips to kernel space.
  • fcntl(): Used to inspect and configure file descriptor properties, notably toggling non-blocking mode (O_NONBLOCK) when modern flags cannot be set directly during socket creation.
  • close(): Closes client sockets upon connection termination, timeouts, or unrecoverable protocol errors, automatically deregistering them from the kernel event table.

High-Throughput Network I/O

To reduce user-to-kernel context switches, Memcached avoids multiple separate write calls per protocol interaction:

  • writev() (Scatter-Gather I/O): Memcached frequently uses vectored I/O via writev() to assemble outgoing responses. Because responses often consist of an ASCII or binary protocol header located in one memory buffer and the cached item payload in another, writev() allows Memcached to transmit disjoint memory segments in a single system call without copying or concatenating buffers in user space.
  • readv(): Similarly, Memcached can read incoming data packets into non-contiguous memory chunks when processing streaming pipelined commands.
  • recv() / send() / read() / write(): Standard non-blocking data exchange calls. These calls return EAGAIN or EWOULDBLOCK when network buffers are empty or saturated, signaling Memcached to yield control back to the event loop.

Inter-Thread Coordination

Memcached employs a multi-threaded architecture consisting of a primary dispatcher thread and several dedicated worker threads. Each worker runs its own event loop and communicates with the dispatcher thread via specific kernel primitives:

  • pipe() / pipe2(): On standard POSIX systems, the dispatcher creates a unidirectional communication pipe for each worker. When a new connection arrives, the dispatcher writes the new socket file descriptor into the pipe. The worker's event loop monitors the read end of the pipe, wakes up, and assumes ownership of the connection.
  • eventfd(): On Linux, libevent can use eventfd() as a lightweight alternative to pipes. It functions as an internal kernel counter, reducing memory footprint and context-switch costs compared to traditional file-descriptor-based pipes.
