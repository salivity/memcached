How Memcached Handles Binary Keys vs String Keys

Memcached supports both standard string keys and arbitrary binary keys, handling their validation at the protocol level while unifying their storage in the internal caching engine. While standard string keys processed through the text protocol face strict character-set and whitespace restrictions, binary keys transmitted via the binary protocol allow arbitrary byte sequences. This article breaks down how Memcached parses, validates, and stores both key formats, detailing the operational differences between the text and binary protocols and explaining their shared underlying memory architecture.

Protocol-Level Validation

Validation occurs primarily during protocol parsing before any memory allocation or cache lookup takes place. Memcached implements two distinct interfaces: the ASCII (text) protocol and the binary protocol.

Standard String Keys (ASCII Protocol)

When a client uses the standard text protocol, keys are treated strictly as printable strings:

  • Character Restrictions: Keys cannot contain control characters, whitespace, carriage returns (\r), or newlines (\n). A space is treated as a delimiter separating the key from flags, expiration times, and byte counts.
  • Length Limits: By default, string keys are limited to 250 characters (KEY_MAX_LENGTH).
  • Validation Mechanism: The server parses incoming command lines sequentially. If it encounters a byte value less than or equal to 0x20 (space or control character) within the key segment, the command fails with a client error.

Binary Data Keys (Binary Protocol)

The binary protocol removes text-parsing ambiguities by using structured packet headers:

  • Character Neutrality: Keys can consist of any arbitrary sequence of bytes, including null bytes (\x00), spaces, control characters, or serialized object data.
  • Length Specification: Instead of using delimiters to find the end of a key, the packet header includes a dedicated 16-bit field defining the explicit key length in bytes.
  • Length Limits: While the 16-bit header field theoretically supports keys up to 65,535 bytes, Memcached enforces the server-side KEY_MAX_LENGTH limit (250 bytes by default) unless altered at compile time.
  • Validation Mechanism: The server verifies that the key length field matches the payload size indicated in the frame. Validation checks only that the key length falls within the permitted bound; it does not inspect or restrict the underlying byte values.

Internal Storage Architecture

Once validated, Memcached makes no architectural distinction between a standard string key and a binary key. Both are handled as raw byte sequences in the core engine.

The Item Structure

Memcached stores data inside slab-allocated structures called item. Each item contains metadata followed by the contiguous payload:

  1. Metadata Header: Stores pointers for hash bucket chaining, LRU lists, reference counters, flags, expiration time, and the explicit key length (nkey).
  2. Key Storage: The key's raw bytes are copied directly into the memory block immediately following the metadata.
  3. Value Storage: The associated data payload follows immediately after the key.

Because the nkey field explicitly tracks the exact byte count, the internal engine never relies on null-termination (\0) to determine where a key ends. Consequently, null bytes embedded inside a binary key do not truncate the key or corrupt memory.

Hashing and Lookups

Cache lookups operate identically for both string and binary keys:

  • Hash Computation: Memcached passes the pointer to the key's memory and its nkey length to the internal hashing function (typically Murmur3 or Jenkins hash). The hashing algorithm processes raw bytes regardless of encoding.
  • Collision Resolution: When matching keys during a hash table lookup, Memcached performs a length comparison first, followed by a raw memory comparison (memcmp). It does not use string comparison functions like strcmp.

Summary of Differences

  • Encoding: String keys require standard text representations without whitespace; binary keys accept arbitrary byte streams.
  • Parsing: String keys rely on text delimiters and fail upon encountering control bytes; binary keys rely on fixed-width header fields.
  • Storage Engine: Both formats are stored identically as length-prefixed raw byte arrays within slab-allocated items.
  • Lookups: Hash generation and equality checks treat both key types as raw binary blobs using length-bounded memory comparisons.
