Memcached Memory Page Alignment Explained

Memcached maximizes throughput and reduces access latency by deliberately organizing memory to conform to modern CPU hardware architecture. By utilizing slab allocation, deliberate struct padding, and aligned memory requests, Memcached guarantees that memory addresses align with native word, cache line, and memory page boundaries. This approach prevents unaligned memory access penalties, eliminates split cache line transactions, and minimizes Translation Lookaside Buffer (TLB) thrashing.

The Problem with Unaligned Memory Access

Modern 64-bit processors read and write data in discrete units, usually 8-byte machine words and 64-byte cache lines. When a data structure spans across the boundary of an address divisible by the architecture’s word size or cache line size, it is considered unaligned.

Accessing unaligned data forces the processor to execute multiple memory cycles: it must fetch two separate words or cache lines, mask the irrelevant bytes, and shift and combine the relevant data into a single register. In multithreaded systems, an unaligned atomic operation can cross cache line boundaries, triggering an expensive split lock on the memory bus that stalls CPU execution across cores.

Memcached's Slab Allocator Mechanism

Memcached bypasses the standard C library runtime memory allocator (malloc) during regular read and write operations. Instead, it relies on a slab allocation architecture:

  1. Large Slab Pre-allocation: Memcached requests memory from the operating system in large, contiguous blocks, typically 1 megabyte (MB) per slab page.
  2. Explicit Memory Alignment: When allocating these 1MB pages, Memcached utilizes system calls such as posix_memalign or equivalent alignment routines to guarantee that the base address of the slab page matches the virtual memory page boundary (commonly 4KB, or 2MB if huge pages are enabled).
  3. Subdivision into Sized Chunks: Each slab page is carved into equal-sized chunks based on predefined slab classes (e.g., 96 bytes, 120 bytes, etc.).

Boundary Alignment within Chunks

Because the starting address of each 1MB slab page is strictly aligned to a hardware page boundary, any offset calculated as a multiple of an aligned chunk size remains properly aligned.

Memcached enforces internal padding so that every chunk size is a multiple of the system pointer size—typically 8 bytes on 64-bit platforms. This guarantees that:

  • The starting address of every item within a slab page is divisible by 8.
  • Pointers stored inside the item metadata point to natively aligned memory addresses.

Data Struct Packing and Padding

Within each allocated chunk, Memcached stores an internal metadata header (struct _stritem) followed immediately by the key and value payload.

Memcached designs this struct so that all internal fields (such as 64-bit pointers, 64-bit timestamps, and 32-bit flags) sit at offsets divisible by their own size. The allocator adds trailing padding bytes to the item header to ensure that the variable-length key and data buffer also start on aligned addresses. This allows CPU vector instructions (e.g., SSE/AVX) to process string copies and hashing algorithms without incurring alignment fault penalties.

Cache Line and TLB Efficiency

By aligning slab pages to virtual memory pages and chunks to power-of-two boundaries:

  • Cache Line Conservation: Data payloads fit cleanly into 64-byte L1/L2/L3 cache lines. A read operation rarely straddles two distinct cache lines unless the data itself exceeds 64 bytes.
  • TLB Hit Rates: Page-aligned slabs allow the CPU’s Translation Lookaside Buffer to translate virtual addresses to physical addresses efficiently. If configured with transparent huge pages (THP), the 2MB alignment drastically reduces TLB misses during high-volume random access.
  • Lock-Free Concurrency: Correctly aligned primitive types allow atomic instructions to execute within a single cache line, enabling efficient concurrent access across multiple worker threads without bus locking.
