How Memcached Matches Items to Slab Classes

Memcached manages memory through a slab allocation mechanism designed to eliminate memory fragmentation. When an incoming write request arrives, the engine does not allocate arbitrary bytes from the heap; instead, it calculates the complete memory footprint required for the record—including key length, value size, and internal metadata—and maps it to the smallest available pre-configured slab class that can accommodate it. This article explains how Memcached calculates item overhead, traverses slab classes, and handles edge cases when fitting incoming payloads into memory.

Calculating the Total Item Footprint

An incoming payload is never evaluated purely by the size of the key and the raw value. Memcached must allocate space for an internal C structure known as item, which maintains metadata necessary for cache management.

To determine the true size, Memcached executes an internal function (traditionally item_make_header or equivalent logic) that sums the following components:

  • Header Overhead: The fixed-size item metadata struct containing memory pointers for LRU queues, expiration timestamps, flags, and an optional 8-byte CAS (Check-And-Set) identifier if enabled.
  • Key Length: The length of the key string plus a null-terminator byte.
  • Suffix Overhead: A small text suffix storing ASCII flags and the byte length of the data payload.
  • Payload Size: The actual raw data payload (nbytes).
  • Memory Alignment Padding: Extra bytes added to ensure the total item boundary aligns with 8-byte boundaries (system architecture alignment).

The combined sum of these components represents the required chunk size for the item.

Finding the Target Slab Class via slabs_clsid

Once the total required size is computed, Memcached calls the slabs_clsid function to locate the appropriate slab class identifier (clsid).

Memcached initializes memory at startup by dividing it into slab classes. Each class contains uniform "chunks" configured to grow geometrically by a factor (default 1.25, configurable via the -f flag). For instance, Slab Class 1 might hold 96-byte chunks, Class 2 holds 120-byte chunks, Class 3 holds 152-byte chunks, and so on.

The slabs_clsid function evaluates the item using a simple linear scan or lookup:

  1. It begins checking from the smallest slab class (clsid = 1).
  2. It compares the required item footprint against the chunk size configured for that class.
  3. The first slab class whose chunk size is greater than or equal to the required size is selected.
  4. If the item exceeds the chunk size of the current class, evaluation increments to the next class (clsid + 1).

Because the classes are ordered in strictly ascending chunk sizes, the first match found is guaranteed to be the best fit with the least amount of wasted memory.

Managing Maximum Limits and Rejections

Before an item is assigned to a slab class, Memcached validates that the calculated size does not exceed the absolute threshold defined by item_size_max (which defaults to 1 megabyte unless overridden with the -I startup parameter).

If the total footprint exceeds the chunk size of the largest available slab class, slabs_clsid returns 0. When this happens, Memcached rejects the incoming payload immediately, returning a client error (such as SERVER_ERROR object too large for cache) without attempting memory allocation.

Internal Fragmentation and Chunk Assignment

When a matching slab class is identified, Memcached checks that class's freelist for an open chunk, allocates a new 1MB slab page if capacity allows, or invokes the LRU eviction policy to reclaim an existing chunk within that specific class.

The entire allocated chunk is assigned to the item, regardless of whether the item uses all the space. The difference between the chunk size and the total item footprint becomes internal fragmentation (slack space). By accepting this controlled internal fragmentation, Memcached avoids operating-system-level heap fragmentation and achieves constant-time \(O(1)\) memory allocation and release.
