How Memcached Manages Memory Under Heavy Concurrency

Memcached maintains memory stability and prevents degradation during rapid concurrent key creation and deletion through a pre-allocated slab allocation system, fine-grained thread locking, reference counting, and an adaptive segmented Least Recently Used (LRU) engine. Instead of relying on the operating system's standard memory manager during high-churn workloads, Memcached manages its own fixed memory space internally. This design eliminates runtime memory fragmentation, prevents out-of-memory crashes, and guarantees predictable, low-latency execution under extreme load.

Slab Allocation Prevents Fragmentation

The primary defense against memory instability is the Slab Allocator. When Memcached initializes, it allocates a single, contiguous block of memory up to the user-defined limit (e.g., -m 1024 for 1GB). It never requests additional memory from the operating system via malloc during normal read, write, or delete operations, nor does it return memory via free.

This pre-allocated space is divided into 1MB pages, and pages are assigned to specific "slab classes." Each slab class handles items within a distinct size range, broken into fixed-size chunks:

  • Class 1 might contain 96-byte chunks.
  • Class 2 might contain 120-byte chunks.
  • Subsequent classes scale geometrically (by default, by a factor of 1.25) up to 1MB.

When an item is created, Memcached finds the smallest slab class that can accommodate the key, flags, and payload. Because items are stored in pre-sized chunks, the engine avoids the external memory fragmentation that typically cripples long-running applications handling millions of variable-sized allocations.

Zero-Allocation Deletions and Freelist Recycling

During aggressive key deletion, Memcached does not deallocate memory at the operating system level. Instead, deleting a key marks its chunk as free and appends that chunk back to the slab class’s local freelist.

When a concurrent SET request arrives for an item belonging to that same slab class, Memcached reuses a chunk directly from the freelist. This converts what would be expensive operating system kernel calls into constant-time, pointer-swapping operations in user space. Memory usage from the operating system's perspective remains perfectly flat, regardless of how many millions of keys are created or deleted per second.

Fine-Grained Locking and Reference Counting

High-concurrency stability requires that simultaneous creations and deletions do not cause race conditions or memory corruption. Memcached utilizes a multi-threaded architecture with a shared hash table protected by fine-grained bucket locks:

  • Hash Table Bucket Locks: Instead of a global lock across the entire dataset, the primary hash table is divided into millions of distinct lockable buckets. Concurrent operations only block one another if they hash to the exact same bucket.
  • Item Reference Counters (refcount): Every stored item has a reference counter. If a worker thread is reading or deleting an item while another thread attempts to overwrite or evict it, the reference count increments. If an item is deleted while a reader is still processing it, Memcached unlinks the item from the hash table immediately (hiding it from subsequent lookups), but postpones recycling the underlying chunk into the freelist until the refcount drops to zero. This eliminates dangling pointers and segmentation faults without requiring global synchronization.

Segmented LRU and Background Maintenance

When memory fills entirely and continuous key creation occurs alongside deletions, Memcached relies on a modern Segmented LRU implementation to prevent allocation failures:

  1. TEMP: Short-lived keys (TTL under a few seconds) are placed here and quickly reclaimed to avoid polluting longer-lived caches.
  2. HOT: New keys without immediate expiration start here. Once full, items flow to WARM or COLD.
  3. WARM: Frequently accessed keys are kept here.
  4. COLD: The least active keys land here; when a slab class runs out of free chunks, items are evicted directly from the tail of the COLD queue.

Dedicated background threads—the LRU Maintainer and LRU Crawler—asynchronously scan and move items between queues and invalidate expired items. By shifting reclamation to dedicated background threads, worker threads servicing user traffic do not stall, and memory pressure is systematically relieved before it threatens instance stability.

Dynamic Memory Rebalancing with the Slab Automover

In erratic workloads where key sizes fluctuate, one slab class may run out of memory while another sits largely empty due to deletions. Memcached addresses this imbalance with the Slab Automover thread.

The automover monitors evictions and free space across all classes. If it detects that a specific slab class is suffering heavy evictions while another holds unused pages containing deleted keys, it reassigns entire 1MB pages from the idle slab class to the starved one. This automated rebalancing guarantees that intense churn across changing key sizes does not lead to premature evictions or artificial memory exhaustion.
