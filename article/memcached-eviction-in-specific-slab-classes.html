Memcached Eviction in Specific Slab Classes

Memcached isolates memory allocation by dividing its memory pool into individual slab classes, meaning that memory pressure and item evictions are managed independently within each class rather than across the cache as a whole. When a specific slab class exhausts its allocated space, Memcached applies an isolated Least Recently Used (LRU) policy to remove the oldest items in that class alone. This article explains the internal mechanics of per-slab LRU queues, why localized pressure occurs even if other slabs have free space, and the modern balancing mechanisms Memcached uses to mitigate this issue.

The Slab Allocation Model

Memcached avoids memory fragmentation by pre-allocating memory into 1MB pages and dividing those pages into fixed-size chunks. Each chunk size corresponds to a specific slab class (e.g., class 1 handles items up to 96 bytes, class 2 handles up to 120 bytes, and so on). When an item is stored, Memcached places it into the smallest slab class that can accommodate its data size.

Because items are strictly compartmentalized, each slab class maintains its own distinct memory pool and its own independent LRU list.

Localized Eviction Mechanics

When a write request targets a specific slab class, the following process determines eviction behavior:

  1. Free Chunk Check: Memcached first searches for free or expired chunks within the targeted slab class. If an expired item is found, its space is reused immediately without an eviction.
  2. Page Allocation: If no free chunks exist and the global memory limit has not been reached, Memcached allocates a new 1MB page to this specific slab class.
  3. Per-Slab LRU Eviction: If the global memory limit is exhausted, the slab class cannot acquire a new page. Instead of searching globally for the oldest item across all cached data, Memcached looks strictly at the tail of the target slab class's LRU queue. The oldest item in that specific class is purged to make room for the new record.

Even if other slab classes have millions of unused chunks, traditional Memcached behavior will not allow the starved slab class to claim memory from them on the fly during a set operation.

The Problem of Slab Calcification

This isolated architecture can lead to a condition known as "slab calcification" or "slab imbalance." For example, if an application initially caches millions of 100-byte objects (slab class 1) and later shifts to writing 500-byte objects (slab class 6), slab class 1 keeps its allocated 1MB pages despite no longer receiving traffic.

When slab class 6 fills up, it begins actively evicting items despite significant idle memory residing in slab class 1. The eviction counter (evictions) increments only for the saturated slab class, while the rest of the cache appears underutilized.

Modern Mitigations: Slab Automove and Reassign

To resolve isolated slab pressure without requiring cache flushes, modern versions of Memcached incorporate dynamic page reassignment:

  • Slab Reassign (slabs reassign <source> <target>): An administrative command that manually unbinds a 1MB page from a cold or underutilized slab class and transfers it to a saturated slab class.
  • Slab Automove (-o slab_automove=<mode>): A background maintenance thread that monitors eviction patterns and slab utilization. If it detects that a specific slab class is experiencing sustained evictions while other classes hold dormant pages, it automatically migrates pages to the class experiencing pressure.

Segmented LRU within Slabs

Within each individual slab class, modern Memcached employs a segmented LRU model (divided into HOT, WARM, and COLD queues). New items enter the HOT queue, frequently accessed items are promoted to WARM, and inactive items fall to COLD. When localized memory pressure forces an eviction, only items at the tail of the COLD queue in that specific slab class are evicted, ensuring that frequently accessed items within the active size class remain protected.
