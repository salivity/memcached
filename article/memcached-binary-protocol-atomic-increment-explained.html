Memcached Binary Protocol Atomic Increment Explained

This article provides an overview of how Memcached processes incremental atomic modifications to counter values using its binary protocol. It examines the specific request packet structure, thread locking mechanisms, the arithmetic execution path, boundary conditions such as overflow and key initialization, and the final response structure returned to the client.

Binary Protocol Framing and Extras

Memcached uses dedicated opcodes for counter operations in its binary protocol: 0x05 for Increment (Increment) and 0x06 for Decrement (Decrement). Unlike generic text-mode commands, binary requests use fixed-size header structures and structured extra data fields to execute counter operations efficiently.

An atomic increment request carries an extras section containing three specific fields:

  • Amount (delta): An 8-byte unsigned 64-bit integer specifying the value to add.
  • Initial value: An 8-byte unsigned 64-bit integer indicating the counter's starting value if the target key does not yet exist.
  • Expiration: A 4-byte unsigned integer representing the item’s Time-To-Live (TTL) in seconds if the item is created by this command.

The extras payload is followed immediately by the key identifier in the dynamic body of the packet.

Atomicity and Concurrency Control

When the worker thread receives the binary packet, it extracts the key and computes its hash using the configured hashing algorithm (typically Murmur3 or Jenkins). Memcached enforces atomicity at the item level through granular item locks:

  1. Lock Acquisition: Memcached identifies the hash bucket corresponding to the key and acquires the mutex associated with that bucket or item slice. This stops any concurrent read, update, or delete commands from mutating the state of that key simultaneously.
  2. Key Lookup: With the lock held, the thread searches the primary hash table for the existing item.

Value Evaluation and Mutation Logic

Once the key location is resolved, Memcached evaluates the operation based on whether the key currently exists:

1. When the Key Exists

If the item is present and has not expired, Memcached reads the raw byte value. Counter values in Memcached are internally stored as ASCII string representations of 64-bit unsigned integers:

  • The server validates that the payload can be parsed into a 64-bit unsigned integer. If the existing data is non-numeric, the server rejects the command and returns an error (EINVAL / 0x0004).
  • Memcached parses the numeric value, adds the 8-byte delta, and computes the new value.
  • Overflow Behavior: Increments wrap around automatically using standard 64-bit unsigned integer arithmetic (\(2^{64}-1\) wraps to \(0\)). In contrast, decrements clamp at zero and do not wrap to negative numbers or maximum values.
  • The thread allocates a new item structure to hold the updated ASCII string representing the new counter value, copies over existing metadata (such as flags), generates a new unique Compare-And-Swap (CAS) identifier, inserts the new item into the slab allocator, and frees the old item.

2. When the Key Does Not Exist

If the lookup misses or the existing item has expired:

  • Memcached inspects the 4-byte expiration field sent in the binary extras.
  • If the expiration is set to 0xFFFFFFFF (all bits set), the server treats the request as a strict mutation on existing keys only. It aborts the operation and returns a Key Not Found (0x0001) response status.
  • If the expiration is any other value, Memcached creates a new key. The new item’s value is set directly to the initial value supplied in the request, and its expiration is set according to the provided TTL.

Release and Binary Response

After mutating or creating the item:

  1. The server updates the internal stats counters (e.g., cmd_touch, incr_hits, or incr_misses).
  2. The item lock for the hash bucket is released, allowing subsequent operations on the key.
  3. Memcached constructs a binary response packet containing:
    • Header with status 0x0000 (Success).
    • The newly generated 64-bit CAS ID.
    • An 8-byte binary body representing the updated 64-bit integer counter value encoded in network byte order (big-endian).
