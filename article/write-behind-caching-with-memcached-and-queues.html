Write-Behind Caching with Memcached and Queues

Write-behind (or write-back) caching optimizes database write performance by updating the in-memory cache immediately and offloading the persistent database updates to an asynchronous background worker. This article explains how to design and implement a write-behind caching architecture using Memcached for fast data retrieval and a message queue system (such as RabbitMQ, Apache Kafka, or Redis Streams) to guarantee reliable, deferred persistence to your primary database.

Architecture Overview

In a typical write-behind pattern with Memcached:

  1. Application Write: The client application receives a write request.
  2. Cache Update: The application immediately updates the record in Memcached.
  3. Queue Enqueue: Simultaneously, the application pushes an event containing the mutation details to a message queue.
  4. Immediate Response: The application returns a success response to the client with minimal latency.
  5. Asynchronous Persistence: A background consumer process pulls messages from the queue, batches or debounces the updates, and persists the changes to the primary database.

Because Memcached is purely an in-memory key-value store without native persistence or transactional integration, the message queue acts as the temporary durability layer ensuring updates are not lost if Memcached restarts or evicts keys.

Implementation Steps

1. Structure the Queue Payload

The message sent to the queue should contain sufficient context for the background worker to execute the database write without needing to read back from Memcached. A typical JSON payload includes:

{
  "entity": "user_profile",
  "operation": "UPDATE",
  "primary_key": 48291,
  "data": {
    "display_name": "JaneDoe",
    "status": "active"
  },
  "timestamp": 1710000000
}

2. Handle Application Writes

When an update occurs, update Memcached first, then enqueue the event. If the queue publish fails, invalidate or roll back the Memcached entry to maintain consistency:

def update_user_profile(user_id, updated_data):
    cache_key = f"user:{user_id}"
    
    # 1. Update Memcached
    memcached_client.set(cache_key, updated_data, expire=3600)
    
    # 2. Push mutation event to the message queue
    message = {
        "entity": "user",
        "operation": "UPDATE",
        "primary_key": user_id,
        "data": updated_data,
        "timestamp": time.time()
    }
    
    try:
        queue_client.publish("db_write_queue", message)
    except Exception as e:
        # Prevent dirty cache state if queueing fails
        memcached_client.delete(cache_key)
        raise DatabaseSyncException("Failed to enqueue write operation") from e

3. Build the Asynchronous Consumer

The worker listens to the queue and persists incoming payloads to the database. To maximize database throughput, process messages in micro-batches:

def process_write_queue():
    while True:
        messages = queue_client.fetch_batch("db_write_queue", batch_size=100, timeout=1.0)
        if not messages:
            continue
            
        try:
            # Consolidate updates by primary key to prevent redundant writes
            consolidated_writes = deduplicate_updates(messages)
            
            # Execute batch update inside a database transaction
            db.bulk_update(consolidated_writes)
            
            # Acknowledge messages after successful persistence
            queue_client.ack(messages)
        except Exception as err:
            # Route failed records to a Dead-Letter Queue (DLQ) for inspection
            handle_failure(messages, err)

Critical Production Considerations

Idempotency and Write Ordering

Network retries and concurrent consumers can lead to out-of-order writes. Ensure the database worker only updates a record if the message's timestamp or version is newer than the record currently stored in the database. Alternatively, partition queue topics by entity ID (e.g., Kafka partition keys) to enforce sequential processing for individual records.

Memcached Eviction Handling

Memcached utilizes an LRU (Least Recently Used) eviction policy. If a key is evicted before the worker writes the change to the database, subsequent read operations may query the database and retrieve stale data. Keeping queue processing latency low (sub-second or a few seconds) minimizes this window of inconsistency.

Failure Handling and Dead-Letter Queues (DLQ)

Database outages or schema validation failures will cause consumer writes to fail. Implement an exponential backoff retry mechanism. If a message repeatedly fails, forward it to a dead-letter queue rather than halting the consumer pipeline, allowing developers to manually replay the failed operations.
