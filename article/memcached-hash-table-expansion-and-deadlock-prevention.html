Memcached Hash Table Expansion and Deadlock Prevention

Memcached maintains high-throughput, low-latency caching by scaling its internal data structures concurrently across multiple threads. During periods of heavy data growth, Memcached automatically expands its primary hash table to prevent excessive hash collision chains and degraded lookup performance. To execute this resizing without causing thread deadlocks or stalling client traffic, Memcached relies on an asynchronous maintenance thread, fine-grained lock striping, an incremental bucket migration pointer, and strict lock-ordering rules that eliminate circular wait dependencies.

The Challenge of Hash Table Resizing

In a multithreaded key-value store, resizing an active hash table poses significant synchronization challenges. If worker threads attempting to read, insert, or delete items collide with a thread reallocating the underlying bucket arrays, memory corruption or data races occur.

Conversely, acquiring a global lock over the entire table during the resizing process eliminates concurrency, degrading throughput and potentially causing worker threads to pile up and deadlock if lock hierarchies are violated. Memcached avoids this through an incremental, lock-striped migration architecture.

Asynchronous Maintenance Thread

Memcached offloads the resizing process entirely from worker threads to a dedicated background thread known as the assoc_maintenance_thread.

When the number of stored items exceeds 1.5 times the capacity of the current hash table (a power-of-two bucket count), an expansion flag is set, and the maintenance thread is awakened via a condition variable (pthread_cond_signal). Worker threads never participate directly in reallocating memory or moving items between buckets, isolating the expansion mechanics to a single controlling entity.

Dual-Table State and the Incremental Migration Pointer

When resizing begins, Memcached creates a new hash table that is double the size of the previous one. The current table becomes the old_hashtable, and the newly allocated memory becomes the primary_hashtable.

To avoid holding locks for long durations, migration occurs incrementally:

  1. A global variable, typically named expand_bucket, tracks the index of the bucket currently being moved.
  2. The maintenance thread moves items bucket by bucket, processing a limited batch of buckets per iteration.
  3. Between batches, the maintenance thread can yield execution, allowing worker threads unimpeded access to other areas of the cache.

Eliminating Deadlocks with Lock Striping

Memcached avoids global table locking by employing lock striping across an array of mutexes (known historically as item_locks). Hash values map to specific lock stripes using a bitmask.

Deadlocks typically arise when threads attempt to acquire multiple shared resources in differing orders (violating the Coffman condition for avoiding circular wait). Memcached prevents this using two primary design rules:

1. Single-Lock Acquisition for Worker Threads

Worker threads never acquire multiple item locks simultaneously. When a worker thread needs to look up, insert, or delete an item during an active expansion:

  • It hashes the key to find the corresponding bucket index.
  • It inspects the expand_bucket pointer.
  • If the bucket index is less than expand_bucket, the worker knows the items in that bucket have already migrated, so it routes the query to the primary_hashtable.
  • If the bucket index is greater than or equal to expand_bucket, the worker accesses the old_hashtable.
  • The worker then acquires only the single striped mutex governing that specific bucket in the appropriate table, completes the operation, and releases the lock.

Because worker threads only hold one item lock at any given time, they cannot enter a circular wait state with other worker threads.

2. Isolation of the Maintenance Thread Lock Scope

During migration, the maintenance thread must read from the old bucket and insert into the new bucket. To prevent deadlocks with worker threads:

  • The maintenance thread locks the specific stripe corresponding to the old bucket index being migrated.
  • It safely moves the linked-list chain of items from the old_hashtable bucket to the appropriate buckets in the primary_hashtable.
  • It increments the expand_bucket pointer.
  • It releases the lock stripe immediately after the batch is migrated.

Because the maintenance thread respects the same lock-striping boundaries as the worker threads and only holds the lock for the current slice of migration, no thread ever waits indefinitely for another thread holding a required secondary lock.

Completion of Expansion

Once expand_bucket reaches the total capacity of the old table:

  1. The maintenance thread acquires the global hash table lock to finalize the transition.
  2. The old_hashtable reference is cleared and its memory freed.
  3. The expansion flag is reset, returning Memcached to single-table operation until the next threshold trigger.

By combining background execution, granular lock striping, and single-lock invariants during table lookups, Memcached guarantees uninterrupted thread progress and complete deadlock prevention during table expansion operations.
