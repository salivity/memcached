How Memcached Prevents Memory Exhaustion

Memcached protects itself from catastrophic memory exhaustion during unexpected traffic surges through a combination of strict memory capping, a pre-allocated slab allocation architecture, and automated Least Recently Used (LRU) eviction mechanisms. Instead of continuously requesting dynamic memory from the host operating system as incoming data spikes, Memcached operates within a rigid, user-defined memory ceiling, actively pruning stale or lower-priority cached items and limiting socket allocations to ensure the daemon never triggers the operating system's Out-Of-Memory (OOM) killer.

Hard Memory Ceilings via Slab Allocation

When Memcached starts, the operator assigns it a fixed maximum memory limit using the -m flag. Memcached enforces this boundary by utilizing a custom memory management system known as the Slab Allocator, rather than relying on standard system calls like malloc and free for every write operation.

The slab allocator divides the reserved memory pool into 1-megabyte pages, which are further divided into chunks of predetermined sizes (slab classes) tailored to fit various data payloads. Because all operational memory is pre-reserved and managed internally, Memcached avoids memory fragmentation and is physically incapable of allocating more system RAM than configured, regardless of how many write requests arrive simultaneously.

The Segmented LRU Eviction Engine

When an unexpected traffic spike fills a specific slab class to maximum capacity, Memcached does not crash or reject new items by default. Instead, it triggers its Least Recently Used (LRU) eviction algorithm to overwrite existing data.

Modern versions of Memcached use a segmented LRU system divided into distinct queues:

  • HOT: New items enter here. Items in this queue are never bumped to the head on read hits; they simply age out into the WARM queue.
  • WARM: Stores items that have had sustained read activity.
  • COLD: Items that fall out of HOT or WARM land here. When memory is full, the tail of the COLD queue is evicted first to make space for incoming traffic.

This segmented design prevents sudden bursts of new, single-use keys from wiping out frequently accessed hot data, allowing the cache to absorb high write volumes while preserving vital working sets.

Lazy Expiration and Background Reclaiming

Memcached implements "lazy expiration," meaning it does not actively scan millions of keys to see if their Time-To-Live (TTL) has passed. Instead, it checks the expiration timestamp only when an item is requested. If an expired item is read, Memcached immediately purges it and frees the chunk.

To handle cases where expired items are never read again during traffic surges, a background maintenance thread called the LRU Crawler continuously scans slab classes, identifies dead items, and reclaims their memory before forced evictions of active keys become necessary.

Dynamic Slab Reassignment

Traffic spikes often introduce payloads of varying sizes that do not match the historical distribution of slab classes. In older architectures, this caused "slabcalc exhaustion," where one slab class ran out of memory while others remained empty. Modern Memcached includes an automated slab reassignment engine (Slab Automove). If it detects that a specific slab class is suffering from heavy evictions while another sits idle, it dynamically unbinds pages from the idle class and reassigns them to the exhausted class.

Connection Throttling and Network Limits

Catastrophic memory failures during traffic spikes are not only caused by cached data; thousands of concurrent incoming TCP connections can also consume massive amounts of kernel and buffer memory.

Memcached uses an event-driven networking model powered by libevent and enforces a hard limit on open connections (configured via the -c flag). When traffic surges push the concurrent connection count to this limit, Memcached stops accepting new socket requests rather than allocating additional buffer memory. Once active requests complete and connections close, the server resumes accepting new traffic, maintaining stability under extreme load.
