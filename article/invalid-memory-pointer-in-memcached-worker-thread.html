Invalid Memory Pointer in Memcached Worker Thread

When a Memcached worker thread encounters an invalid memory pointer during request handling, the operating system immediately issues a segmentation fault (SIGSEGV), which crashes the entire Memcached process rather than isolating the single failed thread. Because Memcached is written in C and utilizes a shared-memory, multi-threaded architecture without per-thread memory isolation, dereferencing a bad pointer triggers fatal process termination, causing all connected clients to be abruptly disconnected and resulting in the complete loss of all in-memory cached data.

Hardware Exception and Signal Generation

Memcached uses a multi-threaded model where worker threads process read and write commands (such as get, set, and delete) assigned by a main dispatcher thread. If a worker thread attempts to read from or write to an invalid address—such as a null pointer, an unmapped address, a pointer to freed memory (use-after-free), or a corrupted slab memory reference—the CPU's Memory Management Unit (MMU) fails to translate the virtual address into a valid physical address.

This triggers a hardware-level page fault exception. The operating system kernel intercepts this fault, identifies that the memory access violates process permissions, and sends a termination signal—typically SIGSEGV (signal 11) or rarely SIGBUS (signal 7)—to the Memcached process.

Entire Process Termination

Although the error occurs inside a single worker thread, POSIX threads (pthreads) share the same address space. Memcached intentionally does not catch SIGSEGV to recover individual threads for several critical reasons:

  • State Undefined: A corrupted pointer indicates that memory integrity has been compromised. Continuing execution could corrupt the internal slab allocator, hash tables, or LRU lists.
  • Lack of Isolation: Threads operate directly on shared data structures protected by locks. If a thread crashes while holding a lock (such as an item lock or the global hash table lock), any other thread waiting on that lock would deadlock.

Because the signal is unhandled, the default kernel action is executed: the entire Memcached process terminates immediately.

Client-Side Consequences

The sudden termination of the Memcached process impacts all active client connections:

  1. Abrupt Connection Drop: The kernel closes all open file descriptors associated with the process, sending TCP RST (Reset) or FIN packets to all connected clients.
  2. Read/Write Failures: Clients with in-flight requests experience immediate socket read errors, timeouts, or broken pipe exceptions.
  3. Cache Stampede (Thundering Herd): When the instance crashes, subsequent application queries fail over to the primary database. If the cache layer is heavily relied upon, this sudden flood of database queries can lead to backend saturation.

Complete Loss of Cached Data

Memcached is purely an in-memory key-value store with no default disk persistence mechanism. When the process crashes, the entire virtual address space allocated to the slab engine and hash tables is reclaimed by the operating system. When the service restarts, it starts completely empty, requiring the cache to be repopulated from scratch.

Diagnostics and Recovery

When an invalid pointer crash occurs, the environment handles the failure based on its configuration:

  • Core Dumps: If system limits (ulimit -c) allow it, the kernel writes a core dump file containing the process memory state at the moment of the crash. Engineers can load this file into GDB (gdb /usr/bin/memcached core) to inspect the stack trace and identify the exact line of code and pointer value responsible.
  • Process Supervisors: In modern production environments, supervisors such as systemd, supervisord, or container orchestrators (like Kubernetes or Docker) detect the nonzero exit code and automatically restart the Memcached container or service, restoring network availability with an empty cache.
