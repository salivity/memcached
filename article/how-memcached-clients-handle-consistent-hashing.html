How Memcached Clients Handle Consistent Hashing

When scaling a Memcached cluster horizontally, adding or removing servers risks triggering a catastrophic cache stampede if key distribution is not managed properly. To solve this, modern Memcached client libraries implement consistent hashing algorithms—most notably libketama—which distribute keys across a logical continuum rather than relying on the total server count. This overview explores how client-side hashing rings, virtual nodes, and minimal key remapping ensure that altering cluster capacity invalidates only a tiny fraction of cached data, preserving database integrity and application performance.

The Limitation of Modulo Hashing

Traditional server selection uses a simple modulo operation: hash(key) % N, where N is the number of servers in the cluster. While simple and fast, this approach fails dynamically. When a single server is added or removed, N changes, causing almost every key in the cache to resolve to a completely different server index. This invalidates roughly N / (N + 1) of all cached keys, suddenly exposing the underlying primary database to massive, unthrottled traffic.

The Consistent Hash Ring

Because Memcached follows a shared-nothing architecture, servers do not communicate with each other; routing is handled entirely on the client side. Client libraries solve the modulo problem by using consistent hashing, typically mapped onto an abstract circular keyspace ranging from \(0\) to \(2^{32}-1\) (a 32-bit integer range).

  1. Mapping Servers: The client hashes the identifier (such as IP address and port) of each configured server onto points along this 360-degree ring.
  2. Mapping Keys: When performing a read or write operation, the client hashes the cache key using algorithms like MD5 or MurmurHash to place it on the exact same ring.
  3. Resolving Targets: The client moves clockwise from the key's position until it encounters the first server point. That server becomes the designated target for storing or retrieving the value.

Virtual Nodes (Weighting and Uniformity)

A basic hash ring can lead to non-uniform distribution (hot spots), where one server handles significantly more keys than others. To prevent this, client libraries implement "virtual nodes" (vnodes).

Instead of placing a server on the ring once, the library hashes each server multiple times (often 100 to 160 tokens per physical machine) using modified strings like server_ip:port-0, server_ip:port-1, and so on. These virtual nodes are interspersed randomly throughout the ring. This balances the distribution of keys evenly across all available hardware and allows administrators to allocate higher weights to servers with larger RAM allocations by assigning them more virtual nodes.

Adding a Server

When a new server is introduced to the cluster configuration, the client adds its corresponding virtual nodes to the hash ring. Only the keys located immediately counter-clockwise from the new server's virtual nodes are affected.

Because these keys now encounter the newly added server first when moving clockwise, they map to the new instance. The rest of the keys continue resolving to their existing servers uninterrupted. Statistically, adding a node only remaps \(K / (N + 1)\) keys (where \(K\) is the total key count and \(N\) is the original number of servers), eliminating cluster-wide cache invalidation.

Removing or Losing a Server

When a server is decommissioned or fails, the client library removes its virtual nodes from the ring. Keys that previously mapped to the removed server simply continue moving clockwise along the ring until they encounter the next operational virtual node.

The keys previously assigned to the dead node will register as cache misses on the newly designated node and must be refetched from the database. However, the data stored on all other unaffected nodes remains valid, localized, and instantly accessible, maintaining cluster stability.
