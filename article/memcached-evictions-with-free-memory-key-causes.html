Memcached Evictions with Free Memory: Key Causes

Memcached instances often report unexpected item evictions even when total system or process memory appears readily available. This counterintuitive behavior occurs primarily because Memcached does not manage memory as a single contiguous pool, but rather through a rigid chunk-allocation architecture. This article breaks down the primary technical causes of unexpected evictions under free memory conditions, explaining the internal mechanisms of slab classes, the limits of the Least Recently Used (LRU) algorithm, and configuration bottlenecks.

1. Slab Class Memory Exhaustion

Memcached uses a slab allocation mechanism to prevent memory fragmentation. Memory is partitioned into 1MB pages, which are assigned to specific "slab classes." Each slab class handles items within a predefined byte-size range using fixed-size chunks.

  • Independent Allocations: Once a 1MB memory page is assigned to a specific slab class (e.g., Slab Class 10 for items up to 1KB), that memory is locked to that class.
  • Localized Evictions: If Slab Class 10 fills up and a new 1KB item arrives, Memcached must evict an older item from Slab Class 10, even if Slab Class 20 (for 8KB items) has hundreds of megabytes of completely unused memory.

2. Workload Shifts and Inactive Slabs

When an application's data profile changes over time, older memory pages often remain trapped in obsolete slab classes:

  • If an application initially caches millions of 200-byte objects, Memcached allocates most of its memory to small-chunk slabs.
  • If a code update shifts the average object size to 1.5KB, Memcached quickly exhausts the few pages assigned to the larger slab class.
  • Because the older, smaller pages are already claimed and hold valid (or unexpired) data, Memcached evicts keys within the larger slab class rather than consuming unused capacity locked elsewhere.

3. Disabled or Ineffective Slab Automove

Memcached includes a feature to rebalance pages across slab classes dynamically (slab_automove), but it has limitations:

  • Default Settings: In some versions or configurations, slab_reassign and slab_automove are disabled by default. Without dynamic reassignment, a slab class cannot steal unused pages from other classes.
  • Conservative Automove Algorithms: Even when enabled (e.g., slab_automove=1 or 2), the rebalancing thread acts conservatively to prevent performance spikes. If an influx of writes exceeds the speed at which pages can be unmapped and reassigned, evictions will occur before rebalancing can catch up.

4. Per-Slab LRU Eviction Logic

Evictions in Memcached are evaluated locally, not globally:

  • Each slab class maintains its own LRU queue.
  • Memcached does not search globally for the oldest overall key across the entire server to evict.
  • As long as a specific slab class runs out of free chunks within its allocated pages, it immediately triggers an eviction at the tail of its own local LRU list, disregarding whether total instance memory usage is far below the -m (maximum memory) threshold.

5. Premature Evictions via the Modern Segmented LRU

Modern versions of Memcached feature a segmented LRU (HOT, WARM, COLD, and TEMP queues) to avoid lock contention and protect frequently read items:

  • Items enter the HOT or WARM queues based on access patterns.
  • Under heavy write loads, if the background maintainer thread cannot migrate items between queues quickly enough, items may drop out of the COLD queue of an active slab class prematurely, even if total RAM metrics suggest idle headroom.

Diagnostic Verification

To identify which slab class is suffering from premature evictions, run the following commands via telnet or nc:

  • stats slabs: Displays page distribution, chunk sizing, and eviction counts broken down per individual slab class. Look for high eviction numbers isolated to specific slab IDs.
  • stats items: Shows detailed LRU status, expired items, and age of the oldest evicted items for each slab class.
