Memcached Stats Items: Troubleshoot Memory Usage

The stats items command is a vital diagnostic tool for investigating Memcached memory allocation, cache turnover, and data loss. Memcached manages memory using a slab allocation system, grouping data into distinct classes based on chunk size. This article explains how the stats items command breaks down item storage across these individual slab classes, why metrics like evictions and item age are critical for diagnosing memory pressure, and how to use this data to optimize cache performance.

Understanding the Role of stats items

When troubleshooting memory issues in Memcached, server-wide statistics via stats only provide a high-level picture of overall usage. Memcached avoids operating system memory fragmentation by allocating memory into 1MB pages, which are then subdivided into chunks of fixed sizes called slab classes.

Because memory is tied up inside specific slabs, a server may report free global memory while an individual slab class is completely full and evicting items. The stats items command exposes the internal telemetry of each slab class, allowing administrators to pinpoint precisely where memory exhaustion occurs.

Critical Metrics Exposed by stats items

The command outputs statistics prefixed by STAT items:<slab_id>:<metric>. When troubleshooting memory bottlenecks, focus on these primary fields:

  • number: The total count of active items currently stored in the specified slab class. Tracking this shows which object sizes dominate your cache.
  • age: The age, in seconds, of the oldest item in the slab's Least Recently Used (LRU) queue. A very low age relative to expected item Time-To-Live (TTL) indicates rapid cache turnover.
  • evicted: The cumulative count of valid items forcibly removed before their TTL expired to make room for new writes. Any non-zero or rapidly increasing eviction count indicates that this specific slab class is out of memory.
  • evicted_nonzero: The number of times an item with an explicit expiration time was evicted.
  • evicted_time: The seconds elapsed between an evicted item’s creation and its eviction. A low value indicates critical memory starvation for that chunk size.
  • outofmemory: Tracks instances where the engine failed to allocate memory for a write (typically relevant if the -M flag is used to disable automatic evictions).

Diagnosing Memory Problems

Identifying Slab Imbalance and Calcification

Memcached assigns 1MB memory pages to slab classes on demand. Historically, once a page was assigned to a slab class, it could not be reassigned. The stats items command helps detect this "slab calcification" pattern: if one slab class reports zero evictions with a high item age, while another class shows millions of evictions and an age of only a few seconds, the cache memory is distributed disproportionately to the workload.

Pinpointing Inefficient Chunk Sizing

Comparing the item counts across slabs reveals the size distribution of cached objects. If items are clustering heavily in higher slab classes unexpectedly, application payloads may have grown. This bloat requires larger chunk sizes, which consume slab pages much faster and lead to premature evictions.

Remediation Strategies Based on Diagnostic Data

Once stats items identifies the distressed slab classes, apply targeted adjustments:

  1. Enable Slab Automove: If using modern Memcached versions, enable automatic page reassignment (slab_automove=1 or slab_automove=2 via stats settings or startup arguments). This allows Memcached to reclaim memory pages from cold slabs and assign them to the starving slabs identified by your eviction stats.
  2. Tune the Growth Factor: If data sizes are clustering inefficiently, alter the -f (slab growth factor) setting. A smaller growth factor (e.g., 1.1 instead of the default 1.25) creates more slab classes with finer size increments, reducing wasted internal padding within chunks.
  3. Optimize Application Serialization: If a specific slab shows continuous eviction spikes, inspect the application keys stored in that size bracket. Applying compression or stripping unnecessary metadata from the payload can drop the items into smaller, less contested slab classes.
