Memcached Touch Command: Extending Key Expiration

This article explains the function and operational mechanics of the touch command in Memcached, focusing on how it extends the time-to-live (TTL) of cached keys without reading or modifying their underlying data. It highlights how this command eliminates unnecessary network transfer, prevents race conditions, and simplifies the implementation of sliding expiration windows for high-traffic applications.

The Purpose of the Touch Command

In Memcached, every stored item can be assigned an expiration time after which it is considered invalid and eligible for eviction. By default, updating this expiration time using commands like set requires sending both the key and its entire data payload over the network.

The touch command solves this problem by updating the expiration timestamp directly in the item's metadata without modifying, retrieving, or re-transmitting the stored value.

How the Touch Command Works

When a client issues a touch command, Memcached locates the item in memory via its key and updates its internal expiration attribute.

  • No Value Transfer: The client does not need to send the value, nor does the server return the value. Only the key and the new expiration parameter are sent.
  • In-Memory Modification: The operation changes only the internal expiration timer. The value payload and any flags associated with the key remain unchanged.
  • Eviction Prevention: By resetting the item's lifetime, the item remains active and protected from passive expiration or LRU (Least Recently Used) cleanup routines for an extended duration.

Syntax and Implementation

The text protocol syntax for the touch command is straightforward:

touch <key> <exptime> [noreply]\r\n
  • <key>: The identifier of the stored item.
  • <exptime>: The new expiration time, either as a relative time in seconds from the current moment (up to 30 days) or as an absolute Unix timestamp.
  • [noreply]: An optional parameter instructing the server not to send a response, reducing round-trip latency.

The server responds with TOUCHED\r\n if the item was successfully updated, or NOT_FOUND\r\n if the key does not exist or has already expired.

Advantages Over Read-and-Rewrite Patterns

Prior to the introduction of touch, extending a key's lifespan required fetching the data (get), modifying the expiration locally, and saving it back (set). Using touch provides several distinct advantages:

  1. Bandwidth Optimization: Large payloads (e.g., serialized objects or cached HTML fragments) do not cross the network merely to keep the key alive.
  2. Atomic Extension: The operation is isolated and direct. Unlike a get followed by a set, touch does not risk overwriting changes made by another process in a concurrent environment.
  3. Reduced Latency and Server Load: Because no memory allocation, deallocation, or large data transfers take place, Memcached processes the request with minimal CPU and I/O overhead.

Common Use Cases

The most frequent use of the touch command is the implementation of sliding session windows. In web applications, user sessions typically remain active as long as the user continues to interact with the service. Rather than querying the session state and rewriting it on every HTTP request, an application can issue a touch call (or a gat—get-and-touch—command if reading the session is also required) to effortlessly extend the user's active window.
