Memcached Append on Non-Existent Keys

This article explains how Memcached handles the append command when the target key is not present in the cache. In short, Memcached will not create a new key-value pair if the key is missing; instead, it rejects the operation and returns a NOT_STORED response code. Understanding this behavior is essential for preventing silent cache misses and ensuring proper state management in application caching layers.

In the Memcached protocol, the append command is strictly an update mechanism rather than an upsert. Its purpose is to attach raw data to the end of an already existing key's value. Because the command is designed solely to modify existing records, it requires a pre-existing target to execute successfully.

When a client sends an append request, Memcached checks its internal hash table for the specified key. If the lookup determines that the key does not exist, or has already expired due to its time-to-live (TTL), the server terminates the operation immediately. In the ASCII text protocol, the server responds with:

NOT_STORED

In the binary protocol, Memcached returns a status code of 0x0005 (KEY_ENOENT), indicating that the key was not found.

The reason for this behavior lies in how Memcached manages metadata. Every stored item requires operational flags and an expiration time. The append command syntax does not include parameters to specify these metadata fields; instead, it retains the flags and TTL of the original item. If Memcached were to create a new key upon an append attempt, it would have no valid TTL or flag definitions to assign to the new entry.

To handle cases where a key may not yet exist, applications should implement fallback logic. When an append operation returns NOT_STORED, the application should catch this response and initialize the key using a standard add or set command with the appropriate data, flags, and expiration time.
