How Memcached Handles Expiration During Clock Drift

This article explains how Memcached manages item expiration and the direct impact of host machine clock drift on cached data. Memcached relies on internal time calculations converted into absolute timestamps to determine item validity. When host clocks drift or suddenly jump due to synchronization adjustments, Memcached will either expire items prematurely or serve stale data for longer than intended. Understanding the mechanisms behind TTL interpretation, internal time loops, and clock drift mitigations is essential for maintaining reliable caching layers.

Expiration Time Representation: Relative vs. Absolute

Memcached accepts expiration times (Time-To-Live, or TTL) in two formats based on a 30-day threshold (2,592,000 seconds):

  • Relative Offsets: If a client provides a TTL of 2,592,000 seconds or fewer, Memcached treats the value as an offset from the current moment.
  • Absolute Timestamps: If the supplied value is greater than 2,592,000, Memcached interprets it as a standard Unix epoch timestamp (seconds since January 1, 1970).

Internally, Memcached does not retain relative counters. When an item with a relative offset is stored, the daemon calculates an absolute expiration time by adding the offset to its current concept of the system time. Consequently, all items in memory ultimately hold an absolute epoch timestamp representing their moment of expiry.

Internal Time Management

Calling system-level time functions like gettimeofday() or clock_gettime() on every read or write request would introduce unnecessary kernel overhead. To maintain high throughput, Memcached maintains a global internal clock variable within its event loop. A periodic timer updates this cached time approximately once per second using the host system’s clock (CLOCK_REALTIME).

When an item is requested via a get command, Memcached compares the item's stored expiration timestamp against this internal clock variable. If the current internal time is equal to or greater than the item's expiration timestamp, the item is considered expired, discarded, and treated as a cache miss.

The Impact of System Clock Drift

Because all expirations resolve to absolute timestamps derived from the host's real-time clock, any drift or sudden shift in the host machine's system time directly alters expiration behavior.

Forward Clock Drift

If the host clock drifts forward—or if an NTP synchronization steps the time forward—the internal time variable advances ahead of real-world time.

  • Premature Expiration: Items with absolute expiration timestamps that should still be valid suddenly appear expired when evaluated against the advanced clock.
  • Immediate Purging: Cached values may vanish before their intended lifecycle finishes, leading to sudden cache misses and unexpected load spikes on backend databases.

Backward Clock Drift

If the host clock drifts backward—or steps backward after correcting a previous forward error—the internal time variable rolls back.

  • Stale Data Retention: Items scheduled to expire will remain valid longer than intended. Because the current time is now lower than the stored expiration timestamp, Memcached continues to serve stale records that should have expired.
  • Infinite or Broken Expirations: If an item is stored with an absolute timestamp that is now far in the future due to an uncorrected backward jump, it may persist until pushed out by memory exhaustion.

Passive Expiration and Memory Reclamation

Memcached primarily utilizes passive (lazy) expiration. It does not actively hunt for expired keys across the entire memory space unless the LRU (Least Recently Used) crawler is explicitly enabled and running.

When clock drift alters expiration states:

  • If the clock jumps forward, memory is not freed immediately for all expired keys; instead, each key is evicted individually upon its next access attempt.
  • If memory becomes full before expired keys are requested, Memcached relies on its LRU eviction policy to overwrite the least recently accessed items, regardless of whether clock drift has extended or shortened their validity.

Mitigating Clock Drift Issues

Because Memcached does not independently verify time against external sources or use monotonic clocks for Unix-based TTLs, stability depends entirely on the host operating system's timekeeping configuration.

  1. Use Time Slewing Over Stepping: Configure NTP daemons (such as chrony or ntpd) to slew the clock smoothly rather than stepping it abruptly. Slewing adjusts clock frequency gradually, preventing large, discontinuous time jumps that disrupt expiration checks.
  2. Apply Consistent Client Formats: Standardize whether application clients send relative offsets or absolute Unix timestamps. Relative offsets reduce the window of vulnerability to the moments surrounding the set operation, whereas mismatched system clocks on client machines sending absolute timestamps can immediately corrupt cache validity.
  3. Monitor Host Time Drift: Implement alerting for clock offsets across all cache cluster nodes to detect and correct synchronization drift before it causes noticeable cache churn or stale read anomalies.
