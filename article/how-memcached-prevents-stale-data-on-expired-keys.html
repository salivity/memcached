How Memcached Prevents Stale Data on Expired Keys

Memcached prevents the retrieval of stale data primarily through a passive mechanism known as lazy expiration, coupled with immediate timestamp validation during read operations. Rather than running intensive background processes to constantly purge out-of-date records, Memcached validates the life of a key at the exact moment a retrieval request is made. This article explains how Memcached evaluates key expiration, ensures zero stale reads, and manages memory reclamation for expired items that are never accessed again.

Lazy Expiration and Read-Time Verification

When a key-value pair is stored in Memcached with an expiration time (Time-To-Live, or TTL), Memcached computes and stores an absolute expiration timestamp alongside the item's metadata.

When a client sends a retrieval command—such as get or gets—Memcached performs the following steps before returning any data:

  1. Lookup: The server locates the item in the hash table.
  2. Timestamp Comparison: Memcached inspects the item's expiration timestamp and compares it to the current server time.
  3. Validation Outcome:
    • If the current time is less than the expiration timestamp, the data is valid and returned to the client.
    • If the current time is equal to or greater than the expiration timestamp, Memcached immediately treats the item as non-existent.

Because this validation occurs prior to returning any payload to the network buffer, an expired key will never be returned to the client. Instead, the server returns a cache miss (NOT_FOUND).

Immediate Memory Invalidation

Once a key is determined to be expired during a read operation, Memcached does not merely mask the data; it actively unlinks the item from the internal hash table and the Least Recently Used (LRU) list. The memory chunk allocated to that item within the slab allocator becomes immediately available for future writes, ensuring that expired records cease to consume logical address space as soon as they are encountered.

Handling Expired Keys That Are Never Requested

Because expiration checks are lazy, keys that expire and are never queried again will remain in memory. Memcached handles these untouched, expired records without returning stale data through two secondary mechanisms:

  • LRU Eviction: When a slab class runs out of memory to store new entries, Memcached searches the tail of the LRU queue. If it encounters an expired item, it frees that item immediately and reuses the memory slab for the new data without incrementing the eviction counter. If no expired items are found, the oldest active item is evicted.
  • The LRU Crawler: Modern versions of Memcached include an optional background thread called the LRU Crawler. This thread slowly traverses the memory slabs to find and free expired items proactively, reclaiming memory without waiting for a read miss or an LRU replacement event.

TTL Format and Clock Sensitivity

To ensure expiration accuracy, Memcached interprets TTL values based on their magnitude:

  • Relative Time: Values up to 30 days (2,592,000 seconds) are treated as relative offsets from the current Unix timestamp.
  • Absolute Time: Values greater than 30 days are treated as absolute Unix epoch timestamps.

Because all expiration decisions rely on comparisons against the host's system clock, ensuring that server clocks remain synchronized via NTP (Network Time Protocol) is critical to maintaining accurate expiration enforcement across distributed cache clusters.
