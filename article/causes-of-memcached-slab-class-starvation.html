Causes of Memcached Slab Class Starvation

Slab class starvation occurs in Memcached when an application with varying payload distributions exhausts memory in specific slab classes while other classes retain underutilized space, resulting in unexpected cache evictions and degraded hit rates. Memcached’s slab allocation model separates memory into rigid, class-specific pools to eliminate external memory fragmentation. However, when workload characteristics shift or an application writes a diverse mix of object sizes, this rigid partitioning causes localized memory pressure. This article details how Memcached manages memory, why uneven item sizes trigger slab class starvation, and the primary mechanisms responsible for this performance bottleneck.

The Mechanics of Slab Allocation

Memcached manages memory by dividing its total allocated pool into 1MB pages. These pages are assigned to specific "slab classes," where each class is configured to store chunks of a specific maximum size based on a geometric growth factor (defaulting to 1.25). For example, Slab Class 1 might hold items up to 96 bytes, Slab Class 2 holds items up to 120 bytes, and so on.

When a new item arrives, Memcached finds the smallest slab class that can accommodate the item's payload and associated metadata. If that slab class has no free chunks, Memcached requests a new 1MB page from the global memory pool, slices it into chunks of that class's size, and stores the object.

Why Varying Payload Distributions Cause Starvation

In an ideal, static workload, memory pages are distributed proportionally to the frequency of payload sizes. However, dynamic applications with varying payload distributions create severe imbalances through the following mechanisms:

1. Permanent Page Allocation and Inelasticity

Once a 1MB page is assigned to a specific slab class, it historically remains tied to that class for the lifetime of the process. If an application initially generates a high volume of small payloads (e.g., 100-byte session tokens), Memcached allocates most of its 1MB pages to the smaller slab classes. If the application's traffic profile shifts toward larger payloads (e.g., 4KB serialized objects), the larger slab classes quickly consume any remaining free global pages. Once the global pool is empty, the larger slab class cannot claim pages from the smaller slab classes, even if those smaller classes are idle or contain stale data.

2. Class-Local LRU Evictions

Memcached does not use a single, global Least Recently Used (LRU) queue across the entire instance. Instead, each slab class maintains its own distinct LRU list. When a slab class exhausts its allocated chunks and no free 1MB pages remain in the global pool, Memcached immediately triggers an LRU eviction within that specific slab class.

As a result, an application with fluctuating object sizes will experience premature evictions in the starved slab class. Frequently accessed items in the stressed class will be discarded while dormant, rarely accessed items in over-allocated slab classes sit untouched.

3. Internal Fragmentation and Chunk Spacing

The growth factor between slab classes determines the step size between chunk capacities. If an application writes items that consistently fall just above a slab class boundary, those items are forced into the next larger class. For example, an object that is 1 byte larger than Slab Class 5's chunk limit will be placed into Slab Class 6, leaving a substantial portion of that chunk empty. This internal fragmentation accelerates page consumption in larger slab classes, hastening starvation when payloads fluctuate around these boundaries.

4. Asymmetrical Key Lifetimes

Varying payload sizes often correspond to different data types with different Time-to-Live (TTL) values. For instance, large bulk-query results might have short TTLs, while small configuration strings have long TTLs. If short-lived, large items arrive in bursty waves, they can trigger rapid page consumption in their respective slab classes. Once the global allocation limit is reached, sudden spikes in traffic for those larger payloads cause severe eviction loops within those specific classes, even though the total memory occupied by expired chunks throughout the server could easily accommodate the incoming data.
