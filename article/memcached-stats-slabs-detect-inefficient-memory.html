Memcached Stats Slabs: Detect Inefficient Memory

Memcached organizes memory into slab classes with fixed-size chunks, but poor sizing factors or mismatched item distributions can lead to significant memory waste. The stats slabs command exposes low-level allocation telemetry for each slab class, allowing administrators to diagnose both internal chunk fragmentation and stranded memory. This article breaks down the essential metrics provided by stats slabs—specifically mem_requested, used_chunks, total_chunks, and free_chunks—and explains how to use them to identify and resolve inefficient memory utilization.

1. mem_requested vs. Allocated Chunk Capacity (Internal Fragmentation)

Internal fragmentation occurs when stored data is substantially smaller than the chunk size of the slab class holding it.

  • mem_requested: The exact number of bytes used by stored keys, values, and flags within a specific slab class.
  • chunk_size: The fixed byte size allocated to every item assigned to that slab class.
  • used_chunks: The number of chunks actively storing data.

To detect internal fragmentation, compare the total allocated chunk capacity against the actual requested memory:

\[\text{Wasted Chunk Bytes} = (\text{used\_chunks} \times \text{chunk\_size}) - \text{mem\_requested}\]

If mem_requested is significantly lower than used_chunks * chunk_size, items are wasting the tail end of their assigned chunks. This usually indicates that the chunk growth factor (the -f configuration flag) is too aggressive, resulting in wide gaps between slab sizes.

2. free_chunks and free_chunks_end (Stranded Slab Capacity)

Memcached allocates memory in 1 MB pages. Once a page is assigned to a slab class, it remains dedicated to that chunk size by default.

  • total_chunks: Total capacity of the slab class across all allocated pages (total_pages * chunks_per_page).
  • free_chunks: Chunks that were previously used but have been freed (via deletions or expirations) and are waiting for new data.
  • free_chunks_end: Chunks at the end of the most recently allocated 1 MB page that have never been written to.

A consistently high ratio of free_chunks + free_chunks_end to total_chunks in a specific slab class means memory is locked up and unavailable to other slab classes that might be starved. If other slab classes are actively evicting items while one slab maintains a large pool of free chunks, you are experiencing slab calcification.

3. total_pages vs. Working Set Distribution

  • total_pages: The number of 1 MB pages permanently allocated to the slab class.

Examining total_pages across all active slab classes reveals your memory footprint distribution. If slabs with large chunk sizes consume a disproportionate number of pages but have low read/write activity, large items are monopolizing memory that could be better utilized by high-frequency, smaller items.

Key Remediation Steps

  • Adjust Chunk Growth Factor (-f): If mem_requested reveals high internal fragmentation, lower the growth factor (e.g., from the default 1.25 down to 1.1 or 1.05) to create slab classes closer in size to your actual payload sizes.
  • Enable Dynamic Slab Reassignment: If you notice stranded free_chunks alongside evictions in other classes, run Memcached with -o slab_reassign,slab_automove=1 (or 2) to allow the engine to automatically move unused memory pages to slab classes facing eviction pressure.
