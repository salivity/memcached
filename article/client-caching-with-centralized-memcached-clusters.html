Client Caching with Centralized Memcached Clusters

In high-throughput microservices architectures, combining client-side (in-process) caching with a centralized Memcached cluster creates a two-tier caching strategy that drastically reduces latency and network overhead. This article explains how client-side L1 caches operate alongside centralized L2 Memcached clusters, outlining the read and write paths, cache invalidation mechanisms, and strategies for managing data consistency across distributed services.

The Two-Tier Architecture: L1 and L2

A multi-tier caching architecture balances speed and resource distribution:

  • L1 (Client-Side Cache): Stored directly in the memory space of the microservice instance (e.g., using Guava, Caffeine, or a local dictionary). Access takes nanoseconds because it bypasses the network completely.
  • L2 (Centralized Memcached Cluster): A shared, distributed caching layer accessible by all microservice instances over the network. Access typically takes 1 to 5 milliseconds. It holds a larger volume of data and prevents duplicated storage across multiple application instances.

The Read Path

When a microservice requests data, it executes a tiered lookup sequence:

  1. L1 Query: The service first checks its local memory. If a cache hit occurs, the data is returned immediately without network I/O.
  2. L2 Query: On an L1 miss, the client library contacts the centralized Memcached cluster using consistent hashing to locate the appropriate node. If found, the service populates its local L1 cache with the retrieved value before returning it.
  3. Source of Truth: If both L1 and L2 miss, the service queries the underlying database or downstream service. The retrieved data is then written asynchronously to both the centralized Memcached cluster and the local L1 cache.

The Write Path and Invalidation Strategies

Maintaining consistency between the local memory of multiple service replicas and a central Memcached cluster is the primary engineering challenge. Writes are generally handled using the following patterns:

1. Central Invalidation with Short Local TTLs

The microservice updates the database and immediately deletes the key in the central Memcached cluster. Instead of coordinating complex broadcast invalidations to every running instance, the L1 caches rely on aggressive, short Time-To-Live (TTL) values (e.g., 5 to 30 seconds). While this introduces a small window of eventual consistency, it minimizes system complexity and overhead.

2. Event-Driven Eviction (Pub/Sub)

For systems requiring tighter consistency, an update triggers an event via a message broker (such as Apache Kafka, RabbitMQ, or Redis Pub/Sub):

  1. The mutating service updates the database and evicts the key from Memcached.
  2. The mutating service publishes a cache-invalidate event containing the target key.
  3. All microservice instances subscribe to this topic and invalidate their local L1 caches upon receiving the message.

3. Change Data Capture (CDC)

Using tools like Debezium, database transaction logs are streamed directly to an invalidation pipeline. A dedicated consumer intercepts the changes, deletes stale entries from Memcached, and broadcasts invalidation commands to the microservices to clear their L1 tiers.

Mitigating Stampedes and Hotkeys

Centralized Memcached clusters can experience bottlenecks when thousands of service pods request the same "hotkey" simultaneously. The client-side L1 cache absorbs this traffic entirely, ensuring the centralized Memcached nodes do not suffer from network saturation or CPU spikes.

To prevent cache stampedes when an L1 and L2 entry expires simultaneously, clients often implement probabilistic early expiration (such as XFetch) or local mutex locking, ensuring only one instance queries the central Memcached cluster or database to re-populate the cache.
