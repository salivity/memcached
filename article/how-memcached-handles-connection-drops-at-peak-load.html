How Memcached Handles Connection Drops at Peak Load

During peak client concurrency, Memcached relies on an asynchronous, multi-threaded event-driven architecture powered by libevent to detect, isolate, and clean up severed connections without blocking the server. When high-volume traffic causes connection drops—whether from client-side timeouts, network partitions, or OS-level resource limits—Memcached rapidly reclaims internal memory buffers and file descriptors while preventing cascading failures across its worker thread pool.

Event-Driven Failure Detection

Memcached assigns accepted client connections across a pool of pre-allocated worker threads via a round-robin dispatch mechanism. Each worker thread runs its own libevent instance using kernel-level event multiplexing (such as epoll on Linux or kqueue on BSD/macOS).

When a connection terminates unexpectedly, Memcached detects it through non-blocking I/O event notifications:

  • Zero-Byte Reads: If a client abruptly closes a TCP socket, the read event triggers a standard system call (recv() or read()), which returns 0, signaling EOF.
  • Kernel Error Flags: If the connection is reset via a TCP RST or a broken pipe occurs, the kernel generates flags such as EPOLLRDHUP, EPOLLERR, or EPOLLHUP.
  • Write Failures: When Memcached attempts to flush response data to a dropped connection, the underlying system call yields EPIPE or ECONNRESET.

Connection State Machine and Teardown

Memcached tracks every network interaction using an explicit connection state machine. Once an I/O error or EOF is detected, the worker thread shifts the connection state to conn_closing.

The teardown process follows a strict sequence:

  1. Unregistering Events: The worker thread immediately removes the socket’s file descriptor from its active libevent monitoring list to stop processing subsequent events.
  2. Closing the Socket: The system call close() is invoked on the file descriptor. This releases the kernel-level socket resources and allows the operating system to initiate the TCP teardown sequence (e.g., entering the TIME_WAIT or CLOSED state).
  3. Buffer Management: Dynamic read and write buffers allocated to that specific connection are returned to Memcached’s internal buffer pools or deallocated, preventing memory bloat during massive connection churn.

Resource Recycling via Connection Pools

Allocating memory structures repeatedly during traffic spikes degrades CPU performance due to heap fragmentation and lock contention. Memcached mitigates this by maintaining a free list of internal connection objects (conn structs).

Instead of freeing the underlying conn structure back to the system heap via free(), the connection teardown routine cleans its state, resets its counters, and returns the pointer to a per-thread or global free list. When a new client arrives, Memcached retrieves an existing conn structure from the pool, minimizing allocation overhead during heavy traffic bursts.

Thread Isolation and Concurrency Protection

Because Memcached uses a shared-nothing model for network I/O, a connection drop on one worker thread does not disrupt or block others.

  • No Global Lock Contention: Network cleanup occurs entirely within the context of the worker thread managing that connection. Only item lookups and slab operations acquire global or fine-grained hash table locks; connection teardown itself operates purely on thread-local event loops.
  • Mitigating "Slowloris" and Timeouts: If thousands of connections fail simultaneously due to upstream timeouts, each worker thread processes socket closures as standard non-blocking events in its queue. The O(1) nature of socket deregistration ensures that the event loop remains responsive to healthy client connections.
  • Protection Against Descriptor Exhaustion: Memcached tracks active connections against the -c (max connections) threshold. If dropped connections linger at the TCP level, Memcached stops accepting new incoming sockets at the listener thread until active connections fall back below the limit, preventing process crashes caused by EMFILE (Too many open files) errors.
