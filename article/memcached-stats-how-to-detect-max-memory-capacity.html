Memcached Stats: How to Detect Max Memory Capacity

Monitoring Memcached memory usage is essential for maintaining application performance and preventing unexpected data loss through early evictions. This article outlines the specific metrics returned by the Memcached stats and stats slabs commands that reveal when a node is approaching its maximum configured memory limit, enabling administrators to scale resources proactively.

Primary Utilization: bytes and limit_maxbytes

The most direct indicator of memory consumption is the relationship between the currently stored data and the maximum allowable memory.

  • limit_maxbytes: The total memory capacity allocated to the Memcached instance (defined at launch using the -m flag).
  • bytes: The current number of bytes used by the process to store items.

Calculating (bytes / limit_maxbytes) * 100 gives the overall percentage of memory utilized. When this ratio approaches 90% or higher, the node is nearing its capacity threshold.

Active Evictions: evictions

When a Memcached instance reaches its maximum memory and requires space for new writes, it uses a Least Recently Used (LRU) algorithm to remove existing items before their TTL (Time to Live) expires.

  • evictions: The total count of valid, unexpired items purged to accommodate new data.
  • evicted_time: The number of seconds since the last item was evicted.

Under normal operation on a node with spare capacity, evictions should remain at zero. If the evictions counter begins to climb steadily, the node has reached capacity and is aggressively shedding valid cache entries, leading to cache churn and increased load on backend databases.

Expired Item Overwrites: reclaimed

  • reclaimed: The number of times Memcached reused an existing expired item's memory slot to store a new item.

While an increasing reclaimed count is a normal part of lifecycle management, a sudden spike alongside high memory usage indicates that memory is saturated and the engine is forced to scan for expired items aggressively to avoid evicting active data.

Slab-Specific Saturation: stats slabs

Memcached allocates memory in fixed-size chunks grouped into slab classes. A node can experience localized memory exhaustion within a specific slab class even if overall memory appears available.

  • total_chunks vs. used_chunks: When used_chunks equals total_chunks in a specific slab class, no additional items of that size class can be written without allocating a new slab page or evicting items.
  • mem_requested: Comparing mem_requested to the total memory assigned to a slab class reveals internal fragmentation. High memory usage with low mem_requested values indicates wasted chunk space, which can artificially exhaust memory prematurely.

Allocation Failures: out_of_memory

If Memcached is started without LRU eviction enabled (using the -M flag to return errors on memory exhaustion instead of evicting entries), monitor the following:

  • out_of_memory: The count of storage operations that failed because the node ran out of memory. Any non-zero value indicates that the node has hit 100% capacity and is actively failing client write requests.
