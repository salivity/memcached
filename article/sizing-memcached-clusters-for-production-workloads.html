Sizing Memcached Clusters for Production Workloads

Sizing a Memcached cluster for production requires balancing active dataset requirements, internal memory overhead, network throughput, and redundancy. This guide outlines the essential best practices for determining memory capacity, CPU allocation, network limits, and node counts to ensure high availability and prevent cache thrashing under heavy production workloads.

1. Calculate the True Working Set Size

Sizing begins with calculating the raw data footprint and accounting for Memcached’s internal data structures:

  • Raw Data Formula: (Average Key Size + Average Value Size) × Expected Item Count
  • Internal Metadata Overhead: Memcached adds internal overhead (typically 48 to 56 bytes) to every cached item for pointers, flags, and expiration times. Factor this into your per-item calculation.
  • Target Eviction Rate: Memcached operates as a Least Recently Used (LRU) cache. Size your memory so that cold data is evicted naturally, while the primary working set stays in memory. If your hit ratio drops or eviction rates spike, the memory allocation is insufficient.

2. Account for Slab Allocation and Fragmentation

Memcached does not allocate arbitrary byte sizes; it uses a slab allocator to avoid OS-level memory fragmentation:

  • Chunk Waste: Memory is pre-divided into slab classes containing fixed-size chunks. An item is placed in the smallest chunk that can accommodate it. For example, a 150-byte item placed in a 200-byte chunk leaves 50 bytes of unused padding.
  • Growth Factor Tuning: The default growth factor (-f 1.25) scales chunk sizes by 25% between slab classes. Tuning this factor according to your actual payload distribution reduces internal fragmentation.
  • Safety Buffer: Always add a 15% to 25% memory safety buffer above your working set size to absorb slab class imbalances and prevent unexpected evictions.

3. Plan for Network Bandwidth and Packet Limits

In many production environments, network capacity saturates before CPU or RAM:

  • Bandwidth Saturation: High-throughput caching can easily saturate network interfaces. A server serving 50,000 requests per second with an average payload of 20 KB requires approximately 8 Gbps of sustained bandwidth.
  • Packets Per Second (PPS): Cloud instances often impose strict PPS throttling. Ensure the selected instance type provides dedicated network performance (e.g., 10 Gbps, 25 Gbps, or higher) rather than burstable allocations.

4. Right-Size CPU and Threading

Memcached uses a multi-threaded architecture based on libevent, but CPU scaling has limits:

  • Core Scaling: Memcached scales efficiently up to 4–8 CPU cores. Beyond 8 to 16 cores, lock contention on internal data structures can degrade returns per core.
  • Process Separation: Running multiple smaller Memcached instances on a single large multi-core machine often yields higher throughput and lower lock contention than running a single massive instance.

5. Account for Connections and OS Overhead

Memcached maintains connections using event loops, which demand system resources:

  • Connection Memory: Each active TCP connection consumes server memory. Budget for connection memory by configuring the max connections parameter (-c).
  • OS Overhead: Reserve at least 1 GB to 2 GB of RAM on each host for the operating system, monitoring agents, and system buffers to prevent the Linux Out-Of-Memory (OOM) killer from terminating the Memcached daemon.

6. Design for Blast Radius and Redundancy

A Memcached cluster lacks native replication; consistent hashing on the client side determines key distribution:

  • Avoid Giant Nodes: A few large instances create a high blast radius. If you have two 64 GB nodes and one fails, 50% of your cache is lost, overwhelming your primary database.
  • Use More, Smaller Nodes: Favor clusters with multiple smaller nodes (e.g., eight 16 GB nodes instead of two 64 GB nodes). The loss of a single node then only removes a small percentage of cached keys.
  • N+1 Headroom: Ensure your database layer can handle the cache miss storm of at least one failed node, or size the cluster capacity to tolerate redistributing traffic across remaining nodes.
