How to Run Multiple Memcached Instances on One Host

Running multiple Memcached instances on a single physical server allows system administrators to maximize hardware utilization, isolate caching layers for different applications, and bypass single-thread bottlenecks on multi-core systems. This article outlines the essential technical requirements for process separation and demonstrates how to configure and manage independent Memcached daemons using systemd template units and distinct runtime parameters.

Core Configuration Requirements

To run several Memcached processes simultaneously without conflicts, each instance must have its own isolated parameters:

  • Network Port or Unix Socket: The default port is 11211. Additional instances must bind to alternative unused TCP/UDP ports (e.g., 11212, 11213) or distinct Unix domain socket paths.
  • Memory Allocations: The cumulative memory (-m flag) assigned across all instances must not exceed the physical RAM minus the memory required by the operating system and other running services to prevent swapping.
  • PID Files: Each background daemon requires a dedicated PID file path so process managers can monitor and terminate specific instances accurately.

Managing Instances via Systemd Template Units

On modern Linux distributions, systemd template units provide the most robust method for managing multiple service instances from a single base configuration.

1. Define Instance Configurations

Create individual configuration files for each instance. For example, create an /etc/memcached directory and define two instances:

File: /etc/memcached/instance1.conf

-m 4096
-p 11211
-u memcache
-l 127.0.0.1
-P /run/memcached/instance1.pid

File: /etc/memcached/instance2.conf

-m 4096
-p 11212
-u memcache
-l 127.0.0.1
-P /run/memcached/instance2.pid

2. Create the Systemd Template Service

Create the template unit file at /etc/systemd/system/memcached@.service:

[Unit]
Description=Memcached Instance %I
After=network.target

[Service]
Type=simple
EnvironmentFile=/etc/memcached/%i.conf
ExecStart=/usr/bin/memcached $OPTIONS
Restart=always
User=memcache
Group=memcache

[Install]
WantedBy=multi-user.target

If your configuration file holds raw command arguments rather than environment variables, adjust ExecStart accordingly to parse the parameters directly using an environment variable wrapper or pass parameters explicitly. On Debian and Ubuntu systems, the default package includes a wrapper script or template /lib/systemd/system/memcached@.service that reads /etc/memcached_%i.conf.

3. Enable and Start the Services

Reload the systemd manager configuration, enable each instance to start on boot, and initiate the processes:

sudo systemctl daemon-reload
sudo systemctl enable --now memcached@instance1
sudo systemctl enable --now memcached@instance2

Verify the status of both processes:

sudo systemctl status memcached@instance1
sudo systemctl status memcached@instance2

Manual Execution

For non-systemd environments or custom init scripts, invoke the memcached binary directly with the -d flag to run it as a detached background daemon:

# Instance 1
memcached -d -m 2048 -p 11211 -u memcache -P /var/run/memcached/memcached_1.pid -l 127.0.0.1

# Instance 2
memcached -d -m 2048 -p 11212 -u memcache -P /var/run/memcached/memcached_2.pid -l 127.0.0.1

Hardware Optimization: NUMA and CPU Pinning

On multi-socket servers, performance can be increased by binding specific Memcached instances to distinct NUMA nodes and CPU cores. This prevents cross-node memory latency:

numactl --cpunodebind=0 --membind=0 /usr/bin/memcached -d -m 8192 -p 11211 -u memcache
numactl --cpunodebind=1 --membind=1 /usr/bin/memcached -d -m 8192 -p 11212 -u memcache

This isolation guarantees that each daemon process accesses memory strictly local to its assigned CPU socket.
