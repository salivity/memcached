How Memcached Slab Classes Prevent Memory Fragmentation

Memcached prevents external memory fragmentation by implementing a slab allocation system that divides memory into isolated, pre-allocated regions called slab classes. Instead of relying on traditional runtime heap allocation routines like malloc and free, which inevitably create scattered, unusable gaps of memory over time, Memcached partitions its total memory pool into fixed 1-megabyte pages assigned to specific chunk sizes. This design isolates memory usage by item size, ensuring that items of varying dimensions never compete for the same physical memory addresses, thereby eliminating external fragmentation.

The Foundation of Slab Allocation

When Memcached initializes, it requests a large, contiguous block of memory from the operating system. Rather than dynamically managing allocations of arbitrary sizes within this block, Memcached splits memory into 1 MB units called "pages."

These pages are assigned to distinct "slab classes." Each slab class is responsible for managing items within a specific size threshold, beginning with a base size (typically 96 bytes) and scaling upward by a growth factor (defaulting to 1.25) until reaching the maximum item limit (defaulting to 1 MB).

Total Isolation Between Chunk Sizes

Every 1 MB page allocated to a slab class is immediately carved up into equal-sized "chunks." For example:

  • Slab Class 1 might contain 1 MB pages divided into 96-byte chunks.
  • Slab Class 2 might divide its 1 MB pages into 120-byte chunks.
  • Slab Class 3 might divide its 1 MB pages into 152-byte chunks.

Because each slab class manages its own distinct pool of identical chunks, memory operations inside one class cannot affect another. When a cached item expires or is deleted, its chunk is returned to the free list of that specific slab class. Because every chunk within that class is identically sized, any new incoming item routed to that class will fit seamlessly into the vacated slot. This completely avoids external fragmentation, as free slots are never too small or misshapen for subsequent writes of that class.

Mitigating Internal Fragmentation

While slab isolation eliminates external fragmentation, it shifts the engineering challenge to internal fragmentation—the unused bytes left over when an item's size is smaller than the chunk it occupies. Memcached handles this through its configurable growth factor.

By scaling chunk sizes incrementally across classes, Memcached minimizes the disparity between the item size and the chunk size. An item is always placed in the smallest chunk capable of holding it, keeping the unused headroom within acceptable limits. Operators can tune the growth factor via configuration to optimize chunk distribution based on real-world workload characteristics.

Dynamic Slab Rebalancing

Historically, slab class isolation carried the risk of memory starvation: if a class filled up and traffic patterns shifted to larger or smaller keys, memory assigned to one class could sit idle while another evicted items prematurely.

Modern versions of Memcached resolve this through dynamic slab rebalancing (slab automove). A background thread monitors class eviction rates and free memory. If an imbalance is detected, Memcached reclaims an entire 1 MB page from an underutilized class, clears its contents, and reassigns it to the starved slab class. The page is then carved into the new class's chunk dimensions. This preserves memory isolation at the chunk level while preventing rigid memory traps across the overall system.
