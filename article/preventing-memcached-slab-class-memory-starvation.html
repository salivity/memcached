Preventing Memcached Slab Class Memory Starvation

In high-throughput environments, Memcached instances can experience memory starvation in small slab classes due to slab calcification, where memory pages permanently lock into larger classes and starve smaller, high-churn keys of space. This article explores the root causes of slab imbalance and provides concrete technical solutions—including automatic slab rebalancing, growth factor optimization, modern LRU thread management, and application-level payload strategies—to maintain consistent throughput and eliminate premature evictions.

Enable Automated Slab Rebalancing (slab_automove)

Memcached allocates memory in 1MB pages assigned permanently to specific slab classes upon initialization. Under shifting workloads, earlier traffic patterns may consume available pages for larger objects, leaving small slab classes unable to claim new pages.

To resolve this dynamically, enable the built-in slab automover:

  • Mode 1 (slab_automove=1): A conservative algorithm that monitors memory usage and moves an unallocated or idle page to a starved class if the target class experiences three consecutive evictions while another class has unused pages.
  • Mode 2 (slab_automove=2): A more aggressive, windowed algorithm introduced in modern versions that continuously balances memory based on the highest eviction rate over time, shifting pages toward slabs with the highest ratio of evictions to hits.

Configure this at startup using -o slab_automove=2 or at runtime via the administrative interface:

set slab_automove 2

Manual Slab Reassignment

When automated rebalancing is disabled or too slow to respond to an emergency spike, operators can intervene manually through the Memcached management console.

First, query slab metrics to find donor and recipient classes:

stats slabs

Look for classes with high evictions and low free_chunks (recipients), and classes with high free_chunks or zero recent writes (donors). Manually reassign a page using the administrative command:

slabs reassign <source_slab_id> <destination_slab_id>

Optimize the Slab Growth Factor (-f)

The slab growth factor controls the size multiplier between consecutive slab classes (defaulting to 1.25). A high growth factor leaves wide gaps between item sizes, which causes excessive internal fragmentation and accelerates slab consumption.

For small, uniform keys:

  • Reduce the growth factor using -f 1.05 to -f 1.15.
  • This creates narrower boundaries between slab sizes, packing small payloads more tightly and generating more usable chunks per 1MB page.
  • Pair this with -n <bytes> to lower the minimum chunk size if stored keys and metadata are exceptionally small (e.g., -n 48).

Enable Modern Segmented LRU and the Maintainer Thread

Traditional Memcached implementations use a single LRU queue per slab class, making small items vulnerable to immediate eviction during burst writes. Modern Memcached mitigates this by segmenting the LRU into three distinct queues: HOT, WARM, and COLD.

Enable the modern storage engine with:

-o modern

This flag activates:

  • lru_maintainer: A background thread that moves active items between queues and assists slab_automove in identifying truly idle memory.
  • lru_crawler: A background worker that proactively scans slabs and frees expired items, returning chunks back to the small slab pools before an eviction is triggered.

Application-Side Padding and Cluster Partitioning

When architectural configurations within Memcached reach their limits, application-level designs prevent starvation from taking place:

  • Payload Normalization: Pad variable-length small keys to fit into a predictable set of slab classes, preventing erratic slab page distribution across dozens of intermediate classes.
  • Instance Isolation: Separate caching tiers based on object lifecycle and payload size. Route high-volume, small items (such as session tokens or counters) to a dedicated Memcached cluster tuned specifically for sub-kilobyte payloads, completely isolated from large cached objects.
