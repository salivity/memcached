Impact of Too Few Worker Threads in Memcached

Configuring Memcached with an insufficient number of worker threads restricts its ability to process concurrent operations, creating an immediate performance bottleneck in high-traffic environments. Because Memcached relies on an event-driven, multi-threaded model to read, process, and write client requests, a thread deficit leads to severe request queuing, elevated latency, decreased throughput, and potential client-side connection timeouts.

How Memcached Uses Worker Threads

Memcached utilizes a master-worker architecture powered by libevent:

  • The Dispatcher Thread: Listens for incoming TCP/UDP connections on the network socket and distributes newly accepted connections to worker threads using a round-robin mechanism.
  • Worker Threads: Handle all subsequent network I/O, parse incoming commands (e.g., get, set), interact with the internal hash table and slab allocator, and return responses to clients.

The number of worker threads is defined at startup via the -t flag (defaulting to 4 threads). If this value is set too low relative to your concurrency demands and available CPU resources, the following issues occur.

Key Effects of Insufficient Worker Threads

1. Increased Latency and Head-of-Line Blocking

Each worker thread processes events for multiple assigned connections. When the number of threads is too low, each thread must service an excessive number of active connections. If several long or complex requests hit a single thread simultaneously, other connections assigned to that same thread are forced to wait. This introduces queuing delay, causing spikes in 95th and 99th percentile response latencies.

2. Severely Capped Throughput (IOPS)

Modern servers feature high core counts and fast network interfaces capable of handling hundreds of thousands of operations per second. If Memcached is configured with only one or two threads on a machine with 16 or 32 cores, it cannot leverage the hardware's parallel processing capabilities. Throughput will plateau prematurely once the active worker threads reach 100% CPU utilization, leaving the rest of the host's compute capacity idle.

3. Connection Backlogs and Client Timeouts

When existing worker threads become saturated, they struggle to keep up with incoming socket buffers. In extreme cases:

  • Read and write buffers fill up, slowing down socket processing.
  • The main dispatcher thread continues to accept and distribute connections, but the overloaded worker threads cannot acknowledge them in time.
  • Clients experience connection timeouts, read timeouts, or dropped connections, which can cascade into application-tier failures.

4. Asymmetric CPU Core Utilization

An insufficient thread count leads to an unbalanced system profile. System metrics will show a few CPU cores pinned near maximum capacity, while the remaining cores remain underutilized. This mismatch creates an artificial bottleneck long before the server's actual resource limits are reached.

Identifying the Bottleneck

To determine if Memcached is constrained by an insufficient thread count, monitor the following metrics:

  • Per-Core CPU Usage: Check if individual cores running Memcached threads are pinned at 100% while overall host CPU utilization remains low.
  • listen_disabled_num: Run memcached-tool <host> stats or query stats directly. A rising listen_disabled_num indicates that Memcached has temporarily stopped accepting new connections because worker threads cannot keep up.
  • Client-Side Latency: A divergence between low network latency and high Memcached command response times indicates internal processing delays.

Optimal Configuration Guidelines

To resolve thread starvation, set the -t parameter appropriately:

  • Align with Core Count: As a standard baseline, set -t equal to the number of physical CPU cores allocated to Memcached, up to a practical limit.
  • Avoid Over-Threading: Setting the thread count excessively high (e.g., well beyond 8 to 16 threads) can cause lock contention on internal structures, particularly the cache item locks and slab allocator locks. Most production workloads achieve peak efficiency between 4 and 16 worker threads, depending on traffic volume and CPU architecture.
