Memcached Request Queuing During CPU Saturation

Memcached relies on a multi-threaded, non-blocking I/O model powered by libevent to achieve high throughput and low latency. When system CPU resources become fully saturated, Memcached does not maintain an internal, unbounded application-level queue for incoming commands. Instead, request queuing naturally shifts down to the operating system's network stack, kernel socket buffers, and TCP connection backlogs. Understanding this behavior reveals how CPU bottlenecks trigger network-level backpressure, client-side timeouts, and dropped connections rather than application memory exhaustion.

The Thread Model and Libevent

Memcached operates with a single main thread (dispatcher) and multiple worker threads configured via the -t parameter. The main thread listens on the network port and distributes incoming TCP connections to worker threads using a simple round-robin mechanism via internal connection queues.

Once a connection is assigned to a worker thread, that thread handles all subsequent reads, writes, and cache operations for that connection using its own libevent event loop. Memcached processes requests as discrete events triggered when sockets become readable. Because worker threads execute operations synchronously within their event loops, a saturated CPU directly starves these loops of execution cycles.

Kernel-Level Queuing and Socket Buffers

Because Memcached does not queue inbound requests in application memory beyond the immediate command read buffers, unserviced data accumulates in the Linux kernel:

  1. Socket Receive Buffers (SO_RCVBUF): As clients send get, set, or batch operations, the data arrives over the network and fills the OS socket receive buffer. When the CPU is at 100%, worker threads cannot call read() or recv() fast enough to drain these buffers.
  2. TCP Window Shrinking: Once a connection’s receive buffer fills up, the OS TCP stack advertises a smaller TCP receive window (rwnd) to the client. If the worker thread remains unable to process the backlog, the receive window drops to zero (TCP Zero Window), instructing the client to halt packet transmission immediately.
  3. TCP Listen Backlog: If the main dispatcher thread is starved of CPU time, it cannot invoke accept() quickly enough to process incoming connection handshakes. New connections accumulate in the kernel's SYN and accept queues (governed by the system's somaxconn and Memcached’s -b backlog settings). Once full, the kernel silently drops incoming SYN packets or sends TCP reset (RST) packets back to the client.

Worker Thread Event Loop Latency

Under heavy CPU load, the Linux scheduler must divide scarce CPU time among all active threads, including the Memcached worker threads and any other host processes.

Even though existing connections remain established, the worker threads spend more time waiting for scheduled execution slices. When a thread finally runs, it processes the readable events registered with libevent. However, the latency between an event firing and the thread finishing the operation stretches significantly. Because the CPU cannot retire instructions faster, the processing time per request rises, increasing the turnaround time for every connected client.

Client-Side Impact

Because Memcached pushes the burden of request queuing onto the TCP layer, the failure modes appear on the client side:

  • Connection Timeouts: New clients fail to establish a connection because the listen backlog is full, resulting in connection timeouts or ECONNREFUSED errors.
  • Read/Write Timeouts: Established clients sending commands stall when their local send buffers fill (due to the server's TCP Zero Window), or they exceed their configured socket read timeout waiting for Memcached to process the query and write the response.
  • Thundering Herd Exacerbation: If clients react to timeouts by retrying requests or re-establishing connections, they inject more traffic into the saturated kernel queues, deepening the CPU starvation loop.

By avoiding large application-level request queues, Memcached protects its own process memory from ballooning out of control during CPU saturation, delegating traffic management to standard TCP flow-control mechanisms.
