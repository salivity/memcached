Memcached Memory Allocation with Custom Chunk Size

This article examines how Memcached constructs its internal slab memory subsystem when started with a custom minimum chunk size. By overriding the default minimum allocation value, operators alter the baseline chunk dimension of the initial slab class, which directly shifts the geometric growth scale for all subsequent classes, controls the total number of slab classes generated, and dictates how 1MB memory pages are partitioned. Understanding this behavior allows for optimized memory utilization, minimized internal fragmentation, and better alignment with expected payload profiles.

The Slab Allocation Model

Memcached manages memory through a slab allocation system designed to prevent memory fragmentation caused by frequent allocations and deallocations. Rather than allocating arbitrary byte sizes for each incoming key-value pair, Memcached pre-allocates memory in fixed blocks called pages (defaulting to 1 megabyte).

These pages are divided into uniform chunks. Each collection of pages with identical chunk sizes belongs to a distinct slab class. When an item is stored, Memcached identifies the slab class with the smallest chunk size capable of fitting the item (including its key, value, internal flags, and metadata) and places it into an available chunk.

Setting the Custom Minimum Chunk Size

The minimum chunk size is configured at startup using the -n (or --min-item-size) command-line flag. This parameter specifies the minimum space allocated for the item key, value, and flags.

When a custom value is provided, Memcached determines the total chunk size of Slab Class 1 by adding the configured value to the internal item header overhead (the item C-struct, which typically occupies 48 to 56 bytes on 64-bit architectures, plus suffixes and alignment padding).

If an operator specifies -n 128, Memcached uses that value as the base payload size, resulting in a Class 1 chunk size of approximately 176 to 184 bytes (aligned to an 8-byte memory boundary).

Class Progression and the Growth Factor

Once the initial chunk size for Slab Class 1 is established, Memcached generates subsequent slab classes geometrically based on the growth factor (-f, which defaults to 1.25).

The allocation sequence proceeds as follows:

  1. Slab Class 1: Initialized with custom_min_size + metadata_overhead, rounded up to the nearest 8-byte boundary.
  2. Slab Class n: Initialized as Chunk_Size(n-1) * growth_factor. The calculated size is continuously rounded up to preserve memory alignment.
  3. Termination: This progression repeats until the chunk size reaches the maximum slab page size (controlled by -I, default 1 megabyte).

Altering the minimum chunk size shifts the entire baseline upward. For example, doubling the minimum chunk size does not merely expand Slab Class 1; it shifts the boundary of every subsequent class rightward, reducing the total count of active slab classes between the minimum chunk size and the 1MB ceiling.

Page Partitioning Mechanics

When a slab class requires memory, Memcached allocates a 1MB page from the global memory pool to that specific slab class. The page is then immediately sliced into uniform chunks corresponding to that class's dimensions:

\[\text{Chunks per Page} = \left\lfloor \frac{\text{Page Size}}{\text{Chunk Size}} \right\rfloor\]

Any remaining bytes at the end of the 1MB page that are smaller than the class chunk size cannot be used and remain idle as unusable page-tail padding. With a custom minimum size:

  • Larger minimum chunk sizes result in fewer chunks per page in the lower slab classes.
  • The amount of unused page-tail padding varies depending on how cleanly the calculated chunk size divides into the total page size.

Memory Trade-offs and Considerations

Configuring a custom minimum chunk size introduces specific architectural trade-offs:

  • Internal Fragmentation: If an application stores items smaller than the custom minimum chunk size, the unused space inside the allocated chunk is wasted. Setting the minimum too high increases internal fragmentation for smaller payloads.
  • Slab Class Consolidation: If an application guarantees that all items exceed a certain threshold (e.g., 512 bytes), raising -n eliminates redundant small-capacity slab classes. This prevents memory pages from being tied up in smaller classes that will never receive writes.
  • Slab Eviction Distribution: Because memory pages are assigned permanently to specific slab classes (unless slab reassignment/automove is triggered), tuning the baseline chunk size ensures that memory pages are only distributed across size ranges that match the live workload.
