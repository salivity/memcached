Securing Memcached in Docker Containers

Running Memcached within Docker simplifies deployment and scaling for high-performance caching, but it introduces distinct security risks if containers are misconfigured. Because Memcached was designed for trusted internal networks and traditionally lacks robust native security controls, containerization requires deliberate isolation strategies. This article outlines the key security considerations for containerized Memcached instances, focusing on network exposure, UDP amplification risks, access control, and container hardening.

Network Exposure and Interface Binding

By default, Memcached listens on port 11211 without requiring authentication. When deploying inside a Docker container, mapping this port directly to the host using flags like -p 11211:11211 often binds the service to 0.0.0.0. This makes the cache publicly accessible to anyone who can reach the host network.

  • Avoid Public Port Publishing: Do not expose port 11211 to the public internet. Instead, rely on Docker internal networks to connect application containers to the Memcached container directly.
  • Explicit Host Binding: If host-level access is strictly necessary, bind the port explicitly to the host's loopback interface using -p 127.0.0.1:11211:11211.
  • Use Dedicated Docker Networks: Place Memcached inside a custom, user-defined bridge or overlay network so that only designated application containers can communicate with it.

Mitigating UDP Amplification Attacks

Historically, open Memcached instances have been weaponized for massive Distributed Denial of Service (DDoS) amplification attacks due to the stateless nature of UDP.

  • Disable UDP: Unless explicitly required, completely disable UDP support by passing the -U 0 argument to the Memcached entrypoint or command (memcached -U 0).
  • Restrict Ingress Protocols: Ensure your host firewalls and container network security groups block inbound UDP traffic targeted at caching ports.

Authentication and SASL Configuration

Standard Memcached configurations do not require credentials, allowing any client with network access to read, modify, or flush stored data.

  • Enable SASL: If your application environment requires authentication, compile or configure Memcached with Simple Authentication and Security Layer (SASL) support enabled using the -S flag.
  • Environment Variables and Secrets: When providing SASL credentials, never hardcode passwords in the Dockerfile. Use Docker Secrets or environment variables injected via a secure secrets manager at runtime.

Container Hardening and User Privileges

A compromised container should not grant attackers control over the underlying host system. Restricting the container’s operating environment limits the potential blast radius.

  • Run as a Non-Root User: While official Memcached Docker images often default to the memcache user, verify that the container does not execute as root. Specify --user memcache if necessary.
  • Drop Linux Capabilities: Strip unnecessary kernel capabilities by running the container with --cap-drop=ALL and only adding back explicitly required capabilities.
  • Read-Only Root Filesystem: Memcached operates entirely in memory and does not require local disk writes. Mount the container’s root filesystem as read-only using the --read-only flag to prevent unauthorized modifications to system binaries or malicious script placement.

Resource Allocation and Denial of Service

Without resource boundaries, an attack or a misconfigured cache can consume excessive host memory, triggering the host's Out-Of-Memory (OOM) killer and crashing critical co-located services.

  • Memcached Memory Limits: Configure the internal memory allocation limit within Memcached using the -m flag (for example, memcached -m 1024 for 1GB).
  • Docker Resource Constraints: Impose strict limits at the container level by setting --memory and --cpus flags. Always ensure the Docker memory limit is slightly higher than the Memcached internal limit to accommodate process overhead without invoking the OOM killer.
