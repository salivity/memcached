How Memcached Handles Pointer Cleanup on Eviction

When Memcached evicts an entry to reclaim space, it manages internal pointer cleanup through an unlinking process across its primary internal data structures: the hash table and the LRU (Least Recently Used) doubly linked list. Rather than deallocating memory back to the operating system using standard heap allocation routines like free(), Memcached severs the pointers routing to the targeted item, decrements its internal reference counter, and immediately reassigns the underlying slab memory chunk to the incoming data.

Core Data Structures Involved in Eviction

To understand pointer cleanup, it is necessary to identify the three sets of pointers associated with every cached item:

  1. Hash Table Pointers (h_next): Memcached uses a global hash table with bucket chaining to handle collisions. Each item points to the next entry in the same bucket via an internal h_next pointer.
  2. LRU List Pointers (prev and next): Items are tracked within slab-specific doubly linked lists to track usage order. Each item maintains prev and next pointers to navigate the LRU chain.
  3. Reference Count (refcount): An atomic integer tracking active readers or operational locks currently referencing the item's memory block.

The Pointer Unlinking Sequence

Eviction is triggered when a slab class runs out of available chunks and the global memory limit has been reached. When Memcached selects an item from the tail of the target slab's LRU list for eviction, it carries out pointer cleanup through a dedicated routine (historically executed via do_item_unlink):

1. Hash Table Unlinking (assoc_delete)

Before an item can be evicted, it must be hidden from incoming read requests. The engine walks the hash bucket chain containing the item:

  • The predecessor's h_next pointer is updated to point directly to the target item’s h_next.
  • If the item is at the head of the bucket, the bucket's head pointer is updated.
  • The evicted item's h_next pointer is set to null, eliminating any reference to the hash table.

2. LRU List Unlinking (item_unlink_q)

Next, the item is removed from its slab class's doubly linked list:

  • The preceding item's next pointer is updated to point to the evicted item's next.
  • The succeeding item's prev pointer is updated to point to the evicted item's prev.
  • If the item sat at the tail or head of the LRU, the slab's global tail or head pointers are updated accordingly.
  • The item’s prev and next pointers are cleared.

Reference Counting and Memory Reclamation

Memcached implements strict reference counting to prevent memory corruption while concurrent worker threads service requests:

  • Checking refcount: An item can only be immediately repurposed if its refcount indicates no external references (typically a reference count of 1 for the storage system itself). If another connection is concurrently reading the item (resulting in a higher refcount), Memcached will not immediately overwrite the chunk; it will either crawl backward up the LRU to find an unlocked candidate or defer destruction.
  • Decrementing References: Once unlinked from the hash table and the LRU, the storage reference is dropped. If the reference count hits zero, the memory chunk is fully disconnected.
  • In-Place Reuse: Memcached does not return memory to the OS. Instead, the memory address of the cleared item is retained directly by the thread performing the write. The header data of the new item is written over the old item's header, resetting all internal pointers for the incoming key-value pair and placing it at the head of the LRU list.
