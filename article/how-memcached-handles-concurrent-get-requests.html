How Memcached Handles Concurrent Get Requests

Memcached is engineered for high-throughput, low-latency caching and handles concurrent get requests targeting the exact same key using a multithreaded, event-driven architecture coupled with fine-grained item locking. Instead of serializing operations or blocking threads, Memcached processes simultaneous reads independently by utilizing atomic reference counting and non-exclusive memory reads. This allows hundreds or thousands of clients to retrieve identical data at the same time without creating bottlenecks or deadlocks.

Multithreaded Architecture and Connection Assignment

Memcached utilizes libevent to manage concurrent network I/O. When Memcached initializes, it establishes a main connection thread and a configurable pool of worker threads (defaulting to four).

  • Connection Distribution: The main thread accepts incoming TCP connections and assigns them to worker threads via a round-robin mechanism.
  • Independent Execution: If multiple clients connect and issue a get command for the exact same key, these requests typically land across different worker threads in the pool. Each worker thread processes its assigned client connection independently within its own event loop.

Hash Table Bucket Locks

To manage concurrent access to its internal hash table, Memcached divides hash table items into partitions guarded by item locks (often referred to as bucket locks).

  1. Hash Lookup: When a worker thread receives a get <key> command, it computes the hash of the key to determine which hash bucket holds the pointer to the item.
  2. Lock Acquisition: The thread acquires a mutex lock associated with that specific hash bucket. In modern Memcached versions, this is an item lock that covers a range of hash table buckets to minimize contention across different keys.
  3. Short-Lived Mutex: This lock is held only long enough to locate the memory address of the item in the hash table and increment its reference counter. It is not held for the duration of the data transmission over the network.

Atomic Reference Counting

The core mechanism enabling safe, concurrent reads of the identical key is reference counting (it->refcount).

  • Pinning the Item: Once the hash bucket lock is acquired and the target item is located in memory, the worker thread increments the item's refcount. This informs the memory allocator (the slab allocator) and the Least Recently Used (LRU) eviction crawler that the memory block is actively in use and must not be freed, overwritten, or evicted.
  • Releasing the Lock: Immediately after incrementing the reference counter, the worker thread releases the item lock.
  • Concurrent Reads: Because the lock is released instantly, subsequent or simultaneous get requests for that exact same key—handled by other worker threads—can immediately acquire the lock, increment the counter, and release the lock. Consequently, multiple threads hold an active reference to the identical memory address at the same time.

Data Transmission and Cleanup

Once the worker thread holds a valid reference to the cached item and releases the hash bucket lock, it streams the payload directly from memory to the client socket:

  1. Zero-Copy Network I/O: Memcached constructs network packets pointing directly to the item's memory address in the slab allocator, minimizing memory copies.
  2. Decreasing Reference Count: After the operating system kernel accepts the data into the socket buffer (or when the transmission completes), the worker thread re-acquires the item lock briefly to decrement the item's refcount.
  3. Reclaim Eligibility: Once all concurrent readers finish and the refcount drops back to its idle state, the item becomes eligible for eviction or deletion if updated by a write operation.

Cache Misses and the Cache Stampede Reality

While Memcached seamlessly serves concurrent reads for an existing key, it does not implement internal request coalescing (also known as single-flight request deduplication).

If concurrent get requests target a key that does not exist or has expired, every requesting thread will independently encounter a cache miss and return END to its respective client. Memcached does not pause identical requests to wait for a backend database to repopulate the missing key. Applications mitigating this behavior typically implement client-side locking mechanisms or probabilistic early expiration algorithms to avoid overwhelming downstream services.
