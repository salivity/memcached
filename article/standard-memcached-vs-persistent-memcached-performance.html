Standard Memcached vs Persistent Memcached Performance

This article examines the core performance differences between standard, purely in-memory Memcached and Memcached coupled with persistent storage backends. Standard Memcached is designed strictly for volatile caching, prioritizing raw throughput and microsecond latency by operating entirely in RAM. In contrast, persistent Memcached variants (utilizing engines like RocksDB, LevelDB, or custom write-ahead logs) balance fast data access with durability, introducing distinct operational trade-offs in read/write speeds, resource utilization, and disaster recovery.

Latency Profiles: Memory vs. I/O Operations

Standard Memcached stores all key-value pairs in dynamic RAM via a slab allocator. Because it never interacts with a storage device, both read and write operations consistently execute in sub-millisecond ranges (often 100 to 300 microseconds over a local network).

Persistent Memcached implementations introduce secondary storage into the request lifecycle.

  • Write Latency: If writes are synchronous (requiring an explicit disk flush or fsync), write latency increases by orders of magnitude—ranging from 1 to 10 milliseconds on fast NVMe drives. Even with asynchronous persistence (writing to a memory buffer before flushing to disk), operating system context switching, buffer management, and thread synchronization increase baseline write latency compared to pure RAM.
  • Read Latency: If the entire active dataset fits in RAM, read latency remains comparable to standard Memcached. However, once the dataset exceeds available memory, "cache misses" must retrieve data from disk, creating significant latency spikes that standard Memcached avoids simply by evicting older items.

Throughput and Scalability

Standard Memcached scales almost linearly across multi-core systems by utilizing non-blocking network I/O (libevent) and fine-grained locking on memory slabs. It regularly achieves millions of operations per second per server node.

Persistent backends face input/output operations per second (IOPS) and write amplification limits imposed by physical storage:

  • Log-Structured Merge (LSM) Trees: Frequently used for persistence, LSM trees require background compaction processes. Compaction consumes significant CPU cycles and disk I/O bandwidth, leading to throughput drops during peak write loads.
  • Lock Contention: Managing persistent logs or B-Trees requires additional locking mechanisms, which reduce concurrent multi-threaded execution efficiency under heavy workloads.

Cache Stampede Mitigation vs. Raw Speed

The key performance advantage of persistent Memcached does not appear during standard operations, but during service restarts and failovers:

  • Standard Memcached: A restarted instance starts with an empty cache (cold cache). This frequently triggers a "cache stampede" or "thundering herd" problem, where thousands of client requests bypass the cache simultaneously, potentially overwhelming and crashing backend relational databases.
  • Persistent Memcached: Because data survives crashes or reboots, the cache remains immediately warm upon startup. Read requests continue to be served without redirection to backend databases, protecting core architecture at the expense of everyday write overhead.

Resource Utilization and Overhead

Standard Memcached runs with predictable, minimal memory overhead. The slab allocator prevents memory fragmentation, and CPU usage is tied strictly to network traffic and memory lookups.

Persistent Memcached requires a significantly higher resource budget:

  • Memory Division: RAM must be shared between the active cache, the persistent engine’s block/index caches, and operating system page cache buffers.
  • Disk I/O and Wear: High-frequency write-heavy workloads will exhaust SSD write endurance rapidly due to write amplification inherent in append-only files and WAL updates.
  • CPU Consumption: Serialization, checksum calculations, compression algorithms (e.g., Snappy, ZSTD), and background sync routines substantially raise baseline CPU usage.
