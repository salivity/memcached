Memcached Stats total_items: Definition and Purpose

This article explains the purpose of the total_items metric provided by the Memcached stats command. It covers what the metric tracks, how it fundamentally differs from related metrics like curr_items, and how system administrators and developers use this data to monitor cache throughput, assess key churn, and optimize memory capacity.

What is total_items?

In Memcached, the stats command outputs a variety of operational metrics reflecting server activity. The total_items field is a cumulative counter representing the total number of new items successfully stored in the cache instance since the server process was started. Every time a new key-value pair is written via commands such as set, add, or cas, Memcached increments this counter by one.

total_items vs. curr_items

Understanding total_items requires contrasting it with curr_items:

  • total_items is a strictly monotonic, cumulative counter. It records the lifetime total of items ingested. It does not decrease when keys are deleted, when they expire naturally due to time-to-live (TTL) limits, or when they are evicted by the Least Recently Used (LRU) algorithm.
  • curr_items is a point-in-time gauge. It represents the actual number of active keys currently held in memory at the exact moment the stats command is run. When keys expire or are evicted, curr_items decreases.

Key Operational Uses

1. Calculating Write Throughput

By sampling the total_items metric across regular time intervals, monitoring systems can compute the rate of new items being written to the cache:

\[\text{Write Rate} = \frac{\Delta \text{total\_items}}{\Delta t}\]

This helps engineering teams observe traffic spikes, track application write patterns, and benchmark ingestion loads across different periods.

2. Identifying Cache Churn

Comparing the growth of total_items against curr_items and evictions reveals the behavioral health of the cache:

  • If total_items increases rapidly while curr_items remains plateaued near capacity and evictions increase at a similar pace, the instance is suffering from excessive cache churn. This indicates that new entries are immediately pushing out older, potentially useful entries before they can serve cache hits.
  • If total_items and curr_items grow at similar rates, the cache is operating well within its allocated memory footprint and retaining newly inserted data without forced evictions.

3. Capacity and Architecture Planning

A consistently steep upward trend in total_items coupled with high cache misses indicates an application that writes large volumes of short-lived or unread data. Tracking this counter helps determine whether the infrastructure requires additional memory, updated TTL policies, or architectural changes to avoid overwhelming downstream databases.
