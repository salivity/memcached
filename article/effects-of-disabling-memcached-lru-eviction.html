Effects of Disabling Memcached LRU Eviction

Disabling Least Recently Used (LRU) eviction in Memcached alters how the service handles capacity limits, transitioning it from a self-managing cache into a strict, memory-bounded store. When memory is fully allocated, the system stops reclaiming space from dormant items, causing new write operations to fail with out-of-memory errors until space is freed manually or via time-to-live (TTL) expiration. This behavior prevents silent data loss from premature evictions but significantly increases the risk of application write failures and downstream database pressure.

The Mechanics of Disabling LRU

By default, Memcached operates as a dynamic cache. When its memory limit is reached, it automatically removes the least recently accessed keys to accommodate incoming writes.

Starting the Memcached daemon with the -M flag disables this behavior. Instead of reclaiming memory by evicting older records, the engine strictly enforces the allocated memory boundary. Once the slab allocator cannot allocate additional memory chunks for incoming data, write operations are rejected immediately.

Immediate Failure of Write Operations

When LRU eviction is disabled and the allocated memory ceiling is reached, any operation attempting to store new data or increase the size of existing data will fail:

  • Error Responses: Commands like set and add return an out-of-memory (OOM) error (typically SERVER_ERROR out of memory storing object) back to the client.
  • Deterministic Rejection: Every subsequent write fails until memory is explicitly cleared, meaning partial updates or burst traffic cannot be absorbed by the cache.
  • Read Continuity: Read operations (get) continue to function normally for keys already resident in memory.

Impact on Data Retention and Expiration

Disabling LRU does not mean data persists indefinitely; it only disables automatic eviction driven by capacity pressure:

  • TTL Expiration: Keys set with an expiration time still expire. Memcached will invalidate these items once their TTL elapses, freeing memory when the items are either accessed (lazy expiration) or cleared via the internal LRU crawler.
  • Explicit Deletion: Manual delete or flush_all commands remain the primary administrative mechanisms to reclaim memory immediately.

If write traffic outpaces the natural TTL expiration rate, memory exhaustion will occur, leaving the cache in a read-only state for all non-existent keys.

Architectural and Application Consequences

Running Memcached with the -M parameter fundamentally changes how upstream applications must handle cache interactions:

  • Application Exceptions: If client applications do not cleanly catch cache write exceptions, failed set commands can bubble up as unhandled errors, disrupting end-user requests.
  • Increased Database Load: When writes fail, subsequent read requests for new keys result in cache misses. This forces read traffic directly onto primary databases or backend services, increasing latency and creating the risk of a cache stampede.
  • Loss of Cache Elasticity: The cache can no longer silently adapt to shifts in working set sizes. Capacity planning becomes rigid, requiring strict monitoring of memory usage metrics to intervene before exhaustion occurs.

Disabling LRU eviction is typically reserved for specialized workloads where cached items must never be dropped before their explicit expiration, or where an out-of-memory error is preferable to serving stale data or losing critical cached state.
