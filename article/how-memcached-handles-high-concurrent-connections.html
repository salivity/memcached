How Memcached Handles High Concurrent Connections

This article explores the architectural mechanisms that allow Memcached to sustain sub-millisecond latencies under massive concurrency. By leveraging an asynchronous event-driven network model, dedicated multithreading pipelines, granular hash-table locking, and a deterministic slab allocation memory system, Memcached processes hundreds of thousands of concurrent connections without exhausting system resources or suffering from lock contention.

Asynchronous Event-Driven I/O

Memcached relies on libevent, a high-performance event notification library, to manage socket connections asynchronously. Instead of allocating a dedicated operating system thread per connection—which would cause severe context-switching overhead and memory exhaustion—Memcached uses non-blocking I/O multiplexing primitives such as epoll on Linux or kqueue on BSD.

When a client initiates a request, the network socket is registered with the event loop. The system kernel notifies Memcached only when data is ready to be read or written. This allows a tiny number of operating system threads to monitor tens of thousands of open file descriptors simultaneously without blocking on slow or idle network clients.

Multi-Threaded Dispatcher-Worker Architecture

Memcached isolates connection handling from request execution through a master-worker thread model:

  1. Dispatcher Thread: A single master thread listens on the network port for new incoming TCP connections. Once accepted, it assigns the connection to a worker thread using a round-robin distribution strategy.
  2. Worker Threads: Configured via the -t parameter (typically matching the host's CPU core count), each worker thread runs its own independent libevent loop. Worker threads handle all subsequent read, write, parse, and protocol processing operations for their assigned sockets.

Communication between the dispatcher and worker threads happens via lightweight Unix pipes or event notification queues, ensuring the dispatcher thread remains unblocked and ready to accept new handshakes.

Granular Locking and Reduced Lock Contention

Older versions of caching engines suffered from a single global lock that serialized all memory reads and writes. Memcached resolves this bottleneck using fine-grained, split-lock mechanisms:

  • Hash Table Bucket Locks: The global hash table is divided into multiple segments, each protected by an individual mutex. Two threads writing keys that map to different hash buckets do not block one another.
  • LRU Locks: Least Recently Used (LRU) maintenance operations use dedicated lock domains separated from general read operations.
  • Atomic Primitives: For counters and reference tracking, atomic CPU instructions are preferred over mutexes to keep CPU cycles focused on request processing rather than lock waits.

O(1) Memory Access via the Slab Allocator

Dynamic memory allocation using standard C malloc and free leads to heap fragmentation and variable lock contention under continuous read-write traffic. Memcached circumvents this with its custom Slab Allocator:

  • Memory is pre-allocated at startup in contiguous 1MB pages.
  • Pages are partitioned into slab classes containing fixed-size chunks tailored to different item sizes.
  • Inserting an item requires finding an appropriately sized chunk, while evictions or expirations simply return the chunk to its slab class's free list.

Because memory lookups, assignments, and evictions execute in strict \(O(1)\) time complexity, request latency remains constant regardless of the total number of connected clients or cache saturation levels.

Compact Connection State and Pipelining

To handle hundreds of thousands of connections, memory consumed by idle connections must remain minimal. Memcached structures each client state inside a lightweight internal structure (conn), dynamically allocating read and write buffers only when active payloads are processed. Additionally, support for binary protocols and multi-get pipelining allows clients to batch multiple commands into single TCP packets, minimizing network syscall overhead and maximizing throughput across high-concurrency environments.
