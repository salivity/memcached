Memcached GET and GETS: Processing CAS Tokens

This article explains how Memcached handles read operations through the get and gets commands, focusing specifically on how the server retrieves, generates, and returns Check-and-Set (CAS) tokens. You will learn about the internal item memory structure, how CAS tokens are assigned and incremented during mutations, and the exact protocol-level differences between standard reads and CAS-aware retrievals.

The Internal Representation of CAS in Memcached

In Memcached, every cached entry is represented internally by an item structure defined in the C source code. Along with the key, flags, expiration time, and data payload, each item contains a 64-bit integer (uint64_t) dedicated to the CAS identifier.

Memcached maintains a single global atomic counter for CAS generation. Whenever an item is created or updated through mutating commands like set, add, replace, append, prepend, or an atomic incr/decr, the server atomically increments this global counter and assigns the new 64-bit value to the item's internal CAS field. This ensures that every state change of a cache key receives a globally unique, monotonically increasing CAS identifier.

How the get Command Is Processed

When a client issues a standard get <key> command (using the Memcached text protocol):

  1. Parsing and Hashing: The server parses the key from the request stream and computes its hash value to locate the target bucket within the primary hash table.
  2. Lookup and Validation: The worker thread acquires the appropriate bucket lock and traverses the hash chain to find the matching item. Once found, Memcached checks whether the item has expired based on its TTL. If expired, it triggers an immediate lazy deletion and behaves as a cache miss.
  3. Response Construction: If the item is valid, Memcached reads the metadata (flags and byte length) and writes the response header to the client buffer in the format:
    VALUE <key> <flags> <bytes>\r\n
    Followed by the raw data chunk and ending with \r\nEND\r\n.
  4. CAS Omission: Although the underlying item structure contains the 64-bit CAS token in memory, the get command intentionally suppresses this field to conserve network bandwidth and maintain backward compatibility with older implementations.

How the gets Command Is Processed

The gets (Get with CAS) command uses the exact same hashing, lookup, lock management, and validation logic as the get command, but it changes how the response is formatted:

  1. Field Extraction: After successfully resolving the item in memory, the engine accesses the internal 64-bit CAS identifier alongside the flags and data length.
  2. Extended Header Output: The text protocol appends the CAS token as an additional numeric field at the end of the VALUE line:
    VALUE <key> <flags> <bytes> <cas_token>\r\n
    Followed by the value payload and the standard termination delimiter:
    <data>\r\nEND\r\n
  3. Multi-Key Support: When multiple keys are requested (e.g., gets key1 key2), Memcached iterates through the keys sequentially, returning a separate VALUE line with the respective CAS token for each hit, and completes the entire transmission with a single END\r\n.

Binary Protocol Differences

In the Memcached binary protocol, the distinction between get and gets is streamlined. The binary response header contains an explicit 8-byte field in its fixed 24-byte header structure reserved specifically for the CAS identifier.

When a standard binary Get or GetK request is processed, the server automatically populates the CAS field in the response header with the current 64-bit token stored in the item header. Clients using the binary protocol do not need a distinct command equivalent to gets to receive the CAS identifier; every standard read operation automatically surfaces the token for optimistic locking workflows.
