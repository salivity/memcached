Memcached Hash Table Expansion Under Heavy Writes

Under heavy write workloads, dynamic hash table expansion can introduce severe latency spikes and degraded throughput if handled synchronously. Memcached mitigates these performance hits by offloading hash table resizing to a dedicated background maintenance thread that incrementally migrates keys between tables. Combined with dual-table routing and granular bucket-level locking, this asynchronous design ensures client threads can continue executing reads and writes with minimal lock contention during large-scale expansions.

The Dedicated Maintenance Thread

In traditional hash table implementations, when the number of stored keys exceeds a set threshold, the thread initiating the write must allocate a larger table and rehash every item. In a cache storing millions of entries, this synchronous "stop-the-world" operation can block the entire process for hundreds of milliseconds or even seconds.

Memcached avoids this by delegating all rehashing operations to an asynchronous background thread known internally as the assoc_maintenance_thread. Worker threads simply serve client requests. When a worker thread inserts a key and detects that the total item count has exceeded 1.5 times the current hash table bucket capacity, it signals the maintenance thread via a condition variable and continues servicing client traffic without pausing.

Dual-Table Architecture

To facilitate expansion without interrupting traffic, Memcached allocates a new primary hash table that is double the size of the previous one. During the migration phase, Memcached operates with two active tables simultaneously:

  1. old_hashtable: The original hash table containing existing items awaiting migration.
  2. primary_hashtable: The newly allocated, larger hash table that receives migrated items and new inserts.

A global cursor index tracks the progress of the migration through the buckets of the old table.

Incremental Migration in Batches

Rather than locking the entire dataset, the maintenance thread processes migrations incrementally. It iterates through the old_hashtable in small, configurable batches (typically a few dozen to a few hundred buckets per cycle, governed by settings such as hash_bulk_move).

After moving a batch of items to their new bucket locations in the primary_hashtable, the maintenance thread updates the migration cursor and briefly yields execution. This incremental batching ensures that long-lived lock acquisitions do not starve incoming worker thread operations.

Granular Bucket-Level Locking

To keep lock contention low during key migration, Memcached relies on an array of fine-grained locks rather than a single global hash table lock.

  • The hash space is partitioned across thousands of discrete mutexes (item_locks).
  • When the maintenance thread moves a bucket, it acquires only the specific lock governing that bucket chain.
  • Worker threads serving reads or writes on unaffected buckets proceed in parallel without waiting.

Even when a worker thread accesses a bucket currently being processed by the maintenance thread, it experiences only the negligible microsecond delay needed to move that specific small batch of items.

Request Routing During Migration

While the maintenance thread is actively rehashing, incoming read, update, and delete requests must seamlessly find keys regardless of whether they have already moved. Memcached determines item locations using the migration cursor:

  • Reads (get): The worker thread computes the hash of the requested key. If the hash points to an index in the old table that has already been cleared (an index less than the migration cursor), it checks the primary_hashtable. If the index is equal to or greater than the cursor, the key may still reside in the old_hashtable, and the worker checks there before falling back to the new table.
  • Writes (set/add): New items are mapped and written directly to the primary_hashtable to avoid putting new entries into buckets slated for deprecation.
  • Deletes (delete): The worker checks the cursor and removes the item from whichever table currently holds it.

Completion and Cleanup

Once the migration cursor reaches the end of the old_hashtable, the maintenance thread releases the old table's memory allocation, resets its state, and enters an idle sleep state waiting on the condition variable for the next expansion trigger. Through this pipeline of asynchronous execution, batch processing, and fine-grained locking, Memcached maintains near-constant O(1) latency even under sustained high-frequency key insertions.
