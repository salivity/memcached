Memcached Variable Length Key Lookup Explained

Memcached delivers sub-millisecond data retrieval by combining a fast hashing algorithm with an associative hash table designed to handle variable-length keys. This article explains the internal mechanics of how Memcached hashes arbitrary-length string keys, maps them to hash table buckets, resolves collisions, and verifies exact matches to achieve an average lookup complexity of \(O(1)\).

Protocol Limits and Key Ingestion

Client applications can send keys of varying lengths up to a default limit of 250 bytes. When a command such as get <key> arrives, the Memcached worker thread receives the key as a raw byte sequence along with its length. Because memory management in Memcached requires deterministic behavior, the 250-byte limit ensures that key metadata fits cleanly into internal memory allocation units known as slabs.

Fixed-Size Hashing

Variable-length keys cannot be directly indexed into an array, so Memcached transforms the variable-length byte array into a fixed-size 32-bit integer.

Modern versions of Memcached use Murmur3 hash by default (or historically, Bob Jenkins' lookup3 hash). These non-cryptographic hash functions process the key in blocks of bytes, outputting a uniform 32-bit integer hash. This step ensures that regardless of whether a key is 3 characters or 200 characters long, it yields a uniform, fixed-length identifier.

Bucket Determination

Memcached maintains a primary hash table whose size is always a power of two (\(2^n\)), managed by an internal variable called hashpower. To map the 32-bit hash value to an index in the table, Memcached avoids expensive division operations and instead uses a bitwise AND mask:

\[\text{bucket\_index} = \text{hash} \ \& \ \text{hashmask}(\text{hashpower})\]

Where hashmask(hashpower) is equal to \((2^n - 1)\). This bitwise operation immediately directs the lookup process to a specific bucket slot in the hash table.

Bucket Traversal and Match Verification

Because different keys can hash to the same bucket index (hash collisions), each bucket slot contains a pointer to the head of a singly linked list of item structures.

Memcached traverses this linked list to find the target item using a two-step verification process to maintain high performance:

  1. Length Comparison (nkey check): Each item structure in memory stores an internal nkey field representing the exact length of the stored key. Before evaluating string contents, Memcached checks whether the search key's length equals it->nkey. If the lengths do not match, the entry is immediately skipped without reading the key payload.
  2. Byte-Level Comparison (memcmp): If the length matches, Memcached invokes memcmp to compare the raw bytes of the query key with the key stored inside the item structure. If every byte matches, the correct item is found, its access time is updated for the Least Recently Used (LRU) cache policy, and the item pointer is returned to the client handler.

Maintaining \(O(1)\) Performance with Rehashing

If the number of stored items significantly exceeds the number of available hash table buckets, the linked lists inside each bucket grow longer, degrading lookup speed from \(O(1)\) to \(O(n)\).

To prevent this, Memcached monitors its load factor. When the number of stored items exceeds 1.5 times the table capacity, a dedicated background maintenance thread triggers rehashing. This thread allocates a new hash table with double the buckets (\(2^{n+1}\)) and incrementally migrates linked list nodes from the old table to the new table. During migration, lookups seamlessly check both tables based on the migration progress, ensuring that key lookup latency remains consistently constant regardless of variable key lengths.
