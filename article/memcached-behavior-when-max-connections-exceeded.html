Memcached Behavior When Max Connections Exceeded

When Memcached receives connection requests beyond its configured limit, it does not crash or terminate active sessions; instead, it temporarily pauses accepting new TCP connections while continuing to serve established clients. This article explains how Memcached handles connection saturation at the event loop level, the role played by the operating system's network backlog, the exact errors client applications encounter, and how to identify and mitigate connection bottlenecks.

The Internal Mechanism: Halting Connection Acceptance

Memcached enforces a maximum concurrent connection ceiling controlled by the -c runtime parameter, which defaults to 1,024 connections. Memcached relies on an event-driven networking library (libevent) to process incoming network traffic.

When the number of active connections reaches the maxconns threshold, Memcached disables the read event on its listening socket. By taking this action, the server intentionally stops executing the accept() system call. It completely ignores new connection handshakes until at least one currently active connection terminates and frees up a slot.

The Role of the Operating System TCP Backlog

Because Memcached ceases to accept new connections, incoming TCP requests are held at the operating system kernel level in the TCP listen backlog queue. The size of this queue is determined by the Memcached -b parameter and the operating system’s net.core.somaxconn configuration.

  • Backlog has available capacity: The kernel completes the three-way TCP handshake (or leaves it half-open depending on OS configuration), but the connection remains stuck waiting for the application to accept it.
  • Backlog is fully saturated: The kernel cannot queue further connection requests. Depending on the operating system’s TCP stack settings (such as Linux's tcp_abort_on_overflow), the OS either silently discards incoming SYN packets or responds with a RST (reset) packet.

Impact on Client Applications

Clients experience distinct behaviors depending on whether they are already connected or attempting to initiate a new connection:

  • Existing Connections Remain Normal: Active connections continue to send commands (GET, SET, etc.) and receive responses without interruption. Hitting the connection limit does not degrade the throughput of already-established connections.
  • Connection Timeouts: Clients attempting to establish a new connection typically block. If the backlog queue holds the request without an accept(), the client application usually waits until its local connection timeout threshold expires, throwing errors such as ETIMEDOUT or framework-specific socket connection timeouts.
  • Immediate Connection Refusal: If the operating system backlog queue overflows and actively rejects packets, client applications receive immediate ECONNREFUSED (Connection Refused) errors.

Automatic Recovery

Once an existing client disconnects or times out, the active connection count drops below maxconns. Memcached detects this state change and re-enables the read event on the listening socket. The server immediately begins calling accept() again, draining the waiting connections from the TCP backlog in the order they arrived.

Diagnosing and Resolving the Issue

To verify whether Memcached is hitting its connection limit, query the server using the stats command via Telnet or nc:

stats

Look for the following key metrics:

  • curr_connections: The number of currently open connections.
  • maxconns: The configured maximum connection limit.
  • listen_disabled_num: The number of times Memcached hit its connection limit and temporarily stopped accepting new connections. If this value is greater than zero and increasing, the limit is being exceeded.

To resolve connection exhaustion, increase the limit by passing a higher value to the -c flag at startup (e.g., -c 4096), ensuring that the operating system's file descriptor limits (ulimit -n) are raised accordingly. Additionally, applications should use persistent connection pooling instead of opening and closing connections on every request, reducing connection churn and aggregate concurrency.
