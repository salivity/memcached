Graceful Shutdown of Memcached Containers

Graceful shutdown of running Memcached containers involves coordinating container orchestrators, process signal handling, and client-side routing to terminate instances without dropping active connections or causing cache stampedes. Because Memcached stores data in volatile memory and focuses on ultra-low latency, orchestrators like Docker and Kubernetes rely on phased teardowns—deregistering instances from service discovery, waiting for in-flight requests to complete, and safely terminating the daemon via operating system signals.

The Container Termination Sequence

When a container orchestrator initiates the shutdown of a Memcached container, it follows a structured lifecycle:

  1. Endpoint Deregistration: The orchestrator removes the target container's IP address from active service pools, endpoints, or DNS records to stop new traffic from reaching the node.
  2. Signal Dispatch (SIGTERM): The orchestrator sends a SIGTERM signal to PID 1 inside the container, notifying the application that shutdown has commenced.
  3. Grace Period Countdown: A predefined timer (such as Kubernetes' terminationGracePeriodSeconds) begins counting down.
  4. Forced Termination (SIGKILL): If the container does not exit before the grace period expires, the orchestrator sends a SIGKILL signal, abruptly terminating the process.

Process Handling and PID 1 Pitfalls

Memcached responds to standard termination signals like SIGINT and SIGTERM by breaking its event loop, closing active listening sockets, and exiting. However, inside a container, process isolation requires that the signal properly reaches the binary:

  • Signal Forwarding: If Memcached is launched via a shell wrapper script without using exec (e.g., sh -c memcached), the shell runs as PID 1 and may swallow incoming SIGTERM signals. To ensure graceful handling, use the exec form in the Dockerfile ENTRYPOINT or CMD, or use an init system like tini or dumb-init.
  • Immediate Socket Closure: By default, Memcached terminates rapidly once it receives SIGTERM. It does not support extensive connection draining mechanisms natively; it immediately stops accepting new connections and exits after current event iterations.

Coordinating with Kubernetes PreStop Hooks

Because Memcached terminates almost instantly upon receiving SIGTERM, an orchestrator may deliver the termination signal before networking layers (such as kube-proxy, cloud load balancers, or ingress controllers) have completely removed the pod IP from routing tables. This race condition leads to client connection errors.

To prevent this, deployments use a preStop lifecycle hook:

lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 5"]

The preStop hook executes before SIGTERM is sent. A short pause (e.g., 5 to 10 seconds) delays the container's shutdown, giving network layers, service meshes, and client libraries sufficient time to detect node withdrawal and stop routing read/write operations to the shutting-down instance.

Handling Client Connections and Data Volatility

Because Memcached is an ephemeral cache rather than a persistent database, graceful shutdown focuses on network stability rather than flushing state to disk:

  • Client-Side Hashing and Ejection: Memcached clients typically employ consistent hashing (such as Ketama). When a container shuts down, clients must detect the socket closure or receive updated cluster topologies to redirect keys to remaining nodes or degrade gracefully to the primary datastore.
  • Connection Draining: Applications using persistent connection pools must handle dropped connections gracefully. The delay introduced by network deregistration allows clients to complete pending get and set commands rather than receiving TCP reset (RST) packets during an active transfer.
  • Warm-up Strategies: Shutting down multiple Memcached containers simultaneously can trigger a cache stampede against downstream databases. Orchestrators should enforce rolling updates with a conservative maxUnavailable setting (e.g., terminating only one replica at a time) to allow backend databases to absorb the temporary drop in cache hit ratio.
