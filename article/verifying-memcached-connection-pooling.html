Verifying Memcached Connection Pooling

Connection pooling in Memcached improves application performance by maintaining a set of reusable TCP connections, avoiding the high overhead of establishing a new handshake for every cache operation. Verifying that connection pooling functions correctly involves inspecting Memcached server statistics, monitoring operating system socket states, and analyzing network traffic under load. This guide details the practical methods developers can use to ensure their client-side connection pool is active, correctly sized, and avoiding connection churn.

1. Monitor Server-Side Connection Statistics

The most direct way to check connection behavior is by querying the Memcached server's internal metrics. You can inspect these stats using telnet or nc (netcat):

echo "stats" | nc 127.0.0.1 11211

Pay close attention to two specific metrics:

  • curr_connections: The number of currently open connections to the server.
  • total_connections: The cumulative count of connections opened since the Memcached service started.

Verification criteria: Under consistent application traffic, curr_connections should stabilize around your expected pool size (e.g., client instances multiplied by configured pool capacity). More importantly, total_connections should remain relatively static. If total_connections increments continuously with every incoming cache read or write, the client is tearing down and reopening connections rather than reusing them from a pool.

2. Inspect OS Socket States with ss or netstat

You can verify connection lifecycle behavior directly on either the application host or the database host by checking the state of TCP sockets.

Run the following command on the client or server:

ss -tan '( sport = :11211 or dport = :11211 )'

Verification criteria:

  • Persistent ESTABLISHED sockets: You should observe a steady number of sockets in the ESTABLISHED state corresponding to your pool configuration.
  • Absence of TIME_WAIT churn: A high number of sockets in the TIME_WAIT state indicates that connections are being actively closed and reopened. While a few TIME_WAIT sockets can occur during pool resizing or node rebalancing, continuous TIME_WAIT generation under load is a definitive sign that connection pooling is failing.

3. Trace Network Packets Using tcpdump

For definitive proof at the protocol level, inspect the raw network traffic between your application and Memcached. Run a packet capture on the Memcached port:

sudo tcpdump -i any -nn port 11211

Verification criteria:

  • Healthy pooling: You should see TCP packets containing payload data (Psh/Ack flags) exchanged over the same source and destination port pairs repeatedly.
  • Failed pooling: If you observe frequent 3-way handshakes ([S] / SYN flags) followed immediately by connection terminations ([F] / FIN or [R] / RST flags) for individual requests, the client is operating in a single-use connection pattern instead of drawing from a managed pool.

4. Enable Client-Side Debug Logging and Metrics

Most mature Memcached client libraries (such as Spymemcached for Java, EnyimMemcached for .NET, or PyMemcache for Python) offer configuration options to expose pool telemetry.

  • Client Metrics: Export client metrics into monitoring systems like Prometheus or Datadog. Track pool-specific metrics such as active_connections, idle_connections, pool_exhausted_count, and borrow_wait_time.
  • Debug Logging: Temporarily set the client logger level to DEBUG or TRACE in a staging environment. Verify log outputs to confirm that worker threads are acquiring existing connections from the pool queue and releasing them back, rather than triggering initialization routines on each operation.

5. Run a High-Concurrency Load Test

Connection pooling issues frequently disguise themselves during low-traffic local development. Simulate concurrent traffic using tools like Apache Bench (ab), k6, or custom scripts executing multiple simultaneous cache requests.

Observe the relationship between request volume and connections. When connection pooling functions correctly, an increase from 10 to 1,000 requests per second should significantly increase throughput and maintain stable socket counts without triggering connection timeout errors or running out of local ephemeral ports.
