How Memcached Maintains Stable Memory Footprints

Memcached achieves predictable, long-term memory stability in high-throughput production environments through an architecture designed to prevent memory fragmentation and leaks. Rather than allocating and freeing memory dynamically via standard system calls, Memcached relies on a pre-allocated slab allocation system, a strict memory ceiling, categorized Least Recently Used (LRU) eviction algorithms, and dynamic page rebalancing. Together, these mechanisms ensure that Memcached maintains a flat, deterministic memory footprint over months or years of continuous operation.

The Slab Allocation Engine

The primary reason Memcached avoids memory growth over time is its slab allocator. Standard operating system memory management using malloc and free often leads to severe external fragmentation when handling millions of variable-sized keys, causing process memory to balloon even when the actual stored data size remains constant.

To eliminate this, Memcached allocates its entire configured memory space upfront in a single, large pool during startup. This pool is subdivided into 1MB pages, which are then assigned to specific "slab classes." Each slab class is responsible for storing items within a defined size range, divided into uniform chunks (e.g., class 1 for items up to 96 bytes, class 2 for items up to 120 bytes, scaling by a default growth factor of 1.25). When an item is stored, Memcached places it into the smallest slab class that can accommodate it. Because chunks are reused in place without releasing memory back to the OS kernel, external memory fragmentation is practically eliminated.

Segmented LRU Eviction

When the pre-allocated memory pool fills up, Memcached does not request additional RAM from the host operating system. Instead, it maintains a strict ceiling by evicting stale data using an optimized Least Recently Used (LRU) mechanism.

Modern Memcached architectures employ a Segmented LRU (also known as the crawler/segmented LRU) to prevent memory churn and transient cache storms from flushing out valuable hot data. Memory within each slab class is split into distinct queues:

  • HOT: Holds newly inserted items; items are not updated here.
  • WARM: Holds items that have been accessed more than once, shielding long-lived cache data from one-hit wonders.
  • COLD: Holds inactive items that flow down from HOT and WARM queues.

Evictions only occur from the tail of the COLD queue when a specific slab class runs out of available chunks and cannot claim new pages. By constraining evictions to specific slab classes, Memcached guarantees that memory reclamation is continuous and predictable without causing execution pauses.

Slab Rebalancing and Automove

A historical weakness of slab allocation was "slab calcification"—a scenario where an application's data size profiles shift over time, leaving unused memory trapped in certain slab classes while other classes suffer frequent evictions.

Memcached resolves this through an internal background thread called the slab rebalancer. When configured with slab automove, the engine monitors eviction rates and free chunk counts across all classes. If it detects that one class is starved of memory while another has unused pages, it safely unlinks a 1MB page from the donor class, clears the memory, and assigns it to the starved class. This background migration allows Memcached to adapt dynamically to changing workloads without restarting or inflating its resident set size (RSS).

Zero-Allocation Hot Paths

During normal request handling, Memcached operates on zero-allocation principles for key-value operations. Buffers for incoming network requests and outgoing responses are reused, and item metadata is tracked with fixed-overhead headers. Because execution threads cycle through existing pointers rather than creating new OS-level allocations, heap growth remains effectively flat, securing rock-solid memory stability under prolonged production workloads.
