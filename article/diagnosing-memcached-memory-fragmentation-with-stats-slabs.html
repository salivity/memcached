Diagnosing Memcached Memory Fragmentation with Stats Slabs

Memcached relies on a slab allocation mechanism to manage memory and prevent operating system-level memory fragmentation, but it can still suffer from internal memory fragmentation and slab calcification. The stats slabs command is the primary diagnostic tool used to inspect the internal state of these slab classes. By providing detailed metrics on page allocations, chunk utilization, and wasted space within each class, the command allows administrators to identify mismatched chunk sizes, uneven memory distribution, and inactive memory pools that hinder caching efficiency.

Understanding Memcached Slab Allocation

Memcached divides its assigned memory into 1MB pages. These pages are assigned to specific "slab classes," each tailored to store items within a particular size range determined by the chunk size and a growth factor. Once a page is assigned to a slab class, it is sliced into uniform chunks.

Fragmentation in Memcached generally occurs in two ways:

  1. Internal Fragmentation: Occurs when the size of a stored object is smaller than the assigned chunk size, leaving unused bytes inside the chunk.
  2. Slab Calcification (External Allocation Imbalance): Occurs when pages are permanently assigned to slab classes based on historical traffic patterns, leaving high-demand classes out of memory while low-demand classes hold idle, unreleased pages.

Key Metrics Provided by stats slabs

Executing the stats slabs command via Telnet or netcat returns operational statistics for each active slab class (represented by an integer ID), followed by global slab counters. The most critical per-slab fields for diagnosing fragmentation include:

  • chunk_size: The maximum size of an item (in bytes) that can fit into this slab class.
  • chunks_per_page: The number of chunks created per 1MB page (1,048,576 / chunk_size).
  • total_pages: The total number of 1MB pages currently allocated to the slab class.
  • total_chunks: The total capacity of the slab class (total_pages * chunks_per_page).
  • used_chunks: The number of chunks currently storing active data.
  • free_chunks: The number of chunks that have been freed (e.g., via item deletion or expiration) and are available for immediate reuse.
  • free_chunks_end: The number of allocated chunks at the end of the newest page that have never been written to.

Identifying Internal Fragmentation

Internal fragmentation is directly tied to the relationship between the chunk_size of a slab class and the average size of the keys and values being inserted.

If a slab class has a chunk_size of 512 bytes, but the application consistently writes items that are 260 bytes, nearly half of the memory allocated to that slab class is wasted. While stats slabs gives the static capacity via chunk_size, pairing it with the stats items command—which reports item counts and age—allows you to calculate the delta between allocated space (used_chunks * chunk_size) and the actual byte payload stored. A large discrepancy indicates that the chunk growth factor is too aggressive, creating overly large gaps between sequential slab classes.

Identifying Slab Calcification and Idle Memory

Slab calcification can be spotted using total_pages, used_chunks, and free_chunks:

  • Underutilized Classes: A slab class showing a high total_pages count alongside a low used_chunks count and a high free_chunks count indicates reserved memory that is sitting idle.
  • Starved Classes: Conversely, if another slab class has high used_chunks, zero free_chunks, zero free_chunks_end, and experiences frequent evictions (visible in stats items), that class is memory-starved.

Because Memcached historically locked pages to classes permanently, pages in the underutilized class could not be borrowed by the starved class.

Remediation Based on stats slabs Output

Once stats slabs pinpoints the nature of the fragmentation, you can apply targeted configuration changes:

  • Tuning the Growth Factor (-f): If internal fragmentation is high, lower the growth factor (default is typically 1.25). A lower factor (e.g., 1.1) creates more slab classes with smaller size increments, minimizing wasted space per chunk.
  • Enabling Slab Rebalancing: To solve slab calcification, enable runtime page reassignment by starting the daemon with -o slab_reassign,slab_automove=1 (or slab_automove=2 for aggressive balancing). This allows Memcached to automatically detect classes with high numbers of free pages and reassign them to classes experiencing eviction pressure.
  • Adjusting Minimum Chunk Size (-n): If tiny items are causing waste in the lowest slab classes, adjust the minimum allocated chunk size to closely match the application's smallest payload.
