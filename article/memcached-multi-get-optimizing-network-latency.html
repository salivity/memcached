Memcached Multi-Get: Optimizing Network Latency

Memcached’s multi-get operation allows applications to retrieve values for multiple keys in a single operation rather than issuing discrete queries sequentially. This article explains how multi-get mitigates network latency by reducing round-trip times (RTT), optimizing socket utilization through protocol-level batching, routing requests efficiently across distributed clusters, and streaming server responses.

Eliminating Round-Trip Time Overhead

The primary source of latency in distributed cache access is the network round-trip time (RTT), not the in-memory lookup. When querying \(N\) keys individually, a traditional approach incurs \(N \times \text{RTT}\) in synchronous execution. Even with connection pooling or threading, issuing discrete requests increases TCP packet overhead, operating system context switching, and network queueing.

Memcached resolves this by grouping multiple keys into a single command. By requesting a batch of keys at once, the client reduces the network cost from \(N \times \text{RTT}\) down to essentially a single RTT per involved cache node.

Client-Side Grouping and Parallel Dispatch

Because Memcached operates as a shared-nothing distributed architecture, individual keys are distributed across different nodes using consistent hashing. The Memcached server itself does not coordinate with other nodes. Consequently, the multi-get optimization begins entirely on the client side:

  1. Key Hashing: The client library hashes each requested key to identify which target server holds it.
  2. Batch Segmentation: The client groups the keys into separate batches, one for each relevant server.
  3. Concurrent Execution: The client dispatches these batch requests across multiple server connections in parallel using non-blocking, asynchronous I/O (such as epoll or event loops).

This ensures that network latency is bound only by the slowest responding server node rather than the cumulative response times of all servers.

Protocol Optimization: Text vs. Binary

Memcached optimizes packet transmission differently depending on the protocol version used:

  • Text Protocol: The client sends a single command line containing all keys separated by spaces: get key1 key2 key3 ...\r\n. The server processes this line, writes matching VALUE responses sequentially, and appends an END\r\n marker.
  • Binary Protocol (GetKQ): The binary protocol offers an even higher level of optimization using the "Get Quiet" (GetKQ) command. Instead of sending a miss response for every missing key, the server only responds to cache hits. The client appends a standard, non-quiet command (such as a dummy No-op or a standard GetK) at the end of the batch. When the client receives the response to the terminal command, it knows the batch is complete and that any unreturned keys were cache misses. This eliminates the transmission of empty or error responses, significantly conserving bandwidth.

Socket Buffering and Kernel-Level Efficiency

Multi-get maximizes Ethernet frame utilization. Sending keys individually produces many small TCP packets that may fall victim to Nagle's algorithm or incur significant overhead from TCP/IP headers (typically 40 to 60 bytes per packet).

With multi-get, both the request and response payloads are aggregated into the socket buffer. The operating system packs as many keys and values as possible up to the Maximum Transmission Unit (MTU)—typically 1,500 bytes—before transmitting a packet. On the server side, Memcached looks up the keys in memory and streams the data back into the network buffer in bulk, minimizing system calls (read and write) on both ends of the connection.
