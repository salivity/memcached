Memcached CPU Spikes on Idle Servers Explained

Even when a Memcached server is not actively serving client traffic, scheduled maintenance routines and internal background processes can cause sharp spikes in CPU utilization. This article breaks down the primary architectural and system-level causes of these spikes, including background LRU maintenance, hash table resizing, slab rebalancing, memory defragmentation, and OS-level maintenance processes.

1. LRU Maintainer and Crawler Threads

Memcached uses a segmented Least Recently Used (LRU) algorithm to manage memory across hot, warm, and cold tiers. When background maintenance is enabled:

  • LRU Maintainer (lru_maintainer): Periodically wakes up to balance items between the hot, warm, and cold LRU chains. If millions of keys reside in memory, scanning and moving items between queues consumes significant compute cycles.
  • LRU Crawler (lru_crawler): Scans memory to identify and reclaim expired items. Triggering a crawl—either automatically or via administrative command—requires traversing deep linked lists, creating bursts of CPU activity while an idle server processes dead data.

2. Hash Table Expansion and Rehashing

When an idle server still holds a large volume of previously written keys, the internal hash table might undergo expansion or maintenance:

  • The assoc_maintenance_thread is responsible for resizing the primary hash table when the ratio of items to buckets exceeds a predefined threshold.
  • Rehashing is performed in chunks to avoid blocking operations, but on large datasets, this background iteration consistently consumes CPU cycles until the hash table migration is complete.

3. Slab Automove and Page Rebalancing

Memcached organizes memory into slab classes based on item sizes. When slab automove is enabled (slab_automove):

  • Background threads evaluate whether memory pages are trapped in underutilized slab classes.
  • Moving a 1MB memory page from one slab class to another requires detaching, re-allocating, and updating pointers for the memory block.
  • This process acquires locks on slab classes, and the continuous evaluation loop can drive up CPU usage, particularly when memory is fragmented.

4. Processing flush_all Commands

Executing a flush_all command invalidates all existing items by updating an internal global timestamp rather than immediately freeing memory:

  • Subsequent background scans or lazy-expiration routines must evaluate items against the new invalidation timestamp.
  • If combined with an active LRU crawler run to physically free pages, the CPU will jump significantly while processing the sudden mass-expiration of the entire cache.

5. Transparent Huge Pages (THP) and Kernel Compaction

System-level memory management can directly affect an idle Memcached process:

  • If Linux Transparent Huge Pages (THP) are enabled, the kernel's khugepaged thread actively attempts to locate, allocate, and defragment contiguous 2MB blocks of physical memory.
  • Because Memcached allocates large heaps, the memory compaction process triggers extensive memory scanning and page copying, resulting in high kernel/system CPU time (sys%) rather than user CPU time (user%).

6. Contention on Global Locks

During internal maintenance, Memcached threads frequently rely on mutexes:

  • Heavy maintenance routines—such as large-scale rehashing or slab reassignment—acquire global locks to ensure data integrity.
  • If multiple worker threads or background maintenance threads spin or contend for these locks, the operating system registers increased CPU utilization due to context switching and lock contention overhead.
