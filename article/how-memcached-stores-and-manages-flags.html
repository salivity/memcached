How Memcached Stores and Manages Flags

Memcached stores flags as opaque, 32-bit unsigned integers directly within its internal memory structures alongside the key, value, and expiration time. Rather than interpreting or modifying these values, the server treats flags strictly as client-defined metadata, saving them in the item header allocation and returning them unaltered during read operations. This design allows client libraries to attach critical contextual information—such as serialization formats or compression states—without imposing any parsing or processing overhead on the Memcached engine itself.

The Role and Definition of Flags

In both the text and binary Memcached protocols, the flags parameter is provided by the client during write operations such as set, add, replace, append, and cas. Originally implemented as a 16-bit integer, modern versions of Memcached standardize flags as a 32-bit unsigned integer (uint32_t), providing values ranging from 0 to 4,294,967,295.

Because Memcached only accepts raw byte arrays for values, it has no native concept of data types. Flags bridge this gap on the client side. Common client-side use cases include marking whether a payload:

  • Is a raw string, an integer, or a serialized object (such as JSON, PHP serialize, or Python pickle).
  • Has been compressed using algorithms like zlib, Snappy, or Gzip.
  • Has been encrypted before transit.

Internal Storage Architecture

Memcached uses a slab allocator to manage memory efficiently and prevent fragmentation. Memory is divided into slabs, which are further divided into uniform chunks allocated to store cache entries called item structures.

When an item is stored, Memcached allocates a chunk that accommodates:

  1. The primary item C-struct header (containing pointers, LRU metadata, reference counts, and time-to-live attributes).
  2. The key string.
  3. Auxiliary metadata, which includes the flags value.
  4. The actual data payload.

In the internal C source code, the flags are maintained directly alongside the item definition. When an allocation request is processed, the server copies the incoming integer flag value into this reserved header space within the assigned memory chunk. The flag occupies a fixed 4 bytes of memory per cached item, regardless of whether the client sets the value to 0 or uses the full 32-bit range.

Zero-Interpretation and Pass-Through Management

The fundamental architectural principle behind Memcached's flag management is complete passivity. The server does not parse, evaluate, or execute any logic based on the flag value.

  • Write Phase: When a command like set user:1000 1 3600 5\r\n is received, the second argument (1) is read as an unsigned integer and placed directly into the item's metadata field.
  • Storage Phase: The flag remains unchanged in RAM inside the assigned slab chunk throughout the item’s lifecycle. It does not affect LRU eviction priority, slab class assignment, or memory expiration calculations.
  • Read Phase: When a client issues a get user:1000 command, Memcached locates the item, reads the 4-byte flag from the item header, and emits it in the response line (VALUE user:1000 1 5\r\n).

Protocol Differences

While the storage mechanism in RAM is identical, the protocols expose flags slightly differently:

  • Text Protocol: Flags are represented as human-readable ASCII integers separated by spaces in write commands and retrieval responses.
  • Binary Protocol: Flags are packed into a dedicated 4-byte field inside the "extras" section of the binary request frame (for mutation commands) and response frame (for retrieval commands), eliminating the string-parsing overhead of the text protocol.

By maintaining flags as opaque, 4-byte metadata fields preserved through read-write cycles, Memcached provides an extensible communication layer for client libraries while preserving optimal memory layouts and microsecond-level retrieval speeds.
