Impact of Linux Swap on Memcached Latency

Memcached relies entirely on Random Access Memory (RAM) to provide predictable, sub-millisecond response times for distributed caching. When Linux swap space is active, the operating system's kernel can page idle or allocated Memcached memory blocks out of physical RAM and onto disk storage. This transition from nanosecond-speed memory access to millisecond-speed disk I/O introduces severe page faults, leading to erratic tail latencies, CPU stalling, and unpredictable caching performance across client applications.

The Conflict Between Memcached and the Linux Virtual Memory Subsystem

Memcached implements its own internal memory manager using a slab allocator. It pre-allocates large chunks of memory and uses an internal Least Recently Used (LRU) algorithm to evict expired or older items when memory limits are reached. Memcached operates under the architectural assumption that all its allocated address space resides in physical RAM.

Linux, by default, optimizes memory usage by balancing anonymous memory (process memory) and page cache (file buffers). Even when total RAM appears sufficient, the Linux kernel's virtual memory subsystem may proactively move inactive anonymous memory pages to swap storage to prioritize disk caching, particularly when the vm.swappiness kernel parameter is left at its default value (typically 60).

Major Page Faults and Latency Spikes

The primary hazard of swap space to Memcached is the major page fault. Under normal operation:

  • RAM access: Operates in tens to hundreds of nanoseconds.
  • NVMe/SSD access: Operates in tens to hundreds of microseconds.
  • Spinning disk access: Operates in milliseconds.

When a client queries a key whose memory page has been evicted to swap, the CPU cannot complete the operation immediately. The kernel halts the requesting Memcached worker thread and initiates a synchronous major page fault to retrieve the data block from disk.

Because Memcached uses non-blocking event loops across a finite pool of worker threads, a single blocked worker thread servicing a swap-induced page fault cannot process other incoming network requests. This causes request queuing, which inflates 99th and 99.9th percentile (P99/P999) latencies by factors of 100x to 1,000x. To client applications, this erratic latency manifests as sudden, intermittent connection timeouts.

Disruption of Built-In Eviction Logic

Memcached is explicitly designed to handle low-memory scenarios by evicting cold data based on its own metrics. The presence of swap disrupts this mechanism:

  1. Kernel Subversion: The Linux kernel manages swap at the OS page level (typically 4 KB pages), completely blind to Memcached's slab structures and object keys.
  2. Hidden Memory Pressure: Memcached cannot detect that its memory has been offloaded to disk. Because memory appears available from the process's perspective, Memcached will not trigger its internal LRU eviction logic, even though physical RAM is fully saturated.
  3. Throttled Garbage Collection: Eviction routines scanning through slabs to clear old records risk touching swapped-out pages, forcing the system to read expired data back into RAM just to discard it, amplifying disk I/O thrashing.

Recommended System Configuration for Stability

To preserve Memcached latency stability, the memory footprint must remain locked in physical RAM. Standard production practices include:

  • Disabling Swap Completely: The most effective way to eliminate swap-induced latency jitter on dedicated cache servers is running swapoff -a and removing swap partitions from /etc/fstab.
  • Locking Process Memory: Starting Memcached with the -k (--lock-memory) flag causes the daemon to call mlockall(). This system call instructs the Linux kernel to lock all current and future process memory into RAM, preventing it from ever being paged out.
  • Tuning vm.swappiness: If swap cannot be disabled due to operational policies, reduce the system swappiness parameter to 1 via sysctl vm.swappiness=1. This tells the kernel to avoid swapping process memory unless the system is on the verge of an Out-Of-Memory (OOM) condition.
  • Accurate Sizing (-m flag): Ensure the memory allocated to Memcached via the -m parameter leaves enough headroom (typically 15% to 25% of total physical RAM) for operating system overhead, network buffers, and monitoring agents to prevent system-level OOM killer invocations.
