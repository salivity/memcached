How Memcached Scales Across Multiple CPU Cores

Memcached avoids single-thread CPU bottlenecks by implementing a multi-threaded, event-driven architecture that distributes network traffic and data operations across multiple processor cores. Instead of relying on a single execution thread for all tasks, it combines a dedicated connection dispatcher, independent worker threads with isolated event loops, and granular locking mechanisms across its storage engine. This design allows high-throughput read and write operations to execute concurrently without causing severe lock contention or idle CPU capacity.

The Master Dispatcher and Worker Thread Model

Memcached divides execution duties between a primary master thread and a pool of worker threads configured at startup. The master thread is responsible solely for listening on network sockets and accepting incoming TCP connections.

Once a client establishes a connection, the master thread assigns the resulting file descriptor to one of the worker threads using a round-robin distribution strategy. Communication between the master and worker threads is handled via internal pipes or event file descriptors (eventfd). This handoff ensures that the master thread is never blocked by data processing and can continuously accept new connections, preventing network-level bottlenecks.

Independent Per-Thread Event Loops

Each worker thread runs its own instance of libevent, an asynchronous event notification library. When a worker thread receives an assigned connection, it takes full ownership of that client's socket for the remainder of the session.

Because each worker handles its own I/O polling, network reads, protocol parsing, and response serialization occur independently across multiple CPU cores. A slow network client or a compute-heavy query on one worker thread does not degrade the processing capacity of other worker threads. Furthermore, pinning a connection to a specific worker enhances CPU cache locality, as thread context switching and core migration are minimized.

Granular Locking for Shared Memory Access

While independent worker threads prevent I/O bottlenecks, concurrent access to the shared key-value cache requires synchronization. Memcached prevents threads from blocking one another through fine-grained locking rather than a single global mutex:

  • Hash Table Bucket Locks: Instead of locking the entire hash table during key lookups or insertions, Memcached uses striped item locks. The hash table is divided into multiple lock partitions based on key hashes. Multiple threads can read, insert, or delete items simultaneously as long as the items map to different hash buckets.
  • Per-Slab Memory Allocation Locks: Memory in Memcached is organized into slab classes based on item size. Memory allocations and deallocations acquire locks specific to the targeted slab class rather than locking the entire memory allocator.
  • Segmented LRU Locks: The Least Recently Used (LRU) eviction system is split into sub-LRU lists (such as HOT, WARM, and COLD) within each slab class. Dedicated background threads handle memory compaction and item migration between these lists, isolating background maintenance work from active read and write operations handled by worker threads.

By decoupling connection handling from data processing and using partitioned locks over shared memory, Memcached scales throughput linearly with CPU core counts, eliminating the single-thread limitations common to simpler in-memory datastores.
