What Happens When Memcached Worker Queues Fill Up?

When Memcached worker queues fill completely, the server can no longer process incoming operations at the rate they arrive, leading to severe latency spikes, client-side timeouts, and dropped connections. This article examines the internal mechanisms triggered inside Memcached during queue exhaustion, how active client requests are affected, and why communication between the application and cache layer breaks down.

Memcached Threading and Queue Architecture

Memcached uses a multi-threaded, event-driven model powered by libevent. It consists of a single master thread and multiple worker threads:

  1. The Master Thread: Listens for incoming network connections and dispatches them across worker threads using a round-robin algorithm. It places connection notifications onto each worker thread's internal connection queue (CQ).
  2. Worker Threads: Each worker thread runs its own event loop, responsible for reading requests, processing key lookups or storage operations, and writing responses back to its assigned client connections.

When an extreme load spike occurs or worker threads become blocked, the internal queues and associated operating system socket buffers saturate.

The Breakdown of Active Operations

When thread worker queues reach maximum capacity, active client operations suffer the following chain reaction:

1. Severe Processing Latency

Worker threads processing commands sequentially on their event loops fall behind. While items wait inside the worker's queue, the time to service an active operation shifts from sub-millisecond execution to tens or hundreds of milliseconds. Operations already accepted into the queue remain held until the thread can cycle through previous commands.

2. TCP Backpressure and Socket Buffer Saturation

Because the worker thread is overwhelmed, it stops reading data off the socket. This causes the operating system’s kernel TCP receive buffer to fill completely.

Once the receive buffer is full, the server sends a TCP Zero Window notification to the client. This tells the client operating system to halt transmission of any further packets. As a result, active client operations attempting to write new requests become completely blocked at the kernel level.

3. Client-Side Timeouts

Memcached protocol operations do not have internal server-side timeouts that drop slow requests proactively. Instead, the failure manifests on the client side:

  • Read Timeouts: The client has sent a command (such as get or set), but the worker thread has not processed it before the client's configured timeout window expires.
  • Write Timeouts: The client cannot write the full request payload because TCP backpressure has blocked the socket.

When these thresholds are exceeded, the client runtime marks the operation as failed and typically throws a timeout exception to the application.

4. Connection Termination and Reset Storms

When a client application experiences a timeout on an active operation, standard Memcached client libraries abort and close the broken connection to prevent out-of-order response matching.

When the Memcached worker thread finally catches up and attempts to read from or write to that connection, it receives a Broken pipe (EPIPE) or Connection reset by peer (ECONNRESET) error. The worker thread then destroys the connection state, discarding any queued responses or unread requests associated with that specific connection.

5. Master Thread Rejection of New Operations

If the worker queues remain full, the master thread can no longer push new connections into worker queues. Depending on system limits, the master thread either stops accepting new connections—causing connection backlogs at the OS listen() queue—or immediately drops new connection attempts, returning Connection refused to the clients.

Preventing Queue Saturation

To prevent worker queues from filling completely under heavy loads:

  • Tune Worker Thread Count: Ensure Memcached is running with an optimal number of worker threads via the -t parameter (commonly matching the number of physical CPU cores).
  • Enable Connection Pooling: Reuse existing persistent connections to avoid overwhelming the master thread with constant connection setup and teardown.
  • Configure Sensible Client Timeouts: Keep client timeouts realistic to fail fast without prematurely severing connections during transient traffic spikes.
  • Scale Horizontally: Shard data across additional Memcached nodes to reduce the per-instance request load before hardware limits are reached.
