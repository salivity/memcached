How Memcached Enforces Slab Chunk Item Boundaries

Memcached enforces strict memory boundaries across cached items by pairing a deterministic slab allocation model with precise byte-level offsets inside pre-allocated chunks. During a set operation, the engine computes the exact memory footprint required for an incoming record, selects an appropriately sized chunk, and relies on fixed-length headers and controlled memory copies to prevent data from bleeding into adjacent slots. This architecture guarantees memory isolation without the overhead of runtime memory defragmentation.

Total Size Calculation and Slab Selection

Before allocating any memory during a set command, Memcached determines the exact byte count required to store the item. The total size is computed as the sum of:

  • The internal item metadata structure (sizeof(item)).
  • The key length plus a null terminator (nkey + 1).
  • The suffix containing flags and ASCII representations of data size.
  • The actual payload length (nbytes).
  • Optional features such as CAS (Check-And-Set) 64-bit identifiers.

Once the total size is determined, the engine checks whether it exceeds the maximum allowable item size (typically 1MB by default). If the size is valid, Memcached consults its slab class catalog to find the smallest slab class whose fixed chunk size is greater than or equal to the calculated item size.

Chunk Isolation within Slab Pages

Memcached organizes memory into 1MB pages assigned to specific slab classes. Each page is cut into uniform, fixed-size chunks at initialization. Because chunks represent distinct physical address ranges, Memcached manages them via pointer arrays and free lists.

When a chunk is selected for an incoming set operation—either from the free list or by evicting an existing item via the Least Recently Used (LRU) algorithm—the engine operates solely within the memory bounds assigned to that specific chunk's pointer. There is no contiguous write pointer traversing across multiple chunks, meaning an operation in one chunk cannot physically spill over into an adjacent chunk on the page.

Layout Enforcement and Bounded Writes

Inside the assigned chunk, the data layout is strictly ordered: the item header sits at the base address, followed immediately by the key, the text suffix, and finally the value payload.

Memcached enforces item boundaries through the metadata fields stored directly in the item header:

  • nkey: Stores the 8-bit length of the key.
  • nbytes: Stores the 32-bit length of the data payload.

When populating the chunk during a network read or buffer copy, Memcached executes bounded memory copies (such as memcpy) utilizing these explicit length values. The network subsystem reads exactly nbytes into the payload section located at the computed memory offset. It does not read unbounded data or look for null terminators to signal the end of a value.

Internal Fragmentation as an Isolation Buffer

Because a chunk’s capacity is rarely an exact match for the combined length of the header, key, and payload, the remaining bytes at the end of the chunk represent internal fragmentation.

Memcached treats this surplus memory as padding. The chunk boundary remains fixed at the class-defined limit, and the unused tail is ignored by read and write operations. The engine tracks the valid boundary exclusively via the header's length attributes rather than the slab chunk’s physical end, ensuring subsequent reads only retrieve the exact bytes placed during the set operation.
