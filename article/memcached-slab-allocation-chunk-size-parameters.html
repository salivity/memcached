Memcached Slab Allocation Chunk Size Parameters

Memcached utilizes a slab allocation mechanism to efficiently manage memory and avoid fragmentation by grouping memory into pre-allocated pages containing fixed-size chunks. This article provides a technical breakdown of the core startup parameters—specifically -n (minimum chunk size), -f (slab growth factor), and -I (maximum item size)—that directly control the sizing, scaling, and distribution of item chunks across Memcached slab classes.

How Memcached Allocates Memory

Memcached divides its allocated memory into 1 MB pages (by default), which are then assigned to specific slab classes. Each slab class is subdivided into equal-sized slots called chunks. When an item (key, value, and internal metadata) is stored, Memcached assigns it to the slab class containing the smallest chunk size capable of fitting the item.

The dimensions of these chunks across different slab classes are governed by three primary command-line parameters.

Key Parameters Controlling Chunk Sizes

1. Minimum Item Size (-n or --min-item-size)

  • Default Value: 48 bytes
  • Function: Sets the base chunk size for Slab Class 1, the smallest allocation tier.
  • Impact: Every item requires memory not only for its payload but also for its key, internal flags, and pointer overhead (typically around 32 to 48 bytes of metadata depending on architecture). Setting -n ensures that the smallest chunk can comfortably house small keys and their associated overhead without allocating unnecessary space.

2. Slab Growth Factor (-f or --slab-growth-factor)

  • Default Value: 1.25
  • Function: Dictates the multiplier used to determine the chunk size of each subsequent slab class relative to the previous one.
  • Impact: The chunk size of class \(k\) is calculated approximately as: \[\text{Chunk Size}_k = \text{Chunk Size}_{k-1} \times f\] A lower growth factor (e.g., 1.1) creates more slab classes with granular size differences, reducing internal memory waste (slack space) at the cost of using more memory to maintain class metadata. A higher growth factor (e.g., 1.5 or 2.0) creates fewer slab classes with wider gaps, which can lead to higher internal fragmentation if item sizes vary widely.

3. Maximum Item Size (-I or --max-item-size)

  • Default Value: 1m (1,048,576 bytes)
  • Function: Defines the upper boundary for an individual item and the absolute maximum chunk size in the slab structure. It also sets the slab page size.
  • Impact: Memcached terminates the creation of new slab classes once the chunk size reaches the value specified by -I. Any item larger than this value is rejected by the server. Increasing this value allows storage of larger objects (e.g., -I 5m), but it also increases the base slab page allocation to match the new maximum size.

How Chunk Sizes Are Calculated

During startup, Memcached builds the slab class table sequentially:

  1. Class 1 Initialization: Slab Class 1 starts with the value set by -n (aligned to an 8-byte boundary).
  2. Exponential Scaling: Each subsequent class calculates its chunk size by multiplying the previous chunk size by -f.
  3. Memory Alignment: Chunk sizes are rounded up to the nearest 8-byte boundary to maintain memory alignment requirements.
  4. Termination: The process repeats until the next calculated chunk size meets or exceeds -I, which forms the final slab class.

Example Configuration

To configure Memcached with an 80-byte initial chunk size, a 15% growth rate, and a 2 MB ceiling, start the daemon using:

memcached -n 80 -f 1.15 -I 2m

Inspecting Configured Chunk Sizes

To verify the generated chunk sizes on a running instance, execute the following command via telnet or nc:

stats slabs

Each slab class will report its chunk_size, chunks_per_page, and usage statistics, allowing you to monitor for internal fragmentation and tune -n and -f to match your application's specific item size profiles.
