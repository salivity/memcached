Memcached Single Instance Scalability Limits

While Memcached is renowned for its high-throughput, low-latency in-memory caching capabilities, scaling a single instance vertically encounters definite architectural and physical boundaries. This article outlines the primary factors that limit the maximum scalable size of an individual Memcached server, focusing on multi-threading lock contention, the mechanics of the slab memory allocator, operating system network stack constraints, hash table overhead, and operational failure risks.

Multithreading and Lock Contention

Memcached utilizes a multithreaded model based on libevent to distribute connections across worker threads. However, memory access requires synchronization to maintain data integrity. Key operations rely on mutexes—specifically for the hash table lookup, item reference counting, slab memory allocation, and LRU (Least Recently Used) list updates. As the number of CPU cores assigned to a single instance increases, thread contention on these shared locks intensifies. Beyond 8 to 16 cores, the overhead of lock acquisition, cache line bouncing between CPU sockets (NUMA effects), and context switching often results in diminishing returns or even performance degradation.

Slab Allocator and Memory Architecture

Memcached manages memory through a custom slab allocator to avoid the performance penalties and memory fragmentation associated with native system malloc calls. Memory is partitioned into predefined slab classes capable of storing items of specific size ranges.

This design imposes several scaling limits:

  • Memory Inefficiency and Fragmentation: Items rarely match slab chunk sizes perfectly, leading to internal fragmentation. In an excessively large memory instance, skewed key-value distributions can leave substantial portions of pre-allocated slab memory underutilized.
  • Item Size Limits: By default, Memcached caps the maximum size of a single stored item at 1 megabyte (MB). While this can be modified via configurations, increasing item size degrades slab allocation efficiency and increases network transfer latency.
  • NUMA Inefficiencies: Allocating hundreds of gigabytes across a multi-socket motherboard means worker threads running on one CPU socket must access memory managed by another, leading to increased memory access latency over interconnects such as Intel UPI or AMD Infinity Fabric.

Network I/O and Kernel Stack Bottlenecks

Memcached is frequently network-bound rather than memory- or CPU-bound. A single instance processing hundreds of thousands or millions of small requests per second stresses the operating system's networking stack:

  • Packet Processing Overhead: The Linux kernel spends significant CPU cycles processing incoming and outgoing packets, managing TCP buffers, handling soft interrupts (softirqs), and managing context switches between user space and kernel space.
  • NIC and Socket Saturation: Even with high-bandwidth network interfaces (e.g., 25GbE, 40GbE, or 100GbE), packet-per-second (PPS) limits become the primary operational bottleneck rather than raw gigabit bandwidth. Single-instance throughput eventually plateaus regardless of available host memory or CPU capacity.

Hash Table Resizing and LRU Maintenance

All keys are tracked in an internal primary hash table. As an instance scales to hundreds of millions of keys:

  • Hash Table Expansion: When the number of stored keys exceeds the hash table capacity, the table must dynamically double in size. The maintenance thread gradually migrates buckets to the new table, consuming CPU cycles and periodically increasing lock contention.
  • LRU List Overhead: Memcached tracks item access to evict stale data when memory is exhausted. Large memory instances maintain enormous LRU chains. Maintaining, locking, and traversing these lists during heavy read/write traffic introduces significant CPU overhead.

Failure Domain and Blast Radius

Beyond pure software and hardware metrics, practical scalability is constrained by the operational risk of the failure domain. Running an exceptionally large Memcached instance (such as hundreds of gigabytes on a single bare-metal server) creates a single point of failure. If the instance crashes, reboots, or undergoes network partition, the resulting cache loss instantly routes an overwhelming volume of requests to the backend databases. To prevent database collapse, architecture best practices mandate horizontal scaling (sharding across multiple smaller instances) over scaling a single instance indefinitely.
