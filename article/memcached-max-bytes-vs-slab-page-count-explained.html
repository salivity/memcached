Memcached Max Bytes vs Slab Page Count Explained

In Memcached, memory management relies on a slab allocation system to minimize memory fragmentation and avoid expensive operating system allocations. The configuration setting maxbytes (configured using the -m flag) defines the total memory ceiling available to the process, while the slab page count represents how that total memory is divided into individual storage blocks (pages). Understanding the direct mathematical and operational relationship between these two parameters is crucial for optimizing cache capacity, avoiding memory calcification, and preventing premature data evictions.

The Mathematical Relationship

The relationship between maxbytes and slab page count is fundamentally proportional:

\[\text{Total Slab Page Count} = \left\lfloor \frac{\text{maxbytes}}{\text{slab\_page\_size}} \right\rfloor\]

  • maxbytes (-m): The maximum amount of RAM in megabytes that Memcached is allowed to use for storing data. For example, -m 4096 allocates 4,096 MB (4 GB).
  • Slab Page Size (-I): The discrete allocation unit used by Memcached. By default, a slab page is 1 megabyte (1,048,576 bytes), though it can be adjusted from 1 KB up to 1024 MB using the -I or --max-item-size parameter.
  • Slab Page Count: The integer count of discrete memory pages Memcached can carve out of the maxbytes pool.

If you configure Memcached with -m 1024 and the default 1 MB page size, Memcached has a maximum capacity of exactly 1,024 slab pages.

Slab Classes and Page Allocation

Memcached does not allocate all slab pages at startup. Instead, it maintains a pool of free pages up to the limit allowed by maxbytes.

When items are stored, Memcached categorizes them by size into distinct "slab classes":

  1. Each slab class contains chunks of a specific size, determined by the growth factor (-f).
  2. When a slab class runs out of empty chunks to store incoming items, it requests a new 1 MB slab page from the unallocated pool.
  3. This new page is divided into fixed-size chunks dedicated solely to that specific slab class.
  4. The total slab page count increases by one, reducing the remaining pool of unallocated memory governed by maxbytes.

Operational Impact on Cache Performance

The bound between maxbytes and the page count influences runtime behavior in two critical ways:

  • Pool Exhaustion: When the number of allocated pages reaches the maximum slab page count permitted by maxbytes, Memcached can no longer allocate new pages to any class.
  • Evictions (LRU) vs. Free Pages: If the maximum slab page count has been reached and a specific slab class needs more space, it cannot obtain a new page from the global pool. It must either evict the least recently used (LRU) item within its own class or utilize Memcached's slab automove feature (slab_automove) to transfer an idle page from another class.
  • Memory Overhead: A negligible amount of the memory defined by maxbytes is reserved for internal tracking structures, meaning the usable page count may occasionally be slightly less than the raw division of maxbytes by page size.
