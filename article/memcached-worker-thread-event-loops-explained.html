Memcached Worker Thread Event Loops Explained

Memcached achieves high-throughput, low-latency performance by using a multi-threaded architecture driven by asynchronous event loops. This article explains the role of worker thread event loops in processing incoming socket requests, detailing how connections are dispatched from the main thread, managed via dedicated libevent instances, and processed through non-blocking network state machines.

The Master-Worker Architecture Overview

Memcached separates network connection acceptance from request execution. It runs a single main thread (often called the dispatcher thread) alongside multiple worker threads, the count of which typically defaults to the number of available CPU cores.

The primary role of the main thread is to bind to listening network sockets and wait for new client connections (accept()). It does not process client commands like GET or SET. Instead, it hands off accepted client sockets to worker threads, which handle all subsequent network I/O, protocol parsing, and cache operations.

Connection Handoff to Worker Threads

When a new client establishes a TCP connection:

  1. Acceptance: The main thread's event loop detects incoming activity on the listening socket and accepts the connection, generating a new file descriptor (fd).
  2. Selection: The main thread selects a target worker thread, typically using a round-robin algorithm to distribute load evenly.
  3. Queueing: The connection details are wrapped in a connection queue item (CQ_ITEM) and placed into the worker thread's incoming queue.
  4. Notification: The main thread writes a single byte to a thread-specific notification pipe (or eventfd on Linux).

The Worker Thread Event Loop

Each worker thread initializes and runs its own instance of libevent (event_base_loop). This event loop is the core driver of the worker thread's lifecycle, allowing a single thread to multiplex hundreds or thousands of client connections without blocking.

When the worker thread starts:

  • It registers the read end of its internal notification pipe with its local event loop.
  • It blocks inside the event loop until an event is triggered on monitored file descriptors.

When the main thread sends a notification byte, the worker thread's event loop wakes up and executes the pipe's read callback. The worker pops the CQ_ITEM from its queue, retrieves the client socket file descriptor, and instantiates an internal connection state structure (conn).

The worker then registers this client socket with its own libevent instance, setting it to monitor for read availability (EV_READ) and persistent events (EV_PERSIST).

Processing Incoming Socket Requests

Once a socket is monitored by the worker thread's event loop, the connection becomes entirely the responsibility of that specific worker.

The request-handling sequence operates as follows:

  1. Event Trigger: When a client sends bytes over the socket, the worker's event loop detects readability and invokes the network handler callback.
  2. Non-Blocking Read: The worker reads available bytes into a per-connection read buffer. Sockets are non-blocking, ensuring the thread does not halt if network transmission is incomplete.
  3. State Machine Execution: Memcached drives connections via an internal state machine (e.g., conn_read, conn_parse_cmd, conn_nread, conn_write). The worker parses the binary or ASCII protocol to determine the command.
  4. Data Retrieval and Mutation: The worker performs the requested operation directly against the shared hash table and slab allocator. Fine-grained locking protects individual hash table buckets and item structures, allowing other worker threads to read and write without global locks.
  5. Response Transmission: When the command is processed, the worker formats the response into an I/O vector. If the socket cannot immediately accept the entire response, the event loop monitors the socket for write readiness (EV_WRITE) and flushes data asynchronously.

Connection Termination

When a client closes a connection or an unrecoverable network error occurs, the worker's event loop triggers the close transition. The worker unregisters the socket from its libevent base, closes the file descriptor, frees associated buffers, and returns the connection structure to an internal pool for reuse.
