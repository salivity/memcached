Memcached Binary Protocol Packet Header Layout

The Memcached binary protocol optimizes communication between clients and the caching server by using a compact, framed structure that reduces parsing overhead compared to the older text-based protocol. At the core of every binary packet is a fixed-size, 24-byte header that precedes any dynamic data such as command extras, keys, or values. This article breaks down the exact 24-byte structural layout of both request and response packet headers, detailing each field's offset, size, and purpose.

Header Structure Overview

Every binary protocol packet begins with an identical 24-byte layout transmitted in network byte order (big-endian). The general 32-bit word alignment of the header is structured as follows:

  Byte/     0       |       1       |       2       |       3       |
     /              |               |               |               |
    |0 1 2 3 4 5 6 7|0 1 2 3 4 5 6 7|0 1 2 3 4 5 6 7|0 1 2 3 4 5 6 7|
    +---------------+---------------+---------------+---------------+
 00 | Magic byte    | Opcode        | Key length                    |
    +---------------+---------------+---------------+---------------+
 04 | Extra length  | Data type     | vBucket ID / Status           |
    +---------------+---------------+---------------+---------------+
 08 | Total body length                                             |
    +---------------+---------------+---------------+---------------+
 12 | Opaque                                                        |
    +---------------+---------------+---------------+---------------+
 16 | CAS (Bytes 0-3)                                               |
    +---------------+---------------+---------------+---------------+
 20 | CAS (Bytes 4-7)                                               |
    +---------------+---------------+---------------+---------------+

Detailed Field Descriptions

1. Magic Byte (Byte 0, 8 bits)

Identifies the direction of the packet:

  • 0x80: Request packet (Client to Server)
  • 0x81: Response packet (Server to Client)

2. Opcode (Byte 1, 8 bits)

Specifies the command being executed. Common opcodes include:

  • 0x00: Get
  • 0x01: Set
  • 0x02: Add
  • 0x03: Replace
  • 0x04: Delete
  • 0x05: Increment
  • 0x06: Decrement
  • 0x07: Quit
  • 0x08: Flush
  • 0x09: GetQ (Get Quietly)
  • 0x0A: No-op
  • 0x0C: Version

3. Key Length (Bytes 2–3, 16 bits)

An unsigned integer indicating the length in bytes of the text key included in the body. If the command does not include a key, this value is 0x0000.

4. Extra Length (Byte 4, 8 bits)

An unsigned integer representing the byte length of command-specific metadata (extras) positioned immediately after the 24-byte header. For example, a Set command uses extras for flags and expiration time.

5. Data Type (Byte 5, 8 bits)

Reserved for defining the payload representation. In standard Memcached, this is set to 0x00 (raw bytes).

6. vBucket ID / Status (Bytes 6–7, 16 bits)

The purpose of this field changes depending on whether the packet is a request or a response:

  • Request (vBucket ID): Specifies the virtual bucket target for cluster routing (commonly used in systems like Couchbase). Set to 0x0000 in standard Memcached standalone servers.
  • Response (Status): A 16-bit status code indicating the outcome of the command:
    • 0x0000: No error / Success
    • 0x0001: Key not found
    • 0x0002: Key exists
    • 0x0003: Value too large
    • 0x0004: Invalid arguments
    • 0x0005: Item not stored
    • 0x0006: Non-numeric value
    • 0x0081: Unknown command
    • 0x0082: Out of memory

7. Total Body Length (Bytes 8–11, 32 bits)

An unsigned 32-bit integer specifying the total length of the payload following the 24-byte header. The total body length must equal:

\[\text{Total Body Length} = \text{Extra Length} + \text{Key Length} + \text{Value Length}\]

The receiving end calculates the length of the dynamic value payload by subtracting the extra length and key length from this value.

8. Opaque (Bytes 12–15, 32 bits)

A client-generated identifier echoed directly back by the server in its response. This field allows asynchronous clients to map incoming responses back to their corresponding pipelined requests.

9. CAS - Compare and Swap (Bytes 16–23, 64 bits)

A 64-bit integer providing data versioning. In a request, it provides optimistic locking checks; the command only succeeds if the provided CAS matches the item's current token on the server. In a response, it returns the newly assigned CAS identifier for the item.
