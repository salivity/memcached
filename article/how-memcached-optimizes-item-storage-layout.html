How Memcached Optimizes Item Storage Layout

Memcached maximizes data density within its memory footprint by combining a slab-based memory allocator with a compact, contiguous item storage layout. By pre-allocating memory into uniform 1MB pages, organizing data chunks into geometrically scaled slab classes, and stripping the per-item metadata down to essential fields, Memcached prevents external memory fragmentation while fitting the maximum possible data payload into every allocated byte. This article explains the internal structure of Memcached items, how payloads are packed into slab pages, and the mechanisms used to minimize internal fragmentation.

Slab Allocation and Page Division

Memcached bypasses standard dynamic memory allocation (like standard malloc) during runtime to avoid memory fragmentation and allocation latency. Instead, it reserves a large pool of virtual memory at startup and divides it into 1MB pages.

Each 1MB page is assigned to a specific slab class. A slab class defines a fixed chunk size:

  • Slab Class 1 might hold 96-byte chunks.
  • Slab Class 2 might hold 120-byte chunks.
  • Each subsequent class increases in size by a configurable growth factor (defaulting to 1.25).

A 1MB page assigned to a specific slab class is subdivided evenly into chunks of that class's fixed size. An item is assigned to the smallest slab class that can completely accommodate its total footprint.

Contiguous Item Layout

To eliminate pointer-chasing overhead and reduce memory waste, Memcached serializes the entire item—metadata, keys, and values—into a single contiguous block of bytes that fits directly inside a single chunk.

The binary layout of an item chunk consists of four contiguous sections:

  1. Item Header (item struct): A fixed-size C structure containing memory management and lookup metadata.
  2. Key: The raw string identifier for the key, stored without a null-terminating byte to save space.
  3. Suffix: A small, plain-text ASCII metadata string storing flags and the length of the raw value.
  4. Value (Payload): The raw binary or text data provided by the client.

By appending the key, suffix, and payload immediately after the header in memory, Memcached avoids allocating separate memory regions or pointer arrays for keys and data.

Minimizing Header Overhead

The primary static overhead in any cached record is the internal item structure. Memcached has heavily optimized this structure across versions to keep it as compact as possible (typically between 32 and 48 bytes, depending on 32-bit vs. 64-bit architecture and compile-time options).

Key elements of this optimization include:

  • Bidirectional Pointers: The header includes forward and backward pointers (next and prev) to maintain the Least Recently Used (LRU) doubly linked lists, as well as an h_next pointer for hash table collisions.
  • Bit-Packed Fields: Flags, slab class IDs, and reference counters are packed into smaller integer types (such as uint8_t and uint16_t) rather than full 32-bit or 64-bit integers to prevent struct padding waste.
  • Conditional CAS Storage: The 64-bit Check-And-Set (CAS) identifier is conditionally compiled or placed such that it only consumes memory when CAS functionality is enabled.
  • Explicit Length Tracking: Instead of using null terminators, Memcached stores explicit 1-byte or 2-byte lengths for the key and suffix, ensuring that string boundaries consume minimal space.

Mitigating Internal Fragmentation

Internal fragmentation occurs when an item does not completely fill the fixed chunk size of its assigned slab class. For example, storing a 100-byte total item in a 128-byte chunk wastes 28 bytes of space.

Memcached mitigates this waste through two primary configurations:

1. Tuning the Growth Factor

The -f command-line flag adjusts the multiplier between adjacent slab classes (default: 1.25). A lower factor (e.g., 1.1) creates more slab classes with smaller size differences between them. This tighter spacing reduces the gap between an item's true size and the chunk size, minimizing wasted bytes per chunk at the expense of managing more slab classes.

2. Chunk Size Minimums

The -n parameter controls the minimum chunk size (default: 48 bytes), which covers the baseline header, a minimal key, and small payload. Tuning this floor ensures that very small items are not placed into disproportionately large default chunks.

Slab Rebalancing and Page Reassignment

Historically, once a 1MB page was assigned to a slab class, it remained locked to that chunk size indefinitely. If workload patterns shifted—such as payload sizes growing from 100 bytes to 500 bytes—memory assigned to smaller slab classes sat idle while larger classes evicted items prematurely.

Modern Memcached versions resolve this with the Slab Automover and Slab Rebalance threads:

  • The engine continuously monitors page usage, eviction rates, and memory pressure across all classes.
  • When a slab class experiences heavy evictions while another class has free, unused pages, Memcached unlinks an entire 1MB page from the underutilized slab class.
  • The page is cleared, formatted into chunks of the new size, and reassigned to the constrained slab class.

This dynamic reallocation ensures that pages constantly reflect the active payload distribution, maximizing the storage capacity of the total allocated memory pool.
