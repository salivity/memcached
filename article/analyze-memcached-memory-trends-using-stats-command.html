Analyze Memcached Memory Trends Using Stats Command

Memcached provides built-in diagnostic telemetry through its text-based statistics interface, enabling systems operators to diagnose capacity constraints and track memory utilization spikes over time. Because Memcached stores data in-memory without persistent logging, analyzing peak memory utilization trends requires polling commands like stats, stats slabs, and stats items, interpreting the relationship between allocated bytes, slab page distributions, and eviction rates, and piping these metrics into time-series collectors.

Essential Metrics in the Base stats Output

Running the fundamental stats command via Telnet or nc outputs key memory-related counters:

  • bytes: The current number of bytes used by the cache to store active items.
  • limit_maxbytes: The maximum allowed storage space configured for the instance.
  • evictions: The lifetime count of valid items removed early to free up memory for new writes.
  • reclaimed: The number of times an expired entry was purged to make room for a new entry.

To determine peak memory saturation, operators track the ratio of bytes to limit_maxbytes. However, reaching near 100% does not inherently indicate performance degradation, as Memcached is designed to operate near capacity. Operators identify unhealthy peak trends when an elevated bytes ratio correlates with a non-zero, rising evictions metric, demonstrating that the allocated memory can no longer sustain the active working set.

Identifying Allocation and Fragmentation with stats slabs

Memcached manages memory by dividing memory into 1MB pages assigned to specific "slab classes" geared toward different object size ranges. The general bytes metric reflects only the raw size of stored items, not the total memory allocated to pages. The stats slabs command reveals the operational footprint:

  • total_pages: The number of 1MB pages assigned to each slab class. Summing total_pages across all slabs multiplied by 1MB indicates the total memory committed by the operating system.
  • used_chunks vs. total_chunks: Indicates the fill rate within a specific slab class. A class where used_chunks consistently approaches total_chunks indicates that items of that specific size are driving peak memory demand.
  • mem_requested: The actual byte count requested by stored items within a slab. Comparing mem_requested against the slab's total capacity (total_chunks multiplied by chunk_size) highlights internal fragmentation—memory allocated to chunks but unused due to object size discrepancies.

When analyzing historical peaks, operators look for "slab calcification," where pages allocated to a specific slab during an earlier spike remain locked to that class even if write patterns shift toward different object sizes.

Tracking Working Set Pressure with stats items

The stats items command exposes item-level behaviors across slab classes that indicate peak pressure:

  • evicted and evicted_time: Tracks the number of seconds since the most recently evicted item was fetched. A low evicted_time during high traffic windows indicates severe memory pressure, proving that actively used cache lines are being dropped prematurely.
  • outofmemory: Tracks instances where the engine failed to allocate memory even after trying to evict items. Any growth in this counter indicates critical memory exhaustion.

Establishing Trend Analysis Pipelines

Because Memcached does not retain historical high-water marks internally, operators establish persistent trend analysis by querying these commands at regular intervals (such as every 10 to 60 seconds) through metric exporters like the Prometheus memcached_exporter or Datadog agents. By graphing bytes, slab page consumption, and evictions across peak traffic windows, operators can distinguish between normal cache warming, genuine capacity exhaustion, and internal fragmentation.
