Memcached set vs add: Key Differences Explained

Memcached provides several commands to manage in-memory data, with set and add being two of the most common storage operations. The primary difference between them lies in how they handle pre-existing keys: the set command unconditionally writes data regardless of whether the key already exists, while the add command only stores data if the key does not exist on the server. Understanding this distinction is crucial for maintaining data consistency, managing cache updates, and avoiding race conditions in distributed applications.

The set Command

The set command is an unconditional write operation. When you issue a set command, Memcached evaluates the key and performs one of two actions:

  • If the key does not exist, Memcached creates it and stores the value.
  • If the key already exists, Memcached completely overwrites the existing value and resets any associated metadata (such as flags and expiration time).

Because it always replaces existing data, the set command typically returns STORED under normal operating conditions. It is the default choice for general caching, cache warming, and scenarios where the freshest data should immediately replace stale data.

The add Command

The add command is a conditional write operation. It only stores data if the specified key is entirely absent from the cache:

  • If the key does not exist, Memcached creates the key, stores the value, and returns STORED.
  • If the key already exists, Memcached rejects the operation, leaves the existing data untouched, and returns NOT_STORED.

This atomic check-and-set behavior makes add valuable for synchronization patterns. For example, it can be used to implement primitive distributed locks, simple leader-election mechanisms, or to prevent "cache stampedes" where multiple processes attempt to compute and write the same expensive data simultaneously.
