What Happens with an Outdated Memcached CAS Token?

When a client sends a Check-And-Set (CAS) command with an outdated CAS token to Memcached, the server detects a version mismatch and explicitly rejects the write operation. Designed as an optimistic locking mechanism, Memcached prevents the stale data from overwriting newer updates, leaving the stored value untouched and returning an error status to notify the client that a race condition occurred.

The CAS Validation Process

Memcached assigns a unique, monotonically increasing 64-bit integer to every key whenever its value is created or modified. Clients obtain this identifier by issuing a gets command (in the text protocol) or requesting CAS metadata (in the binary protocol). When the client is ready to update the item, it sends the cas command containing the key, the new payload, and the previously retrieved token.

Before applying the write, Memcached compares the incoming token against the current token stored in memory:

  • If the tokens match, the data is updated, and a new CAS token is generated.
  • If the tokens differ, it indicates that another client has modified or overwritten the key in the interim, rendering the client's token obsolete.

Server Response to an Outdated Token

When a token mismatch occurs, Memcached halts the update and responds according to the protocol in use:

  • Text Protocol: The server responds with the plain-text status line EXISTS.
  • Binary Protocol: The server returns a response packet with the status field set to 0x0002 (KEY_EXISTS).

In both cases, the existing value, its metadata, and its expiration time in the cache remain completely unaltered.

Client-Side Handling

Receiving an EXISTS or KEY_EXISTS status indicates to the client that its cached view of the data is stale. Standard application logic handles this rejection by implementing a retry loop:

  1. Catch the CAS collision error (EXISTS).
  2. Re-fetch the item from Memcached alongside its newly assigned CAS token.
  3. Re-apply the application-level modification or business logic to the fresh data.
  4. Attempt the cas operation again with the updated token.

This pattern ensures safe, concurrent updates across distributed systems without relying on pessimistic locking overhead.
