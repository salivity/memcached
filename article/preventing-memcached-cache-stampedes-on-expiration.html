Preventing Memcached Cache Stampedes on Expiration

A cache stampede, or thundering herd problem, occurs when a heavily requested cache key expires, prompting massive numbers of concurrent client requests to hit the backend database simultaneously to recompute the value. Memcached does not feature a single automatic switch to resolve this server-side; instead, it provides atomic primitives—most notably the ADD command and Check-and-Set (CAS) tokens—that client applications and libraries use to implement concurrency control. By combining these atomic operations with application-level strategies such as distributed mutex locks, soft expirations, and probabilistic early computation, systems using Memcached can effectively eliminate stampedes during key expiration.

The Role of Atomic Primitives in Memcached

Memcached processes commands atomically on a single thread per bucket or memory slab. This atomicity allows clients to build synchronization primitives without needing external lock managers:

  • The ADD Command as a Distributed Lock: The ADD command stores a key-value pair only if the key does not already exist on the server. If multiple clients attempt to ADD the same lock key simultaneously, only one succeeds (STORED), while all others fail (NOT_STORED).
  • Check-and-Set (CAS): CAS ensures that a client updates a key only if it has not been modified since the client last fetched it, preventing race conditions during concurrent cache writes.

Primary Prevention Strategies

1. Mutex Locking via the ADD Command

When a cache miss occurs, the application attempts to acquire a temporary lock key using Memcached's atomic ADD operation before querying the database.

  1. Query Cache: The client checks Memcached for the requested data.
  2. Handle Miss: If the key has expired, the client issues an ADD request for a mutex key (e.g., lock:item_id) with a short expiration time (e.g., 5 to 10 seconds).
  3. Lock Winner Recomputes: The single client that receives STORED queries the database, writes the result to Memcached under the primary key, and deletes the lock key.
  4. Other Clients Wait or Fall Back: Clients that receive NOT_STORED either sleep briefly and retry fetching the cached key, or immediately return a stale value if one is maintained.

2. Soft Expiration (Logical TTL)

Soft expiration decouples the lifetime of the data in Memcached from its validity period in the application logic.

  • The cached object stores both the payload and a logical_expiration timestamp.
  • The physical Memcached Time-to-Live (TTL) is set significantly higher than the logical expiration (e.g., physical TTL of 24 hours versus a logical TTL of 1 hour).
  • When a client reads the item and detects that current_time > logical_expiration, it triggers an asynchronous background process to re-fetch the data and update the cache.
  • Meanwhile, the current request immediately serves the existing (stale) data without blocking the user or overloading the database.

3. Probabilistic Early Expiration (XFetch Algorithm)

Probabilistic early recomputation prevents the key from ever expiring under active traffic by refreshing it dynamically before it lapses.

Under the XFetch algorithm, every time a client reads a key, it evaluates a probability function based on:

  • The time remaining until expiration (\(\Delta\)).
  • The computation cost or time required to regenerate the value (\(\beta\)).
  • A randomly generated float.

As the remaining TTL approaches zero, the probability of recomputation increases toward 100%. A single client randomly triggers the recomputation early, recalculates the value, updates the cache, and resets the TTL, ensuring high-traffic keys remain continually populated.
