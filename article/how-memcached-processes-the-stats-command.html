How Memcached Processes the Stats Command

This article provides an in-depth breakdown of how Memcached executes the stats command to deliver real-time operational metrics. When invoked, Memcached reads the command through its event-driven network layer, aggregates distributed thread-local counters and memory structures without halting caching operations, formats the data into key-value pairs, and streams the diagnostic output directly back to the client.

1. Connection Ingestion and Command Parsing

Memcached relies on libevent to manage concurrent network connections asynchronously. When a client issues a stats command over a TCP socket, the following sequence occurs:

  1. The main event loop notifies the assigned worker thread that incoming data is available on the client's file descriptor.
  2. The worker thread reads the payload into its connection read buffer.
  3. The parser evaluates the command token. In the text-based ASCII protocol, it detects the stats keyword; in the binary protocol, it evaluates the opcode 0x10 (PROTOCOL_BINARY_CMD_STAT).
  4. The parser checks for optional arguments, such as slabs, items, sizes, or settings, routing the request to the appropriate handler subroutine.

2. Aggregating Thread-Local and Global Counters

To maintain sub-millisecond read and write latencies, Memcached minimizes lock contention by avoiding a single global lock for counters like hits, misses, reads, and writes. Instead, it utilizes thread-local storage and segregated structures:

  • Thread-Local Metrics (thread_stats): Metrics such as get_hits, get_misses, cmd_get, and cmd_set are maintained independently inside each worker thread's local memory structure. When processing a general stats request, the executing worker thread iterates through the array of all worker thread instances, summing these per-thread values to calculate the cluster-wide totals.
  • Global Server Counters: System-wide properties—such as uptime, total memory allocation, current connections, and process IDs—are pulled directly from global structs (stats and settings), some of which are protected by short-lived mutexes (stats_lock).

3. Processing Sub-Commands and Deep Memory Introspection

If the client appends a parameter to the command, Memcached queries specialized subsystems instead of the general counters:

  • stats slabs: The thread enters the slab allocator module, reading metadata about chunk sizes, allocated pages, used chunks, and free chunks per slab class.
  • stats items: The thread queries the Least Recently Used (LRU) management structures, reporting the number of items, evictions, out-of-memory triggers, and age metrics per slab class.
  • stats settings: The thread extracts static configuration flags, such as maximum memory limits, interface bindings, and thread counts.

4. Buffer Construction and Network Transmission

Once the metrics are gathered, Memcached converts the internal numeric representations into standard output formats:

  • Output Formatting: For the ASCII protocol, lines are written in the format STAT <name> <value>\r\n.
  • Dynamic Buffering: Data is written directly to the worker thread's write buffer. If the generated metrics exceed the default buffer size, Memcached dynamically expands the buffer using its internal IO vector arrays (iovec) to prevent truncation.
  • Termination: Once all key-value pairs are staged, Memcached appends the termination marker END\r\n (or an empty binary packet with an End of Stats flag).
  • Delivery: The worker thread registers a write notification with libevent, flushing the buffer non-blockingly over the network to the requesting client.
