Memcached Thread Count vs CPU Cores Performance

Setting a Memcached worker thread count significantly higher than the number of available CPU cores often degrades system performance instead of improving it. While Memcached uses a multithreaded architecture designed to handle concurrent operations, allocating excessive threads introduces severe operating system and architectural bottlenecks. This article details the primary performance penalties associated with over-allocating Memcached threads—including context switching, lock contention, and CPU cache thrashing—and outlines optimal configuration practices.

Increased Context Switching Overhead

When the number of active Memcached threads exceeds the physical or logical CPU cores, the operating system kernel must constantly switch execution contexts to give every thread CPU time. Each context switch forces the CPU to save the state of the current thread (registers, program counter, and stack pointers) and load the state of the next thread.

As thread counts rise, the CPU spends an increasing percentage of its cycles managing thread scheduling in kernel space rather than processing network requests in user space. This results in elevated overall CPU utilization accompanied by a noticeable drop in total requests per second (RPS).

Lock Contention and Serialization

Although modern versions of Memcached utilize fine-grained locking, several shared internal structures still require thread synchronization. Key areas of synchronization include:

  • Slab Allocators: Memory allocation and chunk distribution.
  • Hash Table Buckets: Item lookup, insertion, and deletion.
  • LRU (Least Recently Used) Lists: Eviction tracking and cache maintenance.

With an excessive number of threads, multiple threads attempt to acquire the same mutex locks simultaneously. Instead of executing operations in parallel, threads enter spinlocks or are put to sleep by the kernel. This contention creates a serialization bottleneck, increasing latency—especially tail latency (p95 and p99 metrics)—as requests queue up behind locked resources.

CPU Cache Thrashing and Memory Latency

Modern CPU cores rely heavily on fast L1, L2, and L3 hardware caches to maintain high instructions-per-cycle (IPC) rates. When a core executes a single Memcached worker thread consistently, frequently accessed data remains in these high-speed local caches.

Over-subscribing threads forces the operating system to migrate threads across different CPU cores. When a thread is moved, its working data is no longer present in the local L1/L2 cache, resulting in frequent cache misses. The CPU must repeatedly fetch data from the slower L3 cache or main memory (RAM). This cache thrashing dramatically reduces execution efficiency and increases the average retrieval time for cache keys.

Network Event Loop Inefficiency

Memcached utilizes libevent to manage non-blocking I/O, assigning each worker thread its own event loop and a set of incoming client network connections. When too many threads are configured:

  1. Uneven Load Distribution: Many threads remain idle or handle very few active sockets, wasting memory and kernel polling resources.
  2. Kernel Overhead: The operating system must monitor a larger number of epoll/kqueue file descriptors across hundreds of threads, increasing the overhead of the network stack.

Once the network interface card (NIC) queues or the kernel TCP buffers become the primary bottleneck, adding more threads provides zero additional I/O capacity.

Recommended Configuration Practices

For optimal Memcached throughput and predictability:

  • Match Cores Directly: Configure the thread count (-t parameter) to equal the number of physical CPU cores, or at most the number of logical cores (hyperthreads). For example, on an 8-core machine, start with -t 8.
  • Observe Diminishing Returns: Due to lock overhead, Memcached rarely scales linearly beyond 8 to 16 threads, even on machines with dozens of cores. Often, -t 4 or -t 8 yields higher throughput and lower latency than -t 32.
  • Scale Horizontally: If additional throughput or memory is required beyond what 8 to 12 cores can provide, run multiple independent Memcached instances pinned to specific NUMA nodes or CPU cores rather than scaling a single process with a massive thread count.
