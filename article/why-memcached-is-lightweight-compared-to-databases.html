Why Memcached Is Lightweight Compared to Databases

Memcached achieves exceptional speed and a minimal footprint by intentionally omitting the complex subsystems found in full-featured database engines. Rather than managing complex relational structures, transactions, and persistent disk storage, Memcached operates strictly as a distributed, in-memory key-value cache. This article examines the core architectural decisions—including its simple hash-table model, custom slab memory allocator, lack of ACID persistence mechanisms, and non-blocking event-driven network architecture—that make Memcached dramatically more lightweight than traditional database engines.

Pure In-Memory Operations Without Persistence

Traditional databases incur significant overhead because they must guarantee data durability. Writing to disk, maintaining a Write-Ahead Log (WAL), handling crash recovery, and managing data flush checkpoints all consume substantial CPU cycles and I/O bandwidth.

Memcached skips persistence entirely. It stores data exclusively in volatile RAM. Because it treats data loss as an acceptable trade-off for speed (assuming the underlying primary database can re-populate the cache), it completely eliminates the file system abstractions, synchronization locks, and disk-commit latency that govern database engine design.

Minimalist Key-Value Architecture

Relational and document databases must interpret queries, maintain schemas, optimize execution plans, and navigate complex index trees (such as B-Trees or LSM-Trees). These features require substantial runtime metadata, complex parsers, and memory-intensive execution engines.

In contrast, Memcached provides a simple \(O(1)\) key-value data model. It relies on a single internal hash table for data retrieval and storage. The server does not inspect payload contents, evaluate secondary indexes, or support filtering, joins, or aggregations. By treating keys and values merely as raw strings or byte arrays, the CPU overhead per request remains exceptionally low.

Slab Memory Allocation

Standard operating system memory allocation (malloc and free) can introduce severe memory fragmentation over time, leading to degraded performance and unpredictable memory spikes.

Memcached solves this using a specialized slab allocator:

  • Memory is pre-allocated in large chunks (slabs), typically 1 MB in size.
  • Slabs are divided into smaller, uniform chunks tailored to specific data size classes.
  • When an item is stored, Memcached places it into the closest fitting pre-allocated chunk.

By reusing these fixed-size memory slots instead of constantly allocating and deallocating memory from the OS, Memcached avoids memory fragmentation and keeps garbage collection overhead at near zero.

Omission of ACID Transactions and Locking Overhead

Full-featured database engines maintain transactional integrity (Atomicity, Consistency, Isolation, Durability) via complex mechanisms such as Multi-Version Concurrency Control (MVCC), table- or row-level locking, and distributed two-phase commits. These mechanisms introduce high coordination costs across threads.

Memcached completely discards transactional semantics. Individual operations are atomic at the single-key level, but multi-key transactions, rollbacks, and isolation levels do not exist. Eviction is handled straightforwardly via a Least Recently Used (LRU) algorithm; when memory is full, the oldest, least active data is quietly overwritten. This eliminates the need to manage lock contention, undo logs, or read views.

Event-Driven, Multi-Threaded I/O

Memcached uses a non-blocking network I/O model built around the libevent library. A master thread handles incoming connections and delegates them to a fixed pool of worker threads through simple connection queues.

Because operations are pure memory lookups with execution times measured in microseconds, worker threads rarely block. Memcached requires only a minimal network protocol—available in simple text or lightweight binary formats—to parse incoming requests with minimal CPU instruction counts. This allows a single Memcached instance to handle hundreds of thousands of concurrent requests per second with negligible resource consumption.
