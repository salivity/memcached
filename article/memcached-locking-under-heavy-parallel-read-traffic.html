Memcached Locking Under Heavy Parallel Read Traffic

This article examines how Memcached optimizes its internal locking mechanisms to sustain high throughput and low latency under heavy parallel read workloads. Memcached mitigates lock contention primarily by replacing monolithic locks with fine-grained item lock arrays, employing reference counting to shorten lock hold times, decoupling read paths from write-heavy LRU updates, and using non-blocking background threads for hash table expansions. Together, these internal memory management strategies allow concurrent reader threads to scale efficiently across modern multi-core systems.

Fine-Grained Item Lock Striping

Early versions of Memcached utilized a single global lock (cache_lock) covering the entire cache structure, which created severe thread serialization bottlenecks when multiple CPU cores attempted simultaneous lookups. Modern Memcached replaces this global lock with a striped item lock table (item_locks).

Instead of locking the entire hash table or every single entry individually, Memcached allocates an array of discrete locks (typically power-of-two sized, scaling with worker threads). When a thread executes a read operation (get), it computes the hash of the requested key and maps it to a specific lock in the striped array using a bitmask. Multiple parallel reads accessing keys that map to different hash buckets execute concurrently without blocking one another.

Minimizing Hold Time with Reference Counting

Even with fine-grained item locks, holding locks during data retrieval and network transmission would degrade throughput under concurrent read bursts. Memcached circumvents this by using internal reference counting (it->refcount).

During a parallel read:

  1. The worker thread acquires the specific item lock for the key's hash bucket.
  2. It locates the item pointer in the primary hash table.
  3. If found, the thread increments the item's reference counter.
  4. The thread immediately releases the item lock.

Because the lock is released as soon as the reference count is incremented, the lock hold duration is measured in nanoseconds. The memory chunk cannot be reclaimed, overwritten, or freed by the slab allocator or the Least Recently Used (LRU) eviction algorithm as long as its reference count remains above zero. Once the thread finishes writing the data to the network buffer, it re-acquires the short-lived lock, decrements the reference counter, and releases the lock.

Read-Optimized LRU Maintenance

Traditionally, a read operation requires moving the accessed item to the head of the LRU queue to prevent premature eviction. In multi-threaded environments, updating the doubly-linked LRU list requires exclusive write locks, effectively transforming pure read traffic into internal write contention.

To prevent this lock contention, Memcached separates read operations from synchronous LRU updates:

  • Time-Gated Access Updates: Memcached checks the item's last access timestamp (it->time). If the item was updated recently (e.g., within a predefined window such as 60 seconds), the read thread skips updating the LRU list entirely, eliminating the need to acquire the LRU lock.
  • Segmented and Background LRU: Modern implementations use a segmented LRU system (HOT, WARM, COLD queues) managed by a dedicated background maintainer thread (lru_maintainer). This isolates structural memory movements from the read path, keeping the reader threads bounded only by the quick item lock lookup.

Non-Blocking Hash Table Expansion

As parallel read traffic increases, hash buckets can accumulate longer collision chains, increasing lookup times. Memcached dynamically resizes its primary hash table when the item count exceeds 1.5 times the hash table size.

Under heavy traffic, resizing the entire structure synchronously would stall parallel reads. Memcached handles this through an incremental background expansion thread:

  1. The system allocates a new hash table twice the size of the previous table.
  2. A dedicated maintenance thread moves items incrementally, bucket by bucket, from the old table to the new table.
  3. While rehashing, reader threads check the expansion state. Memcached locks only the individual bucket pair (source bucket in the old table and target bucket in the new table) being migrated.
  4. Reads directed at already-migrated buckets proceed directly to the new table, while reads for unmigrated buckets access the old table.

This granular migration ensures that parallel read operations execute uninterrupted, even when internal structural reallocation occurs under peak traffic loads.
