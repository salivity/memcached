Memcached on Multi-NUMA Sockets

Deploying Memcached on multi-NUMA (Non-Uniform Memory Access) socket systems requires careful resource partitioning to avoid severe latency degradation and bus saturation. This article outlines key architectural considerations, including why running multiple pinned instances outperforms a single monolithic process, how cross-socket interconnects impact throughput, network interface card (NIC) alignment, and relevant Linux kernel tuning parameters.

The NUMA Bottleneck in Memcached

In a multi-socket server, each CPU socket accesses its directly attached local memory significantly faster than remote memory attached to another socket. When a standard Memcached instance spans multiple sockets, worker threads running on Socket 0 frequently access cache items allocated in memory physically attached to Socket 1. This generates heavy cross-socket traffic over the interconnect (such as Intel UPI or AMD Infinity Fabric), introducing latency spikes and reducing total operations per second (OPS).

Furthermore, Memcached utilizes global and per-slab locks. When threads on different sockets contend for these locks, cache-line bouncing occurs across the CPU interconnect, further degrading performance.

Single Instance vs. Multi-Instance Strategy

Running a single, large Memcached process across all sockets is rarely optimal. The two primary deployment models are:

  1. Multiple Independent Instances (Recommended): The most efficient pattern involves running one isolated Memcached daemon per NUMA node. Each instance is pinned strictly to its local CPU cores and local memory node. A client-side hashing mechanism (such as consistent hashing) or a lightweight local proxy (such as Twemproxy or Envoy) distributes cache requests across these instances. This guarantees that 100% of memory accesses remain local and locks are never contested across sockets.
  2. Single Instance with Interleaving (Compromise): If application architecture strictly demands a single large port/endpoint without an intermediary proxy, you must configure memory interleaving. This distributes memory allocations round-robin across all NUMA nodes to prevent one node from exhausting its memory while others remain empty, though it incurs a consistent remote-access latency penalty on roughly half or more of all operations.

CPU and Memory Pinning via numactl

To achieve strict NUMA node isolation for separate instances, use the numactl utility rather than relying on automatic OS scheduling.

For an instance bound to Node 0:

numactl --cpunodebind=0 --membind=0 memcached -m <RAM_MB> -p 11211 -t <thread_count> -u memcached

For an instance bound to Node 1:

numactl --cpunodebind=1 --membind=1 memcached -m <RAM_MB> -p 11212 -t <thread_count> -u memcached
  • --cpunodebind restricts execution strictly to CPUs inside that NUMA node.
  • --membind ensures memory is only allocated from the specified node, returning an out-of-memory error rather than spilling over to remote memory.
  • Set the thread count (-t) to match the physical core count of that single NUMA domain (avoiding hyperthreads if deterministic latency is required). Memcached internal lock scaling typically drops off beyond 8 to 16 threads.

NIC Locality and Network IRQ Affinity

Network interface cards are connected directly to specific PCIe root complexes associated with a single socket. If network traffic arrives at a NIC attached to Socket 0, but the processing Memcached instance resides on Socket 1, packets must travel over the cross-socket interconnect before processing begins.

To eliminate this overhead:

  • Identify which PCIe bus and NUMA node the network card belongs to using lspci -tv or /sys/class/net/<interface>/device/numa_node.
  • Ensure network interrupt requests (IRQs) for that interface are pinned to the CPU cores belonging to that same NUMA node via smp_affinity.
  • If scaling across multiple nodes, deploy dual-port or multi-NIC setups where each NIC is wired to a different socket, routing traffic directly to the local Memcached instance.

Operating System and Kernel Considerations

  • Disable Automatic NUMA Balancing: The Linux kernel includes an automated mechanism to scan and migrate pages closer to active threads (kernel.numa_balancing). For high-throughput in-memory caches, this introduces CPU overhead and latency jitter. Disable it via:

    sysctl -w kernel.numa_balancing=0

  • Transparent Huge Pages (THP): THP often causes unpredictable tail latencies during allocation and defragmentation cycles. Disable THP or set it to madvise to keep allocations predictable.

  • Zone Reclaim Mode: Ensure vm.zone_reclaim_mode is set to 0. Enabling zone reclaim causes the kernel to aggressively reclaim cached disk pages within a node rather than allocating from a remote node, leading to severe stall times.
