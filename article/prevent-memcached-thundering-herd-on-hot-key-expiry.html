Prevent Memcached Thundering Herd on Hot Key Expiry

In high-concurrency systems, the simultaneous expiration of heavily requested "hot keys" in Memcached can trigger a thundering herd—also known as a cache stampede—where thousands of concurrent requests bypass the cache and overwhelm the underlying database. This article outlines the primary engineering strategies used to mitigate this risk, detailing implementation patterns such as distributed locks, probabilistic early expiration, background cache warming, and soft expiration mechanisms.

Distributed Mutex Locking (Dogpile Lock)

The distributed mutex pattern ensures that only one worker queries the database to recompute an expired key, while all other incoming requests either wait or return a fallback response.

In Memcached, this is typically implemented using the atomic ADD command:

  1. A process detects that a key is missing.
  2. The process attempts an ADD lock:key_name 1 [TTL].
  3. If ADD succeeds, this worker owns the lock, fetches the data from the primary datastore, updates Memcached, and deletes the lock.
  4. If ADD fails (indicating another worker is already refreshing the data), the worker briefly sleeps and retries reading the cache, or returns a degraded response.

The lock key must always include an aggressive TTL (e.g., 5 to 10 seconds) to prevent permanent deadlocks if the acquiring worker crashes mid-refresh.

Probabilistic Early Expiration (XFetch)

Instead of waiting for a key to strictly expire, probabilistic early expiration recalculates the cached value before it expires. The likelihood of a worker triggering an early background recalculation increases as the key approaches its expiration time.

The most widely adopted model is the XFetch algorithm:

\[\Delta \cdot \beta \cdot \ln(\text{rand}()) > \text{TTL} - (\text{currentTime} - \text{writtenTime})\]

  • \(\Delta\) (delta) is the compute time required to regenerate the cache.
  • \(\beta\) (beta) is an aggressiveness factor (usually set to \(1.0\)).
  • \(\text{rand}()\) generates a uniform random value between \(0\) and \(1\).

As the remaining TTL shrinks, the probabilistic threshold dynamically adapts to traffic volume. High-traffic keys automatically recompute earlier because the sheer volume of reads increases the statistical probability that a single request triggers the background recalculation before the data actually expires.

Soft Expiration (Stale-While-Revalidate)

Soft expiration separates the logical lifespan of data from its physical existence in Memcached.

  1. Payload Structure: Store the data wrapped in metadata containing a logical expiration timestamp: { "data": ..., "expires_at": 1718000000 }.
  2. Physical Expiration: Set Memcached's actual eviction TTL significantly longer than expires_at (e.g., adding an extra 30 minutes).
  3. Execution: When a read occurs, the application checks expires_at. If the logical timestamp has passed, the application immediately serves the stale data to the user and asynchronously dispatches a background job (or acquires a mutex) to update both the database and the cache.

This pattern eliminates user-facing latency spikes and guarantees that the database is never hit synchronously by hundreds of concurrent processes.

TTL Jittering

When multiple hot keys are generated or updated at the same time (such as bulk data updates or batch cache invalidations), setting identical TTLs creates synchronized expiration windows.

Adding random variation (jitter) desynchronizes key evictions:

\[\text{Actual TTL} = \text{Base TTL} + \text{random}(-\text{jitter}, +\text{jitter})\]

While jitter does not prevent a herd on a single ultra-hot key, it prevents compounding stampedes caused by multiple related keys expiring simultaneously across the cluster.

Proactive Background Refreshing

For predictable hot keys—such as top-ten lists, site banners, or aggregated counters—the application layer should decouple cache population entirely from user reads.

A dedicated background daemon, cron worker, or event-driven consumer updates the key in Memcached on a fixed schedule before it expires. Under this pattern, user-facing requests only read from the cache and are never allowed to execute database queries for that specific key.
