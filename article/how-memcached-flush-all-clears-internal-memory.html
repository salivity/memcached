How Memcached flush_all Clears Internal Memory

The flush_all command in Memcached does not immediately purge or reinitialize internal memory structures, allocate new slab buffers, or delete hash table entries. Instead, it performs an instant, lazy invalidation by updating an internal global timestamp variable known as oldest_live. This design enables the command to execute in constant \(O(1)\) time, avoiding severe latency spikes that would otherwise occur if millions of keys were synchronously dereferenced and unlinked from memory.

The oldest_live Timestamp Mechanism

When a client issues the flush_all command, the Memcached server updates the internal settings.oldest_live attribute to the current server timestamp (using current_time). If an optional integer parameter is supplied (e.g., flush_all 30), Memcached sets settings.oldest_live to a future timestamp equal to current_time + delay.

At the moment the command is processed, the memory footprint of Memcached remains unchanged. All slab classes, chunk allocations, and the global item hash table retain their data in physical RAM.

Lazy Invalidation on Read Operations

The actual clearing of memory occurs incrementally when items are requested via standard retrieval commands like get. Whenever a key is accessed:

  1. Memcached locates the item in the internal hash table.
  2. The server compares the item's creation timestamp (time) against the current settings.oldest_live value.
  3. If the item's timestamp is less than oldest_live, Memcached treats the item as expired, even if its individual time-to-live (TTL) has not elapsed.
  4. The server unlinks the item from the hash table and the Least Recently Used (LRU) list, returns a cache miss to the client, and releases the chunk back to its designated slab class.

Memory Reclamation During Writes and Allocations

Items that are never queried after a flush_all command are reclaimed by Memcached's slab allocator and LRU maintenance routines:

  • Slab Page Reuse: When a write command requires space within a specific slab class, Memcached searches the tail of that class's LRU queue. Any item marked as expired—either via individual TTL or through comparison with oldest_live—is immediately reclaimed and overwritten with new data.
  • LRU Crawler: If the background LRU crawler thread is enabled, it incrementally traverses the internal item lists, detects items rendered invalid by the oldest_live timestamp, and unlinks them to release memory chunks without requiring client read requests.

Through this lazy deletion pattern, Memcached avoids blocking the event loop and safely clears its internal storage structures on demand.
