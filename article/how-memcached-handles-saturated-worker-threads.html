How Memcached Handles Saturated Worker Threads

This article explains how Memcached handles incoming request queues when its worker threads reach full saturation. It details the event-driven architecture, internal connection queuing mechanisms, the role of operating system network buffers, and the backpressure strategies Memcached uses to prevent thread starvation and manage resource exhaustion during extreme traffic spikes.

The Architecture: Main Dispatcher and Worker Threads

Memcached utilizes an event-driven network architecture powered by libevent. Its threading model consists of a single primary dispatcher thread and a pool of pre-allocated worker threads.

The primary thread binds to the network port and handles incoming connection requests (accept()). When a client establishes a connection, the dispatcher assigns that connection to a specific worker thread using a round-robin distribution algorithm. The dispatcher pushes a connection item (CQ_ITEM) into that specific worker thread's internal connection queue (CQ) and writes a single byte through a notification pipe (pipe or eventfd) to notify the worker's event loop that work is waiting.

Once assigned, an established client connection remains tied to that specific worker thread for the lifetime of the connection. The worker thread registers the client's file descriptor with its local libevent loop to monitor for incoming read and write events.

Behavior Under Thread Saturation

Thread saturation occurs when worker threads become CPU-bound, often caused by heavy serialization/deserialization, lock contention (such as cache eviction or slab allocation locks), or handling millions of requests per second. When a worker thread is fully saturated, request execution flows through several defense and buffering layers.

1. Internal Event Loop Latency

Because worker threads operate on non-blocking I/O using an event loop, a saturated thread does not simply block; rather, the time required to complete a full iteration of its event loop increases significantly. While a worker is executing commands for one socket, pending network events on other sockets assigned to that same thread sit unprocessed in libevent's internal dispatch queue.

2. Event Throttling via maxreqs_per_event

To prevent a single active client connection from monopolizing a worker thread and starving other sockets assigned to the same thread, Memcached utilizes the maxreqs_per_event parameter (often defaulting to 20 or dynamic settings).

When a worker thread reads commands from a client connection, it processes up to the configured limit of requests before intentionally yielding control. It resets the event trigger and returns to the event loop to service other pending connections before reading from that socket again. When threads are saturated, this mechanism guarantees fair scheduling among connections assigned to that thread, ensuring all clients experience uniform latency degradation rather than total starvation.

3. Operating System Socket Buffers

Memcached does not maintain unbounded application-level queues for raw requests. When a worker thread cannot execute requests as fast as clients send them, the client sockets' kernel-level TCP receive buffers (SO_RCVBUF) fill up.

When the OS receive buffer becomes full, the TCP window shrinks to zero (TCP ZeroWindow). This signals the client operating system to halt sending additional packets, pushing the backpressure directly onto the client applications.

4. New Connection Queue Overflow

Saturation also impacts the arrival of new connections. If worker threads are too busy to read from their internal notification pipes, their incoming connection queues (CQ) accumulate unacknowledged connection objects.

If saturation spreads to the dispatcher thread or reaches global connection limits (-c flag), new connections cannot be accepted. At this point, the operating system's TCP listen backlog queue (SOMAXCONN / listen backlog) fills up. Once the listen queue is exhausted, the operating system drops incoming TCP SYN packets or responds with connection resets (ECONNRESET), causing connection timeouts and connection-refused errors on the client side.

Summary of Failure Modes

When Memcached worker threads are fully saturated:

  • Existing connections experience increased latency as requests wait in operating system TCP receive buffers and the worker's fair-share event iterations.
  • Fairness is maintained across existing clients via maxreqs_per_event, preventing individual sockets from monopolizing CPU time.
  • New connections stall in the listen backlog and eventually drop once OS-level queues fill.
  • No unbound memory growth occurs inside Memcached because the backpressure mechanism delegates request queuing back to the kernel and the client TCP stack.
