How Memcached Handles Atomic Incr and Decr Commands

Memcached executes atomic increment (incr) and decrement (decr) commands by parsing existing string values into 64-bit unsigned integers, modifying them directly in memory, and securing the operation with item-level locks. This article breaks down how the server processes these requests, manages thread synchronization to prevent race conditions, handles boundary limits like underflow, and writes the updated values back to its internal storage engine.

Data Representation and Validation

Memcached stores all key-value payloads as raw byte arrays without native numerical data types. When an incr or decr command is received, Memcached locates the target item and inspects its payload.

  1. Existence Check: The key must already exist. In the standard text protocol, applying an increment or decrement to a non-existent key fails and returns a NOT_FOUND error.
  2. Format Validation: The existing payload must represent a valid decimal number. Memcached reads the ASCII string and converts it into a native C uint64_t (an unsigned 64-bit integer). If the value contains non-numeric characters, the operation aborts with a client error.

Concurrency and Item-Level Locking

Atomicity is maintained through Memcached’s multi-threaded concurrency model:

  • Hash Bucket and Item Locks: Memcached divides its internal hash table into buckets protected by fine-grained locks. When a worker thread processes an incr or decr command, it computes the hash of the key and acquires the specific lock associated with that key's item or hash bucket.
  • Mutual Exclusion: While this lock is held, no other worker thread can read, write, or modify that key. This completely prevents read-modify-write race conditions, ensuring that concurrent operations execute sequentially without the client needing external distributed locks.

Arithmetic Execution and Edge Cases

Once the current value is converted to a 64-bit unsigned integer, Memcached applies the specified delta:

  • Increment Behavior: Memcached adds the delta to the integer. If the addition exceeds the maximum 64-bit unsigned integer value (\(2^{64} - 1\), or 18,446,744,073,709,551,615), the value wraps around starting from 0.
  • Decrement Behavior: Memcached subtracts the delta from the integer. Unlike standard unsigned integer overflow, Memcached enforces a lower bound: if the decrement delta is greater than the current value, the result halts at 0 rather than wrapping around to the maximum unsigned integer.

In-Memory Modification and Response

After computing the result, Memcached converts the 64-bit integer back into a decimal ASCII string:

  • In-Place Updates: If the length of the new string is less than or equal to the character length of the original string, Memcached rewrites the bytes directly into the existing memory allocation and updates the item's internal size metadata.
  • Reallocation: If the resulting string requires more bytes than the original payload and exceeds the item's current slab allocation, Memcached allocates a new item chunk from its slab allocator, writes the new value, links it into the hash table, and unlinks the old item.
  • Lock Release: The item lock is released, and the server returns the updated numeric value to the client as an ASCII string or a 64-bit binary integer, depending on whether the text or binary protocol is used.
