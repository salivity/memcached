Memcached Replace Command on Missing or Expired Keys

The Memcached replace command is a conditional storage operation designed to update the value of an existing key without risking accidental creation of new data. When executed against a key that is either completely missing from the cache or has surpassed its expiration time (TTL), Memcached rejects the operation and returns a NOT_STORED response. This article examines the internal mechanics of how Memcached evaluates missing and expired keys during a replace operation, the role of lazy expiration, and how developers should handle these outcomes.

Understanding the Replace Command

In Memcached, storage commands behave according to strict state conditions. The standard syntax for the command is:

replace <key> <flags> <exptime> <bytes> [noreply]\r\n
<data>\r\n

Unlike the general set command (which creates or overwrites a key unconditionally) or the add command (which only writes if the key does not exist), replace requires the key to already exist in active memory.

Behavior on a Missing Key

When a client issues a replace command for a key that does not exist in the hash table:

  1. Hash Lookup: Memcached hashes the key and searches its internal hash table for the item.
  2. Item Check: The lookup returns a null pointer because the key has never been stored, was explicitly deleted, or was previously evicted due to memory pressure.
  3. Rejection: Because the precondition of existence fails, Memcached terminates the write operation immediately. It does not allocate slab memory or store the payload.
  4. Response: The server returns NOT_STORED to indicate that the update was aborted (unless the noreply flag was passed, in which case nothing is returned).

Behavior on an Expired Key

Memcached primarily utilizes a mechanism known as lazy expiration (or lazy eviction). Expired items are not constantly scanned and removed in the background; instead, their expiration is evaluated when the key is accessed.

When the replace command targets an expired key:

  1. Hash Lookup: Memcached finds the item in the hash table.
  2. Expiration Evaluation: Before performing the write, Memcached compares the item's stored expiration timestamp against the current server time.
  3. Item Invalidation: Because the current time exceeds the expiration timestamp, Memcached marks the item as dead. It frees the associated memory chunk, removes the item from the LRU (Least Recently Used) list, and updates internal statistics.
  4. Treatment as Missing: Once invalidated, the key is treated as completely non-existent.
  5. Rejection: Because the key is now recognized as missing, the precondition for replace fails.
  6. Response: Memcached does not write the new value and returns NOT_STORED.

Practical Implications for Developers

  • Error Handling: Applications should not treat NOT_STORED from a replace call as a system failure. It usually indicates a normal cache miss or expiration event.
  • Fallbacks: If data persistence is required regardless of cache state, the application logic should catch the NOT_STORED response and fall back to either fetching the source data from the primary database or using a standard set command.
  • Concurrency and Race Conditions: The replace command is not an atomic compare-and-swap mechanism for data integrity. If two clients attempt to update the same key, both operations may succeed sequentially. If concurrent update protection is required, use the cas (Check-And-Set) command instead.
