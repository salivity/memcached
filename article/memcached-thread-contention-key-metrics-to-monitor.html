Memcached Thread Contention: Key Metrics to Monitor

High-throughput Memcached instances can experience performance degradation caused by internal lock and thread contention rather than raw hardware saturation. This article outlines the essential system-level metrics and internal Memcached statistics you need to monitor to accurately identify thread contention on heavily loaded nodes, enabling proactive scaling and configuration adjustments before throughput drops.

Operating System Metrics

Thread contention typically manifests as excessive thread synchronization overhead at the operating system level. Monitor these key OS-level indicators:

  • Voluntary and Involuntary Context Switches: Track context switching using tools like pidstat -w or system metrics collectors. A sharp increase in voluntary context switches (cswch/s) indicates that Memcached worker threads are regularly yielding CPU execution to wait on locked resources (such as mutexes) rather than completing operations in user space.
  • System vs. User CPU Utilization (%sys vs %user): On an optimal Memcached instance, the vast majority of CPU cycles are spent in user space processing cache items. A disproportionate rise in system (kernel) time (%sys) relative to user time (%user) usually reflects the overhead of lock acquisition attempts, thread parking, and waking via system calls such as futex on Linux.
  • Off-CPU Wait Time: Use eBPF-based profiling tools (such as offcputime) to measure how long worker threads sit blocked in the kernel waiting to re-acquire mutexes, specifically targeting the Memcached process.

Internal Memcached Metrics

Query the Memcached stats interface regularly to capture application-specific metrics related to processing and resource tracking:

  • rusage_system and rusage_user: Retrieved via the primary stats command, these counters reflect the accumulated CPU time used by the process. Comparing the rate of growth of rusage_system against rusage_user provides application-level confirmation of excessive kernel synchronization calls.
  • conn_yields: This counter tracks the number of times connections yielded to allow other connections to be processed. A rapid increase shows that worker threads are struggling to keep up with active socket workloads within their allotted event limits.
  • stats conns and listen_disabled_num: If thread contention prevents worker threads from draining event queues, the main listener thread will eventually exhaust connection limits. A growing listen_disabled_num indicates workers are saturated and blocking new incoming requests.

Dedicated Mutex Profiling (Lock Stats)

If your Memcached binary is compiled with lock-tracking support (available by enabling lock statistics during build and querying stats locks):

  • Lock Collision Counts (slabs_lock, cache_lock, lru_locks): Monitor collisions across critical sections. High collision numbers on the slab allocator or global LRU locks signal that multiple threads are contending for memory allocation or eviction routines simultaneously.
  • Item Lock Contention: High contention rates on specific item lock buckets indicate that heavily requested "hot keys" are forcing concurrent worker threads to serialize on the same memory segments.
