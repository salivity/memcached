How Memcached Handles Expired Keys and Memory

Memcached prevents expired entries from consuming system memory indefinitely through a multi-layered approach consisting of lazy expiration, Least Recently Used (LRU) evictions, and an automated background LRU crawler. Rather than maintaining expensive global timers that consume CPU cycles to delete keys the instant they expire, Memcached defers cleanup until a key is accessed, overwrites expired data when memory is constrained, and uses dedicated background threads to harvest abandoned keys.

1. Lazy Expiration (Passive Deletion)

At its core, Memcached uses passive, or "lazy," expiration. When a key is stored with a Time-To-Live (TTL), Memcached records its expiration timestamp but does not schedule an active timer to destroy it.

When a client sends a get request for that key:

  • Memcached inspects the stored expiration timestamp against the current time.
  • If the item is expired, Memcached does not return it; it treats the request as a cache miss.
  • The memory occupied by the expired item is immediately freed and returned to the appropriate memory pool for future allocations.

Because lazy expiration only triggers when an item is requested, it introduces virtually zero CPU overhead during normal operations.

2. Slab Allocation and LRU Eviction

Memcached pre-allocates memory using a slab allocation system, dividing memory into slab classes dedicated to specific item size ranges. When a specific slab class runs out of free memory chunks and a new item must be stored:

  • Memcached checks the tail of the slab class's LRU queue.
  • If it finds an expired item at the tail, it immediately claims that chunk for the new entry.
  • If no expired items are found and memory is completely exhausted (with no room to allocate new slab pages), Memcached will forcibly evict the oldest, least recently used item—even if that item has not yet reached its expiration time.

This ensures that the server never exceeds its assigned memory limits, prioritizing active and frequently accessed data over dormant data.

3. The LRU Crawler (Active Reclamation)

A limitation of relying solely on lazy expiration and LRU eviction is the problem of "dead memory": keys that expire but are never requested again. If a slab class is not actively receiving new writes, these abandoned keys could technically sit in memory indefinitely.

To resolve this, modern versions of Memcached include an integrated LRU Crawler.

  • Background Threading: The crawler operates on an independent, low-priority background thread to minimize impact on read and write latency.
  • Proactive Scanning: It walks through the LRU lists of each slab class, inspecting the TTL of stored entries.
  • Immediate Reclamation: When the crawler detects an item whose expiration timestamp has passed, it frees the chunk and returns it to the slab's free list.

By routinely sweeping the slab queues, the LRU crawler guarantees that expired entries are reclaimed even if they are never accessed again, ensuring that available memory is preserved for valid, active cache entries.
