Memcached Storage Requests During Host Disk Swapping

Memcached is designed strictly as an in-memory key-value store and remains entirely unaware of the underlying operating system's virtual memory paging activities. When host disk swapping becomes active, Memcached continues to process read and write requests as if all data resided in physical RAM; however, accessing swapped-out memory pages triggers kernel-level page faults that force synchronous disk reads, resulting in severe latency spikes, thread blocking, and client-side timeouts.

How Memcached Manages Storage

Memcached utilizes a slab allocation system to manage memory. During startup, it pre-allocates a continuous block of virtual memory defined by the -m parameter. Memcached treats this memory as pure physical RAM, relying entirely on the operating system kernel to manage hardware-level page tables. It contains no internal logic to detect whether a virtual memory page currently resides in physical memory or has been moved to the swap partition on a storage drive.

The Request Lifecycle Under Active Swapping

When an application sends a storage request—such as a GET, SET, or DELETE—the following sequence occurs on a swapping host:

  1. Request Ingestion: The network worker thread accepts the command and parses the key.
  2. Hash Table Lookup: Memcached consults its internal hash table to locate the pointer corresponding to the item or slab.
  3. Hardware Page Fault: When the thread attempts to read or write to the virtual address associated with that item, the CPU recognizes that the memory page is absent from physical RAM.
  4. Synchronous Disk I/O: The operating system suspends the Memcached thread and issues an I/O request to read the page from the swap file or partition on disk. If physical memory is completely exhausted, the kernel may first need to swap out another page to free space.
  5. Execution Resumption: Once the required page is loaded back into physical RAM, the CPU unblocks the worker thread, allowing Memcached to complete the item retrieval or insertion and return a response to the client.

Performance and Operational Impacts

Because disk I/O operations are several orders of magnitude slower than direct RAM access, active swapping profoundly disrupts Memcached's primary function:

  • Latency Degradation: Operations that typically complete in fractions of a millisecond take tens or hundreds of milliseconds when bound to disk speeds.
  • Worker Thread Starvation: Memcached uses an event-driven, non-blocking architecture, but synchronous page faults force the underlying threads to pause. A single worker thread stalled on disk I/O cannot service other connections assigned to that thread.
  • Connection Queue Saturation: As threads stall, pending requests back up in the network listen queue, eventually hitting operating system limits (backlog) and causing connection drops.
  • Cascading Timeouts: Upstream application servers waiting for cache responses encounter timeouts. These applications often fall back to querying the primary database, shifting the bottleneck and potentially causing wider service outages.

Preventing Swapping in Memcached Environments

To prevent disk swapping from degrading cache operations, server environments should be configured using the following practices:

  • Proper Sizing (-m Flag): Ensure the memory allocated to Memcached leaves sufficient headroom (typically 20% to 30%) for the operating system, network buffers, connection overhead, and other host processes.
  • Adjusting Swappiness: Lower the Linux kernel swappiness parameter by setting vm.swappiness = 1 (or 0 on modern kernels) to avoid moving cache pages to swap unless physical memory is completely depleted.
  • Disabling Swap: On dedicated cache servers, entirely disabling swap (swapoff -a) ensures that if the system runs out of memory, the Out-Of-Memory (OOM) killer triggers immediately rather than permitting sustained high-latency disk thrashing.
  • Memory Locking: In specific performance-critical configurations, use operating system utilities or compile Memcached to use mlockall to pin allocated memory directly to physical RAM, preventing the kernel from swapping those addresses under any circumstance.
