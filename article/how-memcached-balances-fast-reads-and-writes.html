How Memcached Balances Fast Reads and Writes

Memcached maintains sub-millisecond latency by decoupling network I/O, thread concurrency, and memory management into dedicated subsystems. By pairing an event-driven multi-threaded architecture with fine-grained hash table locking and a pre-allocated slab storage engine, the system ensures that high-volume read operations execute without blocking, while resource-heavy write operations allocate memory predictably without degrading overall throughput.

Multi-Threaded, Event-Driven Networking

Memcached uses libevent to implement an asynchronous, non-blocking I/O model. It operates with a single main thread dedicated to accepting incoming TCP/UDP connections and assigning them across a configurable pool of worker threads via a round-robin mechanism.

Each worker thread runs its own event loop and manages its assigned client sockets independently. Because read and write operations are processed by worker threads rather than a single monolithic thread, network I/O operations do not serialize. Fast read requests are parsed and answered concurrently without being stalled by network transmission delays from slower client write payloads.

Fine-Grained Hash Table Locking

To prevent race conditions between concurrent reads and writes, Memcached relies on an internal hash table partitioned by locks:

  • Bucket-Level Locks: Instead of a single global lock over the entire cache, Memcached divides the primary hash table into multiple lock partitions (typically thousands of hash buckets per lock).
  • Read-Write Isolation: A write operation (SET, ADD, REPLACE) only acquires the specific lock associated with the target key's hash bucket. Concurrent read requests (GET) targeting items in other buckets proceed entirely unimpeded.
  • Incremental Rehashing: When the volume of items grows large enough to degrade lookup performance, Memcached expands its hash table. This rehashing occurs incrementally across small batches in the background, preventing write spikes from causing global latency pauses for reads.

The Slab Allocation Engine

Standard dynamic memory allocation (malloc and free) introduces memory fragmentation and unpredictable execution times, which severely penalize write-heavy workloads. Memcached bypasses this via a slab allocator:

  1. Memory Pre-Allocation: Memory is reserved at startup and broken down into 1 MB slab pages.
  2. Slab Classes: Slabs are sliced into fixed-size chunks tailored for specific item sizes (e.g., 96-byte chunks, 120-byte chunks, etc.).
  3. Deterministic Writes: When a write request arrives, Memcached maps the item’s size to the nearest fitting slab class and writes directly into a pre-allocated chunk. This transforms what would be an expensive memory allocation into an almost instantaneous \(O(1)\) pointer assignment.

Because memory is never released back to the operating system during standard operations, writes execute with consistent latency, avoiding CPU spikes and memory fragmentation that could otherwise stall concurrent read pipelines.

Non-Blocking LRU Evictions

When memory is full and a write requires space, Memcached relies on a segmented Least Recently Used (LRU) algorithm to evict data without blocking read requests:

  • Split LRU Queues: Modern Memcached splits item management into distinct queues (e.g., HOT, WARM, COLD, and TEMP).
  • Background LRU Maintenance: Moving items between LRU lists is handled by background crawler threads rather than inline on the worker threads.
  • Asynchronous Evictions: When a write needs to reclaim space, it quickly reclaims memory from the tail of the appropriate slab class's COLD queue. Read requests that hit valid keys do not wait on background cleanup or LRU sorting, maintaining strict isolation between write-driven evictions and read execution paths.
