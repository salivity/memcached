How Memcached Uses Libevent for High Throughput

Memcached achieves exceptional throughput and low latency primarily by combining non-blocking network I/O with the libevent library across a multi-threaded architecture. Instead of dedicating a thread or process to each client connection, Memcached uses an event-driven mechanism that monitors thousands of simultaneous connections with minimal overhead. This article explains how non-blocking sockets, OS-level event notification mechanisms like epoll and kqueue managed by libevent, and an efficient master-worker threading model work together to handle heavy traffic loads seamlessly.

The Limitation of Traditional Blocking I/O

In a traditional blocking I/O model, when a thread initiates a read or write operation on a network socket, it pauses execution until data is available or the write buffer is ready. Handling tens of thousands of concurrent clients in this model requires allocating a separate thread or process for each connection. This approach rapidly degrades performance due to:

  • Excessive memory consumption from thread stack allocations.
  • Severe CPU overhead caused by constant OS context switching.
  • Thread starvation while waiting for idle network clients to send requests.

To handle modern web-scale traffic, Memcached avoids blocking calls entirely.

Non-Blocking I/O and Libevent

Memcached configures all network sockets in non-blocking mode. When a socket is non-blocking, a read or write system call returns immediately. If no data is available to read, or if the network output buffer is full, the call returns an error code (EAGAIN or EWOULDBLOCK) rather than stalling the CPU.

Because querying thousands of sockets sequentially to see if they are ready (busy-waiting) would waste CPU cycles, Memcached relies on libevent.

libevent is a high-performance event notification library that abstracts the most efficient event demultiplexing mechanisms provided by modern operating systems:

  • epoll on Linux
  • kqueue on BSD and macOS
  • Event ports on Solaris

Instead of repeatedly polling connections, Memcached registers file descriptors (sockets) with libevent and specifies the events it wants to monitor (such as read readiness, write readiness, or errors). The operating system notifies libevent only when an actual state change occurs, and libevent triggers the appropriate callback function in Memcached.

The Master-Worker Threading Architecture

Memcached pairs libevent with a dedicated multi-threaded design to scale across multiple CPU cores. It divides network responsibilities between a single dispatcher thread and multiple worker threads.

1. The Dispatcher (Main) Thread

The primary responsibility of the dispatcher thread is connection management:

  • It runs its own libevent event loop, listening on the server's TCP/UDP listening port.
  • When a new client attempts to connect, the OS signals the dispatcher thread via libevent.
  • The dispatcher accepts the connection, sets the new socket to non-blocking mode, and packages it into a connection item.
  • It then assigns the connection to one of the worker threads using a round-robin distribution strategy.
  • To notify the chosen worker thread, the dispatcher writes a single byte to an internal pipe or eventfd connected to that specific worker.

2. The Worker Threads

When Memcached starts, it creates a pool of worker threads (typically matching the number of available CPU cores). Each worker thread operates independently:

  • Every worker runs its own isolated libevent instance.
  • The worker thread monitors its internal pipe for notifications from the dispatcher.
  • When notified, the worker reads the new connection details from the pipe and registers the client's network socket with its own libevent loop.
  • From that moment on, that specific worker thread handles all subsequent reads, protocol parsing, memory operations, and writes for that connection.

Request Lifecycle and Event Handling

Once a connection is established, the request-response lifecycle proceeds asynchronously:

  1. Wait State: The worker thread remains idle or processes other connections while libevent monitors the socket.
  2. Read Event: As soon as the client transmits data, the OS alerts the worker's libevent instance, which executes the read callback.
  3. Command Processing: The worker reads the available bytes into a buffer, parses the Memcached command (such as GET or SET), and accesses the internal hash table and slab allocator.
  4. Write Event: When the response is ready, the worker writes the data back to the socket. If the client’s receive buffer is full, the worker registers a write event with libevent and pauses transmission for that client, returning to handle other tasks until the socket is ready to accept more data.

Why This Architecture Drives High Throughput

Memcached maximizes hardware efficiency by eliminating blocking calls and minimizing synchronization bottlenecks:

  • Minimal Context Switching: Threads only run when there is actual work to do, reducing wasted CPU cycles.
  • High Concurrency: A single worker thread can easily juggle thousands of idle or intermittently active connections simultaneously.
  • CPU Cache Affinity: Assigning a connection to a specific worker thread ensures that request processing occurs within the same CPU context, improving memory cache locality.
  • Low Memory Footprint: Without the need for thread-per-connection overhead, system memory is preserved for its primary function: caching key-value data.
