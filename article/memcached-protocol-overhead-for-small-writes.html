Memcached Protocol Overhead for Small Writes

When storing small key-value pairs in Memcached, network protocol overhead often dwarfs the actual data payload being transmitted. This article examines the cumulative overhead introduced at both the transport layer (TCP/IP) and the application layer (Memcached's text and binary protocols), analyzes why small writes suffer from low bandwidth efficiency, and outlines methods to reduce this overhead.

The Problem with Small Writes

In distributed caching, a "small write" typically refers to keys and values that are only a few bytes to tens of bytes in size (for example, storing user session flags, numeric counters, or status indicators). When an application issues a write command, the data does not travel alone; it is encapsulated within multiple networking layers. As payload size decreases, the ratio of protocol metadata to actual payload increases drastically, leading to network inefficiencies, increased latency, and higher packet processing costs on network interfaces.

Application Layer Overhead: Text vs. Binary Protocols

Memcached supports two primary application protocols: the legacy ASCII text protocol and the binary protocol. Both introduce significant per-request overhead for small writes.

1. ASCII Text Protocol

The text protocol requires human-readable commands separated by carriage-return line-feeds (\r\n). A standard write takes the following format:

set <key> <flags> <exptime> <bytes> [noreply]\r\n
<data>\r\n

For a 4-byte key (user) and a 4-byte value (true), the command looks like: set user 0 0 4\r\ntrue\r\n

  • Command overhead: ~25 to 35 bytes of command text and delimiters.
  • Server response: Unless noreply is specified, the server replies with STORED\r\n (8 bytes), generating another packet or payload exchange.

2. Binary Protocol

The binary protocol removes text-parsing requirements by using a structured byte format. However, it enforces a rigid header:

  • Fixed Header: 24 bytes (specifies magic byte, opcode, key length, extra length, data type, vbucket/status, total body length, opaque identifier, and CAS).
  • Command Extras: 8 bytes for set commands (4 bytes for flags, 4 bytes for expiration).
  • Total Application Overhead: 32 bytes minimum before adding the key and value.
  • Server Response: A corresponding 24-byte binary response header indicating success or failure.

While the binary protocol is faster for CPU parsing and avoids formatting nuances, it still introduces at least 32 bytes of request overhead and 24 bytes of response overhead per write operation.

Network and Transport Layer Overhead (L2–L4)

Before leaving the host, the Memcached packet is wrapped in transport, internet, and data link headers:

  • TCP Header: 20 bytes minimum (up to 32–40 bytes with standard TCP options like timestamps).
  • IP Header (IPv4): 20 bytes (or 40 bytes if using IPv6).
  • Ethernet Frame: 14 bytes for the header, plus a 4-byte Frame Check Sequence (FCS) and 20 bytes of preamble and interpacket gap at the physical layer.

Combined, standard TCP/IPv4 over Ethernet requires approximately 54 to 74 bytes of lower-layer overhead per packet, completely independent of the application data inside.

Total Overhead Analysis for a 10-Byte Payload

Consider storing a 10-byte key and a 10-byte value:

Layer Component Approximate Size
L2–L4 Ethernet + IPv4 + TCP Headers ~54–66 bytes
L7 (Memcached) Binary Header + Extras + Key ~42 bytes (32-byte header/extras + 10-byte key)
Payload Value Data 10 bytes
Total Wire Size Single Write Request ~106–118 bytes

In this scenario, actual business data constitutes less than 10% of the transmitted bytes. When taking into account TCP acknowledgments (ACKs) and Memcached response packets, the cumulative wire traffic can exceed 200 bytes for a single 10-byte write.

Latency and Kernel Overhead

Protocol overhead is not merely a bandwidth issue; it directly impacts compute resources:

  • System Call Overhead: Issuing isolated socket writes per small item causes excessive context switching between user space and kernel space.
  • TCP Interaction Issues: When multiple individual writes are sent, the interaction between Nagle’s algorithm (TCP_NODELAY) and TCP Delayed Acknowledgments can introduce artificial latencies of up to 40ms per write if not properly configured.
  • Interrupt Processing: Generating hundreds of thousands of individual packets per second stresses CPU cores with interrupt handling and softirqs.

Optimization Strategies

To mitigate network protocol overhead for small writes, several engineering practices can be applied:

  • Pipelining and Batching: Instead of issuing separate writes, send multiple write commands over a single TCP connection within a single buffer. This amortizes the L2–L4 (TCP/IP/Ethernet) headers across dozens or hundreds of key-value pairs.
  • Use noreply / Quiet Commands: In the text protocol, appending noreply suppresses the server's STORED confirmation. In the binary protocol, "quiet" opcodes (e.g., SetQ) prevent the server from sending response packets for successful operations, cutting return traffic entirely.
  • Data Packing: Aggregate related small values into a unified data structure (such as a serialized JSON, MessagePack, or Protocol Buffer payload) under a single key. This reduces total command metadata and lowers the key-to-value ratio.
  • Persistent Connections: Maintain persistent connection pools with TCP_NODELAY enabled to eliminate TCP three-way handshake overhead and prevent Nagle-related buffering delays.
