Memcached Threading Model for Concurrent Requests

Memcached achieves high-throughput concurrency by employing a multi-threaded, event-driven architecture powered by libevent. Rather than isolating threads strictly into separate "reader" and "writer" pools, Memcached deploys a master thread dedicated to listening for new network connections, which it then delegates to a fixed pool of general worker threads. Each worker thread handles both reading incoming requests and writing back responses for its assigned client connections, relying on fine-grained locking and non-blocking I/O to access the shared cache without bottlenecking the system.

The Master Dispatcher Thread

When Memcached initializes, it creates a main thread (often referred to as the dispatcher thread) and starts a user-configured number of worker threads. The primary responsibility of the master thread is to bind to the listening network socket and accept incoming client connections.

Upon accepting a new TCP connection, the master thread encapsulates the client socket descriptor into a connection object. It then assigns this connection to one of the worker threads using a simple round-robin algorithm. Communication between the master thread and worker threads takes place through a dedicated internal pipe (or eventfd on Linux). The master thread writes a notification byte to the pipe of the selected worker thread, signaling it to register the new connection into its own event loop.

Worker Threads and Asynchronous I/O

Each worker thread runs its own instance of libevent to monitor the file descriptors assigned to it. Once a worker thread takes ownership of a client connection, it assumes responsibility for the entire lifecycle of that connection—including reading commands, parsing protocols, and writing back responses.

Because network operations are non-blocking, a worker thread handles reading and writing dynamically:

  • Reading Phase: When a client sends data, libevent alerts the assigned worker thread that the socket is readable. The thread reads the request bytes into an internal buffer, parses the protocol (text or binary), and determines the target command (e.g., GET, SET, DELETE).
  • Execution Phase: The worker thread executes the command directly against the in-memory hash table and slab allocator.
  • Writing Phase: Once the command is processed, the worker thread prepares the response into write buffers. If the network socket is ready to accept data, the thread immediately transmits the response. If the socket buffer is full, the thread registers the socket with libevent for write events, suspending further writes for that specific client until the socket drains, freeing the thread to process events on other connections in the interim.

Concurrency and Shared Cache Access

Because multiple worker threads simultaneously execute reads and writes against the same global memory space, Memcached relies on targeted synchronization primitives to prevent data corruption while maximizing throughput:

  • Item Locks: Memcached uses a segmented array of locks (hash table bucket locks) rather than a single global lock. When a worker thread executes a write operation (such as SET or ADD), it only locks the specific hash bucket corresponding to that cache key. Other worker threads can simultaneously read or write keys that hash to different buckets.
  • Cache Evictions and LRU: Memory allocation via slabs and updates to the Least Recently Used (LRU) lists are guarded by dedicated slab and LRU locks. Modern versions of Memcached split the LRU into segmented sub-queues (HOT, WARM, COLD) and utilize background threads for maintenance, reducing the lock contention worker threads experience during write-heavy workloads.
  • Global Stats: High-frequency metrics and counters are tracked using thread-local storage or atomic operations, preventing worker threads from contending for global lock structures during standard read/write cycles.

This model ensures that all available CPU cores are utilized efficiently, as worker threads independently multiplex reads, executions, and writes across thousands of concurrent client connections.
