How Memcached SASL Enforces Read and Write Permissions

Memcached uses Simple Authentication and Security Layer (SASL) to authenticate clients, but its native security model handles access control differently than traditional relational databases. While SASL verifies user identities through secure authentication mechanisms, standard open-source Memcached does not natively enforce granular, per-user read and write permissions; instead, it enforces an all-or-nothing access boundary upon successful authentication. To achieve true separation of read and write permissions, administrators must rely on architectural controls, reverse proxies, or multi-instance configurations alongside SASL authentication.

SASL Authentication in Memcached

When Memcached is compiled with SASL support and started with the -S flag, it requires clients to authenticate before executing commands. This authentication flow operates exclusively over the Memcached binary protocol.

The server interfaces with the Cyrus SASL library (saslauthd or libuser), supporting mechanisms such as:

  • PLAIN: Transmits credentials in plaintext (requires TLS or a trusted private network).
  • CRAM-MD5 / DIGEST-MD5: Challenge-response mechanisms that authenticate users without exposing raw passwords over the wire.
  • GSSAPI (Kerberos): Enterprise-grade centralized authentication.

When a client connects, it must issue a SASL_AUTH binary packet. If authentication fails, the connection cannot execute caching commands, effectively providing total read and write blocking for unauthenticated clients.

The Scope of Native Permissions: All-or-Nothing Access

In standard upstream Memcached, the engine does not include a role-based access control (RBAC) matrix. Once a user successfully passes SASL authentication, Memcached grants full access to the entire key-value store.

Native SASL support establishes:

  1. Identity Verification: The server confirms that the connecting client possesses valid credentials defined in the SASL database (such as /etc/sasl2/memcached.conf or a sasldb file).
  2. Monolithic Command Access: Authenticated users have unrestricted access to both read operations (get, gets) and write/mutation operations (set, add, replace, delete, flush_all).

Because the core daemon lacks internal user-to-command permission mappings, SASL alone cannot restrict User A to get operations while allowing User B to execute set operations on the same daemon.

Methods for Enforcing Read vs. Write Permissions

To achieve strict read and write isolation when using SASL with Memcached, production environments implement one of the following strategies:

1. Application-Layer Proxies (e.g., Mcrouter)

The most common approach to command-level authorization is placing an intelligent proxy like Facebook's Mcrouter between clients and the Memcached cluster.

  • The client authenticates with the proxy or dedicated endpoint.
  • The proxy inspects incoming commands.
  • Read commands (get) are routed to cache pools or replicas.
  • Write commands (set, delete) can be rejected or filtered based on the client's source or assigned role before reaching the Memcached storage nodes.

2. Segmented Read-Only and Read-Write Clusters

Organizations frequently deploy separate Memcached pools to enforce access boundaries:

  • Read-Write Primary Nodes: Configured with a restricted SASL user database. Only backend services responsible for cache warming or data mutation receive credentials for this tier.
  • Read-Only Replica/Worker Nodes: Configured for read-heavy consumers. If paired with custom replication or cache-aside design, unprivileged clients only possess credentials to read from these instances.

3. Managed Services and Enterprise Forks

Certain managed cloud platforms (such as AWS ElastiCache or customized enterprise caching servers) implement custom authorization engines on top of the Memcached protocol. In these proprietary environments, the SASL identity is mapped internally to specific IAM roles or access control lists that explicitly disable mutating commands for read-only identities.

Summary

Memcached configured with SASL strictly enforces access authentication rather than fine-grained authorization. Validating a SASL identity unlocks full operational privileges across the instance. Enforcing distinct read and write permissions requires combining SASL's identity validation with network segmentation, proxy filtering, or managed platform access policies.
