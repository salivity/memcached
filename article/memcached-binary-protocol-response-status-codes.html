Memcached Binary Protocol Response Status Codes

This article provides an overview of how the Memcached binary protocol structures and handles command response status codes. Unlike the human-readable text-based ASCII protocol, the binary protocol uses a rigid, fixed-length header to report the outcome of operations. By dedicating a specific 16-bit field within every response header to status codes, Memcached enables fast, deterministic error handling and status verification without requiring string parsing or delimiter scanning.

The 24-Byte Header Structure

Every response packet in the Memcached binary protocol begins with a mandatory, fixed-size 24-byte header. The server uses this uniform structure to transmit metadata about the response before any variable-length data (such as keys, extras, or values) is sent.

The response header layout assigns distinct byte offsets for each field:

  • Byte 0: Magic byte (0x81 indicating a response).
  • Byte 1: Opcode (identifying the command being answered).
  • Bytes 2–3: Key length.
  • Byte 4: Extras length.
  • Byte 5: Data type.
  • Bytes 6–7: Status code (16-bit unsigned integer).
  • Bytes 8–11: Total body length.
  • Bytes 12–15: Opaque identifier (matching the request's opaque token).
  • Bytes 16–23: CAS (Compare-And-Swap) identifier.

While bytes 6 and 7 represent the Virtual Bucket (VBucket) ID in request packets, they are repurposed as the Status field in all response packets.

How Status Codes are Processed

The status code is encoded as a 16-bit unsigned integer in network byte order (big-endian). When a client application receives a response, it inspects bytes 6 and 7 to immediately determine whether the command succeeded or failed.

  • Success: A status code of 0x0000 indicates NoError. The client can proceed to read any returned values or metadata.
  • Failure: Any non-zero status code signifies an exceptional state or error.

When a non-zero status code is returned, the Memcached server frequently includes a human-readable textual error message inside the payload body. The client calculates the length of this message using the Total Body Length field (bytes 8–11), subtracting any key or extra lengths. This design allows the client to programmatically branch based on the numeric code while preserving diagnostic information for logging.

Standard Binary Response Status Codes

The protocol defines standard two-byte hex values for operational states:

  • 0x0000 (NoError): The command completed successfully.
  • 0x0001 (KeyNotFound): The requested key does not exist in the cache.
  • 0x0002 (KeyExists): An attempt to store an item failed because the key already exists (e.g., an Add command) or a CAS mismatch occurred.
  • 0x0003 (ValueTooLarge): The payload data exceeds the server's configured maximum item size.
  • 0x0004 (InvalidArguments): The request contained invalid header flags or an invalid structure.
  • 0x0005 (ItemNotStored): The item could not be stored (e.g., conditions for an append/prepend or replacement were not met).
  • 0x0006 (NonNumeric): An increment or decrement operation was attempted on a non-numeric value.
  • 0x0020 (AuthError): Authentication credentials were missing, incorrect, or invalid.
  • 0x0021 (AuthContinue): Additional authentication steps are required (used during multi-step SASL negotiations).
  • 0x0081 (UnknownCommand): The opcode sent in the request header is unrecognized.
  • 0x0082 (OutOfMemory): The server cannot allocate memory for the item and cannot evict an existing item.
  • 0x0084 (InternalError): An unexpected server-side error occurred.

Advantages of the Binary Status Handling

By embedding status codes directly into a fixed-offset binary field, the protocol eliminates the ambiguities of text parsing. Client libraries do not need to scan for newline characters (\r\n) or match variable-length strings like "STORED", "NOT_FOUND", or "SERVER_ERROR". Instead, clients execute a simple bitwise extraction on bytes 6 and 7, enabling low-overhead dispatching, high-throughput network handling, and clear separation between application-level failures and protocol-level errors.
