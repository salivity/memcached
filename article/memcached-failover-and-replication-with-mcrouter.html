Memcached Failover and Replication with Mcrouter

Memcached is fundamentally an in-memory, key-value store that prioritizes raw performance over built-in clustering, high availability, and replication. To achieve enterprise-grade resilience, infrastructure engineers rely on proxy solutions like Meta’s mcrouter. Sitting transparently between client applications and Memcached servers, mcrouter intercepts memcached protocol requests and dynamically routes them based on configurable routing trees. This article explores how mcrouter implements automated failover, regional failover, and asynchronous cross-region replication to eliminate single points of failure in caching architectures.

The Role of a Caching Proxy

In standard Memcached deployments, the client library uses consistent hashing to map keys directly to specific server instances. If a server crashes, the client either fails the operation or recalculates the hash ring, redistributing traffic and causing heavy cache churn.

A proxy like mcrouter abstracts server topology away from the application. Clients send standard Memcached protocol commands to a local mcrouter instance (typically deployed as a sidecar container or a local daemon). The proxy parses the keys and routes commands through user-defined routing rules known as Route Handles, handling server selection, retry logic, connection pooling, and multi-node synchronization natively.

Mechanisms for High Availability and Local Failover

mcrouter manages node failure through configurable fallback strategies, ensuring applications experience near-zero latency degradation when underlying cache servers drop offline.

FailoverRoute

The primary tool for local resiliency is the FailoverRoute. Under normal operations, queries are directed to a designated primary server pool. If a target node fails to respond, returns a network error, or exceeds a configured timeout, mcrouter immediately attempts the request against one or more backup servers in a fallback pool. This process is completely invisible to the requesting client application.

Health Checking and TBF Rate Limiting

To prevent cascading failures and "thundering herds," mcrouter incorporates Token Bucket Filter (TBF) rate limiters and background health checks. When a backend node starts timing out, mcrouter temporarily marks the connection as degraded or dead, automatically diverting traffic to backups without waiting for full TCP connection timeouts on every subsequent request. Once the primary node passes periodic health checks, mcrouter safely reintegrates it into the active pool.

Cache Warm-Up Routing

Replacing a dead cache node normally floods downstream databases as the new, empty node warms up. Using a WarmUpRoute, mcrouter mitigates this:

  1. A read request goes to the new (cold) target node.
  2. If the key misses, mcrouter reads the key from an existing (warm) backup node.
  3. If the warm node hits, mcrouter writes that data into the cold node before returning the response to the client.

Multi-Region Replication Architecture

Operating across multiple data centers requires serving reads locally to avoid WAN latency penalties while ensuring updates reach all regions. mcrouter achieves this by decoupling read paths from write paths.

Read-Local, Write-Global Routing

Multi-region deployments typically employ an active-active or active-passive pattern:

  • Reads (HashRoute / LatestRoute): Read requests are directed entirely to the local cluster within the same availability zone or region, maintaining sub-millisecond response times.
  • Writes (AllSyncRoute / AllAsyncRoute): When an application issues an update (SET, DELETE, ADD), mcrouter intercepts the write. Through AllSyncRoute, it writes to the local cluster synchronously to ensure immediate read-your-own-writes consistency. Simultaneously, it uses AllAsyncRoute to fire non-blocking writes to remote mcrouter instances or cache pools in secondary regions over WAN connections.

Asynchronous Spooling via AsyncLog

Cross-region network partitions are common. If a WAN link drops, naive cross-region writes either block local clients or drop synchronization updates entirely, leading to stale cache data.

mcrouter resolves this by logging failed cross-region writes to an on-disk transaction log (AsyncLog). When a remote region is unreachable, failed writes are spooled locally as mutation logs. A background daemon continuously inspects the spool and replays the cached mutations once network connectivity to the target region is restored. This guarantees eventual consistency across geographical regions without delaying local application writes.

Prefix-Based Routing for Granular Control

mcrouter supports routing configurations based on key prefixes via the PrefixSelectorRoute. This allows operators to define granular policies per data type:

  • Ephemeral/Session Data: Routed to a local cluster with rapid FailoverRoute to a standby pool, avoiding cross-region overhead.
  • Global Metadata: Routed with AllSyncRoute locally and asynchronously mirrored across every active region.
  • Read-Heavy Static Caches: Directed to locally replicated pools with automated cold-cache warm-up behavior.

By centralizing connection management, health checking, and routing intelligence at the proxy layer, mcrouter converts Memcached from a simple, isolated memory cache into a distributed, fault-tolerant, multi-region caching tier.
