Memcached Network Buffer Allocation Under Load

Memcached handles massive concurrency not by relying on brute-force memory allocation, but by combining an asynchronous, event-driven I/O model with specialized buffer management techniques. Under heavy client concurrency, network buffers can quickly consume gigabytes of memory if left unmanaged. Memcached mitigates this by assigning connections to a pool of worker threads, dynamically expanding and trimming per-connection read buffers, utilizing scatter-gather I/O (writev) to avoid outbound data duplication, and recycling internal connection state objects to minimize allocator overhead.

Multi-Threaded Event Loop Architecture

Memcached uses a multi-threaded architecture driven by libevent. A single main thread binds to the listening socket and accepts incoming TCP connections. Once accepted, it distributes connections evenly via round-robin dispatch to a fixed pool of worker threads through dedicated pipes.

Each worker thread runs its own libevent loop, monitoring only the file descriptors assigned to it. This isolation ensures that socket read and write events are processed concurrently without global locks across all client traffic, localizing network buffer operations strictly to the thread handling that specific socket.

Dynamic Read Buffer Management

When a connection is established, Memcached allocates a connection state structure (conn), which contains a dedicated read buffer (rbuf). Handling thousands of concurrent connections with large static buffers would cause severe memory exhaustion. Memcached balances performance and memory consumption through dynamic read buffer management:

  • Initial Allocation: Read buffers begin at a conservative initial size (typically 2 KB to 4 KB), large enough to fit standard text or binary commands without immediate reallocation.
  • Dynamic Expansion: If a command or pipelined payload exceeds the current buffer capacity, the worker thread invokes realloc() to grow the buffer incrementally to accommodate the incoming data.
  • Buffer Reset and Trimming: Once a complete command is parsed and executed, remaining unparsed bytes are shifted to the front of the buffer. When connections become idle or have processed oversized commands, Memcached can free or resize the buffer back to baseline, preventing idle connections from holding peak memory allocations indefinitely.

Zero-Copy Transmissions via Scatter-Gather I/O

The largest potential source of buffer bloat under heavy read traffic is the outbound response payload. If Memcached copied cached values from the slab memory allocator into per-socket network output buffers, memory usage would double and CPU cache misses would surge.

To avoid this, Memcached utilizes scatter-gather I/O (writev or sendmsg):

  1. Header Assembly: The worker thread constructs small protocol headers in a dedicated, reusable transmission array (an array of struct iovec structures held within the conn context).
  2. Direct Slab Referencing: Instead of copying the cached item payload, the iovec array points directly to the item's memory address located inside the Memcached slab storage.
  3. Reference Counting: The worker thread increments the reference count of the cached item to guarantee it is not evicted or reclaimed while sitting in the socket's outbound queue.
  4. Kernel Offload: A single non-blocking writev system call transmits both the protocol headers and the raw payload directly from slab memory to the socket send buffer.

Once the kernel has received all fragments, the reference count on the cached item is decremented, and the iovec pointers are reset. This approach eliminates the need for large application-level output buffers regardless of connection volume.

Connection Struct Pooling

Calling the system allocator (malloc/free) repeatedly under thousands of transient connection requests introduces severe heap fragmentation and lock contention. Memcached neutralizes this using a freelist for connection structures:

  • When a client disconnects, its associated conn structure is not released to the operating system heap.
  • The structure is sanitized, any oversized buffers attached to it are resized or freed, and the structure is placed on an internal connection freelist.
  • New inbound connections immediately pop an existing conn structure from the freelist, bypassing system allocator bottlenecks entirely.

Concurrency Protection and Socket Throttling

To prevent high connection spikes from exhausting operating system buffers or process memory:

  • Max Connections Cap: Memcached enforces a strict limit (-c, default 1024). When reached, the main listener thread temporarily disables listening on the main socket, refusing new TCP handshakes until active connections complete.
  • Non-Blocking Limits (Max Requests Per Event): To prevent starvation, worker threads process a maximum number of sequential commands per connection (configured via -R) before yielding the CPU back to the event loop, ensuring fair scheduling of socket I/O across all concurrent clients.
