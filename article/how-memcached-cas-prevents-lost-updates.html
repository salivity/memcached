How Memcached CAS Prevents Lost Updates

In high-concurrency distributed caching systems, multiple clients frequently attempt to read, modify, and write the same cached data simultaneously, leading to race conditions known as lost updates. Memcached addresses this concurrency challenge using its Compare-And-Swap (CAS) mechanism. This article explores how Memcached implements CAS tokens to manage optimistic locking, how it detects concurrent modifications, and why it is an essential feature for maintaining data consistency without the overhead of heavy distributed locks.

The Problem: The "Lost Update" Anomaly

When an application updates data in Memcached, it typically follows a three-step cycle:

  1. Read an existing value from the cache.
  2. Modify the value locally within the application logic.
  3. Write the updated value back to the cache using a standard command like set.

A lost update occurs when two or more processes execute this cycle concurrently on the same key:

  • Client A reads key counter (value: 10).
  • Client B reads key counter (value: 10).
  • Client A increments the value to 11 and writes it back to Memcached.
  • Client B increments its local value to 11 and writes it back to Memcached.

Client B's write overwrites Client A's update. The final value in the cache is 11 instead of the expected 12, effectively losing Client A's operation.

What is the CAS Value?

The CAS value is an internal, unique 64-bit integer assigned by Memcached to every key-value pair. Every time an item is created or updated, Memcached generates a new, monotonically increasing CAS token for that item.

The CAS value serves as a version tag. It allows clients to verify whether an item has changed in the cache since it was last read.

How CAS Solves the Problem

Memcached uses the CAS token to implement optimistic concurrency control via two specific protocol operations: gets and cas.

1. Fetching Data with gets

Instead of using the standard get command, a client issues a gets (get with CAS) command. Memcached returns the requested value along with its current 64-bit CAS token.

2. Writing Data with cas

After computing the new value, the client does not use a blind set command. Instead, it issues the cas command, supplying:

  • The key.
  • Flags and expiration time.
  • The new data payload.
  • The original CAS token received during the gets step.

3. Atomic Evaluation

When Memcached receives the cas command, it performs an atomic comparison:

  • Match: If the CAS value provided by the client matches the current CAS value of the stored item, Memcached updates the item with the new value, generates a new CAS token, and responds with STORED.
  • Mismatch: If the CAS values do not match—indicating that another client has modified the item in the interim—Memcached rejects the update and returns EXISTS.
  • Missing Key: If the item was deleted between the read and the update, Memcached returns NOT_FOUND.

Handling CAS Rejections

When an update fails with an EXISTS response, the application must handle the conflict gracefully. The standard pattern is a retry loop:

  1. Receive the EXISTS error.
  2. Re-read the latest data and the new CAS token using gets.
  3. Re-apply the business logic to the updated value.
  4. Attempt the cas write again.
  5. Repeat until successful or until an application-defined retry limit is reached.

Why Use CAS Over Traditional Locking?

Implementing CAS provides several key advantages:

  • No Deadlocks: Because CAS is non-blocking (optimistic), clients do not hold locks on keys, eliminating the risk of distributed deadlocks.
  • Low Overhead: Traditional locking requires acquiring, maintaining, and releasing lock keys, resulting in extra network round-trips. CAS integrates version verification directly into the write operation.
  • High Performance in Low-Contention Scenarios: In environments where collisions are infrequent, CAS operations succeed on the first attempt with zero lock contention delay.
