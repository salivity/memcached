Understanding Memcached stats sizes Command

The stats sizes command in Memcached is a diagnostic tool used to map the exact distribution of item sizes currently stored in memory. By categorizing cached items into 32-byte increments, this command allows administrators to visualize data footprints, identify memory fragmentation, and calibrate slab allocation settings. While it provides indispensable insights into how application data utilizes allocated memory, its execution requires caution due to its impact on active production environments.

How the stats sizes Command Works

Memcached allocates memory using a slab allocator system, grouping memory into pages cut into chunks of specific sizes (slab classes). The stats sizes command bypasses these predefined slab boundaries to examine the actual raw size of every key-value pair, metadata included, across the entire cache.

When invoked, the command groups the raw item sizes into 32-byte buckets. Each bucket counts how many stored items fall within that specific size boundary, rounded up to the nearest multiple of 32 bytes.

The command produces output in a two-column format:

STAT <size_bucket> <item_count>
  • Size Bucket: The upper limit of the 32-byte range (e.g., 64, 96, 128, 160 bytes).
  • Item Count: The number of items in the cache whose combined key, value, and overhead size fits into that specific range.

Primary Functions and Use Cases

1. Fine-Tuning the Slab Growth Factor

Memcached uses a growth factor (configured via the -f flag) to determine the size multiplier between successive slab classes. If the growth factor does not match the actual distribution of your data, you risk significant internal fragmentation—space wasted when small items occupy overly large chunks. The distribution mapped by stats sizes reveals the real-world clustering of your data, enabling you to set a growth factor that closely matches your payload profiles.

2. Identifying Internal Memory Fragmentation

By comparing the distribution returned by stats sizes with the output of stats slabs (which shows the slab class boundaries), you can see how much space is left unused within each chunk. If the bulk of your objects measure 260 bytes, but your slab classes jump from 256 bytes to 384 bytes, those items will occupy the 384-byte chunks, wasting roughly 120 bytes per item.

3. Detecting Data Drift and Application Anomalies

Over time, changes to an application's codebase or payload structures can shift the average size of cached objects. Running stats sizes periodically helps detect unexpected increases in key or value sizes, unintentional payload bloat, or sudden influxes of unusually large items that push older data out via the Least Recently Used (LRU) eviction mechanism.

Critical Production Considerations

While stats sizes provides a complete view of item distribution, it is computationally expensive.

Unlike the standard stats or stats slabs commands—which read pre-calculated metrics—stats sizes traverses every item in the cache. To accomplish this safely, the command acquires the global cache lock, blocking all incoming read and write requests for the duration of the scan. In large caches holding millions of items, running stats sizes can freeze the Memcached instance for seconds, leading to connection timeouts and cascading latency spikes in connected applications.

Because of this behavior, it is best practice to run stats sizes only during maintenance windows, on read replicas, or within isolated staging environments that mirror production data.
