How Memcached Handles Slab Exhaustion

Memcached allocates memory in fixed-size pages assigned to specific slab classes, which can lead to a condition known as slab exhaustion or slab calcification when one class runs out of space while others hold unused capacity. To resolve this imbalance, modern versions of Memcached use a combination of local Least Recently Used (LRU) evictions and dynamic memory reallocation mechanisms—specifically the slabs reassign interface and the automated slab_automove background thread. These tools allow the server to shift 1MB memory pages from idle or over-allocated slab classes to the starved class without requiring a service restart.

The Slab Allocation Architecture

Memcached manages memory using a slab allocator to prevent operating system memory fragmentation. Memory is divided into 1MB pages, and each page is carved into fixed-size chunks corresponding to a specific slab class (e.g., 96 bytes, 120 bytes, 144 bytes). Once a page is assigned to a slab class, its chunk size cannot hold items designated for a different class.

If application access patterns shift, larger or smaller keys may dominate the workload. This creates a scenario where a high-demand slab class fills completely, while slab classes mapped to unused data sizes retain free or idle chunks.

Immediate Handling: Per-Class LRU Eviction

When a slab class is exhausted and no unassigned 1MB pages remain in the global memory pool, Memcached's immediate response is localized LRU eviction:

  • Memcached evaluates only the items within that specific slab class.
  • The least recently used item in that class is evicted to make room for the new entry, even if other slab classes have completely empty chunks.
  • In modern Memcached versions, this is handled through Segmented LRU (separating items into HOT, WARM, and COLD queues within each class) to ensure active keys are not prematurely removed.

While this preserves write availability, it results in continuous evictions and cache misses for the active slab class, despite overall system memory remaining underutilized.

Manual Slab Reassignment

To fix permanent imbalances, Memcached provides the runtime command slabs reassign <source class> <destination class>.

When this command is issued:

  1. The Memcached slab maintenance thread identifies a 1MB page in the source slab class.
  2. The page is unlinked from the source slab's freelist, and any existing items residing in that page are evicted.
  3. The page memory is cleared and re-partitioned into chunks matching the destination slab class.
  4. The newly partitioned chunks are added to the starved slab class's free pool.

This operation runs asynchronously in the background and does not block client reads or writes to other pages.

Automated Slab Reassignment (slab_automove)

Because manual intervention is impractical for variable workloads, Memcached includes an automated mechanism enabled via the -o slab_automove=<mode> startup flag or through the runtime settings interface.

The slab_automove daemon periodically inspects the health of all slab classes using defined heuristics:

  • Mode 1 (Standard): If a slab class has recorded evictions over three consecutive monitoring windows (typically a few seconds apart), it is flagged as starved. The thread then searches for a donor slab class that has not experienced an eviction in a prolonged period and has free pages, or frees a page by taking the oldest data. It then triggers an automated page transfer.
  • Mode 2 (Aggressive / Highly Dynamic): Designed for segmented LRU configurations, this mode moves pages based on the relative age of the oldest items across slab classes. If the oldest item in Class A is significantly younger than the oldest item in Class B, Class B is treated as an over-provisioned donor, and a page is moved to Class A.

By combining strict per-class LRU eviction for immediate writes with automated page rebalancing for macro-level workload shifts, Memcached resolves slab exhaustion without losing performance or wasting provisioned RAM.
