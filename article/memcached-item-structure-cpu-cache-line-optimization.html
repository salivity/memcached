Memcached Item Structure CPU Cache Line Optimization

Memcached achieves exceptionally high read and write throughput by carefully engineering its internal item structure to minimize CPU cache misses and optimize hardware cache line utilization. By organizing item metadata to fit predictably within typical 64-byte L1/L2 cache lines, embedding variable-length keys contiguously to avoid pointer chasing, and aligning slab memory allocations to power-of-two boundaries, Memcached ensures that memory-bound key-value operations require the absolute minimum number of CPU memory cycles.

The Cache Line Challenge in In-Memory Caching

Modern CPU architectures transfer data between main memory and CPU caches in fixed chunks, typically 64 bytes wide, known as cache lines. When a core requests a memory address, the entire 64-byte block containing that address is pulled into the cache hierarchy. If an in-memory database requires multiple non-contiguous memory accesses to read an object, parse its metadata, and fetch its payload, memory bus latency quickly becomes the primary performance bottleneck. Memcached eliminates this overhead by treating cache lines as a core constraint in its data layout design.

Contiguous Memory Layout and Spatial Locality

A central optimization in Memcached is the contiguous layout of the item structure. In naive C implementations, an object might store pointers to separate memory allocations for the key, the payload, and optional metadata. Following these pointers causes cache misses because each dereference typically points to a disparate memory address.

Memcached solves this using the struct layout technique with flexible array members:

+-------------------+--------------------+--------------+---------------+
| struct _stritem   | Optional CAS /     | Key Data     | Value Payload |
| (Header Metadata) | Flags Suffix       | (Contiguous) | (Contiguous)  |
+-------------------+--------------------+--------------+---------------+

The header (struct _stritem), the key, and the data payload reside in a single contiguous chunk allocated from a pre-allocated slab. When the CPU fetches the base address of an item to inspect its state, spatial locality ensures that the key and beginning of the value are either already within the same 64-byte cache line or immediately loaded by the hardware prefetcher into the next line. This eliminates pointer dereferencing entirely during basic key comparisons.

Hot/Cold Field Ordering in Item Metadata

Inside the item header itself, fields are ordered strategically based on access frequency and execution phase:

  1. Pointers for Traversal: Pointers like next, prev (for LRU queue management), and h_next (for the hash table bucket chains) are grouped together. During hash lookups and LRU updates, these pointers are accessed concurrently.
  2. Lookup Validation Fields: The item's expiration time (time), size attributes (nbytes, nkey), and flags are placed adjacent to the traversal pointers.
  3. Reference Counting: The refcount tracks active readers and writers, placed such that state checks avoid crossing unnecessary boundary lines.

By tightly packing the most critical header fields within the first 32 to 48 bytes of the struct (on 64-bit architectures), Memcached ensures that the hash table lookup, expiration validation, and key comparison can often be completed within a single cache line fetch.

Slab Alignment and Boundary Padding

Memcached avoids partial cache line crossings through its slab allocator. When memory is partitioned into slab classes, chunk sizes are aligned to 8-byte boundaries by default, with configuration options to align allocations to full 64-byte boundaries.

Without alignment, an item's header could straddle two separate 64-byte cache lines. A straddled header forces the CPU memory controller to issue two separate cache requests simply to evaluate one item header. By aligning the start addresses of chunks within slabs, Memcached guarantees that the critical header begins at an aligned offset, avoiding split-line penalties.

False Sharing Prevention

In multi-threaded deployments, Memcached prevents false sharing—a scenario where different CPU cores modify unrelated variables that happen to share the same cache line, forcing continuous cache invalidation. Memcached applies thread-local storage patterns, granular LRU locks, and cache-line padding to core control structures. For the items themselves, distinct items are served from distinct slab chunks, preventing writes to one item's reference count or LRU status from invalidating unrelated items residing in adjacent cache lines.
