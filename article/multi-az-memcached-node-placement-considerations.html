Multi-AZ Memcached Node Placement Considerations

Deploying Memcached nodes across multiple Availability Zones (AZs) involves balancing high availability against network latency, bandwidth costs, and architectural complexity. Because Memcached is an in-memory, non-replicated caching system by default, distributing nodes across distinct physical zones protects against zone-level outages but introduces inter-zone communication overhead. This article outlines the core engineering considerations that dictate how and when to place Memcached instances across multiple AZs.

Network Latency

Memcached is fundamentally optimized for sub-millisecond response times. Communication within the same AZ generally takes a fraction of a millisecond, whereas round-trip requests crossing AZ boundaries typically incur an added penalty of 1 to 2 milliseconds. If an application requires hundreds of cache lookups per request, crossing AZ boundaries for every cache miss or hit can degrade user-facing application performance. Designers must determine whether their latency budget accommodates cross-zone hops.

Data Transfer Costs

Major cloud service providers provide free network egress within the same AZ, but charge standard rates for data transferred across AZ boundaries. Because caching layers often handle significant read and write throughput, a high-volume application querying nodes in neighboring AZs can face steep, unexpected bandwidth bills. Placing nodes without considering query locality directly amplifies cross-AZ network costs.

Cluster Topologies: Stretched vs. Siloed

Choosing between a stretched cluster or siloed clusters is the primary structural decision in multi-AZ design:

  • Stretched Single Cluster: All Memcached nodes across all AZs belong to a single cluster. The client uses consistent hashing (such as the Ketama algorithm) to distribute keys uniformly across all nodes regardless of their zone. While simple to manage, this guarantees that a large percentage of requests will cross AZ boundaries, incurring latency and data transfer costs.
  • Siloed Per-AZ Clusters: Each AZ runs an independent, identical Memcached cluster that serves only application instances within that same zone. Application servers read exclusively from their local cache. This eliminates cross-AZ latency and transfer fees during reads, but requires the application layer or a cache proxy to invalidate or update keys across all regional clusters simultaneously to prevent stale data.

Blast Radius and the Thundering Herd

A primary motivation for multi-AZ placement is limiting the blast radius of a data center failure. If an entire AZ becomes unavailable:

  • In a stretched cluster, only a fraction of the cache keys (proportional to the number of nodes in that AZ) are lost. The remaining nodes continue serving their share of keys, preventing the primary database from experiencing a complete cache stampede.
  • In a siloed setup, the loss of an AZ simply takes down the application and cache instances in that zone simultaneously. The remaining AZs handle shifted traffic, provided their local caches are warm and adequately sized to absorb the increased load.

Proxy Routing and Replication

Native Memcached lacks cross-node replication, meaning each key exists on exactly one node. When deploying across AZs, teams frequently employ routing proxies such as Facebook’s Mcrouter or AWS ElastiCache features. A proxy layer can be configured to execute "all-sync" writes—writing data to a node in each AZ—while reading exclusively from the local AZ. This strategy achieves both high availability and sub-millisecond local reads, shifting the latency penalty entirely to write operations.
