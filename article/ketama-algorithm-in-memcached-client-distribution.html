Ketama Algorithm in Memcached Client Distribution

This article explores the Ketama algorithm and its vital role within Memcached client distribution logic. Readers will learn the operational shortcomings of traditional modulo-based hashing, how Ketama implements consistent hashing using virtual nodes on a continuum, and why this mechanism is critical for maintaining high cache hit ratios and system stability when scaling distributed cache clusters.

The Flaw of Traditional Modulo Hashing

Memcached operates on a shared-nothing, distributed architecture where the servers do not communicate with one another. The responsibility of determining which server stores or retrieves a given key falls entirely on the client library.

Historically, Memcached clients used standard modulo hashing:

server_index = hash(key) % number_of_servers

While computationally trivial, this formula introduces a severe vulnerability when the cluster topology changes. If a single server fails or a new server is provisioned, number_of_servers changes. Because the divisor changes, almost every key in the keyspace remaps to a completely different server index. This results in an immediate cache invalidation rate near 100%, triggering massive cache stampedes where backend databases are overwhelmed by sudden spikes in direct read traffic.

What is the Ketama Algorithm?

The Ketama algorithm was developed by Last.fm to solve the cache invalidation problem by implementing consistent hashing. Instead of mapping keys directly to an array of servers using modulo arithmetic, Ketama maps both the servers and the cache keys onto a continuous circular numeric space known as a hash ring (or continuum).

The primary function of the Ketama algorithm in Memcached client distribution is to ensure that when servers are added or removed, only a minimal, predictable fraction of keys (1/N, where N is the total number of servers) are remapped to different nodes.

How Ketama Operates

Ketama executes consistent hashing through three core mechanics:

1. The Hash Ring Continuum

The continuum represents an unsigned 32-bit integer space ranging from 0 to 2^32 - 1. Both cache keys and server identifiers are hashed into this same numerical range using an algorithm like MD5.

2. Virtual Nodes (Replicas)

A naive consistent hashing implementation places each physical server on the ring once. This leads to uneven key distribution because random hash outputs rarely divide a circle into equal segments.

To solve this, Ketama introduces virtual nodes (often referred to as points or replicas). For each physical server, Ketama generates multiple entries on the ring (typically 100 to 160 points per server, depending on the client implementation and server weight). Each virtual node is generated by hashing variations of the server's address (for example, 192.168.1.10:11211-0, 192.168.1.10:11211-1). This spreads a single server's ownership evenly across the entire continuum, ensuring balanced memory and traffic distribution.

3. Key Assignment and Clockwise Traversal

When a client needs to execute a get or set command:

  1. The client hashes the cache key into a 32-bit integer.
  2. The client finds that point on the hash ring.
  3. The client moves clockwise along the ring until it finds the first virtual node entry.
  4. The key is assigned to the physical server associated with that virtual node.

Because the list of points on the ring is kept sorted in memory, clients locate the target server in \(O(\log M)\) time using a binary search, where \(M\) is the total number of virtual points.

The Impact on Node Addition and Removal

When a server is added to or removed from the cluster:

  • Node Removal: If a server goes offline, only the virtual points belonging to that specific server disappear from the ring. Keys that mapped to those points simply move clockwise to the next available server. All keys pointing to remaining, unaffected servers stay intact.
  • Node Addition: A new server inserts its virtual nodes at various positions around the ring. It only claims the keys that sit counter-clockwise behind its new points, leaving the rest of the cluster's mappings undisturbed.

By limiting key redistribution strictly to the nodes involved in the topology change, Ketama prevents cascading failures, protects backend data stores, and provides deterministic, high-performance routing across Memcached clients.
