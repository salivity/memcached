Memcached Efficiency in High Eviction Cycles

This article explores how Memcached sustains microsecond response times and high throughput during massive key insertion and eviction workloads. By replacing standard operating system memory management with a deterministic slab allocation system, utilizing a partitioned Least Recently Used (LRU) cache model, and minimizing thread contention via fine-grained locking, Memcached avoids memory fragmentation and latency spikes even when running at complete capacity under extreme traffic.

Slab Allocation Prevents OS-Level Overhead

Traditional application memory management relies on operating system routines like malloc and free, which rapidly cause heap fragmentation and processor overhead under millions of rapid allocations and deallocations. Memcached completely bypasses this issue using its proprietary Slab Allocator.

When Memcached initializes, it pre-allocates a continuous block of memory and divides it into slabs (typically 1 MB in size). Each slab is assigned to a specific slab class tailored to handle items within a distinct size range, divided into uniform chunks. When a new key-value pair is inserted, Memcached assigns it to the closest fitting slab class and stores it in a pre-allocated chunk.

Because memory is never freed back to the operating system during standard operations, deallocating an expired or evicted item simply marks that chunk as reusable within its slab class. This design ensures that allocation and release operations remain \(O(1)\) constant time without inducing OS-level memory fragmentation.

Modern Segmented LRU Architecture

Under high insertion volumes, caches quickly reach memory limits and must continuously evict old data. Early versions of Memcached used a single global LRU queue per slab class, which caused severe lock contention when concurrent threads attempted to read, update, and evict keys simultaneously.

Modern Memcached versions resolve this bottleneck using a Segmented LRU design, which divides each slab class into distinct queues:

  • HOT Queue: Newly arrived items are initially placed here. Items in this queue are not bumped to the head on reads, reducing lock contention during bursts of read traffic.
  • WARM Queue: Items that receive subsequent access are promoted here, representing active, valuable data.
  • COLD Queue: Items that have not received recent access naturally migrate down to the COLD queue. Evictions occur almost exclusively from the tail of the COLD queue.
  • NOEXP Queue: Reserved for keys configured without time-to-live (TTL) limits.

By decoupling the ingestion point (HOT) from the eviction point (COLD), Memcached prevents high-frequency read and write threads from blocking background eviction operations.

Asynchronous Maintenance and Background Threads

To avoid stalling front-end worker threads that service incoming client traffic, Memcached offloads maintenance tasks to specialized background threads:

  • The LRU Maintainer Thread: Automatically balances memory between the segmented queues and handles the reclamation of expired items before forced eviction is necessary.
  • The Slab Reassigner / Automove: If insertion patterns change and certain slab classes experience heavy evictions while others remain idle, the slab automove thread identifies the imbalance and reassigns 1 MB slabs to the classes facing the highest memory pressure.
  • The Hash Table Expander: When the number of stored keys exceeds the capacity of the current primary hash table, a dedicated maintenance thread incrementally doubles the hash table size and migrates buckets in small increments, preventing latency spikes during key lookups.

Fine-Grained Locking and Non-Blocking I/O

Memcached runs an event-driven network model powered by libevent, distributing incoming client connections across multiple worker threads. High efficiency is sustained during write and eviction storms by replacing global instance-wide locks with fine-grained item locks.

Hash table buckets are protected by individual locks. When a thread inserts a key, triggers an eviction, or updates an item's position, it only locks the specific bucket or relevant LRU queue segment. Unrelated worker threads continue reading and writing to other segments concurrently without interference, allowing Memcached to scale linearly across modern multi-core processors.
