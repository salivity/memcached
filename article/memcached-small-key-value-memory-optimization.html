Memcached Small Key-Value Memory Optimization

This article examines how Memcached handles memory allocation for key-value pairs that are smaller than the configured minimum slab chunk size. It explores the operational design of the Slab Allocator, explains why sub-minimum records incur internal fragmentation rather than dynamic sub-chunking, and details the specific configuration adjustments and structural optimizations used to minimize memory waste for small payloads.

The Slab Allocation System

Memcached avoids dynamic memory allocation on every write to prevent memory fragmentation and ensure predictable \(O(1)\) read and write performance. It pre-allocates memory in 1MB blocks called pages. These pages are assigned to distinct "slab classes," each carved into fixed-size chunks based on an incremental growth factor.

Slab Class 1 represents the smallest chunk size available in the system. Every stored record requires space for the raw key and value, plus an internal header (item struct) that tracks metadata such as pointers, expiration time, flags, and length indicators.

Handling Items Smaller Than the Minimum Chunk

Memcached does not dynamically split chunks or pack multiple distinct key-value pairs into a single chunk when an item's combined data and metadata size is smaller than the minimum slab chunk size. Instead, the item is placed entirely into a chunk from Slab Class 1.

Because each chunk can hold only one item, any space remaining between the total item size and the chunk boundary remains unused. This condition is known as internal fragmentation. Memcached intentionally accepts this localized memory waste to preserve constant-time lookups, thread safety, and lock-free chunk recycles without incurring the overhead of defragmentation routines.

Optimizations for Sub-Minimum Key-Value Pairs

While Memcached does not sub-allocate chunks dynamically at runtime, several mechanisms optimize memory usage for small items:

1. Baseline Chunk Tuning (-n Flag)

The primary method for optimizing tiny key-value pairs is setting the baseline chunk size via the -n (or --min-item-space) startup flag. The default minimum chunk size allocates sufficient space for typical key overhead and small values (typically 48 bytes of data plus metadata). By tuning -n lower, operators can shrink the size of Slab Class 1 to match the exact byte size of their smallest expected payload, directly reducing the wasted space per item.

2. Disabling Optional Metadata Headers

The internal item structure carries metadata overhead for each entry. Memcached allows features such as Compare-And-Swap (CAS) to be disabled using the -C flag. Disabling CAS removes the 8-byte CAS identifier from every item header, shrinking the total footprint of small records and allowing them to fit into tighter chunk boundaries.

3. Growth Factor Calibration (-f Flag)

The slab growth factor (default 1.25, controlled by -f) dictates how rapidly chunk sizes increase across slab classes. Tuning this factor ensures that items just slightly larger than the minimum chunk do not graduate into disproportionately large chunks, keeping the memory allocation slope tight across all small-size boundaries.

4. Client-Side Packing

Because Memcached enforces a one-item-per-chunk rule, the standard pattern for optimizing massive quantities of tiny data (such as boolean flags, IDs, or single counters) is client-side aggregation. Applications pack multiple sub-minimum records into a single structured byte array, protocol buffer, or JSON object before sending it to Memcached. This spreads the fixed header overhead across dozens or hundreds of sub-values within a single appropriately sized slab chunk.
