How to Implement Distributed Locks with Memcached

This article explains how distributed applications implement mutual exclusion locks using Memcached's native atomic operations. By leveraging commands like add, cas, and delete alongside expiration timeouts, systems can coordinate concurrent processes across multiple nodes to prevent race conditions without introducing complex consensus infrastructure. Below, we break down the acquisition, renewal, and release lifecycles of a Memcached distributed lock, as well as the critical edge cases engineers must handle.

The Foundation: The Atomic add Command

The core primitive for acquiring a lock in Memcached is the add operation. Unlike the generic set command, which overwrites existing values, add will only store the data if the key does not already exist on the server. If two or more distributed workers attempt to execute add simultaneously for the same key, Memcached’s single-threaded event loop processes them sequentially. Exactly one worker receives a STORED response, while all others receive NOT_STORED.

A typical acquisition command follows this structure:

add <lock_key> <flags> <expiration_ttl> <byte_count>
<unique_token>

Step 1: Acquiring the Lock

To acquire a lock safely, an application must define three parameters:

  1. A Specific Key: A unique string identifying the shared resource (e.g., lock:order:9876).
  2. A Unique Token: A randomly generated identifier, such as a UUID or a cryptographically secure nonce. This token acts as a proof of ownership so that a client does not inadvertently release a lock owned by another process.
  3. A Time-To-Live (TTL): An expiration time (in seconds). This guarantees that if the acquiring process crashes or loses network connectivity, the lock will eventually expire, preventing a permanent deadlock.

If the add command returns STORED, the application has successfully acquired the lock and can proceed to the critical section. If it returns NOT_STORED, the application can either fail immediately or implement a retry loop using exponential backoff with randomized jitter to minimize contention.

Step 2: Releasing the Lock Using gets and cas

A naive release mechanism simply issues a delete <lock_key>. However, this introduces a race condition: if an application takes longer to complete its task than the designated TTL, the lock will automatically expire, allowing another worker to acquire it. If the first worker finishes and blindly executes delete, it will remove the second worker's active lock.

To avoid this, Memcached provides the gets (get with CAS token) and cas (Check-And-Set) commands. To release the lock safely:

  1. The client executes gets <lock_key>.
  2. Memcached returns the value (the unique token) and a 64-bit CAS identifier.
  3. The client verifies that the returned value matches its own unique token. If it does not, the lock has expired and been reacquired elsewhere; the client aborts.
  4. If the token matches, the client issues a cas command that invalidates or updates the key using the acquired CAS identifier. Alternatively, many client libraries implement a conditional delete via a script or a zero-TTL update via cas to ensure only the owner drops the key.

Step 3: Handling Long-Running Tasks

When tasks risk outlasting their initial TTL, applications should use a background heartbeat thread to extend the lock rather than setting an arbitrarily large TTL upfront. Memcached provides the atomic touch command:

touch <lock_key> <new_expiration_ttl>

A heartbeat periodically refreshes the expiration as long as the worker remains healthy. If the worker crashes, the heartbeat stops, and the lock naturally expires within the original TTL window.

Limitations and Best Practices

While Memcached is fast and lightweight, applications relying on it for distributed locks should be aware of several operational nuances:

  • LRU Eviction: Memcached is fundamentally an in-memory cache. If memory is full, the engine may evict keys based on Least Recently Used (LRU) policy. To prevent active lock keys from being evicted prematurely, use dedicated slabs, allocate sufficient RAM, or disable LRU eviction for specific pools using the -M flag.
  • No Persistence: If a Memcached node restarts, all in-flight locks are lost, potentially allowing concurrent access.
  • Network Partitions: Memcached clusters typically do not implement consensus protocols (like Raft or Paxos). If client-side sharding routes traffic during node failover, split-brain scenarios can occur.

For these reasons, Memcached-based distributed locks are best suited for high-throughput, operational efficiency tasks—such as deduplicating work or throttling access—where an occasional lock drop or contention edge case does not cause catastrophic data corruption.
