Memcached Memory Leak vs Normal LRU Evictions

Distinguishing between an actual memory leak and healthy Least Recently Used (LRU) evictions in Memcached requires looking beyond standard operating system memory charts. Because Memcached pre-allocates memory via its slab allocator and is designed to run near capacity, diagnosing anomalies requires analyzing internal metrics such as evictions, evicted_unexpired, cache hit ratios, and operating system Resident Set Size (RSS) relative to configured limits.

Understanding the Baseline: Memcached Memory Model

Memcached manages memory by allocating slabs of fixed chunk sizes rather than allocating and freeing system memory dynamically per request. Once Memcached starts and absorbs data, its memory usage will climb to its configured limit (limit_maxbytes) and permanently remain there.

Because staying at 100% capacity is by design, observing maximum memory consumption is not evidence of a memory leak. Under normal operation, when memory is full and new data enters, Memcached reclaims space by purging expired keys or evicting the least recently accessed items.

Key Metric Differences

To determine whether your cluster is experiencing standard LRU behavior, an application-level key leak, or a daemon-level C memory leak, compare the following metrics using memcached-tool or the stats command.

1. Operating System RSS vs. limit_maxbytes

  • Normal Operation / LRU Evictions: The OS-level Resident Set Size (RSS) will reach limit_maxbytes plus minor connection overhead (typically 5–15%) and plateau indefinitely.
  • Engine-Level Memory Leak: The RSS continues to grow beyond limit_maxbytes and the connection overhead threshold, ultimately causing the Linux Out-Of-Memory (OOM) killer to terminate the process.

2. evictions and evicted_unexpired

  • Normal LRU Evictions: The evictions counter increases, but eviction rates match predictable traffic spikes. In an adequately sized cache, evicted_unexpired should be zero or negligible, meaning items are naturally expiring via their Time-To-Live (TTL) before being forced out.
  • Capacity Leak / Application Key Leak: The evicted_unexpired metric rises rapidly alongside regular evictions. This occurs when an application writes unbounded unique keys without TTLs or generates massive key bloat, aggressively forcing actively used, unexpired items out of memory.

3. Key Count Stability (curr_items)

  • Normal LRU Evictions: In steady-state workloads, curr_items fluctuates within a consistent range or reaches an equilibrium where the rate of expired/evicted keys equals the rate of newly set keys (cmd_set).
  • Application Leak: curr_items displays a continuous upward trajectory with no plateau until memory is exhausted, followed by a sudden plateau and an immediate surge in evictions.

4. Cache Hit Ratio (get_hits vs. get_misses)

  • Normal LRU Evictions: The cache hit ratio remains stable. The LRU algorithm ensures that frequently requested "hot" items stay in memory, meaning normal evictions primarily discard cold or rarely used data.
  • Memory/Key Leak Impact: The hit ratio degrades drastically. Because unmanaged or leaked keys monopolize slabs, the LRU algorithm is forced to purge active, high-value cached data to accommodate the incoming low-value keys, driving get_misses upward.

5. Slab Distribution (stats slabs)

  • Normal Operation: Slab classes reflect your payload sizes, and used_chunks corresponds proportionally to key access frequency across classes.
  • Slab Calcification (Simulated Leak): If historical traffic introduced large objects into specific slab classes that are no longer requested, memory can become locked into empty chunks within those classes if slab rebalancing (slab_automove) is disabled. This starves other slab classes and triggers high eviction rates despite apparent idle memory inside underutilized slabs.

Diagnostic Checklist

  1. Check process size: Run ps -o rss,vsz -p <memcached_pid>. If RSS significantly exceeds limit_maxbytes, suspect an engine bug or module leak.
  2. Evaluate TTL pressure: Query stats items to inspect evicted_unexpired across all slabs. Elevated numbers indicate cache starvation rather than natural expiration.
  3. Audit key distribution: Sample your keyspace using memcached-tool <host:port> dump to identify un-expiring keys, rogue unique IDs, or bloated data models flooding the cache.
