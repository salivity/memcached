Memcached Atomic Increments Without Global Locking

Memcached performs atomic counter increments and decrements rapidly by avoiding a monolithic, global lock on the entire cache. Instead, it utilizes fine-grained item locking tied to its primary hash table, allowing multiple worker threads to execute arithmetic operations concurrently. This architecture ensures that updating a counter only serializes operations on that specific key—or a small subset of keys sharing a lock partition—while the rest of the memory store handles read and write operations without interruption.

Thread Model and Granular Item Locks

Memcached runs a multi-threaded architecture using a master thread to accept incoming connections and multiple worker threads to process commands. Early versions of Memcached utilized a global cache lock that caused severe thread contention during high write volumes. Modern Memcached replaces this model with partitioned locks known as item locks (item_lock).

The cache maintains an array of mutexes dedicated to item synchronization. When an incr command is received, Memcached hashes the target key to produce a 32-bit hash value. This hash serves two purposes: identifying the bucket in the primary hash table and mapping directly to a specific mutex index in the item lock array via a modulo operation:

lock_index = hash_value & (item_lock_count - 1)

By decoupling synchronization from the global state, threads operating on keys with different lock indexes execute simultaneously across CPU cores.

Execution Path of the incr Command

When a worker thread processes an increment operation, it executes a deterministic, localized sequence:

  1. Lock Acquisition: The thread calculates the key’s hash and claims the corresponding granular item lock.
  2. Item Lookup: Under the protection of the item lock, the thread searches the internal hash table for the key's memory address.
  3. Data Validation: The stored value must be a textual representation of a 64-bit unsigned integer. If the item does not exist or contains non-numeric byte sequences, the operation fails, the lock is released, and an error returns to the client.
  4. Arithmetic Operation: Memcached converts the ASCII string to an unsigned 64-bit integer (uint64_t), adds the requested delta, and handles overflows according to standard 64-bit wrapping semantics.
  5. Memory Updating:
    • In-Place Update: If the new number has the same string length as the old value (for example, incrementing 100 to 101), the bytes are updated directly within the existing slab memory chunk.
    • Reallocation: If the digit count increases (for example, incrementing 999 to 1000), the thread must obtain a new, larger memory chunk from the slab allocator, format the new text value, update hash table pointers, and free the old chunk.
  6. Lock Release: Once the memory pointers and CAS (Check-And-Set) values are updated, the thread releases the item lock.

Collision Management and Concurrency

Because the number of hash table buckets exceeds the number of allocated item locks, multiple distinct keys can occasionally map to the same mutex. However, Memcached sets the lock table size high enough (typically thousands of discrete locks) that lock collision probability across active threads remains extremely low.

By restricting mutual exclusion strictly to the lifespan of the pointer read and string conversion, Memcached achieves atomicity at CPU-bound speeds without stalling the broader key-value storage engine.
