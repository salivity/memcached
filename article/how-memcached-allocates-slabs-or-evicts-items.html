How Memcached Allocates Slabs or Evicts Items

Memcached manages memory through a slab allocation system designed to prevent fragmentation and optimize read/write speeds. When handling new data under memory load, the engine follows a strict hierarchical evaluation to determine whether it should draw a new slab page from global memory or evict an existing item. This article explains the exact criteria Memcached evaluates—including slab class matching, global memory limits, and Least Recently Used (LRU) queues—to decide between allocation and eviction.

The Memory Model: Slabs and Classes

When Memcached initializes, it allocates a single continuous block of memory defined by the -m flag. This memory is divided into 1MB pages. Pages are assigned to specific slab classes, each configured to hold items of a particular size range (determined by a growth factor, usually 1.25).

When a write command (such as set or add) arrives, Memcached maps the item's byte size to the smallest slab class capable of holding it. From there, the engine decides how to acquire a chunk within that class.

The Decision Hierarchy

Memcached evaluates memory availability using a deterministic order of operations:

  1. Check for Available Chunks Within the Slab Class
    Memcached first checks if the target slab class has any unused chunks on its internal freelist. These chunks come from items that were previously deleted or explicitly expired. If a chunk is available, Memcached reuses it immediately without allocating new pages or evicting items.

  2. Check the Global Memory Pool
    If no free chunk exists in the target slab class, Memcached evaluates the total memory consumption of the instance.

    • If total allocated memory < maximum allowed limit (-m): Memcached allocates a new 1MB page from the global pool, assigns it to the target slab class, slices it into chunks of that class's fixed size, and places the new item into the first available chunk.
    • If total allocated memory has reached the limit: No new pages can be created from the global pool. Memcached must resort to eviction within that specific slab class.

  3. Check the Slab-Specific LRU Queue for Evictions
    Because memory cannot grow beyond the configured limit, Memcached inspects the Least Recently Used (LRU) list belonging only to the targeted slab class. It will not evict items from other slab classes to satisfy the write.

    • Expired Items First: Memcached inspects the oldest items at the tail of the slab class's LRU chain. If an item has already expired based on its TTL (Time-To-Live), Memcached reclaims its chunk without incrementing the eviction counter.
    • Active Item Eviction: If the tail items are still valid and have not expired, Memcached checks the eviction configuration. By default, eviction is enabled: the oldest active item at the tail of the LRU is discarded, its memory is reused, and the evictions metric increments.
    • Out of Memory Error: If the -M flag (disable eviction) was passed at startup, Memcached skips item eviction and returns an out-of-memory error to the client.

Slab Calcification and Dynamic Slab Reassignment

In earlier versions of Memcached, a page assigned to a slab class remained locked to that class permanently. This led to "slab calcification," where one slab class could run out of space and evict active items even if other slab classes held idle, unused pages.

Modern Memcached versions resolve this using the slab reassign and slab automove mechanisms:

  • The background thread monitors memory access patterns and eviction rates across all classes.
  • If a class is experiencing consistent evictions while another class has unused pages or low access rates, Memcached can detach a 1MB page from the donor class and reassign it to the starved class.
  • Once reassigned, the memory acts as a newly allocated page for the receiving class, reducing the need for immediate item eviction.
