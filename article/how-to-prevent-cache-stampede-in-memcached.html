How to Prevent Cache Stampede in Memcached

When a heavily requested Memcached key expires or a cache node restarts, thousands of concurrent application requests can simultaneously miss the cache and hit the backend database. This phenomenon—known as a cache stampede or thundering herd—can exhaust database connection pools, spike latency, and trigger cascading system failures. To maintain system reliability, software engineers implement specific architectural patterns designed to coordinate data access, regenerate stale values in the background, and protect databases during massive cache misses.

1. Mutex Locking (Lock-Aside Pattern)

The mutex locking pattern ensures that only one application worker queries the database to regenerate the cached value, while all other concurrent requests wait or read stale data.

When a cache miss occurs:

  • The application attempts to acquire an atomic distributed lock (for example, using Memcached's add command, which succeeds only if the key does not already exist).
  • The single process that acquires the lock queries the database, writes the fresh data to Memcached with a new TTL, and then deletes the lock.
  • All competing processes fail to acquire the lock and either sleep briefly before retrying the cache read or immediately return fallback data.

This pattern eliminates the thundering herd by funneling thousands of duplicate database queries down to a single read operation.

2. Probabilistic Early Expiration (XFetch)

Hard expirations guarantee that all requests arriving after the TTL will miss the cache simultaneously. Probabilistic early expiration avoids this by recomputing the cached value before it officially expires.

The most widely adopted algorithm is XFetch. As a key approaches expiration, read requests execute an algorithm using the remaining TTL, the time it takes to compute the value, and a randomized factor:

\[\Delta - \beta \times \delta \times \ln(\text{random}())\]

If the calculated threshold is greater than the remaining time to live, the current worker asynchronously recomputes the data and resets the TTL in the background. Because the decision is probabilistic, the likelihood of a background refresh increases as the key gets closer to its expiration time, virtually guaranteeing that one worker refreshes the cache before any user experiences a hard miss.

3. Stale-While-Revalidate

In this pattern, the application decouples the data's soft TTL from its hard TTL.

  • Data is stored in Memcached with two timestamps: a logical expiration time (e.g., 5 minutes) and a physical TTL (e.g., 60 minutes).
  • When a request reads an item that has exceeded its logical expiration, it serves the stale data immediately to the user.
  • Concurrently, the application dispatches an asynchronous background task (via a message queue or worker pool) to query the database, update the cache, and reset both the soft and hard timestamps.

Users always experience low-latency responses, and the database handles a controlled, non-blocking trickle of update queries.

4. Application-Level Request Coalescing

Request coalescing (often referred to as "singleflight") groups identical, in-flight read operations within an application server instance.

If ten threads on the same application server encounter a cache miss for the same key at the exact same millisecond, the application wraps the backend call in a coordination construct. The first thread initiates the database call, while the remaining nine threads subscribe to the result of the first thread's execution. Once the first call resolves, the result is shared across all waiting threads. This drastically reduces the total query volume leaving the application tier.

5. Asynchronous Cache Warming

For predictable traffic patterns, such as scheduled reporting or daily product releases, the cache should never rely on user traffic to populate data.

Instead, scheduled background workers or event-driven workers (triggered by database write events or Change Data Capture pipelines) pre-calculate expensive queries and push them into Memcached before user requests occur. By keeping volatile or heavy keys continually populated via background jobs, application reads achieve near 100% hit ratios and avoid hitting the database layer entirely.

6. Graceful Degradation and Circuit Breaking

If widespread misses occur due to a total Memcached cluster failure, locking and coalescing alone may not fully shield the database. Circuit breakers should be configured around database read paths:

  • If database latency or connection pool saturation crosses a defined threshold, the circuit opens.
  • The application immediately degrades gracefully by returning static fallbacks, empty states, or cached values from a secondary local in-memory tier (such as an in-process LRU cache) rather than overwhelming the database with queries.
